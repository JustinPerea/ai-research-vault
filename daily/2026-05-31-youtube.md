### [Why (Senior) Engineers Struggle to Build AI Agents — Philipp Schmid, Google DeepMind](https://www.youtube.com/watch?v=3_gYbhABcAE) — AI Engineer (?min, category: ai-agents)
**TL;DR:** Schmid argues senior engineers carry years of implicit context an agent can't see — and names five concrete shifts to design tools and loops around. _(transcript unavailable — summary based on title + description only)_

**Key insights:**
- The reframe that matters for Ara's tool design: a `deleteItem` endpoint is obvious to the human who built it; the agent only sees the schema + docstring. Senior engineers build tools assuming the implicit context that's the source of their advantage — and that's exactly the context the agent doesn't have. Justin should audit every tool surface in Ara/Familiars: would a stranger reading only the schema know when *not* to call it?
- "Errors are inputs, not restart triggers, especially when the agent has been running for 15 minutes." Direct guidance for long-running agent loops — design error handling as a recoverable input, not a tear-down. Cost of restart compounds with run length.
- "Evals replace unit tests" — the right question is *how often* it works, not whether a fixed input always produces a fixed output. This is the third AI Engineer talk in two weeks to land on the same line; it should be a permanent line in Justin's project setup checklist.
- "Build to delete" — assume you'll rebuild the same agent with a better model in 6 months. Stop over-engineering the scaffolding; bet the abstraction layer is wrong. Good antidote to premature framework-itis when building on rapidly improving base models.
- Text replacing structured state is the fifth shift — worth watching for how he frames the implications for memory/context design.

**Tools mentioned:** none specific (architecture/principles talk)

### [How We Built Zeta2: Training an Edit Prediction Model in Production — Ben Kunkle, Zed](https://www.youtube.com/watch?v=phchDt63qAA) — AI Engineer (?min, category: ai-agents)
**TL;DR:** Zed's edit-prediction pipeline distills opt-in production traces through a frontier teacher, repairs bad predictions, and uses "reversal ratio" as a kill-switch diagnostic. _(transcript unavailable — summary based on title + description only)_

**Key insights:**
- The pipeline is a transferable template for any agent that learns from production traces: pull opt-in production data → distill through a frontier teacher → route bad predictions through a *repair* step → format for student. The repair step is the under-emphasized part of most distillation pipelines and worth lifting wholesale for Ara's eval-improvement loop.
- "Reversal ratio" — how often the model undoes exactly what the user just typed — is the most portable diagnostic in the talk. It's the kind of cheap, behavior-level metric that catches regression before benchmarks do. Justin should pick one analogous metric per Ara agent (e.g., "% of agent actions immediately reverted by user") and gate releases on it.
- The Levenshtein-distance training-example selection is sharp: too close to the settled state is obvious, too far is noise, the middle is the signal. Same shape applies to any agent learning from trajectory data — filter on edit distance from the target, not on raw quality.
- The cost-optimization story (10K examples × 100 frontier calls = $$$ → student model approaches teacher, run it 50x for cheap) is the practical case for distillation: once your student is close to teacher quality, validation becomes ~free. Useful when Ara accumulates enough trace data to consider a small specialized model.

**Tools mentioned:** Zed Zeta2, frontier teacher distillation, Levenshtein distance, reversal-ratio metric

**For /bookmark:** `https://www.youtube.com/watch?v=phchDt63qAA`
