# AI Research Digest — Tuesday, July 21, 2026

## TL;DR
- **RECON (2607.16716)** — first stateful-memory benchmark with 50–100k-token case files across criminal/medical/financial domains; **best non-Oracle system tops out at 22.4% accuracy** on six memory-intensive capabilities (multi-hop chains, cascading invalidations, source-conflict resolution, counterfactual reasoning, temporal constraints, temporal fact retrieval). Direct **CONFLICT** with Oracle Agent Memory's 93.8% LongMemEval headline from 2026-07-16.
- **MSCE (2607.16621)** and **AgentBrew (2607.16851)** — two independent EMNLP 2026 submissions on the same day treat *skills* as first-class memory artifacts: MSCE crystallizes positive-gain policies into callable skills with evidence links + applicability boundaries + verification rules + reliability estimates; AgentBrew's **Ralph Loop** converts student failures into environment-validated teacher notes without weight updates or ground-truth labels. Both extend the harness-engineering pipeline (Handbook → QD → MemoHarness → Compound → Pairwise-Validator → SEED → **skill-as-first-class-memory**) with training-free primitives.
- **Environment-free Synthetic Data (2607.16900, Apple)** — trains API-calling agents from **API specifications alone** using an LLM as an on-the-fly digital world model; evaluated on AppWorld + OfficeBench. Completes the training-side agent-tool stack with ToolVerse (2607.15660) and MCPEvol-Bench (2607.14642) — one week, three papers, three angles on the same MCP-fragility problem.
- **LLM-as-a-Coach (2607.18110, MSR)** — replaces scalar reward with **distilled experiential feedback** from an evaluator model, targeting non-verifiable tasks where "rubric-based RL" underperforms. **Second CONFLICT with the Reward-Free Evolving pairwise-validator (2607.14408)** — coach-mode uses higher-bandwidth feedback than pairwise judgment.
- **FlashRT (2607.18171)** — chain-of-program agent harness for real-time multimodal deployments; **65% latency reduction for Qwen3-Omni text-to-audio vs the expert vLLM-Omni** implementation, up to ~70× overall latency reduction with 2.8×/3.6× throughput on B200/MI355X. Voice-agent local-fit signal.
- **Local-model corner** — **Inkling MLX 2-bit** (975B/41B active MoE from Thinking Machines) shipped this weekend as **~315 GB weights runnable on a 64 GB Mac via SSD expert-offload** — first ~1T-scale open-weight model to have an explicit M5 Max path, however slow. ## Items

### 1. RECON: Benchmarking Agent Memory for Compositional Reasoning over Long Contexts
- **Source:** arXiv (2607.16716) — submitted July 18, 2026
- **Link:** https://arxiv.org/abs/2607.16716
- **Authors:** Mihir Shriniwas Arya
- **Focus area:** Agent memory / evaluation
- **What it is:** 24 case files across criminal / medical / financial domains, 50k–100k tokens each, testing six specific memory-intensive capabilities: (1) reconstructing multi-hop evidence chains, (2) propagating cascading invalidations, (3) resolving source conflicts, (4) counterfactual reasoning, (5) satisfying temporal constraints, (6) temporal fact retrieval. **Strongest non-Oracle system reaches only 22.4% accuracy.**
- **Why it matters for Justin's agents:** This is the missing hard benchmark for the memory thread. LongMemEval, HaluMem, and LoCoMo have all been getting saturated (Oracle Agent Memory hit 93.8% LongMemEval at 10.7× fewer tokens on 2026-07-16), but RECON's dimensions — *cascading invalidations* and *source-conflict resolution* over adversarial 50–100k-token case files — are exactly the failure modes MOSAIC (2607.16211) / Oracle / MemCon (2607.13591) never actually stress-test. Justin's companion-app roadmap sooner or later needs "revoke this belief and propagate," which RECON operationalizes. For any mem0-class stack Justin ships, RECON is now the go-to sealed-test set to score against — expect single-digit accuracy on the vanilla flat-history baseline.
- **Action signal:** `compare` — direct calibration on the *upper bound* of vault-tracked memory claims; clone the benchmark and score every memory arch in the ledger

### 2. MSCE: From Memory to Skills — Evidence-Grounded Co-Evolution Governance for Long-Horizon LLM Agents
- **Source:** arXiv (2607.16621) — submitted July 18, 2026 (EMNLP 2026)
- **Link:** https://arxiv.org/abs/2607.16621
- **Authors:** Bo Tang, Yang Zhang, Guomian Zhuang, Wenqiang Wei, Gaoyang Zheng, Lindong Xie, Yanchao Tan, Feiyu Xiong, Qingyu Yang, Edward Chung, Zhiyu Li
- **Focus area:** Agent memory / skill packages
- **What it is:** **Training-free** framework organizing agent experience into three tiers — grounded step traces, reusable procedural policies (L2), declarative environmental cognition. Positive-gain L2 policies get "crystallized" into callable skills that retain **evidence links + applicability boundaries + decision guidance + verification rules + reliability estimates**. Novel primitive: **reflection-weighted value backfilling** propagates sparse terminal feedback through dense local self-reflections to produce evidence-calibrated trace values that govern which memories/skills evolve. Evaluated on EvoAgentBench + LoCoMo.
- **Why it matters for Justin's agents:** This is the **seventh "skill-as-first-class-artifact" data point** in the vault (SkillOpt, NeMo Autoresearch, Alipay-PIBench, Mistral Studio, Shippy Skills, SEED, and now MSCE) and the first with **verification rules + reliability estimates baked into the skill schema itself**. Direct transplant for Justin's Claude Code skill setup: instead of skills being pure markdown capability files, they carry `verification.md` + `reliability.md` sidecars that get updated by `reflection-weighted value backfilling` during real agent runs. The training-free framing means it slots into any MCP tool without post-training — the Ralph Loop from item 3 becomes the natural pairing (AgentBrew *generates* the notes, MSCE *governs* which ones evolve).
- **Action signal:** `try-now` — rewrite one Claude Code skill (e.g. `create-pr`) with the MSCE schema fields and see whether the verification-rules field alone changes agent behavior

### 3. AgentBrew: Lifelong Knowledge Brewing from Strong Teachers to Weak LLM Agents
- **Source:** arXiv (2607.16851) — submitted July 18, 2026
- **Link:** https://arxiv.org/abs/2607.16851
- **Authors:** Yangqin Jiang, Chao Huang
- **Focus area:** Agent orchestration / harness engineering
- **What it is:** Distills teacher experience into an **external memory** without weight updates, expert demos, or ground-truth labels. Two mechanisms: **(1) failure-triggered Ralph Loop** — student failures trigger the teacher to author environment-validated notes (the *environment* validates, not the teacher, closing the sparse-feedback gap); **(2) student-aware synthesis** — teacher calibrates note complexity to the weaker executor's operational capabilities so notes are actually executable. **No test-time teacher access.** Evaluated across coding + math + tool-use tasks.
- **Why it matters for Justin's agents:** This is the **direct auto-authored companion to MSCE**: MSCE gives the schema (evidence + boundaries + verification), AgentBrew gives the generation loop (failure → teacher note → environment-validation → student memory). Concrete Claude Code transplant — a `SessionStop` hook that, on any failed task, sends the trajectory to a stronger model (Opus supervising Haiku) with the Ralph Loop prompt: "write a note that, if this agent had read it before starting, would have prevented the failure." Notes accumulate in `.claude/lessons/`. The "student-aware synthesis" primitive is the missing ingredient that stops teacher notes from being aspirational-but-unusable — Sonnet writing notes only Opus can actually follow.
- **Action signal:** `try-now` — the Ralph Loop is a ~20-line prompt harness; no waiting on weights, no waiting on releases

### 4. Environment-free Synthetic Data Generation for API-Calling Agents
- **Source:** arXiv (2607.16900) — submitted July 18, 2026
- **Link:** https://arxiv.org/abs/2607.16900
- **Authors:** Seanie Lee, Sanjoy Chowdhury, Chao Jiang, Cheng-Yu Hsieh, Ting-Yao Hu, Alexander T Toshev, Oncel Tuzel, Raviteja Vemulapalli (Apple)
- **Focus area:** Tools & connectors (MCP) / synthetic data
- **What it is:** Trains API-calling agents from **API specifications alone** — no simulated environment, no live sandbox. An LLM plays three distinct roles: (a) task generator producing diverse tasks matching the API spec, (b) teacher agent solving them via iterative tool calls, (c) **on-the-fly digital world model** producing coherent synthetic API responses conditioned on task context and history. An LLM judge filters trajectories for quality. Evaluated on AppWorld + OfficeBench (both info-retrieval + state-changing tasks).
- **Why it matters for Justin's agents:** Third training-side entrant in one week alongside **ToolVerse (2607.15660)** and **MCPEvol-Bench (2607.14642)** — but this one requires **only OpenAPI/JSON schemas**, not the ~400 real MCP servers ToolVerse needs. For any MCP server Justin builds, the Apple recipe means: hand the tool schema to a teacher LLM + a simulator LLM, get a training corpus of tool-call trajectories in minutes with zero environment infrastructure. This is a *strictly cheaper* path than ToolVerse's server harvesting, at the cost of simulator drift (the world model is only as good as the LLM's understanding of the schema). Composes with MCPEvol as the eval: generate synthetic training via Apple recipe → post-train with ToolAnchor (2607.14145) → score fragility on MCPEvol.
- **Action signal:** `try-now` — the recipe is entirely prompt-level; run it on any of Justin's MCP tool schemas today

### 5. LLM-as-a-Coach: Experiential Learning for Non-Verifiable Tasks
- **Source:** arXiv (2607.18110) — submitted July 20, 2026
- **Link:** https://arxiv.org/abs/2607.18110
- **Authors:** Tianzhu Ye, Li Dong, Guanheng Chen, He Zhu, Xun Wu, Shaohan Huang, Furu Wei (Microsoft Research)
- **Focus area:** Reasoning & training-time compute (open-ended tasks)
- **What it is:** Argues that **scalar reward compression discards the textual feedback** an evaluator naturally produces; instead, converts the evaluator into a **coach** that distills its per-response assessment into **transferable experiential knowledge** for the next on-policy rollout. Consistent gains over rubric-based RL across policy families, better OOD generalization, reduced reward hacking.
- **Why it matters for Justin's agents:** This **partially conflicts with Reward-Free Evolving via Pairwise Validator (2607.14408)**. Pairwise-Validator argued the *cheapest* reward substitute is a frozen judge scoring parent-vs-child; Coach argues **the judge's textual explanation is the real signal** and reducing it to a scalar (or even a preference bit) is where quality dies. Not a direct contradiction — pairwise judgment is a special case of coach feedback — but the practical implication is opposite: instead of running many cheap pairwise votes, run *fewer* coach passes that emit dense text. For Justin's federal-data-engineer workflows (many "did this SQL query actually answer the ask?" evaluations), the coach framing is closer to what a senior reviewer would do than a preference-model rubric.
- **Action signal:** `compare` — extend the Pairwise-Validator claim in the ledger with a caveat: cheaper isn't always better; textual feedback carries more signal than any scalar the judge would produce

### 6. FlashRT: Agent Harness for Guiding Agents to Deploy Real-Time Multimodal Applications
- **Source:** arXiv (2607.18171) — submitted July 20, 2026
- **Link:** https://arxiv.org/abs/2607.18171
- **Authors:** Krish Agarwal, Zhuoming Chen, Yanyuan Qin, Zhenyu Gu, Atri Rudra, Beidi Chen
- **Focus area:** Agent orchestration / real-time deployment
- **What it is:** **Chain-of-program paradigm** where coding agents rewrite basic reference implementations into optimized multi-GPU deployments. Uses an intermediate representation to capture dependencies, sequential interpretation to validate, static analysis to find optimization sites, and an iterative implement-verify-benchmark loop under measurement constraints. **Up to ~70× overall latency reduction; 2.8× throughput on NVIDIA B200, 3.6× on AMD MI355X; 65% latency reduction for Qwen3-Omni text-to-audio versus expert vLLM-Omni implementation.**
- **Why it matters for Justin's agents:** The 65% number is against the **expert-implemented** vLLM-Omni baseline, not against a naïve implementation — meaning an agent optimizer beat human-tuned inference code on a real production runtime. For Justin's companion-app roadmap where voice-agent latency is the primary UX bottleneck, this changes the calculus of "should we hand-optimize the inference stack" vs "should we let a coding agent do it." The chain-of-program IR is also the *first* agent-harness paper to explicitly target the deploy-and-benchmark step as an optimization surface — most harness work stops at "generated code compiles."
- **Action signal:** `track` — watch for the code release; the technique likely transplants to MLX runtime optimization for M5 Max voice-agent stacks

### 7. C²KV: Compressed and Composable KV Cache Reuse for Efficient LLM Inference
- **Source:** arXiv (2607.17715) — submitted July 20, 2026 (SIGKDD 2026)
- **Link:** https://arxiv.org/abs/2607.17715
- **Authors:** Chuheng Du, Junyi Chen, Hanlin Tang, Kan Liu, Tao Lan, Lin Qu, Chaoyue Niu, Shengzhong Liu, Guihai Chen, Fan Wu
- **Focus area:** Context engineering (KV cache)
- **What it is:** Unified framework that **jointly optimizes KV extraction and inference-time concatenation**, rejecting the standard split between "compress" and "reuse" as two separate problems. Uses a **lightweight sidecar Extractor with learnable compression tokens** designed to work across input positions, plus a co-training strategy that aligns extraction-time representations with downstream usage patterns. Modular KV representations flexibly reuse + concatenate without modifying the base model. **Up to 17× inference speedup** on long-context RAG + multi-document reasoning.
- **Why it matters for Justin's agents:** C²KV is the **composability primitive** the KV-cache stack has been missing. Vault-tracked: PReM (2607.14327) reshapes during generation, VarRate (2607.15498) assigns variable low-rank per token, Byte-Exact KV Grafting (2607.14431) reloads bit-identical state — but none of these treat *the reused blocks as interchangeable modular units*. C²KV's non-prefix reuse (arbitrary KV segments, not just prefix-caching) means Justin can build a KV *library* for MCP tool descriptions, RAG chunks, system prompts, and instructions, each cached separately and composed per query. SIGKDD 2026 acceptance suggests the technique is mature enough for production.
- **Action signal:** `track` → `try-now` once weights land — 17× speedup for RAG + multi-doc is the biggest single win for Justin's Obsidian-vault companion architecture

### 8. Constraint-Anchored Reasoning Traces (CART)
- **Source:** arXiv (2607.16727) — submitted July 18, 2026
- **Link:** https://arxiv.org/abs/2607.16727
- **Authors:** Zehua Cheng, Wei Dai, Jiahao Sun
- **Focus area:** Reasoning & inference-time compute (multimodal)
- **What it is:** Diagnoses **error snowballing** in state-of-the-art open-source MLLMs — "once the first error occurs, the reasoning cascades into failure across all remaining steps in **65% of such cases**." CART trains models to embed **machine-checkable constraint assertions** (object counts, relational predicates) inline with natural-language reasoning; a dual-module verifier checks anchors against visual features + logical consistency and triggers backtracking on contradiction. **Snowball rate 0.65 → 0.14** with **≤18% inference overhead**; +4.6 pp GQA, 89.1 POPE-all F1; trained on 218K instances (GQA + CLEVR-CoGenT + VCR), applied to LLaVA-NeXT + Qwen2-VL.
- **Why it matters for Justin's agents:** The Proof-or-Stop (2607.14890) primitive said "every lifecycle claim needs verifiable evidence"; CART is the *inside-the-reasoning-trace* version — every intermediate reasoning step gets a machine-checkable receipt. For any agent reading Justin's federal-data-engineering pipelines (row counts, timestamp ordering, foreign-key cardinality), the CART pattern is: emit `ASSERT rows == 1024` inside the chain-of-thought, verify against a cheap tool call, backtrack on failure. The 65% cascade rate is a much sharper number than the fuzzy "hallucinations propagate" intuition — it's a specific failure mode with a specific fix.
- **Action signal:** `try-now` at the prompt level — even without training, adding "insert `ASSERT` statements you can verify" to the system prompt captures a meaningful fraction of the gain

### 9. Lomekwi: Resource-Bounded Tool Discovery in LLM Agents
- **Source:** arXiv (2607.16961) — submitted July 18, 2026 (COLT 2026 workshop)
- **Link:** https://arxiv.org/abs/2607.16961
- **Authors:** Roshan Klein-Seetharaman, Daniel Wang, Andrew Xu
- **Focus area:** Tools & connectors
- **What it is:** Separates *tool use* from *tool discovery* and decomposes discovery into three components — **curiosity** (identifying that a tool is needed), **recognition** (understanding the creation process), **efficiency** (post-creation usage). Applied to Voyager + related benchmarks. Headline finding: **recognition ability *inversely scales* with model size** — larger models are *worse* at recognizing how new tools should be constructed. Replicated in combinatorial games + real-world task emulation.
- **Why it matters for Justin's agents:** Inverse scaling on tool-recognition is a **specific new failure mode** distinct from ToolAnchor's "tool behavioral inertia" (2607.14145). Inertia = "reverts to familiar tools when new tools appear"; recognition failure = "cannot conceive of the new tool's construction even when told it should exist." For Justin's MCP-authoring workflow, this predicts: when Justin invents a new MCP tool that requires *composing* existing primitives in an unfamiliar way, the largest agent (Opus 4.7) will *underperform* smaller agents at spec'ing it correctly. Concrete test: give Opus and Haiku the same "sketch a new MCP server that combines these three existing tools" prompt and measure recognition-quality on the resulting spec. If Lomekwi replicates, the counterintuitive answer is to route *new-tool-design* tasks through smaller models.
- **Action signal:** `compare` — worth an in-house replication; extends ToolAnchor's failure taxonomy with a scale-inverted axis

## Local-model corner

**Model:** Inkling MLX 2-bit (975B total / 41B active MoE, 256 experts / 6 active per token) — via [mlx-community/Inkling-mlx-2bit](https://huggingface.co/mlx-community/Inkling-mlx-2bit)
- **Memory fit:** ~315 GB weights at 2-bit (group-64 affine) with attention / embeddings / RMSNorms / router gate / short convs / relative-position bias kept in BF16. **Runs on a 64 GB Mac via SSD expert-offload** — README notes this is slow but functional because only 6 of 256 experts activate per token, so per-token weight transfer is manageable if the active experts happen to be on-disk or in unified memory. This is the **first ~1T-scale open-weight release with an explicit 64 GB Apple Silicon path**.
- **Realistic tasks:** README says **text generation is "solid"** at 2-bit; **image/audio recognizable but degraded**. So the local use case is text agentic reasoning + code, not the native multimodal Inkling was released for. Expect throughput measured in tokens-per-minute, not tokens-per-second, on M5 Max with heavy expert-offload — this is a "leave it running overnight on a hard reasoning task" model, not an interactive coding-agent substrate.
- **How to run:** `pip install mlx-lm` then `mlx_lm.generate --model mlx-community/Inkling-mlx-2bit --prompt ...` — expert-offload behavior depends on `MLX_METAL_LOAD_LIMIT` and free swap; expect the first few tokens to touch every routing decision (worst-case eviction).
- **Speed estimate:** no published M5 Max benchmark; based on similar expert-offload setups (Qwen2-235B on 96 GB Mac Studio at ~3–5 tok/s with SSD offload), expect **~1–3 tok/s** on M5 Max 64 GB with `MLX_METAL_LOAD_LIMIT` tuned. **Verify next digest.**

**Model:** Nemotron 3 Embed 1B — MLX BF16 / 8-bit / 4-bit variants ([mlx-community/Nemotron-3-Embed-1B-BF16](https://huggingface.co/mlx-community/Nemotron-3-Embed-1B-BF16), [-8bit](https://huggingface.co/mlx-community/Nemotron-3-Embed-1B-BF16-8bit), [-4bit](https://huggingface.co/mlx-community/Nemotron-3-Embed-1B-BF16-4bit))
- **Memory fit:** BF16 ≈ 2.3 GB; 8-bit ≈ 1.2 GB; 4-bit ≈ 600 MB. All three variants trivially fit alongside a 20B–70B main model on M5 Max 64 GB.
- **Realistic tasks:** Direct MLX-native replacement for the embedding layer under any mem0/LangMem/Obsidian-vault stack. Prior digest (2026-07-17) tracked Nemotron 3 Embed's **RTEB #1 (78.5% 8B / 72.4% 1B, 27% error reduction vs predecessor)** and explicit agent-memory targeting; now the 1B is directly runnable on Apple Silicon without llama.cpp intermediation.
- **How to run:** `mlx_lm` sentence-transformers interface, or via HF `pipeline("feature-extraction", ...)` with the MLX backend.
- **Speed estimate:** expect >2,000 embeddings/sec at 4-bit on M5 Max for typical 512-token chunks — encode-bound, not memory-bound.

**Model:** Qwen3.6-27B-NVFP4-mlx ([Brooooooklyn/Qwen3.6-27B-NVFP4-mlx](https://huggingface.co/Brooooooklyn/Qwen3.6-27B-NVFP4-mlx))
- **Memory fit:** 27B at NVFP4 (~4 bpw effective) ≈ 13–14 GB weights + KV headroom, comfortable on 64 GB.
- **Realistic tasks:** vision-language MoE with NVFP4 (Blackwell-first) quantization ported to MLX — worth benchmarking against Qwen3.6-27B Q4_K_M via llama.cpp to see whether NVFP4-in-MLX beats the standard 4-bit path on quality-per-byte. If parity, this becomes the vision hop under a local Justin-companion pipeline that today outsources image understanding to Claude.
- **Speed estimate:** no M5 Max-specific number yet; extrapolating from Qwen3.6-27B Q4_K_M ≈ 40–55 tok/s on M5 Max, NVFP4 should land in a similar range unless MLX's NVFP4 kernel is unoptimized on Metal.

## Conflicts & open questions

Cross-referenced against `_meta/claims-ledger.md`:

- **RECON (2607.16716) ↔ Oracle Agent Memory (arxiv:2607.13157) ↔ MOSAIC (2607.16211) ↔ MemCon (2607.13591) ↔ LongMemEval / LoCoMo / HaluMem saturation:** RECON's **22.4% ceiling** is not a direct refutation of the 93.8% Oracle number, but it **sharply scopes** it — the current wave of memory papers appears to be saturating benchmarks whose hard dimensions (cascading invalidations, source-conflict resolution over adversarial 50–100k-token corpora) were never tested. **Open question:** does *any* vault-tracked memory arch (Oracle, MSCE, MOSAIC, MemCon, EMG, mem0-classical, LangMem) score better than the 22.4% ceiling on RECON? First test would be reproducing the baseline with Oracle Agent Memory's oracle-preserving mode. **New primitive candidate: "benchmark-saturation without adversarial dimensions is not memory competence."**
- **LLM-as-a-Coach (2607.18110) ↔ Reward-Free Evolving Pairwise Validator (2607.14408):** Not a direct contradiction, but a **bandwidth trade-off** — pairwise-validator uses 1 bit per comparison, coach mode uses full textual assessment. **Open question:** at fixed token budget, does *N cheap pairwise votes* or *N/k coach passes* produce better on-policy improvement? First test would be running both on the same task with matched inference budget. This sharpens the pairwise-validator ledger claim: it is the *cheapest* reward substitute, not necessarily the *best*.
- **MSCE (2607.16621) + AgentBrew (2607.16851) ↔ SEED (2607.14777) ↔ Alipay-PIBench (2607.14573) ↔ SkillOpt / Shippy Skills:** Three papers this week converge on the same skill-lifecycle pattern from complementary angles — MSCE governs *which* memories crystallize into skills, AgentBrew *generates* the skill notes via failure-triggered Ralph Loop, SEED *distills* skill descriptions into on-policy signal. **Open question:** does the MSCE governance schema (evidence + boundaries + verification + reliability) compose with AgentBrew's Ralph Loop and SEED's on-policy distillation, or do they collide? First test: run all three on the same LoCoMo trajectory and diff the resulting skill libraries. **Emerging pattern: skill-as-first-class-artifact is now the dominant harness pattern with 7 in-window data points.**
- **Environment-free API-Calling (2607.16900, Apple) ↔ ToolVerse (2607.15660) ↔ MCPEvol-Bench (2607.14642) ↔ ToolAnchor (2607.14145):** Four papers in eight days on training + evaluating MCP-tool-calling agents. Apple's spec-only recipe is *strictly cheaper* than ToolVerse's ~400-server harvest. **Open question:** does the simulator drift in Apple's LLM-as-world-model recipe cause worse MCPEvol-Bench fragility scores than ToolVerse's real-server training? First test: train identical bases on both corpora, score both on MCPEvol's mutation operators.
- **Lomekwi (2607.16961):** **Inverse scaling on tool recognition** contradicts the intuitive "bigger model = better at every subtask" prior. If replicated on frontier models (paper tested at COLT-workshop scale), this is a new axis in the model-family-choice-is-a-safety-decision pattern (Bad Memory, Coercion & Deception): **model-choice for new-tool-design tasks might route smaller not larger**.
