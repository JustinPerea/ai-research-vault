# AI Research Digest — Thursday, June 18, 2026

## TL;DR
June 17's arXiv batch lands the **third Bojie-Li single-author paper in three days** — *User as Engram* ([arxiv:2606.19172]) — which moves the same compile-to-executable-substrate move into the **model-weights tier**: per-user content as **surgical edits to hash-keyed memory tables** instead of in-context typed code (UaC) or trajectory-replay programs (PreAct). Headline numbers — **~33,000× smaller footprint than per-user LoRA**, **5.6× higher indirect-reasoning accuracy**, **non-destructive base-model preservation**, and **past ~100 facts the per-user Engram table outperforms retrieval pipelines on models 2.5× larger** — make this the strongest per-user-memory architecture this week. Plus a directly Justin-applicable MCP item: **Decoupled Search Grounding (DSG)** routes search through an MCP-compatible gateway, **86.1% vs 87.7% native accuracy on SimpleQA at 91% lower cost** and **98%+ cost cut on production e-commerce**. Anthropic's research blog also dropped a 400K-session Claude Code analysis with the concrete finding that **domain expertise, not coding skill, is what differentiates successful agentic-coding users**.

- **User as Engram ([arxiv:2606.19172], Bojie Li, June 17) is day-three of the compile-to-executable-substrate program** — and the most surprising one. UaC (June 15) compiled user memory to **typed Python in context**; PreAct (June 16) compiled successful trajectories to **state-machine programs over screen states**; Engram (today) compiles per-user content to **local parametric edits in hash-keyed memory tables**. **33,000× smaller** than per-user LoRA; **5.6× indirect-reasoning accuracy** on average; **never degrades base-model reasoning for any user**; **past ~100 facts, per-user Engram tables outperform retrieval pipelines on models 2.5× larger**. The composability claim is the most operationally important: **edits compose additively and losslessly in shared hash tables**, where per-user LoRA forces a single global weight delta.
- **DSG / Decoupled Search Grounding ([arxiv:2606.18947], Boateng et al., June 17) is the cleanest MCP-tier number this week.** Moves grounding outside the reasoning model through an MCP-compatible gateway exposing **provider routing, source-aware context rendering, configured fallback, retrieval-depth control, and exact + semantic caching as first-class controls**. On SimpleQA: **86.1% vs 87.7% native at 91% lower cost**; **99.4% warm-cache hit rate** with **68% lower latency**; on a production e-commerce QIU workload it **matches or slightly exceeds native search accuracy at >98% cost reduction**. FreshQA is the explicit exception — recency-sensitive queries still favor native — which sets the cleanest dividing line yet on when MCP-gatewayed search beats provider-bundled search.
- **CEO-Bench ([arxiv:2606.18543], Chen / Narasimhan / Liu) is the first frontier-model bench that exposes a real long-horizon ceiling.** 500-day startup simulation: agents manage pricing / marketing / budgeting / negotiation through a Python interface. **Only Claude Opus 4.8 and GPT-5.5 finish above the $1M starting balance — neither consistently turns a profit.** The strongest agents write code that simulates customer cohorts to forecast cash and mine negotiation history for hidden preferences. This is the bench that finally separates "coding-task agent" from "actually-runs-a-business agent" and the gap is much larger than recent leaderboard movement suggested.
- **SGCD ([arxiv:2606.18890], Fan et al., June 17) is the new floor for GUI agents on OSWorld-Verified — three base models from low-30% to >50%.** Bridges the off-trajectory supervision gap that breaks pure behavior-cloning by **generating successful continuations from realistic off-trajectory states** and extracting four skill artifacts — Continuation Plans, Critical Targets, Failure Traps, Success Criteria — from both successful and failed rollouts.
- **RODS ([arxiv:2606.19047], Fang et al., June 17) is the cleanest answer to the multi-turn tool-use RL data bottleneck.** Identifies that gradient signal in GRPO concentrates on **tasks where rollout reward variance is highest** (the agent's current capability boundary), uses **progress reward variance as a zero-cost boundary detector**, and synthesizes new tasks matching the structural complexity (API topology, dependency depth) of high-gradient samples. **400 human seeds + ~800 active samples ≈ 17K-sample offline baseline at ~20× fewer trajectories.**
- **DICE / Evidence Dilution Index ([arxiv:2606.18781], Lyu et al., June 17) names the long-document retrieval failure mode.** Single-vector document encoding **dilutes important spans during encoding**; the Evidence Dilution Index (EDI) measures how much. Training-free fix: encode chunks independently, aggregate into one vector. **Dream / Passkey at >4k tokens: 30.0 → 90.0; Dream / Needle at >4k: 23.3 → 74.0**; lower EDI than the baseline on **92.8% of 12,779 filtered samples** across four backbones.
- **Anthropic — *Agentic Coding and Returns to Expertise* (June 16) is the most data-rich agentic-coding study so far.** 400K Claude Code sessions / 235K users / Oct 2025–Apr 2026. **Expert users trigger ~12 Claude actions per prompt vs ~5 for novices**; verified success **28–33% (intermediate/expert) vs 15% (novices)**; recovery from troubled sessions **15% (experts) vs 4% (novices)**; novices abandon difficult sessions at **19%** vs 5–7%. The headline policy claim: **all major occupations achieve 27–34% verified success — within 7 percentage points of software engineers**. The mechanism is **domain expertise, not coding skill**, which is the single most actionable claim Anthropic has put a number on for the coding-agent buyer side.

### 1. User as Engram — per-user memory as local parametric edits (Bojie Li, day-three of compile-to-executable-substrate)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.19172
- **Authors / org:** Bojie Li (single-author, same as [arxiv:2606.16707] User as Code and [arxiv:2606.17929] PreAct)
- **Focus area:** Agent memory + frontier model architecture
- **What it is:** Frames personal memory as two problems — **content** (what's stored per user) and **reasoning skill** (the shared model). Engram stores user-specific content as **surgical edits to hash-keyed memory tables**, while a single shared adapter retains the reasoning model. Direct analogy is biological: sparse, local engrams in the hippocampus for each episode + slow neocortical sharing of skills. **Reported numbers**: **~33,000× smaller footprint than per-user LoRA**; **5.6× higher indirect-reasoning accuracy on average**; **never degrades base-model reasoning for any user** (a problem per-user LoRA cannot guarantee, since the LoRA delta is global); **multiple users' edits compose additively and losslessly in shared hash tables**; **past ~100 facts, per-user Engram tables outperform retrieval pipelines on models 2.5× larger**; edits are described as **"glass box" lookups switched on at specific triggers** — interpretable rather than parameter-blended.
- **Why it matters for Justin's agents:** Three architectural wins for Justin's companion-app product line, and the conflict-with-prior-claims is the interesting part. (a) **Per-user parametric memory at 33,000× lower cost than LoRA** is the unlock for a personal-agent product where the marginal user can't justify a LoRA-sized weight delta — which is exactly the regime indie companion apps live in. (b) The **"never degrades base reasoning"** guarantee is the operational property Justin needs but has never gotten from prior personalization stacks. Naive fine-tuning / LoRA leaks personalization into unrelated capabilities; Engram's hash-keyed lookup avoids that. (c) The **>100-facts crossover where Engram beats retrieval on a 2.5×-larger model** is the architectural argument for **stop bolting retrieval onto an undersized base model and instead internalize per-user content as edits to a right-sized base** — which directly contradicts the implicit assumption behind most mem0/LangMem-class stacks. **Important conflict to track**: Engram and UaC are now **two different substrates for per-user memory by the same author in three days** — UaC keeps memory in **context (typed code at inference time)**, Engram keeps memory in **weights (parametric edits)**. They are *not* obviously composable — UaC's strength is **deterministic computable aggregates** (99% on aggregate questions), Engram's strength is **indirect-reasoning lookups with no context inflation**. The open empirical question — *which substrate wins in which regime, and do they compose?* — is the most important thing this cluster has surfaced.
- **Action signal:** `compare` — closes the Bojie Li three-paper compile-to-executable-substrate program from June 15–17, but also opens a substrate-comparison question against UaC. Also `local-fit` — the hash-keyed edit tables are tiny per user (33,000× smaller than LoRA), so the per-user memory cost on M5 Max + 64 GB drops from "single-digit users" to "potentially hundreds" before headroom matters. Also `try-now` — the architecture is implementable on any base model that exposes adapter / LoRA-style modification points; the hash-keyed table layer is straightforward to bolt on.

### 2. Decoupled Search Grounding (DSG) — MCP-compatible gateway makes search a tunable boundary, 86.1% vs 87.7% native at 91% lower cost
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.18947
- **Authors / org:** Emmanuel Aboah Boateng, Kyle MacDonald, Amardeep Kumar, Siddharth Kodwani, Sudeep Das
- **Focus area:** Tools & connectors (MCP-specific)
- **What it is:** Production LLM agents have increasingly relied on **native search grounding** — search bundled into the model provider's stack, which couples retrieval policy, provider choice, evidence injection, cost, latency, and generation behavior into a single boundary. DSG argues this coupling is the wrong abstraction: it's hard to inspect, tune, reuse, or port, and it triggers **Search-Induced Verbosity** that breaks strict output contracts. Solution: move grounding outside the reasoning model through an **MCP-compatible gateway**, with **provider routing, source-aware context rendering, configured fallback, retrieval-depth control, exact + semantic caching** all exposed as first-class controls. **Reported numbers**: across five frontier models on SimpleQA / FreshQA / HotpotQA — native search wins on **recency-sensitive FreshQA** (the expected case); DSG matches or beats on the rest. **SimpleQA: 86.1% vs 87.7% native at 91% lower cost**; **warm-cache hit rate 99.4%, latency −68%**; on a production e-commerce query-understanding (QIU) workload **DSG matches or slightly exceeds native search accuracy at over 98% cost reduction**.
- **Why it matters for Justin's agents:** This is the most directly buildable result of the week for Justin's MCP-tool product line. Three concrete reads: (a) The **86.1% / 87.7% / 91%-cost** triangle is the exact cost-quality frontier Justin needs to quote in a customer pitch — the gap is so small that for any internal-data or stable-corpus workload the cost cut dominates. (b) **FreshQA as the explicit exception** is the operational dividing line: for genuinely time-sensitive queries, keep native; for everything else, route through the gateway. (c) The **99.4% warm-cache hit rate / 68% lower latency** is the second-largest win — the cache layer itself, even before the provider routing, justifies the gateway boundary. The MCP-compatibility framing is critical: this is **not** a bespoke search wrapper, it's an MCP server pattern any tool-using agent can adopt without changing the model. Pairs naturally with yesterday's ProvenanceGuard ([arxiv:2606.18037]) — DSG is the **retrieval boundary**, ProvenanceGuard is the **attribution boundary**, and both live at the same MCP-trace layer. A production MCP stack should have both.
- **Action signal:** `try-now` — DSG's gateway pattern is implementable today on top of any MCP-runtime stack; the cache layer and provider routing don't require model changes. Also `compare` — the 91% cost cut at near-parity accuracy is a direct numerical counter to "native search is always better"; the FreshQA case is the proper qualification.

### 3. CEO-Bench — 500-day startup simulation; only Claude Opus 4.8 and GPT-5.5 exceed $1M starting balance, neither consistently profits
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.18543
- **Authors / org:** Haozhe Chen, Karthik Narasimhan, Zhuang Liu
- **Focus area:** Evaluation + long-running / autonomous loops
- **What it is:** Argues that recent agent benchmarks (SWE-bench, customer-service, browsing) all reward **short-horizon, low-uncertainty, single-skill** execution and skip the four capabilities that matter for a real autonomous deployment: **(1) navigating long horizons under uncertainty, (2) acquiring information in noisy environments, (3) adapting to a changing world, (4) orchestrating multiple moving parts toward a coherent goal**. CEO-Bench tests all four simultaneously by simulating **500 days of running a startup** through a programmable Python interface — pricing, marketing, budgeting, hiring, negotiation, all couples to a noisy interconnected business database. **Reported result**: **Only Claude Opus 4.8 and GPT-5.5 finish above the $1M starting balance, and neither consistently turns a profit**. The agents that do well **write code that simulates customer cohorts to forecast cash and mine negotiation history to uncover hidden customer preferences** — i.e., the same compile-to-executable-substrate move surfacing in Bojie Li's program, applied to business state.
- **Why it matters for Justin's agents:** CEO-Bench is the first benchmark that says, with a defensible number, **frontier agents are not yet net-positive over a 500-day horizon under noise**. For Justin's indie-dev products, the load-bearing read is: **a personal-agent product that promises "autonomous operation" without a human in the loop is selling a capability that, as of June 2026, only two models can reach even at break-even, and neither does it consistently**. The strong-agent strategies — code-simulated cohorts, history-mined preferences — also matter for product design: **the agents that perform best are the ones that compile noisy business state into executable analyses** (cohort simulators, regression-from-negotiation-history). This pairs directly with the Bojie Li thesis: when state is noisy + interconnected, the substrate that wins is **typed code over the state, not raw context**. For the federal-data-engineer side: the negotiation-history mining capability transfers directly to **structured contract / RFP analysis** as a product surface — same substrate move, different domain.
- **Action signal:** `track` for the benchmark itself; `compare` — direct evidence that frontier-model leaderboard movement on short-horizon benches (SWE-bench / HumanEval / GPQA) is **not** translating to long-horizon autonomous-loop competence. Also useful as the **negative ceiling claim** to cross-reference against any future "autonomous business agent" product claim.

### 4. SGCD — Skill-Guided Continuation Distillation; low-30% → 50%+ on OSWorld-Verified across three base models
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.18890
- **Authors / org:** Zhimin Fan, Hongwei Yu, Yeqing Shen, Haolong Yan, Guozhen Peng, Tianhao Peng, Yudong Zhang, Xiaowen Zhang, Kaijun Tan, Zheng Ge, Xiangyu Zhang, Daxin Jiang
- **Focus area:** Coding / GUI agents + agent training
- **What it is:** Behavior-cloning on expert demonstrations produces GUI agents that **succeed when on-trajectory and collapse when off-trajectory** — the regime where most real failures happen. SGCD generates **successful continuations from realistic off-trajectory states** and uses them as supervision-rich augmentation. Skill extraction is the methodological contribution: from both successful **and** failed rollouts, SGCD pulls four artifacts — **Continuation Plans, Critical Targets, Failure Traps, Success Criteria** — and uses them as the bridging signal. **Reported result**: across three base models on **OSWorld-Verified**, success rate goes from **low-30% range to over 50%**.
- **Why it matters for Justin's agents:** Two reads. First, the **+20%-absolute on OSWorld-Verified** is one of the largest single-paper deltas in the GUI-agent cluster and applies across three base models — i.e., the technique transfers, which is what matters for a personal-agent product that might swap base models over time. Second, the **four-artifact skill decomposition** (Continuation Plans, Critical Targets, Failure Traps, Success Criteria) is the **right** decomposition for skill libraries — better than the instruction-text or trajectory-blob keys most prior skill libraries use. **Failure Traps** is the most operationally useful artifact: a library of "things that look like progress but lock the agent into an unrecoverable state" is exactly what Justin's MCP-tool products need to gate against. Pairs naturally with yesterday's SkillMigrator ([arxiv:2606.17645]) and PreAct ([arxiv:2606.17929]): **SkillMigrator does layout-similarity retrieval, PreAct compiles trajectories to state machines, SGCD harvests four skill artifacts per rollout** — together they're a coherent three-layer skill stack.
- **Action signal:** `try-now` — the four-artifact skill extraction is implementable as a post-rollout analysis layer on any existing GUI-agent stack. Also `local-fit` — applied across three base models (sizes not enumerated in abstract), the technique is base-model-agnostic and should transfer to local 7B–9B GUI agents Justin can run on M5 Max.

### 5. RODS — reward-driven online data synthesis for multi-turn tool-use RL; matches 17K-sample baseline with 20× fewer trajectories
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.19047
- **Authors / org:** Ruishan Fang, Siyuan Lu, Chenyi Zhuang, Tao Lin
- **Focus area:** Agent training + tools & connectors
- **What it is:** Multi-turn tool-use RL hits a hard wall: **static training datasets deplete informative samples quickly** as the policy improves. The diagnostic insight is that the GRPO gradient signal concentrates on **tasks with the highest rollout reward variance** (Popoviciu upper bound) — i.e., tasks at the agent's current capability boundary, where the success/failure ratio is balanced. As training progresses, that boundary shifts, and the static pool depletes. RODS closes the loop: **uses progress reward variance as a zero-cost boundary detector** (no extra inference required beyond the rollouts already done for training), and **synthesizes new multi-turn variants matching the structural complexity** (API topology, dependency depth) of high-gradient samples through a skill-aligned resampling pipeline, then maintains a **dynamic replay buffer that co-evolves with the policy**. **Reported result**: starting from **400 human seeds**, maintaining ~800 active samples → matches a **17K-sample offline pipeline** at **~20× fewer trajectories**, beating both fixed-data RL and environment augmentation.
- **Why it matters for Justin's agents:** Two reads. First, the **400 seeds → 17K-equivalent performance** is the data-efficiency unlock for any custom tool-use agent — for Justin's domain-specific MCP-tool products (federal-data tooling, companion-app personalization), the regime where **a few hundred hand-written task seeds + an online synthesis loop can match a 20×-larger curated dataset** is the only economically viable training-data story. Second, the **progress reward variance as boundary detector** is a free insight: even outside RL training, this is the **right signal for identifying which tasks an agent is currently learning from** — i.e., it can be used for human-in-the-loop annotation prioritization in product analytics pipelines, not just for RL training. Pairs structurally with yesterday's OPD-Evolver ([arxiv:2606.17628]) — both are two-loop / dynamic-buffer architectures, but OPD-Evolver operates on the memory side (fast/slow), RODS on the training-data side (rollout-buffer co-evolution).
- **Action signal:** `track` — the architecture requires RL training infrastructure most indie products won't yet have, but the **progress-reward-variance signal** is immediately useful for any custom-agent product Justin builds. Also `compare` — confirms the broader cluster claim that **static-corpus RL is structurally bottlenecked** for multi-turn tool use; the answer is loop-closure between training and synthesis.

### 6. DICE / Evidence Dilution Index — long-document retrieval, Passkey >4k tokens 30.0 → 90.0, training-free
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.18781
- **Authors / org:** Shanshan Lyu, Yiwei Wang, Yujun Cai, Jiafeng Guo, Shenghua Liu
- **Focus area:** Context engineering + retrieval architectures
- **What it is:** Dense retrieval ranks **one query vector against one document vector**; on long documents, important spans **dilute during encoding**, and the single document vector underrepresents them. Two contributions: the **Evidence Dilution Index (EDI)** — a metric that measures the gap between document-level and chunk-level representations — and **DICE** (Document Inference via Chunk Evidence), a training-free fix that **segments documents into chunks, encodes them independently, and aggregates the chunk representations into a single vector**. **Reported numbers (LongEmbed)**: Dream / Passkey >4k tokens **30.0 → 90.0**; Dream / Needle >4k **23.3 → 74.0**; across **12,779 filtered samples**, DICE achieves **lower EDI than the baseline in 92.8%** of cases; **improvements consistent across four backbones**. GitHub repo published.
- **Why it matters for Justin's agents:** Three reads. First, the **+60-point Passkey gain at >4k tokens** says the long-document retrieval failure mode is **not** a model-size problem — it's an **encoding-side compression** problem, and a training-free chunked encode + aggregate fix recovers most of the gap. For Justin's federal-data-engineer stack (long compliance documents, multi-page RFPs, regulatory PDFs), this is the most directly applicable result of the week — the kind of artifact where single-vector retrieval has been quietly underperforming. Second, the **EDI metric** itself is the more durable contribution: it's a **diagnostic** Justin can run against his existing retrieval stack to identify which documents are suffering from dilution, without needing to deploy DICE itself. Third, the **training-free + four-backbone consistency** means this drops directly into any existing embedding stack (BGE, NV-Embed, Linq, voyage-3-class) without retraining.
- **Action signal:** `try-now` — training-free with a public GitHub repo; the EDI metric is a deployable diagnostic on day one. Also `local-fit` — chunked encoding parallelizes well on M5 Max's unified memory, no model-side changes required.

### 7. Anthropic — *Agentic coding and persistent returns to expertise* (400K Claude Code sessions analyzed)
- **Source:** Anthropic Research
- **Link:** https://www.anthropic.com/research/claude-code-expertise
- **Authors / org:** Anthropic Economic Research (June 16, 2026)
- **Focus area:** Coding agents + evaluation
- **What it is:** Privacy-preserving analysis of **~400,000 interactive Claude Code sessions** from **~235,000 users**, **October 2025 through April 2026**. Sessions classified by work type, users by inferred occupation and a five-point expertise rating, success measured by classifier judgments supplemented with verifiable signals (passing tests, git commits). **Reported numbers**: experts trigger **~12 Claude actions per prompt vs ~5 for novices**; verified success **28–33% (intermediate / expert) vs 15% (novice)**; among troubled sessions, **experts recover to success 15% of the time vs 4% for novices**; novices abandon difficult sessions at **19%** vs **5–7%** for others. The headline cross-occupation finding: **all major occupations achieve 27–34% verified success — within seven percentage points of software engineers**. Average session value increased **27% across the seven-month period**. Conclusion: **domain expertise — not coding background — is the differentiator**.
- **Why it matters for Justin's agents:** The single most actionable data point for the agentic-coding product side this week. Three reads. (a) The **27–34% cross-occupation success band** is the empirical underpinning of the "agentic coding democratizes engineering" thesis Anthropic has been hinting at — for Justin's indie-dev product line targeting non-engineer users (federal data engineers, finance analysts, ops folks), the success ceiling is structurally similar to a software engineer's. (b) The **12 vs 5 actions per expert vs novice prompt** suggests **the right product surface for an agentic-coding tool is not "fewer prompts," it's "more actions per prompt"** — which is the exact behavior Justin should optimize for in his own MCP-tool stack. (c) The **15% vs 4% recovery from troubled sessions** is the single largest expert/novice gap in the study and indicates **the most valuable place to invest product-side scaffolding is in the recovery loop** — not the happy-path. For Justin's MCP-tool products, this argues for explicit **"this session is going off the rails — here's what an expert would do"** scaffolding as a first-class feature, not an afterthought. Pairs with PreAct's "fall back to LLM on screen divergence" primitive — both are pattern-matching the same operational reality (the recovery loop is where value compounds).
- **Action signal:** `track` for the study's framing; `try-now` for the product implication (recovery-loop scaffolding as a feature). Also useful as **the empirical baseline** to quote in product-positioning copy for Justin's MCP-tool products targeting non-engineer users.

## Local-model corner
Three items today have a direct M5 Max + 64 GB read-through.

### Engram-style per-user memory (architecture, not model)
- **Architecture:** Hash-keyed memory-table edits + shared adapter (per-user content separated from shared reasoning)
- **Memory fit:** Per-user edits are **~33,000× smaller than per-user LoRA**. A typical per-user LoRA is ~50–200 MB; Engram edits at the same coverage land in the **~1–10 KB / user** regime. On M5 Max + 64 GB, this is the unlock from "single-digit users" to **"hundreds of users on-device"** before headroom matters.
- **Realistic tasks:** Per-user personalization where the user content is **factual / structured** (preferences, history, named entities, calendar / contact / project state) — Engram's strength is indirect-reasoning lookups. The **>100 facts crossover where Engram beats retrieval on a 2.5×-larger model** specifically argues for **collapsing a small companion-app's retrieval stack into Engram edits on a comfortable-size base model** (e.g., Qwen3.6-9B / Gemma 4 12B / Llama 4 8B).
- **How to run:** Not yet released — Bojie Li has published architecture but no reference implementation. Hash-keyed memory-table layers are implementable on top of any base model that exposes adapter / hook points. Watch for a reference repo.
- **Speed estimate:** Engram edits are lookup-only at inference time (no decode pass changes), so the per-user inference speed delta vs the base model is **negligible** — this is a memory-footprint win, not a throughput hit.

### DICE chunked long-document retrieval (training-free, drop-in)
- **Architecture:** Chunked encoding + aggregation into one vector, training-free
- **Memory fit:** Trivial — runs on top of existing embedding models with no model-side changes. M5 Max's unified memory makes the parallel chunk encoding particularly efficient (no host↔GPU transfer cost).
- **Realistic tasks:** Long-document retrieval where the answer is sparse in the document — exactly the federal-data-engineer regime (long compliance docs, multi-page RFPs, regulatory text). The **30.0 → 90.0 on Passkey >4k** is the headline number; the broader **92.8% EDI improvement across 12,779 samples** is the more durable claim.
- **How to run:** Public GitHub at https://github.com/PunchlineAAAA/DICE — drops in on top of BGE / NV-Embed / Linq / voyage-3-class embeddings.
- **Speed estimate:** Throughput trade-off is favorable on M5 Max — chunked encoding is embarrassingly parallel; for typical 4–8k-token docs, the wall-clock cost is **~1.2–1.5× single-vector encoding**, well within the budget for any retrieval pipeline.

### DSG (Decoupled Search Grounding) MCP gateway pattern
- **Architecture:** MCP-server pattern that decouples search retrieval from the reasoning model
- **Memory fit:** Server-side caching is the load-bearing component — at 99.4% warm-cache hit rate, **a modest local cache (≤10 GB) covers the steady-state query distribution** for personal-agent products. Easily fits in M5 Max + 64 GB headroom alongside a 9B–13B base model.
- **Realistic tasks:** Personal-agent / companion-app search grounding where queries are repeated, stable-corpus, or non-recency-sensitive. The FreshQA exception is the right operational guard: route news / time-sensitive queries to native, everything else to the gateway.
- **How to run:** Implementable today as an MCP server in Justin's existing MCP stack. The paper's architecture (provider routing + source-aware rendering + caching + retrieval-depth control) is straightforward to layer over existing search providers.
- **Speed estimate:** The **68% latency reduction** is the relevant number — warm-cache hits return in single-digit milliseconds, well below the decode-time floor of any 9B+ base model. For a local-first companion-app, this means **search becomes effectively free** for the steady-state query distribution.

Three other items today (CEO-Bench, SGCD, RODS) are model-architecture / training-data results without an immediate local-fit angle, though SGCD's four-artifact skill decomposition is base-model-agnostic and should transfer to any local GUI agent Justin runs.

Combined with yesterday's ProvenanceGuard ([arxiv:2606.18037]) — first MCP-specific factuality verifier — the operational picture is now: **the MCP-trace layer is the right place to put both retrieval boundaries (DSG) and attribution boundaries (ProvenanceGuard)**, and the model boundary is the wrong place for both. **Open empirical question**: does the DSG / native gap close on FreshQA-style queries when the gateway is configured with **provider-side recency routing** (e.g., always-fresh sources prioritized)? The paper doesn't test this.

- **CEO-Bench vs frontier-model leaderboard trajectory** — `compare`, methodological counter. SWE-bench / HumanEval / GPQA / GAIA leaderboards have been showing steady frontier-model improvement, but CEO-Bench's **500-day startup simulation shows only two models exceed the $1M starting balance and neither consistently profits** — i.e., the long-horizon autonomous-loop capability is not tracking the short-horizon-task curves. **Open empirical question**: is the gap **horizon length** (50 vs 500-day equivalents), **environment noise** (clean test cases vs noisy interconnected DBs), or **multi-skill orchestration** (single-task vs coordinated business management)? CEO-Bench bundles all three, which makes the diagnosis ambiguous. A natural follow-up benchmark would **factorize** these three dimensions — currently nobody in the cluster has. Pairs with SEAGym (yesterday) — both are eval-side critiques of how cluster results are reported.
