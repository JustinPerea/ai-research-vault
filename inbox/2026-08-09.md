# AI Research Digest — Sunday, August 9, 2026

## TL;DR
- **LLM within MCP Matters** [arxiv:2608.08467] is the MCP-host paper of the week: 54,000 trials × 24 models (9 Claude / 6 Gemini / 9 GPT) on a production legal-information MCP server. Servers embed lookup tables in *server instructions* so the model can skip search. When the search tool is removed, **23/24** models read the embedded table (hit ≥ 98%). When search is merely *present*, **9 models drop below 15%**. A 2³ of instruction-level interventions restores ≥ 86% for 20/24 — but single interventions backfire by family. Per-server prompt engineering is a workaround; the host should put server instructions *ahead of* tool selection.
- **Hierarchical Self-Improvement (HSI)** [arxiv:2608.08466] makes the harness task-specific and hot-swappable: frozen model *M*, task harness *H*, an evolver that rewrites *H*, a meta-evolver that rewrites the evolver, frozen outer anchor. Thinking off at task time, on at self-modify time, to isolate harness credit. BALROG + DeepSeek-V4-Flash-Preview: **+39.3 / +33.0 / +25.0 / +15.0** raw progress on BabyAI / Crafter / TextWorld / MiniHack; held-out BabaIsAI 0.98 / 1.00. On NLE (beyond backbone), harness evolution does **nothing**. Two named bounds: feedback-fidelity and backbone-capability. Code: github.com/TailinZhou/hsi.
- **Skill Runtime Intelligence** [arxiv:2608.08793] is the observability layer progressive-disclosure skills actually need. A Skill can be discovered-but-not-activated, activated-without-instructions, or "successful" without a verified outcome. Run Panorama separates immutable events / deterministic relations / inferred diagnoses / controlled outcomes with four evidence grades. 126 executions × 3 coding agents × 7 conditions: every run preserves the worktree and maps to one session, but the three adapters *do not agree on what a Skill failure looks like*. Raw views emit failure on all 18 clean cases; Panorama emits none.

## Items

### 1. LLM within MCP Matters: Measuring Inefficient Resource Utilization Driven by LLMs
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2608.08467
- **Authors / org:** Minhan Cho / Soyoung Park / Kihyeon Jeong / Byeongkyu Jeon / Daejin Choi / Jinyoung Han
- **Focus area:** Tools & connectors (MCP host behavior)
- **What it is:** Tests whether client LLMs actually consume data that MCP servers embed in server instructions (the system-prompt text handed to the host). 54,000-trial study, 24 LLMs, production legal-information MCP server. Diagnostic: remove the competing search tool → 23/24 models read the embedded table (hit ratio ≥ 98%), so the failure is preference, not capability. With search present, 9 models drop below 15% hit. 2³ factorial of three instruction-level interventions: combining all three restores ≥ 86% for 20/24; individual interventions can *hurt* specific families. Conclusion: stop prompt-engineering each server; the MCP *host* needs an explicit "read server instructions before selecting a tool" stage.
- **Why it matters for Justin's agents:** Claude Code + every Mitamaton MCP server that stuffs enums, ID tables, or "preferred workflow" into server instructions is paying tokens for text the model will ignore the moment a search tool exists. Two concrete moves: (1) do not embed large lookup tables in MCP instructions — expose them as a cheap `lookup` tool or a resource the host pins *above* tool choice, (2) if you must embed, assume Claude will still call search unless the host forces instruction-first. This is a host-app bug, not a server-authoring tip.
- **Action signal:** `try-now` — pick one Mitamaton / Claude Code MCP server that embeds a table, A/B "search tool present vs absent," and count how often the model re-discovers a value that was already in the instructions.

### 2. Hierarchical Self-Improvement: A Framework for Task-Specific Evolvable Agent Harnesses
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2608.08466
- **Authors / org:** Tailin Zhou (independent)
- **Focus area:** Task-specific harness evolution
- **What it is:** Each task family owns a harness, hot-swapped through a fixed task-injection seam, rewritten from environment feedback. Three scopes, one frozen LLM: task harness *H*, evolver (rewrites *H*), meta-evolver (rewrites the evolver's strategy code) under a frozen outer anchor. Thinking-on/off isolates harness credit (reasoning disabled during task execution, enabled during self-modification). Bounds: evolution needs informative reward (feedback-fidelity); it cannot outrun the frozen backbone (backbone-capability). BALROG, DeepSeek-V4-Flash-Preview: +39.3 BabyAI, +33.0 Crafter, +25.0 TextWorld, +15.0 MiniHack (raw % progress vs initial harness). Held-out BabaIsAI: 0.98 BreakStop, 1.00 GoTo on a 20% unseen split. NLE: no gain. Code: https://github.com/TailinZhou/hsi
- **Why it matters for Justin's agents:** Complements HarnessOpt-Bench (Fri) with an actual loop, and Ouroboros (Sat) with a *task-specific* rather than global self-edit. The Mitamaton port is "one harness per task family" (calendar-prep ≠ inbox-triage ≠ coding) and a frozen outer anchor that the evolver cannot touch (authorization, SARA-style argument gates). The NLE zero is the honest limit: if the local 4B cannot do the task, rewriting the prompt will not save it.
- **Action signal:** `compare` — evolve a calendar-prep harness for 5 iterations on a held-out week; keep tool-authorization in the frozen anchor.

### 3. Evidence-Calibrated Runtime Reconstruction for Agent Skills Across Heterogeneous Coding Agents
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2608.08793
- **Authors / org:** Xueping Gao (independent)
- **Focus area:** Agent skills + observability (progressive disclosure)
- **What it is:** Progressive loading creates failure boundaries that session/model/tool traces miss: discovered but not activated; activated without instructions; apparent success without an independently verified outcome. Skill Runtime Intelligence is a *passive* reconstruction layer across heterogeneous harnesses; unsupported stages stay unknown. Run Panorama: immutable events, deterministic relations, inferred diagnoses, controlled outcomes, four evidence grades; optional trace import + OTLP/HTTP. 6 frozen repo profiles × 3 coding agents × 7 clean/fault conditions = 126 executions; each preserves the source worktree and maps to exactly one source session. Adapters disagree: one reports no Skill runs; one reports complete runs and no failure-like events; one reports failure-like events in every operational-failure *and* every clean session. In a 7-template diagnostic, semantic aliases and Panorama localize the same six non-clean boundaries but differ on exact/status; both Raw views emit failure status on all 18 clean cases, Panorama on none. Known-rule graph: 126/126 frozen contracts; a second model completes only 228/378 calls.
- **Why it matters for Justin's agents:** If Justin is going to evolve `SKILL.md`s (WikiSkill / SkillProx / HSI), he needs to know whether Claude Code *loaded* the skill, *followed* it, or just succeeded. Current session logs will not say. Minimum viable: log skill name seen → skill body fetched → first matching tool call → independently checked outcome, and refuse to mark a skill as "working" on the last step alone. The three-adapter disagreement is why you cannot trust an off-the-shelf "Claude Code analytics" export.
- **Action signal:** `compare` — add a four-field skill-lifecycle line to Claude Code session notes for a week (seen / fetched / used / verified) before building anything fancier.

## Conflicts & open questions
- **Conflict flagged:** MCP-Matters says the model *prefers a tool over instructions sitting in context*. Skill-Use [arxiv:2608.04828, Wed] says the model often *fails to trigger* a skill that is sitting behind progressive disclosure. Same family of bug (the model does not consume the thing you put in front of it), opposite surface (over-eager tool vs under-eager skill). A host that forces "read instructions first" (MCP-Matters) might *help* Skill-Use Trigger — unrun.
- **Convergent with HSI + HarnessOpt-Bench + Ouroboros:** three papers, three units of evolution (task-family harness, optimizer protocol, global self-editing repo). No head-to-head. Justin should pick *one* unit.
- **Open question:** Skill Runtime Intelligence's "event presence ≠ boundary fidelity" is a warning for any vault claim that cites Claude Code logs as evidence a skill fired.
