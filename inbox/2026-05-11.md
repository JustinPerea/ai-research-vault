# AI Research Digest — Monday, May 11, 2026

## TL;DR
- **Three new agent-memory papers landed in two days, and they argue different things.** "When Stored Evidence Stops Being Usable" shows HippoRAG drops **16–20 pp** when irrelevant sessions accumulate (even within budget); "MEMOREPAIR" knocks stale-derivative exposure from 69.8–94.3% down to **0%** via cascade repair; and "The Memory Curse" reports that **expanded recall *degrades cooperation* in 18/28 model-game settings** in multi-agent games — deliberation amplifies it. Memory is the unsolved layer of the agent stack.
- **Tool selection is a linear feature.** A single mean-difference vector (one row of the output layer) **steers tool choice with 93–100% accuracy on 4B+ models** across Gemma 3 / Qwen 3 / Qwen 2.5 / Llama 3.1. Models with small top-1/top-2 gaps produce **14–21× more wrong calls**. Practical: cheap pre-call confidence signal for free.
- **Tool-call routing nets 84% cost reduction at matching accuracy.** Switchcraft (DistilBERT classifier) routes function-calling queries across models and reports **82.9% accuracy** matching the best individual model while saving **$3,600+/M queries** — a concrete production lever for MCP gateways.
- **Anthropic donates Petri 3.0** (its agentic-alignment auditing suite) to **Meridian Labs**, a new independent eval nonprofit, alongside Inspect and Scout. Open governance signal for agent eval infrastructure.
- **Slow blog week** — Google DeepMind, Meta, Google Research, Mistral, OpenAI all quiet since last digest. arXiv carried the day.

## Items

### 1. The Memory Curse: How Expanded Recall Erodes Cooperative Intent in LLM Agents
- **Source:** arXiv (cs.CL, May 8, 2026)
- **Link:** https://arxiv.org/abs/2605.08060
- **Authors / org:** Jiayuan Liu, Tianqin Li, Shiyi Du, Xin Luo, Haoxuan Zeng, Emanuel Tewolde, Tai Sing Lee, Tonghan Wang, Carl Kingsford, Vincent Conitzer (CMU)
- **Focus area:** Agent memory / Agent orchestration / Long-running loops
- **What it is:** Tests **7 LLMs across 4 cooperation games**, 500+ rounds each, on 378K analyzed reasoning traces. Finding: **expanded accessible history degrades cooperation in 18 of 28 model-game settings**. Mechanism (via lexical analysis + LoRA-probe cognitive probes + synthetic-memory sanitization): longer recall doesn't increase *distrust* — it erodes *forward-looking cooperative intent*. Counterintuitive secondary finding: **explicit deliberation amplifies the memory curse** rather than countering it.
- **Why it matters for Justin's agents:** Direct empirical pushback on the "just give it more memory" intuition for multi-agent companion-app and orchestration stacks. Two practical takeaways. (1) For multi-agent setups (planner + worker, debate ensembles, persistent personas), **bigger memory windows can make agents *less* cooperative** with each other and with the user — measure cooperation outcomes, not just retrieval recall. (2) **CoT-on-memory is dangerous**: if the chain reasons over its full recall before acting, you may be amplifying defection signals. Argues for memory budgets shaped around *role* rather than just *recency*, and for evaluating memory configs on downstream cooperative outcomes (not benchmark recall).
- **Action signal:** `compare` — directly contradicts the "more memory is better" prior implicit in [arxiv:2605.06614] SkillOS (external markdown skill repo grows over time) and [arxiv:2605.05583] Belief Memory (multi-conclusion entries). Open empirical question: do Belief-Memory or skill-curated approaches inherit the curse, or does the structure of *what* is recalled change the answer?

### 2. When Stored Evidence Stops Being Usable: Scale-Conditioned Evaluation of Agent Memory
- **Source:** arXiv (cs.AI, May 8, 2026)
- **Link:** https://arxiv.org/abs/2605.07313
- **Authors / org:** Jiaqi Shao, Yiyi Lu, Yunzhen Zhang, Bing Luo
- **Focus area:** Agent memory / Evaluation
- **What it is:** Evaluation protocol that **holds task evidence fixed while irrelevant sessions are added** — isolates the failure mode where stored evidence stops being *findable* under scale, independent of whether it's *correct*. Tested 3 memory-interface types (flat / planar / hierarchical) × 2 benchmarks (LongMemEval, LoCoMo) × 4 metrics (budget-compliant reliability, memory-call burden, failure category, usability boundary). Headline: **HippoRAG reliability falls 16–20 percentage points** as irrelevant sessions grow, even while staying within the call budget. Qwen3-8B exceeds the memory-call budget entirely on scale; 32B/235B variants stay reliable in the tested range.
- **Why it matters for Justin's agents:** Most agent-memory evals fix the corpus and vary the query — this paper fixes the *task* and varies the *clutter*. That's the realistic production failure mode for a long-running companion app: the system accumulates irrelevant sessions across months, and even correctly-stored evidence becomes invisible to retrieval. The 16–20 pp HippoRAG drop is a sharp number for a system Justin would plausibly reach for. Plus: **memory-call budget is a real bottleneck on small models** — Qwen3-8B can't stay inside it on this scale. Useful operational target — if your memory backend can't survive an "add N irrelevant sessions" stress test, it won't survive a long-running user.
- **Action signal:** `compare` — sharpens [arxiv:2605.06527] STALE (which isolated implicit-conflict detection) and [arxiv:2605.05583] Belief Memory (multi-conclusion entries) by adding a *third* failure mode (scale-induced usability loss) orthogonal to both. Run this stress test on any memory layer before shipping.

### 3. MEMOREPAIR: Barrier-First Cascade Repair in Agentic Memory
- **Source:** arXiv (cs.AI/cs.CL, May 8, 2026)
- **Link:** https://arxiv.org/abs/2605.07242
- **Authors / org:** Yang Zhao, Chengxiao Dai, Mengying Kou, Yue Xiu
- **Focus area:** Agent memory / Long-running loops
- **What it is:** Targets a specific memory failure: **stale derived artifacts** (summaries, embeddings, cached tool outputs) that remain visible after their source materials become invalid. Three-stage barrier-first protocol: (1) **Withdrawal** — remove affected descendants before any repair; (2) **Construction** — rebuild successors against current interfaces using only retained support; (3) **Publication** — restrict re-publication to predecessor-closed (i.e. fully revalidated) successors. The publication step reduces to a **maximum-weight predecessor closure** problem, solvable via single s-t min-cut. Reports **invalidated-memory exposure 69.8–94.3% → 0%**, recovers **91.1–94.3%** of validated successors vs. exhaustive repair, normalized repair cost **1.00 → 0.57–0.76**. Tested on ToolBench + MemoryArena.
- **Why it matters for Justin's agents:** Any agent that builds derivative artifacts on top of source material (Obsidian summaries derived from notes, agent memory of MCP tool outputs derived from API responses, cached embeddings) has this problem; it usually shows up as stale advice that references a deleted entity or a moved file. The "Withdraw before Repair" invariant is elegant and implementable in any pipeline — you don't need MEMOREPAIR specifically to use the recipe. Production take: **treat your derivative-artifact store like a build graph** with explicit predecessor closures, not a flat cache with TTLs.
- **Action signal:** `try-now` — the algorithmic core (predecessor closure as min-cut) is a few hundred lines to add to an existing memory store, and the barrier-first invariant is a discipline that fits into any artifact pipeline. `compare` — this is the *implementation* layer Belief Memory [arxiv:2605.05583] hand-waves over: when a probabilistic update reweights a memory entry, what happens to summaries that already incorporated the old reading?

### 4. Tool Calling is Linearly Readable and Steerable in Language Models
- **Source:** arXiv (cs.CL, May 8, 2026)
- **Link:** https://arxiv.org/abs/2605.07990
- **Authors / org:** Zekun Wu, Ze Wang, Seonglae Cho, Yufei Yang, Adriano Koshiyama, Sahan Bulathwela, Maria Perez-Ortiz (UCL, Holistic AI, Imperial)
- **Focus area:** Tools & connectors / Frontier models / Reasoning
- **What it is:** Spans **12 instruction-tuned models 270M–27B** across Gemma 3, Qwen 3, Qwen 2.5, Llama 3.1. Three results. (1) **Linear steering**: adding a mean-difference vector between tools' activations switches which tool the model picks at **77–100% accuracy on single-turn prompts, 93–100% for 4B+**. The signal concentrates in **the row of the output layer that produces the target tool's first token** — a single unit vector along that row achieves the 93–100%. (2) **Error prediction**: the gap between top-1 and top-2 tool logits *predicts wrong calls* — narrow-gap calls produce **14–21× more wrong calls** on Gemma 3 12B/27B. (3) **Base models already encode tool identity** at 69–82% via cosine readout of internal state, despite only 2–10% generation accuracy — i.e. instruction-tuning surfaces a pre-existing representation.
- **Why it matters for Justin's agents:** Three operational consequences. (a) **Free pre-call reliability signal** — log the top-2 tool-logit gap at decode time; route low-gap calls through an extra confirmation pass or a Switchcraft-style escalation. No retraining, no judge model. (b) **Steerable tool preference at inference time** — if you have a known correct tool for a domain, you can bias toward it with a single vector added at the output layer instead of fighting the prompt. (c) For local M5 Max deployments of Gemma 3 / Qwen 3 / Llama 3.1 (all open weights), the row-readout and activation-patching analyses are *directly* reproducible — this is the rare mechanistic paper that hands you a production knob.
- **Action signal:** `try-now` `local-fit` — works on the exact model families Justin can run locally; logit-gap monitoring is a one-line addition to a sampling loop.

### 5. Switchcraft: AI Model Router for Agentic Tool Calling
- **Source:** arXiv (cs.AI, May 8, 2026)
- **Link:** https://arxiv.org/abs/2605.07112
- **Authors / org:** Sharad Agarwal, Pooria Namyar, Alec Wolman, Rahul Ambavat, Ankur Gupta, Qizheng Zhang (Microsoft, Stanford)
- **Focus area:** Tools & connectors / Frontier models
- **What it is:** Lightweight **DistilBERT** classifier that routes each function-calling query to one of several backend models. On 5 function-calling benchmarks: **82.9% accuracy — matching or exceeding the best individual model — at 84% lower inference cost, ~$3,600 saved per million queries**. Notable secondary finding: bigger models aren't strictly better at tool-use, and "cheap" reasoning models can become expensive because they burn extra tokens on tool-call deliberation.
- **Why it matters for Justin's agents:** This is the production-pattern paper for MCP gateways. If you front your tools with a router classifier (DistilBERT-class — local-cheap), you can mix Haiku 4.5 / Sonnet 4.6 / Opus 4.7 / local Qwen3 *per call* and get matching-best accuracy at fractional cost. The result also reinforces [arxiv:2605.00136] tool-use tax (May 4): tool calling is its own skill that doesn't track parameter count. Concrete enough to prototype on a real MCP gateway in a weekend — replace a blanket "always Opus" with a Haiku/Sonnet/Opus router for tool-call traffic.
- **Action signal:** `try-now` — small classifier, public benchmarks, immediately portable. Pairs with item #4 (Tool Calling Linearly Readable) — logit-gap is the *runtime* confidence signal; Switchcraft is the *pre-call* router.

### 6. SREGym: A Live Benchmark for AI SRE Agents with High-Fidelity Failure Scenarios
- **Source:** arXiv (cs.SE, May 8, 2026)
- **Link:** https://arxiv.org/abs/2605.07161
- **Authors / org:** Jackson Clark, Yiming Su, Saad Mohammad Rafid Pial, Yifang Tian, Lily Gniedziejko, Hans-Arno Jacobsen, Yinfang Chen, Tianyin Xu (UIUC, Toronto)
- **Focus area:** Evaluation / Coding agents / Tools & connectors
- **What it is:** A **live** SRE benchmark — not static traces — built on top of real cloud-native stacks (Kubernetes, microservices) with **fault injectors** producing metastable failures, correlated failures, and ambient noise across architectural layers. **90 realistic problems** spanning incident categories. Frontier agents show **up to 40% end-to-end performance variation across failure categories**. Open-source and actively maintained.
- **Why it matters for Justin's agents:** Two angles. (1) For the federal data-engineer side of Justin's work, this is the closest current eval to "can an agent triage a real production page?" — and it's open-source, so it can be wired into a personal CI loop to track Claude/Qwen3 capability drift over time. (2) The 40% spread across failure types is the eval-result version of the [arxiv:2605.05716] cross-component-interference finding from last week — agent capability is sharply task-shape-dependent. (3) The "live system + fault injector" methodology is the *correct* answer to the prevailing "static trace replay" benchmarks that [arxiv:2605.04624] AuditRepairBench showed have major ranking-stability problems.
- **Action signal:** `track` — pin an SREGym dashboard. Methodology also worth borrowing for your own internal eval: live system + fault injection > trace replay.

### 7. AutoTTS — LLMs Improving LLMs: Agentic Discovery for Test-Time Scaling
- **Source:** arXiv (cs.AI/cs.CL, May 8, 2026) — Google
- **Link:** https://arxiv.org/abs/2605.08083
- **Authors / org:** Tong Zheng, Haolin Liu, Chengsong Huang, Huiwen Bao, Sheng Zhang, Rui Liu, Runpeng Dai, Ruibo Chen, Chenxi Liu, Tianyi Xiong, Xidong Wu, Hongming Zhang, Heng Huang (Google)
- **Focus area:** Reasoning & inference-time compute / Agent orchestration
- **What it is:** Reframes test-time scaling as **controller synthesis over pre-collected reasoning trajectories** instead of hand-designed TTS heuristics (best-of-N, tree search, self-consistency, etc.). A controller chooses **branch, continue, probe, prune, stop** actions, evaluated against the cached trajectory set rather than fresh LLM calls — so the discovery loop is cheap. Reports better accuracy-cost tradeoffs than hand-tuned baselines and **generalization to held-out benchmarks and model scales**. Headline cost figure: **$39.9 and 160 minutes** to discover a strategy.
- **Why it matters for Justin's agents:** Two takeaways. (1) **Don't hand-tune TTS heuristics anymore** if you can collect a trajectory cache — let a controller discover the policy. Particularly interesting for coding-agent loops where best-of-N vs. iterative-refine vs. branch-and-prune is task-dependent and the trajectory cache is a natural byproduct of normal agent operation. (2) Generalization to held-out *model scales* suggests a discovery run on a small/cheap model can transfer to a larger production model — discovery cost amortizes. The Google-authored framing combined with the $39.9 figure suggests this will get a real implementation, possibly inside Vertex AI Agent Builder.
- **Action signal:** `track` — concrete recipe; watch for a code release. The cached-trajectory-controller pattern is also generalizable beyond TTS to subagent dispatch and tool-call sequencing.

## Local-model corner

**Item #4 (Tool Calling Linearly Readable)** is the most directly local-relevant finding of the week.

- **Models studied:** Gemma 3, Qwen 3, Qwen 2.5, Llama 3.1, 270M → 27B — all open-weight and M5 Max-runnable in either MLX (Gemma 3, Qwen 3 / 2.5) or llama.cpp (all four).
- **Memory fit on M5 Max 64 GB:** Q4 quantization of any 27B-class model from this set fits comfortably in ~16–18 GB with plenty of headroom for KV cache + context.
- **Realistic task it enables:** *runtime tool-call reliability monitoring*. Log `logit[top_tool] - logit[second_tool]` at the moment of tool selection — if the gap is narrow, expect 14–21× higher wrong-call probability. Treat the gap as a free confidence signal: small gap → route through a verifier pass or fall back to a stronger model. Works without any model surgery.
- **Stretch task:** if you have a known-correct tool for a domain, compute the mean-difference vector between the target tool's activations and a generic-call baseline, then add it as a single output-layer steering term at inference time. This is implementable with MLX hooks or llama.cpp's tensor-modification path in about a day.
- **How to run:** MLX for Gemma 3 27B Q4 or Qwen 3 30B-A3B Q4 (preferred — MoE is ~3B active per token); llama.cpp for Llama 3.1 8B / 70B Q4.
- **Speed estimate (M5 Max):** Qwen 3 30B-A3B Q4 on MLX should hit ~50–70 tok/s for single-stream generation; tool-call decisions happen on a small handful of tokens so steering overhead is negligible.

## Conflicts & open questions

Cross-referenced against `_meta/claims-ledger.md`:

- **Memory-size direction**: [arxiv:2605.08060] The Memory Curse (more recall → less cooperation, 18/28 settings, **deliberation amplifies it**) sits in real tension with prior covered work that implicitly assumes monotonic value of memory: [arxiv:2605.06614] SkillOS (growing external markdown skill repo), [arxiv:2605.05413] Constant-Context Skill Learning (procedural memory in weights), [arxiv:2605.05583] Belief Memory (multi-conclusion entries per memory). **Open empirical question**: does the curse apply when the memory is *structured* (skills, beliefs, procedural) rather than *raw* (conversation history, observations)? Memory Curse used cooperation games; the prior items are task-completion benchmarks — different evaluation surfaces.
- **Memory-failure-mode taxonomy is fragmenting fast**. In three weeks: [arxiv:2605.06527] STALE (implicit-conflict detection, 55.2% cap), [arxiv:2605.05583] Belief Memory (commitment-to-single-conclusion failure), [arxiv:2605.07313] Stored-Evidence-Stops-Being-Usable (clutter-induced unfindability, HippoRAG −16–20 pp), [arxiv:2605.07242] MEMOREPAIR (cascade-invalid-derivative exposure 69.8–94.3% → 0%), [arxiv:2605.08060] Memory Curse (longer recall → degraded cooperative intent). These are five distinct failure modes; no current memory framework addresses more than 1–2. A unified eval is overdue.
- **Tool-call vs. tool-use-tax**: [arxiv:2605.07990] (tool-call as linear feature, single-vector steering at 93–100%) gives mechanistic detail about *how* the model decides which tool to call. Combined with [arxiv:2605.07112] Switchcraft (router 84% cost reduction), the picture sharpens: tool *choice* is a small-information decision that doesn't need a frontier model. This explains [arxiv:2605.00136] tool-use tax (May 4) — the tax isn't in the choice; it's in the *integration*.
