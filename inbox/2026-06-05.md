## TL;DR
- **The memory pile-up reaches its second day, and the framing shifts.** Yesterday's cluster (AutoMEM, SegTreeMem, TMEM, RAMPART) argued *flat retrieval is the wrong primitive*. - **First systems-level characterization of agent memory drops** — **[arxiv:2606.06448] Agent Memory** (Pentland, Verhelst, Tambe et al.) builds the first taxonomy and profiling rig over **10 representative memory systems × 4 dimensions × 2 benchmark suites**, then publishes 10 explicit system-design recommendations (construction scheduling, capability floor, query amortization, freshness/latency, fleet-scale). This is the paper to send infra leads.
- **Memory safety is now its own discipline.** **[arxiv:2606.06054] MemGate** (Jia et al.) — a 9M-param, 35.1MB query-conditioned gate that drops between retriever and generator — blocks "memory-induced jailbreaks," cross-domain leakage, and tool-call drift across A-Mem / Mem0 / MemOS / OpenClaw. **[arxiv:2606.06055] RBI-Eval** quantifies how much sensitive memory *actually* changes generator behavior: 8.9–26.6% on GPT-5.4-mini, **51.1–82.9% on Claude-Sonnet-4.6 / DeepSeek-V4-Flash / Qwen3.5-9B**. Implication: most "self-critic" pipelines could be replaced by re-labeling the criticized text.
- **Harness self-optimization closes the loop on yesterday's "persistence > initial quality" finding.** **[arxiv:2606.05922] RHO** picks a coreset of past failures, re-solves in parallel, ranks rollouts by self-preference, applies the best harness diff — and reports **SWE-Bench Pro 59% → 78% in a single optimization cycle, no external graders**. If this reproduces, it materially changes how you build coding-agent harnesses.
- **Tooling moves agent-first.** **[hf-blog] hf CLI for agents** ships dual-mode output, next-command hints, an auto-generated skill reference; **94% pass on Claude Code vs 84% with curl/Python at up to 6× fewer tokens**. Same lesson from two angles: **shrink the surface the agent sees, every step.**

## Items

### 1. Agent Memory — First Systems Characterization of Stateful Long-Horizon Workloads
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.06448
- **Authors / org:** Yasmine Omri, Ziyu Gan, Zachary Broveak, Robin Geens, Zexue He, Alex Pentland, Marian Verhelst, Tsachy Weissman, Thierry Tambe (Stanford / KU Leuven / MIT)
- **Focus area:** Agent memory + infrastructure
- **What it is:** The first *systems-level* characterization of agent memory. The authors build a taxonomy over **4 dimensions** spanning the full agent-memory design space (flat retrieval, LLM-mediated extraction, consolidating fact stores, agentic control flows), then implement a profiling rig measuring construction, retrieval, and generation costs across **10 representative memory systems × 2 benchmark suites**. The output is **10 explicit system-design recommendations** covering construction scheduling, capability floors, query-volume amortization, freshness/latency tradeoffs, and fleet-scale management.
- **Why it matters for Justin's agents:** This is the reference architecture-level paper to anchor companion-app memory decisions on. Every memory paper from now on can be located in their taxonomy, and the 10 recommendations turn "should I run nightly consolidation?" / "what's my retrieval budget?" / "do I need a generator-side memory cache?" from intuition into a checklist. Particularly useful given that yesterday's cluster (AutoMEM, SegTreeMem, TMEM, PersonaTree, RAMPART, LifeSide) lacked a unifying frame — this paper *is* that frame.
- **Action signal:** `track` — adopt as the design vocabulary; map every memory system already in the vault into their 4-dimension taxonomy when reading.

### 2. MAGE — "Memory as Execution State Management" (Beyond Semantic Organization)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.06090
- **Authors / org:** Yaoqi Chen, Haibin Lai, Yuru Feng, Chuyu Han, Qianxi Zhang, Baotong Lu, Menghao Li, Xinjiang Wang, Zhirui Wang, Shusen Xu, Zengzhong Li, Zewen Jin, Hao Wu, Cheng Li, Qi Chen (USTC / MSRA-style team)
- **Focus area:** Agent memory
- **What it is:** Argues that **memory for long-horizon agents should be execution state, not a semantic store.** MAGE represents history as a hierarchical state tree of subgoals + traces, with four coupled operations — `Grow` (record new trace), `Compress` (summarize completed subgoal), `Maintain` (validate summary), `Revise` (restore boundaries / branch new paths). The agent's working state is the active root-to-current path plus summaries of sibling subgoals. **+7.8 to +20.4pp average task success over baselines, −55.1% token consumption** on the MemoryArena benchmark.
- **Why it matters for Justin's agents:** Long-running companion / planner agents *are* execution-state machines — what's the active subgoal, what branched-off work needs revision, what's a finished summary. MAGE makes that structure first-class and reports the largest swing of any memory paper this week. Especially compelling for Claude-Code-style planner-executor loops: the `Revise` operation cleanly models "we hit a wall, back up two subgoals, try a new branch" — which is exactly what long agent runs currently do *informally* in prompt churn.
- **Action signal:** `compare` — directly competes with [arxiv:2606.04555] SegTreeMem (temporal organization, 2026-06-04) and [arxiv:2606.04780] PersonaTree (lifecycle-tree organization, 2026-06-04). Open question: head-to-head on a shared benchmark using the same backbone — does execution-state, temporal, or persona structure dominate, or are they composable?

### 3. MRAgent — "Memory is Reconstructed, Not Retrieved" (ICML 2026)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.06036
- **Authors / org:** Shuo Ji, Yibo Li, Bryan Hooi (NUS)
- **Focus area:** Agent memory
- **What it is:** Replaces the retrieve-then-reason pipeline with **active reconstruction over a Cue-Tag-Content graph**: associative tags act as semantic bridges, and the LLM walks the graph during reasoning, pruning paths via evidence collected mid-search. Avoids combinatorial explosion with evidence-gated expansion. **Up to +23% over strong baselines on LoCoMo and LongMemEval at lower token + runtime cost.** Accepted at ICML 2026.
- **Why it matters for Justin's agents:** This is the second cleanly-stated rejection of the "vector DB + top-k retrieve" pattern in two days (first being yesterday's AutoMEM, which gave the LLM raw file I/O). MRAgent sits one rung up: same anti-retrieval thesis, but it formalizes a graph schema (Cue / Tag / Content) and lets the LLM *steer* path exploration during reasoning rather than during memory construction. Practically reimplementable on top of any agent loop that already calls a vector store — you wrap retrieval inside a reasoning trace and let the model decide what to fetch next based on what it just read.
- **Action signal:** `compare` — extends [arxiv:2606.04315] AutoMEM (yesterday); also worth comparing against [arxiv:2606.03463] DMF (2026-06-03, deterministic LLM-free memory). The 3-way contrast: DMF says *no LLM in memory*; AutoMEM says *LLM owns storage*; MRAgent says *LLM owns retrieval-path search*. None of the three are pipeline memory.

### 4. EMBER — Budgeted Evidence Retention With Learned Policy
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.05894
- **Authors / org:** Yilong Li, Suman Banerjee, Tong Che
- **Focus area:** Agent memory + context engineering
- **What it is:** Reframes memory as a **constrained retention problem**: which source-evidence excerpts must I keep, under a fixed token budget, so I can still answer queries that arrive later? EMBER stores **evidence capsules** — verbatim source excerpts paired with retrieval keys and update metadata — and trains a retention policy with post-query outcome feedback. **EMBER-14B reaches 0.3017 F1 at the 8192-token retained-evidence point on LongMemEval-RR, vs 0.1765 for the strongest budgeted baseline (≈71% relative gain).** Improves on F1, Retain-Recall, and Read-Recall across budgets.
- **Why it matters for Justin's agents:** Local M5 Max agents *always* operate under a retention budget (KV cache + disk read latency). EMBER's eval protocol — fix the token budget, measure recoverable-evidence quality — is exactly the right axis for measuring local-stack memory. The evidence-capsule abstraction (verbatim excerpt + key + metadata) is also a small, deterministic data structure that drops into any MCP filesystem-tool backend. Pair with [arxiv:2606.03463] DMF (deterministic budgeted memory) for an L1; layer MAGE's state tree (item 2) on top for execution-state organization.
- **Action signal:** `track` + `local-fit` — protocol and data structure to adopt; the 14B retention model itself isn't the deliverable, but the eval methodology is.

### 5. MemGate — A 9M-Param Defensive Filter Against Memory-Induced Jailbreaks
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.06054
- **Authors / org:** Jiawen Zhang, Kejia Chen, Jiachen Ma, Yangfan Hu, Lipeng He, Yechao Zhang, Jian Liu, Xiaohu Yang, Tianwei Zhang, Ruoxi Jia
- **Focus area:** Agent memory + safety
- **What it is:** Identifies that memory systems function as a **durable control channel** — semantic-similarity retrieval can surface contextually inappropriate memories, enabling **cross-domain leakage, sycophancy, tool-call drift, and memory-induced jailbreaks**. MemGate is a **9M-parameter, 35.1 MB query-conditioned neural gate** that sits between the retriever and the generator, filtering candidates by task context with **zero changes to the LLM, memory DB, or inference loop**. Evaluated across A-Mem, Mem0, MemOS, and OpenClaw (a real-world personal-agent env with persistent state + tool use).
- **Why it matters for Justin's agents:** Companion apps are the *prototype* of personal-agent stacks with persistent memory + tool use, i.e., the exact target MemGate was built for. Drop-in, model-agnostic, and cheap enough to run on-device on M5 Max with zero noticeable overhead. The general principle — **memory retrievals are control flow, not just data; gate them like you'd gate tool calls** — is the actionable lesson even if you don't use this exact gate.
- **Action signal:** `try-now` — small + drop-in + framework-agnostic; worth integrating before scaling any persistent-memory companion product.

### 6. RBI-Eval — Quantifying How Much Sensitive Memory Bleeds Into Output
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.06055
- **Authors / org:** Lingxiang Xu, Jiaoyun Yang, Min Hu, Hongtu Chen, Ning An
- **Focus area:** Agent memory + evaluation
- **What it is:** A probe-set framework comparing model behavior **with and without access to sensitive memory** under identical prompts. Measures a "separation score" — how much the generator's output changes when a sensitive memory is in context. Tested on **4 LLMs × 4 memory-access settings** (full-context exposure + 3 retrieval systems). Headline numbers: **GPT-5.4-mini shows 8.9–26.6% behavioral divergence for sensitive memory**; **Claude-Sonnet-4.6, DeepSeek-V4-Flash, and Qwen3.5-9B show 51.1–82.9% divergence**. Effect is specific to sensitive content, not general personalization. Retrieval reduces exposure but does not eliminate the effect once sensitive memory reaches the generator.
- **Why it matters for Justin's agents:** RBI-Eval pairs naturally with MemGate (item 5) — RBI-Eval *measures* the leakage; MemGate *blocks* it. For any companion-app feature that touches user history (preferences, prior conversations, health/finance/relationships data), the right pipeline is now: gate at retrieval (MemGate), measure separation post-deployment (RBI-Eval), and re-tune the gate if any sensitive class shows >20% separation. Also a useful empirical counter to the "we'll just RAG it" handwave.
- **Action signal:** `track` — adopt the protocol; the divergence numbers are stark enough to justify standing up the measurement before scaling personalization.

### 7. LatentSkill — Hypernetwork Generates Plug-and-Play LoRA Adapters From Textual Skills
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.06087
- **Authors / org:** Aofan Yu, Chenyu Zhou, Tianyi Xu, Zihan Guo, Rong Shan, Zhihui Fu, Jun Wang, Weiwen Liu, Yong Yu, Weinan Zhang, Jianghao Lin
- **Focus area:** Agent memory (parametric) + skills
- **What it is:** Converts agent skills represented as **in-context text** into **in-weight LoRA adapters** via a pretrained hypernetwork. The hypernetwork is trained once; thereafter, given any new textual skill, it emits a plug-in LoRA at inference time. **ALFWorld: +21.4pp success on seen splits, +13.4pp on unseen, with 64.1% fewer prefill tokens.** **Search-QA: +3.0pp EM with 72.2% lower skill-token overhead.** Generated LoRAs have structured semantic geometry — they compose by parameter-space arithmetic; strength is tunable via the LoRA scaling coefficient.
- **Why it matters for Justin's agents:** Yesterday's [arxiv:2606.04536] TMEM said: *online RL on LoRA weights inside a single episode*. LatentSkill says: *learn a hypernetwork once; emit LoRAs from text on demand*. Together they bracket the fast-weight memory design space — TMEM updates LoRAs from experience at inference; LatentSkill instantiates LoRAs from declarative skills offline. For a companion-app personality / preference system, the LatentSkill direction is more practical: define a user's stable claims declaratively, emit a LoRA, swap it in cheaply per session. Composability by parameter arithmetic is the unexpected bonus.
- **Action signal:** `compare` — extends [arxiv:2606.04536] TMEM (2026-06-04) and [arxiv:2606.03979] Sleep (2026-06-03) into a third corner of the fast-weight memory triangle. Hypernetwork training is a real engineering cost; track until someone publishes a reusable pretrained hypernetwork.

### 8. RHO — Self-Supervised Harness Optimization: SWE-Bench Pro 59% → 78% in One Cycle
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.05922
- **Authors / org:** Wenbo Pan, Shujie Liu, Chin-Yew Lin, Jingying Zeng, Xianfeng Tang, Xiangyang Zhou, Yan Lu, Xiaohua Jia
- **Focus area:** Coding agents + agent orchestration
- **What it is:** Picks a **diverse coreset of challenging tasks from past trajectories**, re-solves them in parallel with the current harness, scores rollouts via self-validation + self-consistency, generates candidate harness updates, and selects updates by self-preference comparison — **no external grader, no labels**. Single optimization cycle on SWE-Bench Pro: **pass rate 59% → 78%**, with sustained improvement on long-horizon sessions and demonstrable shifts in agent behavior. Evaluated across software engineering + two additional domains (technical, knowledge work).
- **Why it matters for Justin's agents:** This operationalizes yesterday's [arxiv:2606.05080] AutoLab finding ("persistence beats initial quality"). RHO *is* the persistence loop: it caches failures, retries them, learns from its own preference signal, edits the harness. Direct fit for Claude-Code-style harness work — the loop "diff the harness, re-run the failing 50 tasks, keep the diff if the rollouts self-prefer it" is implementable with existing trajectory logging and a small ranking model. **Compare flag**: the +19pp gain in one cycle is exceptional; needs reproduction. If it reproduces even at half that magnitude, it's the dominant near-term coding-agent technique.
- **Action signal:** `try-now` + `compare` — extends [arxiv:2606.05080] AutoLab (2026-06-04, persistence) and [arxiv:2606.03461] Terminal-Lego (2026-06-03, harness engineering). Stand up a small reproduction on a 50-task subset before betting on the headline.

### 9. CMTF — Causal Minimal Tool Filtering: 100 Tools → 1 Visible Per Step, ~90% Token Cut
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.06284
- **Authors / org:** Rahul Suresh Babu, Laxmipriya Ganesh Iyer
- **Focus area:** Tools & connectors
- **What it is:** Training-free tool filter that uses **precondition-effect contracts** to expose only the **minimal next-step tool frontier**. On a 102-task, 100-tool benchmark across 4 LLM backends (2,448 task-method-model runs), CMTF reduces visible tools from 100 to **~1 per step** and **~90% token cut** vs all-tools exposure, matching the strongest causal baseline on aggregate success. Beats keyword retrieval, state-aware filtering, and causal-path ablations on wrong-tool calls and premature actions.
- **Why it matters for Justin's agents:** MCP tool menus on real stacks tend toward 50–200 tools across the federated set (filesystem + git + browser + Linear + Slack + custom MCPs). Exposing all of them at every step is both *expensive* and a known source of wrong-tool calls. CMTF is training-free, framework-agnostic, and gives a principled answer to "what tools should the model even see right now?". Drops in front of any MCP-style tool registry without touching the model or the tools themselves.
- **Action signal:** `try-now` — implementable as a pre-call layer in front of an MCP server; pairs with the hf-CLI agent-mode pattern (item 10) — both shrink the surface the agent sees every step.

### 10. Self-Correction Illusion — It's a Chat-Template Artifact, Not a Cognitive Limit
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.05976
- **Authors / org:** Kuan-Yen Chen, Fang-Yi Su, Jung-Hsien Chiang (NCKU)
- **Focus area:** Context engineering + reasoning
- **What it is:** Keeps an identical erroneous claim constant across conditions and varies *only the role label* it sits under: `<thought>` (agent's own reasoning) vs `<user>` vs `<tool_response>` vs `<memory>`. **Relabeling the claim from `<thought>` to an external role lifts the explicit-correction rate by 23–93 percentage points**, with p<0.001 in 10/13 model×domain cells across 7 model families and 3 domains (30 paired tasks per cell). The "LLMs can't self-correct" effect is a chat-template artifact — models *will* correct identical claims labeled as external. Proposed intervention is prompt-structure-only, no training: `<memory>` blocks work best for math; plain user messages work best for logical deduction.
- **Why it matters for Justin's agents:** Every self-critic / self-refine / "have the model check its own work" pipeline in your stack is potentially under-performing for a free reason — the model is treating its own prior output as authoritative because the role label says so. The fix is to **re-wrap the criticized text as a `<memory>` or `<tool_response>` before the critique pass**. Probably the highest-leverage prompt-engineering update in this whole digest: zero training, zero infra, large measurable lift on the right tasks.
- **Action signal:** `try-now` — wire the role-relabel into existing critic pipelines (Claude-Code-style "check your edits" loops, planner-verify loops) and A/B on a recent failure-trajectory set.

### 11. hf CLI for Agents — Dual-Mode Output, Skill Reference, 94% Claude Code Success at 6× Fewer Tokens
- **Source:** Hugging Face Blog
- **Link:** https://huggingface.co/blog/hf-cli-for-agents
- **Authors / org:** Julien Chaumond, Clément Delangue, Victor Sanh, Jeff Boudier, Davanstrien et al. (Hugging Face)
- **Focus area:** Tools & connectors
- **What it is:** Redesigned `hf` CLI built explicitly as **the agent-optimized way to use the HF Hub**. Key features: **dual-mode output rendering** (human-pretty tables vs agent-friendly TSV based on env detection); **next-command hints** (operations suggest the likely follow-up); **safe-to-retry semantics** (destructive actions fail fast with correction guidance instead of blocking on prompts); **auto-generated skill reference** that agents load as context. Headline numbers: **94% pass on Claude Code, 93% on Codex (vs 84% / 92% for curl/Python SDK)**; **up to 6× fewer tokens** on complex multi-step tasks; **~30% fewer tool calls** when the skill reference is loaded.
- **Why it matters for Justin's agents:** This is the first ship of a **CLI designed as a Claude-Code-native interface**, not retrofitted. Two lessons that generalize beyond HF: (1) **dual-mode output** — every tool you ship as an MCP / CLI should detect agent execution and emit machine-friendly TSV/JSON instead of pretty tables; (2) **skill reference auto-generation** — small declarative skill files that the agent loads as context reduce tool calls by ~30%. The pattern is directly portable to any custom MCP server you maintain.
- **Action signal:** `try-now` + `local-fit` — `hf skills add --claude` is one command; it instantly makes HF model browsing, downloading, and uploading cheap from Claude Code on M5 Max. Pair with CMTF (item 9) — both make the agent see less per step, but in complementary ways.

## Local-model corner
Two of today's items are directly useful on M5 Max + 64 GB without further work.

**Most-immediate local-fit: the hf CLI agent-mode (item 11) + CMTF tool filtering (item 9).** Neither needs new model weights; both shrink prompt cost — and on local stacks, **prompt cost is wall-clock cost**, not a billing line. Running Claude Code locally against a Qwen3-14B / Qwen3.6-35B-A3B / GLM-4.6-Air-Q4 endpoint, the per-step token surface dominates throughput; agent-mode CLI output (TSV not tables) and CMTF-style minimal tool exposure compound directly.

**Memory architectures runnable now:**
- **MAGE (item 2)** — pure-prompt state-tree; no model dependency. Implementable on top of llama.cpp / MLX-LM. The Grow/Compress/Maintain/Revise operations are just structured prompt patterns over an external state file (which is also what AutoMEM proved was the right baseline yesterday).
- **MRAgent (item 3)** — Cue-Tag-Content graph with LLM-driven path walk. The graph is cheap to maintain externally; the walk is sequential LLM calls. Works fine with a 14B-class local model; the speedups come from terminating walks early on evidence, which a smaller model with weaker priors actually benefits from *more* than a frontier model.
- **MemGate (item 5)** — 9M params, 35.1MB. Fits in RAM ~5000× over; latency cost is sub-millisecond. Drop-in in front of any retrieval call. No reason not to ship this on a local stack.

**Skip locally for now:**
- **EMBER-14B (item 4)** — the retention *protocol* and the *evidence-capsule data structure* are local-portable; the trained 14B retention model itself is not (weights not yet released, and you'd need the post-query feedback loop to train one). Adopt protocol; skip model.
- **LatentSkill (item 7)** — needs the pretrained hypernetwork. Track until a reusable hypernet drops on HF.
- **RHO (item 8)** — self-supervised harness optimization works locally in principle, but the SWE-Bench Pro headline used a frontier model. Run a small reproduction with a local 14B coder before scaling.

**Speed estimate:** No new M5 Max-specific numbers today. The hf CLI + CMTF combo doesn't change tok/s; it changes how many tokens each step needs, which is the bigger lever on a local stack.

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:

- **MAGE (today, item 2) vs SegTreeMem (2026-06-04) vs PersonaTree (2026-06-04).** Three different organizing primitives for agent memory in 48 hours: **execution-state tree** (MAGE), **temporal segment tree** (SegTreeMem), **lifecycle person tree** (PersonaTree). MAGE explicitly argues against semantic organization; SegTreeMem's ablation argues *for* temporal structure; PersonaTree argues for evidence→claim hierarchy on persons. None of the three benchmarks against each other. Open empirical question: on a shared backbone, which dominates by *task type* (engineering / dialogue / companion) — and are they composable layers (execution-state for trajectory, temporal for recent events, persona for stable user model)?
- **MRAgent (today, item 3) vs AutoMEM (2026-06-04) vs DMF (2026-06-03).** All three reject pipeline-style memory (Mem0/LangMem/Letta-class), but at different layers: **DMF removes the LLM entirely from the memory loop**; **AutoMEM puts the LLM in charge of storage** via tool calls; **MRAgent puts the LLM in charge of retrieval-path search** over a typed graph. Three-way head-to-head on LoCoMo + LongMemEval is now the obvious empirical hole. Likely outcome: DMF wins on cost, MRAgent on accuracy under structured queries, AutoMEM on accuracy on unstructured/agentic tasks.
- **LatentSkill (today, item 7) vs TMEM (2026-06-04) vs Sleep (2026-06-03).** Three rungs of fast-weight memory: **Sleep** (offline consolidation during a "dream" pass), **TMEM** (online LoRA updates inside one episode via RL), **LatentSkill** (offline-pretrained hypernetwork emits LoRAs from textual skills on demand). No contradictions — these compose. Open question: stack all three (Sleep-style consolidation → LatentSkill-emitted user-specific LoRA at session start → TMEM-style online updates within session). Anyone running the joint ablation wins.
- **RHO (today, item 8) extends AutoLab (2026-06-04) and Terminal-Lego (2026-06-03).** AutoLab found "persistence beats initial quality" was the dominant predictor on engineering tasks; Terminal-Lego found the same for the CLI substrate. RHO is the *training-free operational mechanism* that delivers persistence: cache failures, re-solve, self-prefer harness diffs. The +19pp single-cycle gain on SWE-Bench Pro is large enough to warrant skepticism — flagged as `compare` and needs reproduction.
- **Self-Correction Illusion (today, item 10) is a major new tracked claim.** Sits adjacent to (but does not directly contradict) the wider "models can self-refine" literature — it argues most reported self-refine failures are template artifacts. The prediction is testable: any failing self-critic pipeline should improve substantially if the criticized text is re-wrapped in a non-`<thought>` role. **Worth a controlled test in Justin's existing Claude Code self-critic loops.**

Open empirical questions raised today:
- Does MemGate's 9M-param gate generalize to **agentic tool use under partial observability**, where the "sensitive content" isn't a memory excerpt but an emergent state inferred from tool responses? The OpenClaw eval includes persistent state + tool use, but it'd be useful to see CMTF (item 9) and MemGate (item 5) composed on the same eval — gating both *which tools* the model sees and *which memories* it sees.
- Does the Self-Correction Illusion finding hold for **multi-step planner→executor** pipelines where the executor's failure trace gets relabeled into the planner's `<tool_response>`? Theoretically yes, and this would explain why Claude-Code-style harnesses work as well as they do.
