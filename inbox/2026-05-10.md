# AI Research Digest — Sunday, May 10, 2026

## TL;DR
- **Reliability headline of the week:** "DELEGATE-52" benchmarks Gemini 3.1 Pro, Claude 4.6 Opus, and GPT-5.4 on long delegated document workflows and finds **all three corrupt ~25% of document content by the end** — sparse but severe edits that compound silently. Agentic tool use does **not** help. Frontier models are unreliable delegates for in-depth document editing today.
- **Counter-intuitive scaffolding finding:** A factorial study of all 32 combinations of {planning, tools, memory, self-reflection, retrieval} shows **fully-equipped agents lose to subset configurations on 56.3% of cases**. On HotpotQA a single-tool agent beat the All-In agent by 32% F1; on GSM8K a 3-component subset beat the full system by 79%.
- **Skill-learning hits ALFWorld 89.6% with 2-7× fewer prompt tokens.** "From History to State" learns reusable procedures into lightweight task-family modules and conditions inference on (current observation + compact state block) only — a third mechanism converging near the 90% ALFWorld plateau alongside this week's BEACON 92.9% and StraTA 93.1%.
- **Open-source autonomous research frameworks emerging.** ARIS (cross-model adversarial reviewer + 65 Markdown skills + MCP + 5-pass scientific editing pipeline) names the failure mode worth quoting: "plausible unsupported success — a long-running agent produces claims whose evidential support is incomplete, misreported, or silently inherited."
- **Local corner:** OpenSeeker-v2 (open-source release pending) reports a **30B-class search agent** trained via SFT-only on 10.6k trajectories that beats Tongyi DeepResearch on BrowseComp / BrowseComp-ZH / HLE / xbench. Watch for the HF release; if Qwen3-class base, this is M5 Max-deployable.

## Items

### 1. LLMs Corrupt Your Documents When You Delegate
- **Source:** arXiv (cs.CL, April 17, 2026 — surfaced widely yesterday on HN front page, 412 points)
- **Link:** https://arxiv.org/abs/2604.15597
- **Authors / org:** Philippe Laban, Tobias Schnabel, Jennifer Neville
- **Focus area:** Coding agents / Long-running loops / Evaluation
- **What it is:** **DELEGATE-52** — a benchmark of long delegated workflows requiring in-depth document editing across **52 professional domains** (legal, medical, finance, scientific, etc.). Documents go through extended edit chains. Reported: top frontier models (**Gemini 3.1 Pro, Claude 4.6 Opus, GPT-5.4**) **corrupt an average of 25% of document content by the end of long workflows**. Errors are **sparse but severe** — small silent corruptions that compound across turns. **Agentic tool use does not improve performance**; document size, interaction length, and presence of distractor files all worsen results.
- **Why it matters for Justin's agents:** This is the harshest single-number indictment of long-horizon delegated work I've seen, and it lands directly on coding agents and document-editing companions. Two operational consequences. (1) **Treat any agent that edits the same document/file across many turns as a corruption risk** — add diff-based regression checks against the prior version, not just task-completion checks. (2) **The ineffectiveness of tool use** echoes [arxiv:2605.00136] "Tool-Use Tax" from May 4: bolting on tools doesn't fix reliability degradation in extended interaction; the tax is real and partially independent of the protocol overhead. For Claude Code-style workflows over multi-day sessions, this argues for snapshotting + periodic regeneration over single-thread editing. The benchmark is also a candidate to add to a personal eval — 52 domains is broad enough to be portable.
- **Action signal:** `compare` — sharpens the open question raised by [arxiv:2605.00136] (tool-use tax) and [arxiv:2605.06635] (deep-research factual-accuracy decay with tool depth). Three independent papers in 10 days converging on the same point: **frontier-model reliability degrades non-trivially with interaction length, and tools don't paper over it.**

### 2. From History to State: Constant-Context Skill Learning for LLM Agents
- **Source:** arXiv (cs.AI, May 6, 2026)
- **Link:** https://arxiv.org/abs/2605.05413
- **Authors / org:** Haoyang Xie, Xinyuan Wang, Yancheng Wang, Puda Zhao, Feng Ju
- **Focus area:** Agent memory / Context engineering / Long-running loops
- **What it is:** Argues procedural context should live **in weights, not prompts**. Trains lightweight **task-family modules** that condition only on (current observation + compact state block); the running history is replaced by learned weights and a small explicit state. Reports **89.6% ALFWorld unseen** / **76.8% WebShop** / **66.4% SciWorld unseen** with Qwen3-8B (SFT+RL) — and **2–7× prompt-token reduction per turn vs. controlled ReAct prompting baselines**.
- **Why it matters for Justin's agents:** Three converging mechanisms now sit near the 90% ALFWorld plateau: BEACON (milestone reward shaping, 92.9%), StraTA (top-down strategy abstraction, 93.1%), and now Constant-Context Skill Learning (89.6% with much smaller prompts). The interesting axis here is **prompt economics**: same task-family, 2–7× fewer tokens per turn means 2–7× more turns within the same context budget, or 2–7× cheaper per task at fixed turn count. For companion-app loops where context budget is a real production constraint (long sessions, free-tier inference), the prompt reduction may matter more than the raw success rate. Pairs naturally with [arxiv:2605.06614] SkillOS (which keeps skills in an external Markdown repo) — these are two ends of the storage-medium spectrum (weights vs. files).
- **Action signal:** `compare` — extends the BEACON/StraTA cluster with a context-economy axis. Also relates-to [arxiv:2605.04050] LCM (Lossless Context Management): both attack the "context fills up" failure, one via compression of prompts, the other via in-weights procedural memory.

### 3. More Is Not Always Better: Cross-Component Interference in LLM Agent Scaffolding
- **Source:** arXiv (cs.AI, May 7, 2026)
- **Link:** https://arxiv.org/abs/2605.05716
- **Authors / org:** Ming Liu (single author)
- **Focus area:** Agent orchestration / Evaluation
- **What it is:** Full-factorial study of **all 32 combinations of 5 scaffolding components** {planning, tools, memory, self-reflection, retrieval} across two benchmark tasks (HotpotQA, GSM8K), two model scales (Llama-3.1 8B, 70B), and up to 10 random seeds (96 conditions total). Headline numbers: on **HotpotQA, a single-tool agent beat the All-In agent by 32%** (F1 0.233 vs 0.177, p=0.023); on **GSM8K, a three-component subset beat the full system by 79%**. **56.3% of configurations show submodularity violations** — so greedy "add another component if it helps in isolation" fails to find optima. Optimal subsets are task- and model-scale-dependent.
- **Why it matters for Justin's agents:** Direct empirical pushback on the "stack everything" agent design pattern. Two practical takeaways. (1) **Default to the smallest scaffold that solves your task**; only add components when ablation shows a real lift on *your* eval, because in 56% of cases the next component you add will hurt. (2) **Optimal subsets are task-dependent**, so an agent template that works for one user product almost certainly is not optimal for another — fork early rather than building one mega-template. The single-author/single-task framing is a caveat, but the methodology (Shapley values + factorial seeds) is solid enough to take seriously.
- **Action signal:** `try-now` — the methodology is replicable on any agent stack. Run a 5-component factorial on your own eval before shipping a scaffold change.

### 4. AdaGATE: Adaptive Gap-Aware Token-Efficient Evidence Assembly for Multi-Hop RAG
- **Source:** arXiv (cs.CL, May 4, 2026)
- **Link:** https://arxiv.org/abs/2605.05245
- **Authors / org:** Yilin Guo, Yinshan Wang, Yixuan Wang
- **Focus area:** Tools & connectors / Retrieval / Context engineering
- **What it is:** **Training-free** evidence controller for multi-hop RAG that frames evidence selection as a **token-constrained repair problem**. Tracks entity-level gaps in the partial answer, generates targeted micro-queries to close those gaps, and selects evidence under a utility/cost objective. Reports **Evidence F1 = 62.3%** on clean HotpotQA, **71.2%** under redundancy injection, and **2.6× fewer input tokens** than the Adaptive-k baseline.
- **Why it matters for Justin's agents:** Token-efficient RAG that doesn't require retraining is rare and useful. The **gap-aware** framing (track which entities the partial answer is missing, ask only for those) is implementable in any existing RAG stack as a planner-side prompt — no model surgery, no embedding changes. Pairs well with [arxiv:2605.05242] Direct Corpus Interaction (DCI): DCI replaces the coarse retriever; AdaGATE is what the agent should be doing inside its retrieval loop regardless of how documents come in. Especially relevant for Justin's Obsidian/MCP tooling where token cost on the hot path is real.
- **Action signal:** `try-now` — training-free; the entity-gap heuristic is portable to MCP servers without model changes.

### 5. OpenSeeker-v2: Pushing the Limits of Search Agents with SFT-Only Training
- **Source:** arXiv (cs.CL, May 5, 2026)
- **Link:** https://arxiv.org/abs/2605.04036
- **Authors / org:** Yuwen Du, Rui Ye, Shuo Tang, Keduan Huang, Xinyu Zhu, Yuzhu Cai, Siheng Chen
- **Focus area:** Coding agents / Tools & connectors / Local & open models
- **What it is:** Argues that a **simple SFT pipeline** (no RL, no heavy continual pre-training) on **only 10.6k well-synthesized trajectories** can produce frontier search agents — provided the trajectory synthesis follows three rules: expand the underlying knowledge graph, broaden the tool inventory, apply strict low-step filtering. The 30B model reports **BrowseComp 46.0%** / **BrowseComp-ZH 58.1%** / **Humanity's Last Exam 34.6%** / **xbench 78.0%**, beating Tongyi DeepResearch (43.4 / 46.7 / 32.9 / 75.0). Authors commit to open-sourcing the model weights.
- **Why it matters for Justin's agents:** Direct comparison vs. [arxiv:2605.05191] LongSeeker (Qwen3-30B-A3B fine-tune, BrowseComp 61.5 with Context-ReAct paradigm) — LongSeeker still wins on BrowseComp by ~15 points, suggesting **trajectory quality alone isn't enough; the inference-time context-management paradigm matters more**. But OpenSeeker-v2's 10.6k-trajectory SFT recipe is a much cheaper baseline for Justin to fine-tune his own search agent, and the open-sourcing commitment is concrete. If the base model turns out to be Qwen3-class, this is also a candidate for local M5 Max deployment of a real search agent (see Local-model corner below).
- **Action signal:** `track` — pending weight release. `compare` — sits below LongSeeker on BrowseComp, suggests context paradigm > training data scale within the open-30B class.

### 6. Belief Memory: Agent Memory Under Partial Observability
- **Source:** arXiv (cs.AI/cs.CL, May 7, 2026)
- **Link:** https://arxiv.org/abs/2605.05583
- **Authors / org:** Junfeng Liao, Qizhou Wang, Jianing Zhu, Bo Du, Rui Yan, Xiuying Chen
- **Focus area:** Agent memory
- **What it is:** Replaces the standard "store each observation as one deterministic conclusion" memory model with a **belief memory**: each entry retains **multiple candidate conclusions with associated probabilities**, updated via **Noisy-OR rules** as new evidence arrives. Retrieval surfaces alternatives with probability scores rather than committing to one interpretation. Reports best average performance vs. baselines on **LoCoMo** and **ALFWorld**, even with limited training data.
- **Why it matters for Justin's agents:** This is the right shape of fix for the failure mode that [arxiv:2605.06527] STALE isolated last week — frontier-model + memory framework caps at **55.2% accuracy detecting that a later observation invalidated an earlier memory**, because the earlier memory was stored as a single committed conclusion. Belief Memory dodges that by never committing in the first place: when an observation is ambiguous, both readings stay alive with probabilities; when a later observation shifts evidence, the Noisy-OR update reweights rather than requiring explicit negation detection. This is a cleaner mental model for any agent operating on user-provided context that may be wrong. Pairs with [arxiv:2605.06132] MemReranker: MemReranker is a reasoning-aware reranker over flat candidate pools; Belief Memory restructures what's *in* the pool.
- **Action signal:** `compare` — directly addresses the failure mode in STALE; flagged in claims ledger.

### 7. ARIS: Autonomous Research via Adversarial Multi-Agent Collaboration
- **Source:** arXiv (cs.AI, May 4, 2026 — most-voted on HF Daily this week)
- **Link:** https://arxiv.org/abs/2605.03042
- **Authors / org:** Ruofeng Yang, Yongcan Li, Shuai Li
- **Focus area:** Agent orchestration / Long-running loops / Tools & connectors
- **What it is:** Open-source research-agent framework with three explicit layers: **Execution** (65+ reusable Markdown-defined skills, MCP-based model integration, persistent research wiki, deterministic figure generation); **Orchestration** (5 end-to-end workflows with adjustable effort and configurable reviewer routing); **Assurance** (integrity verification, result-to-claim mapping, claim auditing, 5-pass scientific editing pipeline, mathematical proof checks, visual PDF inspection). The default configuration runs **cross-model adversarial collaboration** — one model family executes, a different family reviews intermediate artifacts. Names the central failure mode: **"plausible unsupported success: a long-running agent can produce claims whose evidential support is incomplete, misreported, or silently inherited."**
- **Why it matters for Justin's agents:** Three borrowable patterns even if Justin doesn't run ARIS itself. (1) **Cross-family adversarial review as default**: don't have one model family both execute and check; pair Claude with Gemini or GPT for the review pass. This neutralizes within-family blind spots that single-model self-critique inherits. (2) **Skills as Markdown files** — converges with [arxiv:2605.06614] SkillOS as a pattern; expect this to be the dominant skill-storage convention. (3) **Result-to-claim mapping + claim auditing as a separate layer** is the right architectural answer to DELEGATE-52's corruption finding (item #1) for research/document agents. Direct evolution of [arxiv:2605.06651] AI Co-Mathematician's stateful workspace pattern, but generalized beyond math.
- **Action signal:** `try-now` — open-source code at the GitHub repo named in the abstract; integrate the cross-family reviewer pattern in Justin's stack today.

### 8. Anthropic — Agents for Financial Services

- **Link:** https://www.anthropic.com/news/finance-agents
- **Authors / org:** Anthropic
- **Focus area:** Frontier models / Agent orchestration / Tools & connectors
- **What it is:** Ten ready-to-run financial-services agent templates (pitchbook builder, KYC screener, month-end closer, valuation reviewer, statement auditor, model builder, market researcher, meeting preparer, earnings reviewer, GL reconciler) deployable as Claude Cowork/Code plugins or Claude Managed Agents. Each template = **Skills (domain instructions) + Connectors (governed data access) + Subagents (specialized Claude models for subtasks)**. Powered by **Claude Opus 4.7**, scoring **64.37% on Vals AI Finance Agent benchmark** (claimed industry-leading). Eight new connectors (Dun & Bradstreet, Fiscal AI, Financial Modeling Prep, Guidepoint, IBISWorld, SS&C Intralinks, Third Bridge, Verisk) plus the **Moody's MCP app** with access to >600M public/private companies.
- **Why it matters for Justin's agents:** Two takeaways past the marketing layer. (1) The **Skills + Connectors + Subagents** decomposition is now Anthropic's named architectural pattern for productionized verticalized agents. That's worth aligning with for Justin's MCP work — same naming, same component boundaries means the templates and tooling will be portable. (2) The **Moody's MCP app for 600M companies** is the first large third-party data-provider MCP I've seen at this scale, and it's being shipped through the App Marketplace flow, not as a one-off. Indicates MCP as the productization path for vertical data access (not custom integrations). The 64.37% Vals AI number is vendor-self-reported but on a third-party benchmark, so somewhat third-party-checkable.

## Local-model corner

OpenSeeker-v2 (item #5) is the candidate worth watching for the M5 Max:

- **Model:** OpenSeeker-v2 30B (base architecture not stated in the abstract; **likely Qwen3-30B-A3B given the SFT-only on 10.6k trajectories recipe and the 30B size**, but unverified pending the weight release).
- **Memory fit (if Qwen3-30B-A3B class, ~3B active):** ~17 GB at Q4_K_M quant for a 30B-total / 3B-active MoE; **plenty of headroom** in 64 GB unified memory for KV cache even at 128K context.
- **Realistic tasks:** Open-corpus search agent — multi-hop browse, deep-research, comparative report writing. Reported numbers (BrowseComp 46.0, HLE 34.6) are middle-of-the-pack vs. closed frontier but **strong for a 30B SFT-only open-weight model**, and these are agentic tasks not single-shot QA.
- **How to run:** If it ships in MLX format, MLX is the best path on M5 Max for MoE; otherwise GGUF via llama.cpp. Bracket on Ollama for ease until MLX support is verified.
- **Speed estimate:** For 30B-A3B class on M5 Max with 600 GB/s memory bandwidth, expect **~50–80 tok/s decode at Q4** (similar to Qwen3-30B-A3B benchmarks circulating in r/LocalLLaMA), with sub-second TTFT at moderate context. Search-agent loops will be tool-call latency bound, not generation bound.
- **Caveat:** All of this is conditional on the OpenSeeker-v2 weights actually shipping at the announced size and on a Qwen-class base. If the base turns out to be a denser 30B (e.g., Qwen3-32B), prompt processing speed will be 3-5× slower and memory pressure tighter.

LongSeeker (covered May 7, [arxiv:2605.05191]) remains the stronger M5 Max-deployable open-search agent on benchmarks; OpenSeeker-v2 is interesting because it argues the SFT-only recipe is enough — useful if Justin wants to fine-tune on his own corpus rather than adopt a pre-trained search agent wholesale.

## Conflicts & open questions

Cross-referenced against `_meta/claims-ledger.md`:

- **Reliability degrades with interaction length — three independent confirmations in 10 days.** [arxiv:2604.15597] DELEGATE-52 (25% document corruption by end of long workflows, tools don't help) sharpens [arxiv:2605.00136] "Tool-Use Tax" (May 4) and [arxiv:2605.06635] (deep-research factual-accuracy drops 42% as tool depth scales 2 → 150, May 8). Three different mechanisms (document editing, tool-call protocol, tool-call depth) all converge on: **frontier-model agent reliability is interaction-length-dependent, and naïve tool use does not paper over it**. Open question: which of these decompose to a common underlying cause vs. genuinely orthogonal failure modes?

- **ALFWorld near-90% plateau is now multi-mechanism.** Previously flagged BEACON 92.9% [arxiv:2605.06078] vs. StraTA 93.1% [arxiv:2605.06642] (May 8/9 ledger). Now joined by [arxiv:2605.05413] Constant-Context Skill Learning at **89.6%** via in-weights procedural memory. Three mechanically distinct mechanisms (milestone reward shaping, top-down strategy abstraction, in-weights procedural state) converging within 3.5 points on the same benchmark suggests **ALFWorld is approaching its mechanistic ceiling** — gains are now sub-linear in mechanism diversity. Open question for follow-up: do these compose? A planner-executor split with StraTA-style strategy abstraction + Constant-Context modules + BEACON reward shaping during training is the obvious experiment.

- **Belief Memory (item #6) directly attacks STALE's failure mode.** [arxiv:2605.06527] STALE (May 8 ledger) showed best frontier LLM + memory framework caps at **55.2% on implicit-conflict detection**. [arxiv:2605.05583] BeliefMem proposes never committing to a single conclusion in the first place — multiple candidates with Noisy-OR updates. Open question: **does BeliefMem actually move the STALE number?** Authors report wins on LoCoMo + ALFWorld but did not (per the abstract) evaluate on STALE specifically. Cleanest empirical follow-up of the week.
