# AI Research Digest — Tuesday, June 30, 2026

## TL;DR
- **OSWorld 2.0 redraws the computer-use ceiling: 108 long-horizon workflows averaging 318 tool calls / 1.6 human-hours each; Claude Opus 4.8 finishes only 20.6% (54.8% partial) at 500 steps, GPT-5.5 plateaus near 13%** [arxiv:2606.29537]. The named failure mode is "lose track of constraints, miss information that arrives mid-task, struggle when a task hinges on hidden state they must recover" — long-horizon agent reliability is gated by *state management*, not single-step capability.
- **VISTA argues frontier models are "proprioceptively blind" to their own context — they cannot see how large, how old, or how used each block is, so the gating policy can't decide what to keep. A training-free, model-agnostic interface that exposes per-block token usage / recency / access history lifts Gemini-3-Flash from 22.7% → 50.7% on LOCA-Bench** [arxiv:2606.30005], across four backbones, with gains that grow with context pressure. Context engineering is now an *interface* problem, not a learned-policy problem.
- **MemDelta is a controlled re-eval of the agent-memory zoo and it's brutal: rankings flip across models (Gemini gains +14pp from full context; Sonnet gains +31pp from RAG), embedding model alone moves accuracy ±6.2pp, agent self-memory underperforms basic retrieval (42% vs 47%), and Mem0 matches cloud RAG on 2 of 6 question types — at 50× the cost** [arxiv:2606.29914]. The current memory-architecture leaderboard is largely an embedding-choice and model-family leaderboard in disguise.
- **Entity binding is a silent failure mode of tool-using agents: tool selection accuracy 100%, but wrong-entity rates 24–26% across baselines over 60 tasks × 5 backbones** [arxiv:2606.30531]. "The right tool for the wrong Alex" — and standard tool-use evals don't catch it.
- **Agents-A1 is the first frontier-grade open-weight agent model that fits a M5 Max: a 35B MoE matches Kimi-K2.6 / DeepSeek-V4-pro on long-horizon benchmarks (SEAL-0 56.4, IFBench 80.6, BrowseComp 75.5, HLE 47.6) via 45K-token agentic trajectories + multi-teacher domain-routed on-policy distillation; checkpoints on HuggingFace under InternScience** [arxiv:2606.30616].

## Items

### 1. OSWorld 2.0 — The Long-Horizon Computer-Use Ceiling Is Lower Than the Headline Suggests
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.29537
- **Authors / org:** 36 authors (eq-contrib: Mengqi Yuan, Zilong Zhou, Xinzhuang Xiong; also Frederic Sala, Yu Su, Siva Reddy, Tao Yu)
- **Focus area:** Evaluation / computer-use agents
- **What it is:** Successor to the original OSWorld with a deliberate horizon shift: **108 workflows averaging 318 tool calls per task** and **1.6 hours of human work**, vs. ~30 tool calls in the original. The benchmark explicitly tests what the authors call hidden-state recovery — tasks where critical information surfaces mid-trajectory and must be retained or re-discovered. Two frontier models reported: **Claude Opus 4.8 (max thinking): 20.6% binary completion, 54.8% partial score at 500 steps**; **GPT-5.5: ~13% completion**, "more token-efficient" but doesn't recover the gap. The named failure modes are: lose track of constraints, miss mid-task information, struggle when the task hinges on hidden state.
- **Why it matters for Justin's agents:** This is the third long-horizon real-world CUA benchmark published in 30 days ([arxiv:2606.09426] WeaveBench, [arxiv:2606.11042] Workflow-GYM, and now OSWorld 2.0) and the pattern is consistent: state-of-the-art models complete only ~20–30% of professional-domain workflows, *regardless of the per-step capability ceiling*. For Justin's companion app, the practical read is that any "agent does the whole task end-to-end" pitch is currently a 1-in-5 proposition at frontier model spend; the better-supported architecture is to *decompose* the long horizon into checkpointed sub-tasks where a human (or a verifier) confirms hidden state. Pairs structurally with item 2 (VISTA): if hidden-state-recovery is *the* failure mode, then an interface that surfaces what the agent has and hasn't seen is the lowest-hanging intervention.
- **Action signal:** `compare` (extends [arxiv:2606.09426] WeaveBench and [arxiv:2606.11042] Workflow-GYM; the three benchmarks together set a floor at ~20–30% completion for long-horizon professional CUA work — cross-ref the ledger entries)

### 2. VISTA — Context Engineering Is an Interface Problem, Not a Learned-Policy Problem
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.30005
- **Authors / org:** Binyan Xu, Haitao Li, Kehuan Zhang
- **Focus area:** Context engineering / agent memory
- **What it is:** The paper coins a useful frame — **"frontier language models are proprioceptively blind to their own context"** — and argues that the reason context-management agents fail isn't that they lack a *policy* (capable models already have one latent), it's that they lack the *signals* a keep-or-drop decision needs (per-block size, age, access history). VISTA is a training-free, model-agnostic layer that represents working memory as typed, addressable blocks; surfaces a runtime dashboard of per-block token usage, recency, and access history; and archives blocks as recoverable full-fidelity payloads. On **LOCA-Bench (million-scale), BrowseComp-Plus (100K-scale), GAIA (10K-scale)**, the same untrained interface transfers across all three. Headline number: **Gemini-3-Flash 22.7% → 50.7% on LOCA-Bench**; lift grows with context pressure and holds across four backbones. Ablations confirm the *dashboard* matters beyond just having archive and recovery tools.
- **Why it matters for Justin's agents:** This is the cleanest experimental separation yet of *capability* from *interface* in long-context agents — and the result is that a chunk of what looks like "model needs more training" is actually "model needs to see the metadata of its own context window." For Justin's Claude Code + MCP stack, the immediate lift is to expose the same three signals to any agent that has tool-call memory: a sidecar that tracks per-tool-call output size, age (turns since produced), and access count, surfaced to the agent as a structured dashboard. Nothing in this design requires training or special model support — it's prompt-time scaffolding. Pairs naturally with item 1 (OSWorld 2.0): if hidden-state-recovery is the long-horizon failure mode, then a per-block "what have you actually re-read recently" dashboard is the corresponding fix. Also extends the *"use/policy not storage"* cluster — [arxiv:2606.27472] Supersede, [arxiv:2606.14571] StreamMemBench, [arxiv:2606.14470] GitOfThoughts — by adding a *fourth* independent data point that storage architectures aren't the bottleneck. Three of those four said *use*; VISTA says *interface*.
- **Action signal:** `try-now` (training-free, prompt-level scaffolding; lift the typed-block + dashboard pattern into any tool-using agent today)

### 3. Neural Procedural Memory — Activation Steering as an Implicit Memory Substrate
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.29824
- **Authors / org:** Chengfeng Zhao, Yuqiao Tan, Shizhu He, Yequan Wang, Jun Zhao, Kang Liu
- **Focus area:** Agent memory
- **What it is:** Most agent-memory work injects *text* (retrieved guidelines, summarized procedures) into the model's context — what the authors call the **text-action disconnect**: the model can read the instruction without it actually activating the neural mechanisms that execute the task. NPM is a training-free framework that distills procedural skills from *historical contrastive experiences* into **steering vectors in the activation space**, then injects those vectors at inference time to guide task execution directly. Across **four agent benchmarks**, NPM performs **comparably to baselines using explicit text instructions**; combining NPM with explicit workflows is strictly better than either alone; representational analysis shows the steering vectors form organized task-logic structures in activation space.
- **Why it matters for Justin's agents:** A new shape on the agent-memory map. The text-based memory cluster (HORMA, MRAgent, EMBER, DMF, MAGE) all share one assumption — that procedural memory is best stored and retrieved as text. NPM challenges that frontally: the *same* skill stored as a steering vector activates the right behavior *without* needing to fit into the context window. For Justin's local-runtime work (M5 Max, open-weight models), this is interesting precisely because activation steering only works on models whose internals you control — closed-API models can't accept steering vectors, so this is one of the few memory designs with a *structural* advantage for local deployment. Track for replication; the comparison to text-based memory is suggestive but the paper doesn't yet show *strict outperformance* — only "comparable." The real value would be a hybrid stack where text memory handles facts and steering vectors handle skills.
- **Action signal:** `track` (interesting paradigm with a local-fit advantage; not yet a strict win over text memory — waiting for follow-up that proves the hybrid value claim)

### 4. MemDelta — The Agent-Memory Leaderboard Is Mostly an Embedding-and-Model-Family Leaderboard
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.29914
- **Authors / org:** Kuan Wang
- **Focus area:** Agent memory / evaluation
- **What it is:** A controlled evaluation protocol that tests memory-system components *individually*, on **LongMemEval-S (500 questions, 50+ sessions, three model families)**. Four findings that complicate every recent memory benchmark: (1) **verbatim RAG matches full-context** on GPT-4o-mini (47.2% vs 49.8%, p=0.34) but the ranking *reverses* across model families (Gemini gains +14pp from full context; Sonnet gains +31pp from RAG); (2) swapping the **embedding model alone shifts accuracy ±6.2pp** (n=500, p=0.004); Mem0 beats MiniLM-RAG by +11pp but underperforms cloud RAG; (3) **agent self-memory underperforms basic retrieval (42% vs 47%)**; (4) **Mem0 matches cloud RAG on 2 of 6 question types (n=88, 72.7% vs 73.9%, p=1.0) at 50× the cost**. The paper's prescription: fix the embedding model across comparisons, stratify by model family, report write-path costs.
- **Why it matters for Justin's agents:** This is the meta-eval that the memory-architecture cluster ([arxiv:2606.11680] HORMA, [arxiv:2606.06036] MRAgent, [arxiv:2606.05894] EMBER, [arxiv:2606.03463] DMF, [arxiv:2606.06090] MAGE) badly needed. Read in combination with [arxiv:2606.04315] AutoMEM — which also re-benchmarked 8 memory systems and found the *harness* dominated the *architecture* — the pattern is now overwhelming: most memory-systems comparisons confound architecture with embedding model, with model family, with harness, and with the workload's recall-vs-update mix. For Justin's stack, three concrete moves: (a) any memory eval he runs must report the embedding model and pin it across conditions; (b) stratify by *model family* (Gemini and Sonnet have inverted preferences here); (c) the 50×-cost-for-zero-gain Mem0 result is hard data that "ship Mem0" is not a default — it has to clear a write-path-cost bar, not just an accuracy bar.
- **Action signal:** `compare` (directly tensions every memory-architecture paper that didn't pin embedding model + stratify by family; pairs with [arxiv:2606.04315] AutoMEM and [arxiv:2606.27472] Supersede to make the case that the current memory benchmarks are leaking confounds)

### 5. Agents-A1 — A 35B Open-Weight MoE That Matches Trillion-Param Agents (and Fits on a M5 Max)
- **Source:** arXiv + HuggingFace
- **Link:** https://arxiv.org/abs/2606.30616 — weights at https://huggingface.co/collections/InternScience/agents-a1
- **Authors / org:** Lei Bai, Zongsheng Cao, Yang Chen + 47 others (InternScience)
- **Focus area:** Frontier models / local fit
- **What it is:** A **35B Mixture-of-Experts** agentic model that the authors argue reaches trillion-parameter performance via *agent-horizon scaling* — long-horizon trajectories (avg 45K tokens) and heterogeneous agent abilities — rather than raw parameter count. Training recipe: (1) full-domain SFT to align the base on broad agent behavior; (2) train domain-level teachers via RL; (3) **Multi-Teacher Domain-Routed On-Policy Distillation with Salient Vocabulary Alignment** to fuse six heterogeneous domains into one deployable student. Headline numbers vs **1T-param Kimi-K2.6 and DeepSeek-V4-pro**: SEAL-0 **56.4**, IFBench **80.6**, HiPhO **46.4**, FrontierScience-Olympiad **79.0**, MolBench-Bind **56.8**; competitive on SciCode (44.3), HLE (47.6), BrowseComp (75.5). Checkpoints and eval code open-sourced.
- **Why it matters for Justin's agents:** This is the **first frontier-grade open-weight agent model that fits comfortably on the M5 Max** since DiffusionGemma. The MoE structure means the dense compute per token is much smaller than the 35B parameter count suggests; at Q4 quantization the full weight footprint is ~17–18 GB, leaving room for substantial KV cache headroom on 64 GB unified memory. The training recipe is also independently interesting: the Multi-Teacher Domain-Routed On-Policy Distillation pattern matches today's other distillation paper ([arxiv:2606.30406] MOPD, see Sources Checked) — two same-day papers converging on "RL domain specialists → on-policy distillation into one student" as the right post-training recipe for capability integration. For Justin's M5 Max + open-weight local-runtime path, this is the model to benchmark *now*; for his frontier-API-using companion app it's not a replacement, but it is a meaningful local-fallback option that wasn't on the table 24 hours ago.
- **Action signal:** `local-fit` (open weights, MoE structure, fits 64 GB unified memory at Q4; M5 Max benchmark is the immediate next step)

### 6. Entity Binding Failures — Tool Selection Was Not the Hard Part
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.30531
- **Authors / org:** Rahul Suresh Babu, Shashank Indukuri
- **Focus area:** Tools & connectors
- **What it is:** Tool-use evals score whether the agent picks the right tool, produces valid arguments, and completes the task — but they routinely miss a category of failure the authors name **entity binding failures**: agent picks the right tool, fires it against the *wrong external entity* ("email Alex about the launch" sent to the wrong Alex, with the wrong launch document, in the wrong thread, on the wrong account). Across **60 tasks × 5 model backends × 6 tool-use approaches**, tool selection accuracy was **0.0% error** while entity binding failure rates ran **24.0–26.0%** in action-oriented baselines. The paper proposes entity-resolution preconditions, confidence-based binding, and clarification queries; entity-aware safeguards eliminate wrong-entity errors but raise the deferral rate (the agent stops to ask).
- **Why it matters for Justin's agents:** This is a *named, replicable* version of a failure mode every production tool-using agent ships with silently. For Justin's MCP stack — where many tool calls bind to external entities (Slack channels, files in Obsidian, customer rows in a CRM, GitHub issues) — the takeaway is concrete: **standard tool-use evals will report 100% tool selection accuracy on a system that misroutes 1 in 4 customer actions**. Two practical moves: (a) every MCP tool whose arguments include an external-entity reference should have an entity-resolution precondition (resolve→confirm→act), even if the cost is more turns; (b) any agent evaluation Justin runs should add a *misbinding* axis distinct from tool-call accuracy. The 24–26% number is the budget to beat; the cost is the deferral rate.
- **Action signal:** `try-now` (resolve→confirm→act on entity-bound tool calls is a mechanical guardrail that lifts directly into existing MCP servers; pairs with [arxiv:2606.27416] Glite ARF's "process rules in code, not prompt" pattern from yesterday)

### 7. Minority Sentinel — Multi-Agent Majority Voting Suppresses Correct Minorities ~25% of the Time
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.29270
- **Authors / org:** Chuan He, Zebin Chen, Zhengyi Yang, Shaobo Qiao, Mingchen Ju, Jiate Liu, Dong Wen, Guanfeng Liu
- **Focus area:** Agent orchestration / multi-agent
- **What it is:** Multi-Agent Debate with Majority Voting rests on the **Condorcet Jury Theorem** — which assumes *independent errors*. Because modern LLMs share pretraining corpora, their errors are heavily correlated, and the majority systematically suppresses correct minorities (the authors' term: **Minority Truth**). Empirically on three heterogeneous LLMs × six benchmarks: **~25% of divergent cases have the minority correct**, yielding a **10pp theoretical recovery margin**. The proposed Minority Sentinel is a **lightweight non-LLM meta-classifier** (LightGBM trained on a "debate fingerprint" extracted from debate logs) that decides when to overturn the majority. Result: **81.2% Flip Precision with positive Net Gain across all six datasets and all 20 random seeds**. The LLM-as-Judge baseline gets *negative* Net Gain despite higher recall — the authors' framing is "flip safety, not recovery volume, determines intervention value."
- **Why it matters for Justin's agents:** Three production-relevant claims, all empirically supported. First, the Condorcet assumption is broken for modern LLMs — so the standard "more voters → better answer" intuition that backs LLM ensembles is *quantifiably* losing 10pp of accuracy on average. Second, the *correct* fix is a **non-LLM classifier on debate-log features** — not another LLM judge, which is what most production stacks reach for and is empirically worse (negative Net Gain). Third, "flip safety" is the right loss function — recovering minority truths matters less than not flipping correct majorities. For Justin's planner-executor architectures or any subagent-voting setup, this is a concrete recipe: log the debate, extract a fingerprint (disagreement entropy, confidence asymmetry, etc.), train a small LightGBM, gate flips on it. Directly extends yesterday's [arxiv:2606.27409] Itkin (delayed verification destabilizes multi-agent belief) — Itkin tells you *when* the topology breaks; Minority Sentinel tells you *how to catch it without piling on more LLM critics*.
- **Action signal:** `try-now` (the meta-classifier is small and the recipe is fully specified; this is the rare multi-agent paper that gives you the loss function to actually optimize)

### 8. Always-On Agents — The First Systematic Survey of Persistent-State Agent Systems (435 Works, Six Axes, Eval Protocol)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.30306
- **Authors / org:** Tianyu Ding, Aditya Nannapaneni, Bingfan Liu, Ling Zhang (Cornell)
- **Focus area:** Agent memory / multi-agent / governance
- **What it is:** Survey of **435 works** in what the authors call *always-on agents* — systems whose future behavior depends on **durable state** accumulated across earlier interactions: retrievable memories, task ledgers, permissions, credentials, commitments, provenance and audit records, shared state, trigger conditions, externally committed effects. Six **diagnostic axes**: authority, scope, mutability, provenance, recoverability, actionability. A nine-stage lifecycle (writing, validating, organizing, retrieving, acting upon, updating, forgetting, auditing, rollback). Headline observation about the literature: **the field overwhelmingly emphasizes accumulating and retrieving state, and underweights governance, recovery, and relinquishment** (the second half of the lifecycle). New eval protocol — **Always-On Evaluation Protocol (AOEP-v0)** — that scores **state mutation and recovery obligations**, not just answer quality.
- **Why it matters for Justin's agents:** This survey is the right scaffolding to organize everything that's landed in the ledger over the past 60 days. The "underweighted governance/recovery/relinquishment" diagnosis names exactly the gap that [arxiv:2606.27472] Supersede (memory update is the bottleneck, not storage) and today's [arxiv:2606.29914] MemDelta (write-path costs ignored in benchmarks) are independently identifying. For Justin's companion-app work, the six axes are a useful checklist: every persistent-state primitive in the stack should have a documented answer for **who can write it (authority), what it covers (scope), how it changes (mutability), where it came from (provenance), how to recover or roll back (recoverability), and what real-world action it can trigger (actionability)** — that's the format Justin's memory-design notes should follow. AOEP-v0 is also the right shape of memory eval going forward: score the *mutation* and *recovery* path, not the recall path.
- **Action signal:** `track` (survey + protocol; immediate lift is to adopt the six-axis schema for memory design docs, run AOEP-v0 on any memory system before adding it to the stack)

## Local-model corner
**Agents-A1** (item 5) is the first significant local-fit landing in over a week.

- **Model:** Agents-A1 — 35B Mixture-of-Experts; checkpoints at `huggingface.co/collections/InternScience/agents-a1`; GitHub: `InternScience/Agents-A1`
- **Memory fit:** 35B total params at Q4 ≈ 17–18 GB weights. On 64 GB unified memory that leaves ~46 GB for KV cache, OS, and other processes — comfortable for 64K context at typical batch=1. The paper's training trajectories average **45K tokens**, so the deployment context length is realistic on the M5 Max. (Active-param count is not specified in the abstract; expert routing means per-token dense compute is materially smaller than 35B regardless.)
- **Realistic tasks:** The benchmark suite the model targets is *long-horizon agentic* (SEAL-0, IFBench, BrowseComp, HiPhO) — i.e., the model was trained for the failure regime that OSWorld 2.0 (item 1) measures. Use cases: multi-step research workflows, browsing agents, tool-use chains where each step needs grounding. Not a chat-replacement and probably not the right call for short-form Q&A — frontier APIs still dominate single-turn capability per token.
- **How to run:** Best fit is **MLX** (Apple Silicon-native, MoE-supported) once a community port lands; fallback is **llama.cpp + GGUF** if a Q4_K_M / Q5_K_M conversion appears on HuggingFace. The InternScience GitHub will likely publish reference inference code first; community quantizations usually follow within 1–2 weeks of major MoE drops.
- **Speed estimate:** No M5 Max specific benchmark exists yet. For comparable 35B-class MoE models on MLX (e.g., Hcompany Holo3.1 35B-A3B at Q4), reported tok/s on M-series chips is in the 25–45 tok/s range depending on context depth and quantization; expect Agents-A1 to land in the same band. Worth benchmarking explicitly against [hf-blog-2026-06-02-hcompany-holo31] Holo3.1 once weights are downloadable, since they're the same parameter class with different training targets.

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:

- **Memory-architecture cluster vs MemDelta's meta-eval:** [arxiv:2606.29914] MemDelta joins [arxiv:2606.04315] AutoMEM as a second independent controlled re-eval that finds the agent-memory architecture leaderboard is dominated by confounds (embedding model, model family, harness). Combined with [arxiv:2606.27472] Supersede ("storage is not the bottleneck, policy is"), [arxiv:2606.14571] StreamMemBench ("use/transfer not storage"), and [arxiv:2606.14470] GitOfThoughts ("memory helps only at near-duplicate similarity"), the pattern is overwhelming: **every memory benchmark from the past 60 days either has a leakage problem or finds storage isn't where the gain comes from**. None of [arxiv:2606.11680] HORMA, [arxiv:2606.06036] MRAgent, [arxiv:2606.05894] EMBER, [arxiv:2606.03463] DMF, [arxiv:2606.06090] MAGE has been re-evaluated under MemDelta's fixed-embedding stratified protocol. That's the cleanest cross-check available; until it happens, treat their headline numbers as upper bounds.

- **Long-horizon CUA benchmark trio — consistent ~20–30% ceiling:** [arxiv:2606.29537] OSWorld 2.0 (Claude Opus 4.8: **20.6%**), [arxiv:2606.11042] Workflow-GYM (~30%), and [arxiv:2606.09426] WeaveBench (long-horizon hybrid-interface) now form a triangulated body of evidence that the long-horizon professional CUA completion ceiling is in the low-20s to low-30s — *regardless* of which model family you pick. This is structurally hard to reconcile with the headline "computer use as a first-party tool" framing from [google-blog-2026-06-26-gemini-3-5-flash-computer-use] (Jun 26) unless Google's unreported OSWorld 2.0 number is substantially higher. Open empirical question: does Gemini 3.5 Flash's built-in computer-use tool measurably move OSWorld 2.0 against the Opus 4.8 baseline? The Google post claims "best yet" but doesn't publish the number on OSWorld 2.0 specifically (the 78.4 in the ledger is OSWorld-Verified, not OSWorld 2.0).

- **VISTA's "interface, not policy" framing vs. learned-policy memory architectures:** [arxiv:2606.30005] VISTA argues that what looks like a learned-policy gap is actually a missing interface — capable models can manage context if and only if they can *see* the right signals. This is a meaningful counter to memory architectures that bake the policy into custom retrieval logic (HORMA, EMBER, DMF). Open empirical question worth one targeted experiment: does VISTA's training-free dashboard + archive recover most of the gain claimed by any of the trained-policy memory systems? If yes, the policy work is overfitting to LongMemEval-style retrieval and the interface is the actual bottleneck (consistent with the cluster signal above).
