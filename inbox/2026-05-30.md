### 2. Scaling Laws for Agent Harnesses via Effective Feedback Compute (EFC)
- **Source:** arXiv (May 29, 2026)
- **Link:** https://arxiv.org/abs/2605.29682
- **Authors / org:** Xuanliang Zhang, Dingzirui Wang, Keyan Xu, Qingfu Zhu, Wanxiang Che (Wanxiang Che = HIT NLP cluster, prior agent-evaluation work)
- **Focus area:** Agent orchestration / Long-running autonomous loops / Evaluation
- **What it is:** Argues that **raw test-time-compute coordinates (tokens, tool calls, wall time, cost) don't distinguish useful feedback from redundant or unstable interaction**, and proposes **Effective Feedback Compute (EFC)**: a trace-level scaling coordinate that **credits feedback only when it is informative, valid, non-redundant, and retained for subsequent decisions**. **Predictive R² numbers:** Oracle-EFC R²=0.94; NRS-EFC/D_task on mixed real traces R²=0.92; prospective holdout R²=0.85; **raw tokens / tool calls R²=0.33–0.42**. Most operationally significant: **matched-budget interventions** (fixed cost + fixed tool calls, vary only feedback quality) **raise success rate from 0.27 → 0.90**. Benchmarks combine synthetic controllable tasks, executable code tasks, and real benchmark traces (specific benchmark names not surfaced in the abstract).
- **Why it matters for Justin's agents:** This is **the quantitative companion to the [arxiv:2605.26112] *Scaling the Harness* position paper** from four days ago — Gu's three-bottleneck taxonomy (context governance / trustworthy memory / dynamic skill routing) gets its first empirical anchor here. (a) **R²=0.94 for an EFC-based scaling law vs. R²≈0.4 for raw-compute is a 2× explanatory-power gap**; if reproducible on the named benchmarks once the full paper lands, this is the strongest evidence so far that the "buy more tokens" framing is wrong. (b) **27% → 90% at fixed cost** is the load-bearing number — if you only change *which* feedback gets retained and surfaced to the next decision, you get a 3× win on success rate at zero added budget. This is the most directly actionable finding for Justin's harness work: feedback-curation is the highest-leverage layer to instrument first, ahead of skill stores and memory backends. (c) Pairs structurally with the May-week harness cluster — Scaling-the-Harness (position), HarnessMutation ([arxiv:2605.27328], governance loop), HF Agent Glossary (vocabulary), and now EFC (scaling laws) — four papers in nine days each attacking a different layer of the same operational thesis. (d) Open question: what does an EFC-based scoring function look like in practice for Justin's MCP harness? The abstract gives Oracle-EFC and NRS-EFC as two specific operationalisations; the implementation details aren't in the abstract and will be the first thing to read in the full PDF.
- **Action signal:** `try-now` `compare` — quantitatively confirms the Scaling-the-Harness cluster; reproduction priority depends on which benchmarks the full paper lists. Cross-reference with [arxiv:2605.26112] in the claims ledger.

### 3. Do Proactive Agents Really Need an LLM to Decide When to Wake and What to Anchor?
- **Source:** arXiv (May 29, 2026)
- **Link:** https://arxiv.org/abs/2605.30152
- **Authors / org:** Xiaoze Liu, Ruowang Zhang, Amir H. Abdi, Michel Galley, Zhikai Chen, Siheng Xiong, Xiaoqian Wang, Jing Gao (Michel Galley = Microsoft Research DialogGPT lineage; Jing Gao = Purdue. Likely Microsoft + Purdue collaboration based on author cluster.)
- **Focus area:** Long-running autonomous loops / Local & open models
- **What it is:** A **direct counter-paper to [arxiv:2605.25971] ProAct (May 25)**. ProAct used an LLM call **on every user-activity event** to decide whether to wake the proactive loop and what to anchor on. The authors argue this is the wrong primitive: **user activity is already a structured event stream of (actor, verb, object, timestamp) tuples that the OS maintains in graph form**, so "render to text → ask LLM to recover structure" is a round-trip the system never had to take. Their replacement: a **small temporal-graph-learning (TGL) encoder** that ingests graph updates directly. **One forward pass yields per-event trigger probability + per-entity routing score**; the LLM call only happens when the trigger fires, and only to produce the final user-facing sentence. **Numbers:** **+16.7 mean F1 across 14 backbones (up to +46.0); 11.13 ms/event GPU; 13.99 ms/event on a consumer laptop; 4–7× speedup vs. LLM baselines on GPU, 12–83× on CPU; 220 MiB BF16 memory footprint.**
- **Why it matters for Justin's agents:** This is the **clearest cross-paper *compare* event this week** — two papers four days apart, same use case (idle-time / user-wait proactive triggering), opposite design choice (LLM-as-trigger vs. graph-encoder-as-trigger). (a) **220 MiB BF16 + 13.99 ms/event on a consumer laptop is a stranger-than-fiction local-fit number**: this thing runs entirely as a background-thread on Justin's M5 Max with vanishing memory and CPU cost, replacing what would otherwise be an Opus or Sonnet call on every keystroke for the proactive-companion pattern. (b) The **12–83× CPU speedup vs. LLM baselines** is the more important number than the GPU one — for an always-on local companion, the trigger has to be CPU-resident (the GPU is busy with the foreground model), so the CPU comparison is the load-bearing axis. (c) The **+16.7 F1 improvement across 14 backbones** is what makes this a real *compare* event and not a niche-tradeoff paper — it's *not* a quality vs. speed tradeoff; it's better F1 *and* drastically lower latency. That means the LLM-as-trigger design (ProAct) is dominated on both axes by the TGL design on the same task. (d) Opens a real question about the **ProAct −28.1% hallucination claim** from May 25 — is that hallucination reduction a property of *the LLM-as-trigger architecture*, or of *idle-time anticipation as a primitive*? If the latter, the TGL design should recover it; if the former, ProAct's design still wins on a metric this paper doesn't directly compare. Worth tracking the head-to-head.
- **Action signal:** `try-now` `compare` `local-fit` — wait for code; the TGL encoder fits in 220 MiB and the speedup numbers make it a near-zero-cost addition to any local agent harness with idle-window inference.

### 4. Meta-Cognitive Memory Policy Optimization (MMPO) for Long-Horizon LLM Agents
- **Source:** arXiv (May 29, 2026)
- **Link:** https://arxiv.org/abs/2605.30159
- **Authors / org:** Ziyan Liu, Zhezheng Hao, Yeqiu Chen, Hong Wang, Jingren Hou, Ruiyi Ding, Yongkang Yang, Wence Ji, Wei Xia, Feng Liu
- **Focus area:** Agent memory / Context engineering
- **What it is:** Frames the **recursive-summarisation memory write** (the dominant write path in memory-augmented agents) as an RL problem with a **memory-specific supervision signal** rather than outcome-only RL. The mechanism: introduces **Belief Entropy** as a self-supervised proxy for epistemic uncertainty about the latent task state, computed from intermediate summaries — high belief entropy indicates the summary has discarded task-relevant information. MMPO uses this as a fine-grained per-summary supervision signal that **penalizes high-uncertainty intermediate memories** rather than waiting for the trajectory-level outcome. **Headline number:** **97.1% of original performance retained when context is scaled to 1.75 M tokens** — i.e., the recursive-summary chain stays informative across an order-of-magnitude longer horizon than baseline.
- **Why it matters for Justin's agents:** Joins the memory-system-engineering cluster ([arxiv:2605.23986] MemForest from May 22, [arxiv:2605.28732] MemTrace from May 28, [arxiv:2605.28773] FluxMem from May 28) at a different layer — MemForest is the *storage layout* paper, FluxMem is the *connectivity dynamics* paper, MemTrace is the *attribution* paper, and MMPO is now the *write-policy supervision* paper. Four memory-cluster papers in a week, none competing on the same axis. (a) **Belief Entropy as a self-supervised summary-quality proxy is the operationally interesting primitive** — it gives you a per-step quality signal *without* an outcome label, which is exactly the bottleneck for any companion-app memory system that doesn't get a clean reward at the end of every interaction. (b) **97.1% retention at 1.75M tokens** is the load-bearing number — the prior baseline for recursive-summarisation memory chains was substantial degradation past ~100K tokens; if 1.75M is the new headroom, that's a 17× extension on the context window where recursive-summary memory remains useful. (c) Pairs as the **continuous-write counterpart to [arxiv:2605.30219] BeliefTrack** (May 29, in processed.json from the prior digest) — both papers use belief-state language for memory operations, with BeliefTrack as the *when to update beliefs* policy and MMPO as the *how to score intermediate beliefs during recursive write* policy. Convergence on **belief calibration as the unit of memory quality** in 2026-era memory work, paralleling the rubric-as-unit-of-training-signal convergence flagged in the 2026-05-26 digest.
- **Action signal:** `track` `local-fit` — wait for code + benchmark name disclosure (the abstract elides which long-context benchmarks 1.75M was measured on). The Belief Entropy proxy is implementable today as a harness-side scorer.

### 5. SkillsInjector: Dynamic Skill Context Construction for LLM Agents
- **Source:** arXiv (May 29, 2026)
- **Link:** https://arxiv.org/abs/2605.29794
- **Authors / org:** Yanchao Li, Wanhao Liu, Ben Gao, Jiaqing Xie, Zhehong Ai, Na Zou, Yuqiang Li, Tianfan Fu
- **Focus area:** Context engineering / Agent memory
- **What it is:** Attacks the skill-curation problem from a **fourth angle** — not extraction (Ratchet, SkillOpt), not retirement (Ratchet again), not management policy (CODESKILL), but **injection-time selection and rendering**. The argument: most existing systems pick skills with fixed criteria, fix the budget in advance, and leave skill descriptions unchanged at inject time. SkillsInjector is a two-stage adaptive method: (a) **context planner** learns execution-grounded skill preferences and admits an **adaptive number of skills per task**; (b) **set-aware renderer** tailors how a selected skill description is presented **relative to its co-injected neighbors**. **Headline numbers:** **+3.9 pp on tau2-bench, +6.1 pp on SkillsBench, +7.3 pp on ALFWorld over strongest baseline** — and these are over baselines that already include retrieval-based skill selection, not just no-skill.
- **Why it matters for Justin's agents:** This is the **sixth independent paper in the May skill-curation cluster** ([arxiv:2605.18401] SkillsVote, [arxiv:2605.22148] Ratchet, [arxiv:2605.23899] Skill Consumption, [arxiv:2605.23904] SkillOpt, [arxiv:2605.25430] CODESKILL, and now SkillsInjector) — five different layers of the same problem, none directly competing. The convergence pattern is now clear: **skill curation is the right learning target, but at every layer of the stack**: extraction (CODESKILL), retirement (Ratchet), validation (SkillsVote, SkillOpt), meta-skill (Skill Consumption), and now injection (SkillsInjector). (a) **The adaptive-budget claim is the operationally interesting one** — fixed-budget skill injection is the dominant pattern (top-K retrieved, hard limit), and Justin's MCP harness almost certainly uses fixed-budget injection too; the SkillsInjector finding is that the budget itself should be task-adaptive. (b) **Set-aware rendering** — adjusting each skill's *description* based on its co-injected neighbors — is a primitive that I don't think any existing skill store does. If it's the source of the gains, it's a one-shot harness change: store skill descriptions in a parametric form rather than as fixed strings. (c) **+3.9 to +7.3 pp on three different benchmarks** is the right shape of evidence — not a single-benchmark hero number, but consistent multi-benchmark gains over strong baselines. (d) Open question: does SkillsInjector compose with CODESKILL's RL-trained management policy (orthogonal layers — extraction vs. injection) or replace one of CODESKILL's components? Authors don't address this; it's the next-paper cluster prediction.
- **Action signal:** `try-now` `compare` — wait for code; the adaptive-budget + set-aware-renderer change is harness-side, model-agnostic, and applies on top of any retrieval-based skill store Justin already runs.

### 6. Delta Weight Sync in TRL — Sparse-Delta Async-RL Across the Hub
- **Source:** Hugging Face Blog (May 27, 2026)
- **Link:** https://huggingface.co/blog/delta-weight-sync
- **Authors / org:** Amine Dirhoussi, Quentin Gallouédec, Kashif Rasul, Lewis Tunstall, Edward Beeching + 25 others (Hugging Face TRL team)
- **Focus area:** Tools & connectors / Local & open models
- **What it is:** Production-grade primitive for **async RL where the trainer, vLLM rollout server, and environment are in different regions or clouds**, connected only by an HF Hub bucket. **Core insight:** at typical RL learning rates (e.g., 3e-6), per-step weight updates are **smaller than the precision threshold of bf16** (|Δw| < |w|/256), so **~99% of weights are bit-identical between consecutive optimizer steps**. Instead of broadcasting full weights over NCCL, the trainer detects changed parameters with a bf16 mask hook, uploads **sparse safetensors deltas** to a content-addressed Hub bucket (Xet chunking), and vLLM pulls and applies them with anchor snapshots every N steps. **Numbers:** per-step sparsity ~99% (min 98%) on Qwen2.5 / Llama-3.2 / Gemma-3; **delta size 1.2 GB → 20–35 MB on Qwen3-0.6B (~130× reduction)**; **inference pause 1.1 s on full per-step sync**; **~6 GB extrapolated delta size for Llama-3.1-405B (vs. full broadcast)**; on a 100 GB/s cluster Llama-3.1-405B sees **8 s pause for NCCL broadcast vs. 2 s pause + background upload for delta path**. Released May 27 as `huggingface/trl#5417`; proof-of-concept is full disaggregated async Wordle training with trainer + vLLM + environment on three separate boxes connected only via Hub.
- **Why it matters for Justin's agents:** (a) **This is the first production-grade async-RL primitive that doesn't require a co-located cluster** — for Justin's "indie developer building agent products" position, this is the closest thing to a deployable async-RL primitive that fits the indie budget (single trainer GPU + HF Spaces vLLM rollout + CPU environment, all connected over Hub buckets). The cost model becomes "trainer GPU + Spaces credits" instead of "multi-node H100 cluster." (b) The **99% sparsity-at-bf16-precision finding is a piece of architectural physics** — it's not a TRL-only optimisation; it's an empirical fact about how Adam at typical RL learning rates interacts with bf16. Any async-RL system can exploit this, including local-RL setups on Apple Silicon where MLX has bf16 as its native precision. (c) The **6 GB delta for 405B vs. 8 s NCCL pause** is the load-bearing scaling story — at frontier model size, the delta path becomes mandatory (NCCL doesn't work across clouds), so this isn't an optimisation, it's the path to making frontier-scale RL training disaggregable at all. (d) Justin doesn't need to train at 405B, but the **same primitive applies at 0.6B–7B scale on M5 Max** for any local fine-tuning workflow where he wants to keep an inference endpoint warm while training in the background. (e) Known limitations are honest: two CPU bf16 snapshots until vLLM gains a sparse `load_weights` API, fixed anchor cadence, not yet tested at multi-node FSDP2 scale.
- **Action signal:** `try-now` — code at `huggingface/trl#5417`, runnable example at `examples/scripts/openenv/async_wordle.py`. For Justin: the Spaces-based disaggregated trainer-+-vLLM setup is the immediate deployable pattern.

### 8. Reasoning in Memory (RiM) — Latent Reasoning Without Autoregressive Thoughts
- **Source:** arXiv (May 29, 2026)
- **Link:** https://arxiv.org/abs/2605.30343
- **Authors / org:** Lukas Aichberger, **Sepp Hochreiter** (Johannes Kepler University Linz, LSTM author)
- **Focus area:** Reasoning & inference-time compute / Context engineering
- **What it is:** Argues that **autoregressive generation of intermediate "thinking" tokens conflates internal computation with external communication** — a CoT step has to be a syntactically valid token sequence even when it's only meant to be internal scratch. **Reasoning in Memory (RiM)** replaces the autoregressive reasoning step with **fixed sequences of special "memory block" tokens** that unlock the LLM's latent working-memory capacity. Because the memory blocks are *fixed* tokens (not generated), the whole block is processed in **one forward pass** — eliminating the per-step autoregressive overhead of CoT. Two-stage curriculum: (a) ground the memory blocks by predicting explicit reasoning steps after each block; (b) discard step-level supervision, iteratively refine the final answer only. Reported to **match or exceed existing latent-reasoning methods across LM families and sizes**; the abstract is light on specific benchmark percentages.
- **Why it matters for Justin's agents:** This is the most interesting theoretical paper of the week, even if the abstract is light on numbers — Hochreiter publishing on inference-time compute is itself worth tracking, and the framing (CoT-as-external-communication-mistakenly-used-as-internal-computation) is a clean and operational way to describe what's actually expensive about CoT-based inference scaling. (a) **The single-forward-pass property is the load-bearing efficiency claim** — if RiM scales CoT-equivalent reasoning down to one forward pass, that's a major reduction in test-time compute for any reasoning-heavy agent task. The headline number is missing from the abstract, so the magnitude isn't verifiable from public material yet. (b) **Pairs structurally with the existing latent-reasoning line** (Coconut and successors), which Justin doesn't currently use but which is the right primitive for inference-time-compute optimisation on local agents — every saved token at reasoning time is a token of headroom for the actual response. (c) The **memory-block-as-special-token primitive** is implementable as a fine-tune; the curriculum is two-stage and doesn't require new data, just a re-labelling of reasoning corpora. Reproducible at Justin's scale if code drops. (d) **Open question:** how does RiM interact with explicit thinking-mode primitives in Claude / GPT-5 / Gemini 3.5? Those are user-visible reasoning streams, while RiM is internal-only — they're solving different problems but trading off on the same axis (visibility vs. compute). Worth a `compare` flag once benchmark numbers land.
- **Action signal:** `track` — wait for full PDF + benchmark numbers + code. Strong theoretical priors (Hochreiter), but the abstract doesn't include the headline percentages needed to call it `try-now`.

- **Do Proactive Agents Really Need an LLM? TGL trigger (item #3)** — **Model:** 220 MiB BF16 temporal-graph-learning encoder (not an LLM). **Memory fit:** ~220 MiB resident; negligible against 64 GB. Pure addition to a local harness — doesn't compete for memory with the foreground inference model. **Realistic tasks:** the always-on trigger for any proactive-companion-agent pattern — decides on a per-event basis whether to wake the LLM, and what entity/context to anchor on if it does. **How to run:** wait for code release (abstract claims code; no GitHub URL surfaced in the abstract). **Speed estimate:** **11.13 ms/event on GPU, 13.99 ms/event on consumer laptop, both significantly faster than equivalent LLM-call baselines.** On M5 Max the consumer-laptop number is the relevant one (the GPU is busy serving the foreground model); 13.99 ms means **~70 events/sec processing capacity** on CPU, which is well above the actual event rate of a typical user-activity stream. **CPU-resident background thread is the right deployment pattern.**

- **Delta Weight Sync (item #6)** — **Use case on M5 Max:** the 99%-sparsity insight is *not* M5-Max-specific; it's true for any bf16 RL training pipeline. The local-relevant deployment pattern is **disaggregated training where the M5 Max serves vLLM (or MLX-LM) for rollouts while a separate GPU box runs the trainer**, with the Hub bucket as the sync substrate. The 1.2 GB → 20–35 MB delta on Qwen3-0.6B is the load-bearing number for indie-scale work — at this size, the entire async-RL loop is bandwidth-feasible on a residential connection. **The TRL example at `examples/scripts/openenv/async_wordle.py` is the runnable reference.**

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:

- **Conflict: [arxiv:2605.30152] "Do Proactive Agents Really Need an LLM?" directly attacks [arxiv:2605.25971] ProAct** (May 26 ledger entry). Same use case (idle-time proactive triggering on user-activity streams), opposite design choice (220 MiB temporal-graph encoder vs. per-event LLM call). The new paper claims **+16.7 mean F1, up to +46.0, across 14 backbones with 12–83× CPU speedup** — i.e., dominates ProAct's design on both quality and latency on the trigger sub-task. **What it does not address:** ProAct's headline **−28.1% hallucination rate** on the *downstream* generation step — that's a property of the LLM-as-trigger-as-context-anchor architecture and isn't tested in the TGL replacement (which uses the LLM only at generation time, conditioned on entity routing scores instead of full dialogue context). **Flagged `compare`** — both papers can be right if you split the question: TGL wins on trigger F1 and latency, ProAct's full-context-anchor LLM call may still win on downstream hallucination. Needs a head-to-head ablation that runs *both* trigger systems against the same hallucination metric.

- **Confirms-and-extends: [arxiv:2605.29682] EFC quantitatively confirms [arxiv:2605.26112] Scaling the Harness** (May 26 ledger entry). Scaling the Harness was a position paper with no benchmark numbers; EFC is the quantitative version of the same operational claim — feedback-quality is the right scaling coordinate, not raw compute. **R²=0.94 EFC vs. R²=0.33–0.42 raw-tokens, and 27% → 90% success at fixed budget by varying only feedback quality** is the strongest single piece of evidence for the harness-as-primitive thesis to date. Ledger status on [arxiv:2605.26112] updates from `open` to `confirmed-by [arxiv:2605.29682]`.

- **Open empirical question (continuing from 2026-05-26):** the **skill-curation cluster is now six papers** — SkillsVote (post-execution gating), Ratchet (outcome-driven retirement), SkillOpt (held-out-validation gating + text-space optimisation), Skill Consumption (meta-skill that guides extraction), CODESKILL (RL-trained management policy), and now SkillsInjector (adaptive-budget + set-aware injection rendering). All six attack a different layer of the same problem and none directly compete; the unresolved question is whether the *composition* of all six layers (extraction policy + retirement heuristic + validation gate + meta-skill + injection optimiser + adaptive renderer) is the right operating system for skill stores in 2026-era agents, or whether one of them subsumes the others. No head-to-head ablation has been published; the next-paper-cluster prediction is "skill OS / unified-stack" paper that integrates the layers.

- **Open empirical question (new):** the **memory-cluster is now also a four-layer convergence** — MemForest (storage layout, May 22), MMPO (write-policy supervision via Belief Entropy, today), MemTrace (error attribution, May 28), FluxMem (connectivity dynamics, May 28). Same shape as the skill cluster — four independent layers, no direct competition, no unified-stack paper yet. **Open:** does the combination of MMPO's Belief Entropy with MemForest's hierarchical temporal index produce a useful end-to-end memory system, or are the assumptions about write granularity / index structure incompatible? Worth a `compare` once code lands for both.
