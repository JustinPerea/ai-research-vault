### 2. Infini Memory — Maintainable Topic-Structured Documents for Long-Term LLM Agent Memory; 64.7% on MemoryAgentBench; Iterative Agentic Retrieval Replaces Single-Step Lookup
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.10677
- **Authors / org:** Suozhao Ji, Baodong Wu, Zehao Wang, Lei Xia, Qingping Li, Ruisong Song Wang, Wenbo Ding, Zhenhua Zhu, Boxun Li, Guohao Dai, Yu Wang
- **Focus area:** Agent memory (representation layer)
- **What it is:** Persistent text-based agent memory architecture that treats memory as **topic-structured documents** rather than isolated records, summaries, or indexed fragments. Each *topic document* is a semantic unit collecting related evidence, preserving metadata, and supporting fact revision over time. New observations are first **staged in a buffer**, then **periodically consolidated** into coherent textual contexts. At inference time, instead of a single retrieval step, the LLM **iteratively reads memory through tool calls** ("agentic retrieval"). Result on **MemoryAgentBench: 64.7% overall**. Ablations attribute the gains to two complementary parts — topic-structured maintenance (for fact revision / evidence aggregation) and iterative inspection (for evidence assembly). Authors frame the bottleneck of existing systems as the difficulty of **evidence aggregation, fact revision, and memory maintenance** — exactly the failure modes [arxiv:2605.28732] MemTrace localised as operation-level rather than random.
- **Why it matters for Justin's agents:** Direct successor to the maintenance-vs-retrieval thread the ledger has been building since [arxiv:2605.23986] MemForest (database-systems write-amplification), [arxiv:2605.28732] MemTrace (attribution-level fault localisation), [arxiv:2605.28773] FluxMem (heterogeneous-graph dynamics), and [arxiv:2605.29341] WorldMemArena (four-stage lifecycle). Infini Memory's *topic document* is the **second concrete write-side design** (after MemTree) that treats the memory store as a maintainable artifact rather than an append-only log. For a companion app with months-long user history, "topic document with staged buffer + iterative inspection" maps 1:1 onto the Obsidian-vault pattern Justin already uses — *each topic is a markdown file; the staging buffer is a daily inbox file; consolidation is a nightly sync; iterative retrieval is just the read-many-files-then-decide pattern Claude Code already does*. The architecture is implementable today without specialised infrastructure.
- **Action signal:** `try-now` — the design is small enough to graft onto an existing vault-backed memory layer; MemoryAgentBench is the right evaluation harness. Pair with the daily inbox + nightly consolidation pattern Justin's vault already uses.

### 3. ActiveMem — Distributed Active Memory Decoupling Reasoning from Storage (PFC-Planner vs. Hippocampus-Memory); SoTA on GAIA + BrowseComp-Plus with Significantly Reduced Overhead
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.10532
- **Authors / org:** Yunhan Jiang, Wenbin Duan, Shasha Guo, Liang Pang, Xiaoqian Sun, Huawei Shen
- **Focus area:** Agent memory (process-decoupling layer) / Long-running autonomous loops
- **What it is:** Heterogeneous framework that **decouples agent memory from the core reasoning process**. A high-level **Planner** runs reasoning over *distilled semantic gists*; in parallel, a **lightweight, distributed memory system** actively accumulates and consolidates new gists throughout the task. The cognitive analogy the paper draws is **prefrontal cortex (executive control) ↔ hippocampus (memory management)** — the trade-off "scaling reasoning ↔ context overload" is treated not as inherent but as a **consequence of centralised memory organisation**. Reported result: **SoTA accuracy on BrowseComp-Plus and GAIA with significantly reduced overhead** (no headline percentages in the abstract).
- **Why it matters for Justin's agents:** This is the **process-decoupling answer** to a problem that papers like Infini Memory (rep-layer) and OSL-MR (policy-layer) address from other angles. Architecturally, decoupling the *consolidation worker* from the *reasoning loop* is exactly the heartbeat / monitor-driven pattern Justin's long-running-agent thread has been pushing toward (cf. [arxiv:2605.28424] Skill0.5 difficulty-routing, [arxiv:2606.09483] DCPM's asynchronous System2). The PFC/hippocampus framing makes the *parallelism budget* explicit: an LLM-based Planner agent runs at one cadence, a memory-consolidation worker runs at its own cadence, and they communicate through a shared gist stream. For Justin's MCP + Claude Code stack, the cleanest instantiation is **a memory-consolidation sub-agent that runs on its own schedule** (driven by an external scheduler / monitor / cron rather than inline tool call), writes consolidated gists back into the vault, and the main agent reads from a small distilled top-of-stack. That's both a structural-fit for the Anthropic agent-SDK and the simplest known production path to the "reasoning doesn't overload context" property.
- **Action signal:** `try-now` — the decoupling pattern is implementable with two cooperating Claude Code instances + a shared vault folder + a heartbeat (one for reasoning, one for memory consolidation). Wire the planner side to read distilled gists; wire the memory side to run on a scheduler.

### 4. OSL-MR (Observability-Safe Memory Retention) — Memory Retention as Constrained Stochastic Optimisation with Miss / Reacquisition / Stale-Info Costs; Online-Observable / Offline-Available Supervision Split; Beats Recency + Generative-Agents Scoring on LOCOMO + LongMemEval
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.10616
- **Authors / org:** Qingcan Kang, Liu Mingyang, Shixiong Kai, Kaichao Liang, Tao Zhong, Mingxuan Yuan
- **Focus area:** Agent memory (retention-policy layer)
- **What it is:** Formalises memory retention as a **constrained stochastic optimisation problem** with explicit budget feasibility, evidence utility, and **delayed costs (miss penalty, reacquisition delay, stale-information risk)**. The framework — **OSL-MR** — enforces a strict separation between **online-observable features** (available at deployment) and **offline-available supervision** (available only at training time). Training combines an **evidence learner** (from realised evidence supervision) with a **Mixed-Score heuristic** that serves as both a deployable online-safe baseline and a structured inductive prior for learning. Result: on **LOCOMO and LongMemEval**, OSL-MR **consistently outperforms** recency-based, Generative-Agents-style, and other heuristic baselines — **particularly under tight memory budgets**. The Mixed-Score prior preserves recall while improving precision; sensitivity analysis shows robustness across cost configurations.
- **Why it matters for Justin's agents:** Retention has been the under-formalised side of the memory-systems thread. Most papers treat *what to keep* as a scoring heuristic; OSL-MR treats it as a budgeted stochastic decision with **delayed costs** — the same framing that makes inventory management and ad pacing solvable. Three implications for Justin's stack. (1) The **observability split** is operationally critical: any retention policy that conditions on signals only available at training time will silently degrade in deployment — and most published "learned scoring" memory systems quietly violate this. (2) The **miss-penalty / reacquisition-delay** framing is a cleaner cost model than precision/recall for *long-running* companion-app memory, where missing a fact has a known re-cost (ask the user again — bad UX). (3) The **Mixed-Score baseline-as-prior** pattern is the natural pairing for [arxiv:2606.10677] Infini Memory's topic-document maintenance: Infini handles representation/maintenance; OSL-MR handles which-to-keep when the budget bites. Together they are a complete write-side architecture.
- **Action signal:** `track` — the constrained-optimisation framing is more research-y than the Infini Memory representation work and will take longer to port to a vault-backed deployment, but it is the right framework once the staged buffer + topic documents are in place and memory budget becomes binding. Re-read after first Infini-style implementation hits scale.

### 5. Frontier Coding Agents Use Metaprogramming to Adapt to Unfamiliar Programming Languages — Claude Opus 4.6 / GPT-5.4 xhigh Write Python to Generate Brainfuck/Befunge; Forbidding Metaprogramming Causes Large Drops; Opus-Derived Python Helpers Lift Sonnet 4.6 / GPT-5.4 mini
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.10933
- **Authors / org:** Aman Sharma, Sushrut Thorat, Paras Chopra
- **Focus area:** Coding agents / Tools & connectors
- **What it is:** Evaluates **six contemporary coding agents** on four esoteric programming languages (Brainfuck, Befunge-98, plus two unnamed) with a sequential setup — file editing, local execution, hidden-test grading. The protocol exposes **capability differences that SWE-Bench Verified and Terminal-Bench 2.0 compress into much narrower bands**. Headline finding: the strongest agents (**Claude Opus 4.6** and **GPT-5.4 xhigh**) **often avoid writing the target language directly**. On Brainfuck and Befunge-98, they write **Python programs that generate target-language code and debug those generators locally**. **Forbidding this metaprogramming strategy causes large performance drops.** Text guidance distilled from the strategy doesn't help weaker agents — but **Opus-derived Python helper code** (no solved benchmark programs, no hidden-test answers) **sharply improves Sonnet 4.6 and GPT-5.4 mini** on the same problems. **Haiku 4.5 remains low**. More interpreter calls and output tokens **amplify useful strategies in stronger agents** but leave weaker agents near their original performance. The authors' conclusion: strong coding agents adapt to unfamiliar languages by **using tools, feedback, and workspace state to build a working model of the target language** — metaprogramming is the cleanest case of a broader pattern.
- **Why it matters for Justin's agents:** Three operational reads. (1) **The "Opus writes Python that writes Brainfuck" finding is the simplest published evidence that *agentic strategy* is a separable capability from *language fluency*** — Justin's Claude Code stack regularly does the smaller version of this trick (generate a regex, generate a script, generate a test fixture); the paper formalises it as a strategy class. (2) **The Opus-derived Python helper sharply lifting weaker agents** is the *artifact* analogue of skill distillation — and unlike the [arxiv:2605.25430] CODESKILL / [arxiv:2605.23904] SkillOpt skill papers, the artifact is just *code*, not a curated skill bank. The deployment shape is "run the expensive agent once, ship the resulting Python helper into the cheaper agent's workspace, watch the cheaper agent improve." (3) The paper **directly contradicts the implicit claim of SWE-Bench Verified that frontier agents are converging** — esoteric-language scores spread far wider than SWE-Bench Verified scores. **`compare` signal** vs. multiple prior items in the ledger (e.g., yesterday's Self-Harness Terminal-Bench-2.0 gains) that have leaned on SWE-Bench Verified / Terminal-Bench as the discriminating benchmark — this work argues those benchmarks understate the capability gap.
- **Action signal:** `compare` — flag in claims ledger as a benchmark-saturation counterpoint; the "expensive-agent-derived Python helper lifts cheaper agent" pattern is also a `try-now` for any code-agent stack where Justin runs Opus + Sonnet/Haiku tier alongside.

### 6. Workflow-GYM — Professional Long-Horizon GUI-Agent Benchmark; State-of-the-Art Models Achieve Only Slightly Above 30% Success; Failure Modes: Stage Omission, Error Propagation, Objective Drift, Insufficient Pro-Software Understanding
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.11042
- **Authors / org:** Liya Zhu et al. (57 contributors; corresponds to Jingzhe Ding)
- **Focus area:** Evaluation / Tools & connectors (computer-use / GUI agents)
- **What it is:** Benchmark targeting **long-horizon GUI tasks in professional domains** with **specialised software environments** — the gap most existing computer-use benchmarks miss by focusing on general-purpose software, simpler applications, and short-horizon tasks. State-of-the-art models reach **only slightly above 30%** success. Failure analysis names **four distinct modes**: (1) **workflow stage omission** (skipping required steps), (2) **error propagation** (early mistakes cascade), (3) **objective drift** (losing track of the original goal across a long trajectory), (4) **insufficient understanding of professional software environments**. The benchmark is designed to evaluate "whether agents can autonomously operate domain-specific professional software and accomplish economically valuable work in an end-to-end manner."
- **Why it matters for Justin's agents:** The number to hold is **30% vs. OSWorld-Verified 85% (Fable 5)** — the gap *is* the long-horizon + domain-specific dimension. For Justin's federal-data work, *every* serious deployment surface is a professional-domain GUI / API surface — SAP, ServiceNow, FISMA workflows, agency-specific apps — and the 30% number is closer to the deployment reality than the OSWorld number. The four failure modes also map directly onto patterns Justin has likely seen in long-running Claude Code sessions: **stage omission** ≈ skipping a setup step; **error propagation** ≈ a wrong import that becomes a wrong test; **objective drift** ≈ getting absorbed into yak-shaving; **insufficient pro-software understanding** ≈ guessing at an internal API's contract. The benchmark is also useful as **the right shape of CI for a long-running agent**: a fixed set of long-horizon trajectories with intermediate checkpoints, run nightly against the current model+harness, with per-failure-mode regression tracking.
- **Action signal:** `track` — the benchmark itself isn't a drop-in deployment, but the four-failure-mode taxonomy is immediately useful as a diagnostic vocabulary for Justin's own long-running-agent logs; revisit when SoTA crosses 50% (likely with Fable 5 once it's been benchmarked).

### 7. Attention Amnesia — CoT-SFT Breaks Long-Range Recall in Hybrid LLMs (HypeNet-9B NIAH-S2@256K Collapses 67.2% → 9.4%); QK-Restore Recovers and Even Improves
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.11052
- **Authors / org:** Xinyu Zhou, Boyu Zhu, Yi Xu, Zhiwei Li, Yingfa Chen, Huiming Wang, Zhijiang Guo
- **Focus area:** Context engineering / Reasoning & inference-time compute
- **What it is:** Identifies a specific failure mode named **Attention Amnesia**: **standard CoT supervised fine-tuning biases attention gradients toward short-range patterns, disrupting the query-key projections that handle long-range routing** in hybrid LLM architectures (specifically **HypeNet** and **Jet-Nemotron** class). Concrete collapse: **HypeNet-9B on NIAH-S2@256K drops from 67.2% to 9.4%** post CoT-SFT — a **58-point fall** on long-context needle-in-a-haystack with zero deliberate change to the long-context capability target. The authors' fix, **QK-Restore**, surgically restores or even improves the affected projections: **HypeNet-5B S3@256K: 65.4% → 76.4%** while maintaining the reasoning gains from CoT-SFT.
- **Why it matters for Justin's agents:** This is the **first published evidence** that the "fine-tune for reasoning, deploy at long context" recipe — increasingly the default for hybrid SSM+attention architectures — silently breaks the *other* capability of those models. Two operational reads. (1) For anyone evaluating a hybrid open-weights model (Jet-Nemotron, HypeNet derivatives, or anything advertising "sub-quadratic + frontier reasoning"), **you must benchmark on a long-context recall task before and after any reasoning-distillation fine-tune** — the 58-point collapse is the kind of regression that won't show up on a standard reasoning eval but will quietly break production. (2) For Justin's local-inference stack, this constrains which open-weights variants are worth running for *long-context companion* use cases: a reasoning-tuned hybrid checkpoint that lost long-range recall isn't actually a long-context model anymore, regardless of advertised context window. **Open question**: does the same fragility apply to attention-only Transformers under CoT-SFT? The paper specifically targets hybrid architectures; the bias-gradient mechanism could in principle apply to dense Transformers, but the paper doesn't test this.
- **Action signal:** `track` — short-term defensive: add NIAH-S2/S3 @ 256K to any model-evaluation harness before committing a hybrid-LLM checkpoint to a long-context agent.

### 8. ReasonAlloc — Hierarchical Decoding-Time KV Cache Budget Allocation for Reasoning Models; Two-Level (Offline Layer-Wise + Online Head-Wise); Largest Gains at Small Budgets (128–512 tokens) on MATH-500 + AIME 2024
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.11164
- **Authors / org:** Wenhao Liu, Hao Shi, Yunhe Li, Weizhi Fei, Xiangyuan Wang, Mengzhe Ruan, Hanxu Hou, Peisong Wang, Linqi Song, Shuang Qiu
- **Focus area:** Context engineering (KV cache management for inference-time-compute)
- **What it is:** Two-level KV cache budget allocator targeting **long-CoT reasoning trajectories**, where rapid KV growth is the dominant inference bottleneck. **Offline layer-wise allocation** captures architectural demand patterns the authors call a "Reasoning Wave"; **online head-wise reallocation** dynamically shifts budget toward information-rich attention heads during decoding. **Training-free**; **plug-and-play** with existing token-eviction policies (R-KV, SnapKV, Pyramid-RKV); minimal runtime overhead. Evaluated on **MATH-500 and AIME 2024** with **DeepSeek-R1-Distill-Llama-8B**, **DeepSeek-R1-Distill-Qwen-14B**, and **AceReason-14B**. Greatest improvements appear **at small budgets (128–512 tokens)**, where uniform-budget baselines hurt most.
- **Why it matters for Justin's agents:** Adds a *hierarchical allocation* layer to the KV-cache-codec line that already includes [arxiv:2605.19660] OScaR (per-token quantisation, INT2 near-lossless, 5.3× memory reduction) and [arxiv:2605.22106] ArborKV (tree-of-thought-aware allocation, ~4× peak memory reduction with full retention). The three are **orthogonal axes on the same memory budget**: OScaR shrinks each token, ArborKV exploits tree structure, ReasonAlloc routes budget by layer × head importance — they should compose. Particularly relevant for the M5 Max 64 GB local-inference budget: any local reasoning model (DeepSeek-R1-Distill-Llama-8B, AceReason-14B, Qwen3.6-A3B class) running long CoT on long context hits the KV-cache wall before the FLOPs wall, and a training-free plug-in that "wins largest at small budgets (128–512 tokens)" is exactly the regime where Justin is likely running with aggressive quantisation already.
- **Action signal:** `local-fit` — directly applicable to local-inference rigs running R1-distill or AceReason-class reasoning models; pairs with the existing OScaR + ArborKV recipe to push KV-bounded local long-context reasoning further. Watch for code release (none cited yet).

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:
- **[arxiv:2606.10933] Metaprogramming `compare` flag vs. SWE-Bench Verified / Terminal-Bench convergence narrative.** The paper explicitly argues that **SWE-Bench Verified and Terminal-Bench 2.0 compress frontier-agent capability differences into much narrower bands than esoteric-language evaluation reveals**. This is in tension with the implicit framing of recent self-improvement papers ([arxiv:2606.09498] Self-Harness, [arxiv:2606.05922] RHO, [arxiv:2606.06741] OpenSkill) that use Terminal-Bench 2.0 / SWE-Bench Verified as the discriminating signal. The metaprogramming finding doesn't refute those self-improvement gains, but it does argue that gains measured on these benchmarks understate the underlying capability spread. *Status: open — flag in ledger as benchmark-saturation counter-evidence.*
- **Open empirical question 1:** Does the Attention-Amnesia ([arxiv:2606.11052]) bias-gradient-toward-short-range mechanism apply to attention-only Transformers under CoT-SFT, or is the failure specific to hybrid SSM+attention architectures? The paper only tests HypeNet and Jet-Nemotron.
