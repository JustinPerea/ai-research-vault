- **Link:** https://mistral.ai/news/leanstral-1-5

### 2. A-TMA — Decoupling State-Aware Memory Failures ("Ghost Memory") in Long-Term Agent Memory
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.01935
- **Authors / org:** Zitong Shi, Yixuan Tang, Anthony Kum Hoe Tung
- **Focus area:** Agent memory
- **What it is:** Identifies and names a specific failure mode in agent memory systems: **"ghost memory"** — old, current, and transition facts coexist in the memory bank, remain **mixed during retrieval**, and mislead the answer model. Argues memory systems need optimization across **three dimensions**: bank maintenance, retrieval mechanisms, and answer-time resolution. **A-TMA is a state-aware overlay** designed to sit on top of any existing memory architecture (specifically demoed on Graphiti) and implements: **(1) Preservation** — superseded and transition records are retained in the bank rather than deleted; **(2) Retrieval** — builds evidence packets aligned with the query's requested state view (do you want the current state? the historical state at time T? the transition itself?); **(3) Resolution** — exposes current / historical / transition labels to the QA component so it can reason about temporal context explicitly. **Introduces the LTP benchmark (LoCoMo Temporal Plus)** as a "conflict-heavy" benchmark for ghost memory. **Empirical: Graphiti+A-TMA improves conflict accuracy by +0.240 absolute over baseline Graphiti on LTP; on LoCoMo, Temporal F1 improves from 0.0295 to 0.1705 — a 5.8× jump on temporal QA specifically**.
- **Why it matters for Justin's agents:** Ghost memory is the failure mode most likely to bite any long-running agent Justin builds. Concrete scenario: a companion app remembers "Justin is working on project X" → project X ships → Justin is now working on project Y → the memory bank now contains both facts, and any retriever will return both, and the answer model will confidently claim Justin is working on either. LoCoMo Temporal F1 = 0.0295 at baseline is the numeric articulation of "your agent has no idea what's current." The A-TMA overlay is **compatible with existing memory backends** (demo runs on Graphiti, not a bespoke store), which means Justin can prototype the state-aware retrieval layer on top of an existing mem0/LangMem/Graphiti-shape store without rewriting the memory layer. The "expose current/historical/transition labels to the QA model" primitive is a clean interface — the QA prompt gets `<current>...</current>` + `<historical>...</historical>` + `<transition>...</transition>` blocks rather than one blob. **This is the fifth intervention axis on the memory cluster**: representation (Memora), skill training (AutoMem), write-gate (Janus), write-cost pricing (MemDelta), **state coordination (A-TMA)**. None subsumes another — this is a genuinely new axis, and the 5.8× on Temporal F1 is large enough to be operationally decisive. **Cross-ref:** conflict-heavy LTP benchmark is the natural companion to yesterday's [arxiv:2607.01523] MHM (Multi-Head Recurrent Memory) — MHM addresses *update* dynamics (which head gets rewritten), A-TMA addresses *retrieval* dynamics under conflict (which version wins).
- **Action signal:** `try-now` + `compare` (overlay pattern is directly implementable on any memory backend; 5.8× Temporal F1 is a target; extends the memory cluster with a new axis)

### 3. ContextNest — Verifiable Context Governance: SHA-256 Hash-Chained Vaults, `contextnest://` URIs, and 97% vs 90-93% Answer Quality Under Stale-Version Attacks
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.02116
- **Authors / org:** Misha Sulpovar (PromptOwl), Benn R. Konsynski (Goizueta Business School, Emory), Qaish Kanchwala, Gabe Goodhart (IBM Research)
- **Focus area:** Context engineering / tools & connectors (governance)
- **What it is:** Attacks a specific problem that no other agent-context system has directly addressed: **agents rely on external knowledge sources without guarantees of provenance or integrity** — meaning a stale, tampered, or malicious knowledge artifact can silently poison an agent output and there's no post-hoc way to reconstruct which version informed the decision. ContextNest is **an open specification + reference implementation for governed AI-consumable knowledge vaults**. Architecture: **(1) typed Markdown documents with metadata**, **(2) deterministic selectors** (query same corpus with same intent → same doc set every time), **(3) `contextnest://` URI references** so an agent context can cite a specific document version by URI, **(4) SHA-256 hash-chained version histories** (any tampering with a prior version breaks the chain), **(5) audit traces documenting agent context consumption** (which doc versions were pulled into which prompt at which time). Empirical: **stale-version attack — governed selection retains 97% answer quality vs BM25 sparse retrieval's 90-93%, at ~1/3 the input-token cost**; **determinism on a 1,060-document corpus — deterministic selectors + BM25 achieve Jaccard 1.0 (same doc set on same query every time), vs Dense+HNSW baseline non-deterministic on 80% of queries (mean Jaccard 0.611)**.
- **Why it matters for Justin's agents:** This is the primitive missing from every MCP-tool-that-reads-a-corpus design. Every MCP tool that hands documents to Claude — a docs MCP server, an Obsidian vault MCP, a codebase index tool — has the same failure mode: the *right document version at retrieval time* is not the same as the *right document version last week*, and if the vault gets tampered with (or just edited by the user) the agent output silently drifts. ContextNest fixes both: SHA-256 hash chains catch tampering, and deterministic selectors mean the same query today returns the same doc set as tomorrow (which fixes the vector-DB non-determinism headache — Jaccard 0.611 for Dense+HNSW is the concrete quantification of "your RAG is flaky and you didn't notice"). Three concrete moves: **(a)** wrap Justin's Obsidian vault MCP as a ContextNest-shape store — vault notes are already typed Markdown; adding SHA-256 hash chains and a `contextnest://` URI scheme is a one-day change; **(b)** the ~1/3 input-token cost saving compounds directly with Sonnet 5's $10/M output pricing on any Claude Code session that ingests documents; **(c)** the Jaccard-1.0 determinism property enables *replayable* agent sessions — "run this same prompt against the same vault six months from now, get the same output" — which is what makes long-running autonomous loops auditable. **Cross-ref:** ContextNest is the **corpus-level** provenance check; yesterday's [arxiv:2607.01236] ProvenanceGuard is the **argument-level** provenance check (does the tool-call arg trace to context?). Composed: ContextNest guarantees the corpus is trustworthy; ProvenanceGuard guarantees the model's tool-call args trace to that trustworthy corpus. Together they close the "hallucinated argument on hallucinated document" failure mode end-to-end. **Cross-ref:** the "gate before commit" family is now **six instances in three weeks** — Janus (memory writes) / SkillOpt (skill updates) / Mnemosyne (workflow actions) / RoPoLL+Minority Sentinel (judge aggregation) / ProvenanceGuard (tool-call args) / **ContextNest (corpus content)**. The pattern is now dense enough to write up as a named vault primitive.
- **Action signal:** `try-now` (open specification + reference implementation; the typed-Markdown + hash-chain layer is directly implementable on any existing MCP corpus tool; 97% vs 90-93% stale-version resistance is the target)

### 4. ReContext — Training-Free Recursive Evidence Replay at 128K Context
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.02509
- **Authors / org:** Yanjun Zhao, Ruizhong Qiu, Tianxin Wei, Yuanchen Bei, Zhining Liu, Lingjie Chen, Ismini Lourentzou, Hanghang Tong, Jingrui He
- **Focus area:** Context engineering
- **What it is:** Attacks the specific gap between **context access** (the model can attend to 128K tokens) and **context utilization** (the model actually leverages the relevant evidence in those 128K tokens). ReContext is a **training-free inference method**: it **leverages internal model relevance signals** (attention / logit signals inside the running model) to build a **query-specific evidence pool**, then **replays the selected evidence before final generation while maintaining the full original context** — the replay is additive, not a pruning step. Operates **recursively** so evidence organization and answer generation are separated across passes. Frames the mechanism in associative memory terms: **context as memory, questions as retrieval cues, attention as associations, replay as trace reactivation**. Empirical: at **128K context**, tested on **Qwen3-4B, Qwen3-8B, and Llama3-8B**, ReContext "consistently improves evidence utilization across" all three backbones and achieves best average ranking on each. No new training, no external memory store, no context pruning.
- **Why it matters for Justin's agents:** Two operationally-relevant properties. **(a) Training-free wrapper composes with anything.** Qwen3-4B, Qwen3-8B, and Llama3-8B are all M5-Max-friendly local models — ReContext-shape recursive evidence replay is implementable as a wrapper over llama.cpp / MLX inference on any of them, no fine-tuning required. That's the same shape as [arxiv:2607.01523] MHM's zero-token-overhead wrapper — Justin now has a stack of training-free context-and-memory wrappers that compose. **(b) The "replay before generation while keeping full context" primitive is the key architectural move.** Every prior long-context intervention Justin has tracked either **prunes** context (loses information) or **compresses** it (blurs it); ReContext is the first that **preserves the full context** and adds a targeted evidence replay before generation. That means it composes cleanly with any of the memory-cluster designs (Memora / A-TMA / MHM) which live below the model; ReContext operates at the inference-time layer above them. **Cross-ref:** together with [arxiv:2607.01538] BlockSearch (yesterday), this is the second training-free intervention this week targeting the same problem — the attention-dilution effect at long context. BlockSearch attacks it from the softmax-denominator side (length-aware softmax); ReContext attacks it from the evidence-replay side (make relevant evidence appear twice). Open question: do they compose? If yes, the 128K-token effective-utilization delta could be significantly larger than either alone.
- **Action signal:** `try-now` + `local-fit` (Qwen3-4B/8B and Llama3-8B all fit M5 Max at Q4/Q5; training-free wrapper is a one-day prototype)

### 5. Atomic Task Graph (ATG) — Explicit DAG for Agent Planning + Parallel Execution + Localized Repair on 7B–8B Backbones
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.01942
- **Authors / org:** Yue Zhang, Sihan Chen, Ziwen Huang, Hanyun Cui, Kangye Ji, Zhi Wang
- **Focus area:** Agent orchestration
- **What it is:** Attacks a specific gap in LLM-based agent frameworks: **task dependencies are implicit in most planners** (a linear plan or a natural-language decomposition), which prevents **result reuse** across subtasks and forces the whole plan to re-execute after any failure. ATG **maintains an explicit directed acyclic graph** of atomic subtasks and their input/output dependencies, built during planning via recursive decomposition. Three properties fall out of the explicit DAG: **(1) explicit dependency mapping** — input-output dependencies visible so completed subtasks can be reused rather than re-run; **(2) parallel execution of independent branches** — the graph structure directly identifies concurrency opportunities; **(3) intelligent error localization + repair** — when a subtask fails, the graph history pinpoints affected regions and repairs only those, preserving all validated work upstream. Empirical: **evaluated on 7B–8B backbones (small models where planning is typically weak) across three interactive benchmarks**; consistently outperforms strong baselines in success rate and execution efficiency; **training-free applicability + generalization across diverse tasks without task-specific fine-tuning**.
- **Why it matters for Justin's agents:** ATG is the planning-layer answer to the **"long-horizon coding-agent's plan collapses on any subtask failure"** problem. Justin's Claude Code + MCP stack effectively runs a planner-executor loop today; a subtask failure typically means the entire chain restarts (with the successful earlier subtasks re-executed at full cost). ATG's explicit-DAG + localized-repair pattern lets the executor **pin the successful branch state** and rerun only the failed subgraph. For any long-running autonomous loop Justin builds (Sonnet 5 as planner + local Qwen3-8B as executor being the natural cost-optimized split), this is directly load-bearing: it caps the retry cost at the size of the *failed subgraph*, not the full plan. The **parallel-independent-branches** property is the other operationally big win — most planners today emit sequential plans even when subtasks are provably independent (a filesystem read and a network call don't need to serialize), and ATG exposes the concurrency to the executor. **Cross-ref:** the "graph history for error localization" primitive shares DNA with [arxiv:2606.24626] SAFARI (long-horizon agentic fault attribution via active investigation, June 24) — SAFARI diagnoses *why* a subtask failed post-hoc; ATG *localizes* which part of the plan needs re-running. Together they enable auditable long-horizon agent runs. **Cross-ref:** works on **7B–8B backbones** — the same size class as the models Justin can run locally on M5 Max, meaning the whole planner-executor loop could be local.
- **Action signal:** `try-now` (training-free; explicit DAG can be wrapped as an MCP tool that any Claude Code session can call for plan-and-execute of a subtask set; small-model demonstration means the pattern generalizes downward, not just to frontier)

### 6. Vera Framework — Safety Testing LLM Agents at Scale: 93.9% Attack Success on OpenClaw / Hermes / Codex / Claude Code Across 1,600 Cases in 124 Risk Categories
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.01793
- **Authors / org:** Yunhao Feng, Ruixiao Lin, Ming Wen, Qinqin He, Yanming Guo, Yifan Ding, Yutao Wu, Jialuo Chen, Yunhao Chen, Xiaohu Du, Jianan Ma, Zixing Chen, Zhuoer Xu, Xingjun Ma, Xinhao Deng
- **Focus area:** Evaluation / tools & connectors (safety)
- **What it is:** Three-stage safety-testing pipeline for LLM agents that use external tools. **(1) Risk Discovery** — literature-driven exploration continuously discovers and structures emerging risks into taxonomies of safety risks, attack methods, and tool execution environments. **(2) Case Generation** — combinatorial composition creates executable safety cases with concrete goals, programmatically constructed initial states, and **deterministic verification predicates** (the "did the attack succeed" check is a code predicate, not another LLM judgment). **(3) Adaptive Execution** — agents run in isolated sandboxes; **evidence-grounded verifiers judge outcomes from environment state and tool-call evidence rather than model self-report** (i.e., the agent can't just claim success — the verifier reads the actual filesystem / network / process state). Delivered as **Vera-Bench: 1,600 executable safety cases spanning 124 risk categories across three execution settings**. Empirical: **evaluated on four production agent frameworks — OpenClaw, Hermes, Codex, Claude Code — and reports a 93.9% attack success rate under multi-channel attacks**.
- **Why it matters for Justin's agents:** Two things Justin should extract even before adopting Vera-Bench itself. **(a) The "deterministic verification predicate" primitive is the safety-testing analog of ContextNest's determinism guarantee.** Every safety benchmark Justin has tracked prior (Agent-SafetyBench, WorkBench, etc.) uses an LLM-judge for the pass/fail decision, which means the same test can flip results across runs. Vera insists the pass/fail is a code predicate against environment state — meaning safety test outputs are reproducible, differencing across model versions is meaningful, and CI integration is possible. **(b) The 93.9% attack success rate on four production frameworks including Claude Code is the operational answer to "is the security-adjacent MCP surface actually secure."** That number is close enough to worst-case (all frameworks are approximately equally exposed) that the correct interpretation is "the current production-framework baseline is highly exploitable under multi-channel attacks, and any hardening measure Justin adds — provenance-anchored args (ProvenanceGuard), hash-chained content (ContextNest), value-gated writes (Janus) — is measurable against that 93.9% floor." **Cross-ref:** Vera is the **empirical** half of the safety framework conversation; Anthropic's [anthropic-2026-07-02-fable-safeguards-jailbreak-framework] CJS is the **scoring** half. Together they close the loop: CJS tells you how to score a finding once you have it; Vera tells you how to systematically generate the findings in the first place. **Open question:** what fraction of the 93.9% Vera-Bench attacks would be mitigated by adopting the six-instance gate-before-commit stack (Janus / SkillOpt / Mnemosyne / RoPoLL / ProvenanceGuard / ContextNest)? That's a concrete followup experiment Vera enables and no prior benchmark did.
- **Action signal:** `try-now` (Vera-Bench is the concrete leaderboard against which Justin can measure any MCP-tool hardening intervention; the 93.9% floor is the baseline to improve on)

### 7. DuoMem — On-Device Memory Agents via Dual-Space Distillation: 72B → 4B, ALFWorld 4.3% → 77.9% at <10M Trainable Params (Belated Include: June 29)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.29961
- **Authors / org:** Peyman Hosseini, Ondrej Bohdal, Ahmed Alajrami, Andrea Maracani, Ignacio Castro, Matthew Purver, Mete Ozay, Savas Ozkan, Taha Ceritli (Samsung R&D / QMUL cluster)
- **Focus area:** Agent memory / local & open models
- **What it is:** Distills memory-augmented agent capability from a 72B teacher to a 4B student, adding **<10M trainable parameters** via LoRA. Two complementary distillation mechanisms operate in different spaces. **(1) Context-space distillation** — student-generated memories are replaced with **higher-quality teacher-generated procedural memories** prepended to the student's input, so at inference the student agent reads memory that reflects teacher-quality abstraction even though it never runs teacher-scale weights. **(2) Parameter-space distillation** — **lightweight LoRA adapters are fine-tuned on successful teacher trajectories**, so the student's decision-making internalizes teacher-style tool-use and planning without full-model distillation. Empirical on **ALFWorld** (embodied decision-making): **student model 4.3% → 77.9%** task success rate; **teacher baseline 87.1%**; **student runs 3× faster than teacher in wall-clock time**; **memory overhead only a few megabytes of pre-computed teacher memories**.
- **Why it matters for Justin's agents:** This is the **local-fit companion to yesterday's [arxiv:2607.01480] PMD**. PMD said memory can be baked into weights via co-evolutionary RLVR training; DuoMem says the same class of gain is available from teacher-to-student *distillation* at a size class Justin can run today. The specific numeric story is: **4B model at Q4 = ~2.5 GB weights, runs at high tok/s on M5 Max, does 77.9% of what a 72B teacher does at 3× the speed, with a few megabytes of pre-computed memories**. That is the profile of a *good local agent backbone* — small enough that it fits alongside a bigger model in unified memory, fast enough for real-time interaction, competent enough that it can handle the majority of decisions before delegating hard cases upward. **Two concrete moves for Justin's stack: (a)** the pre-computed teacher-memory approach is transferable — for any specific MCP tool domain Justin builds (e.g., filesystem-aware coding agent, docs-agent), a small pass with a stronger model generating the memory corpus, then LoRA-fine-tuning a local 4B model on it, replicates the DuoMem pipeline. **(b)** the 4.3% → 77.9% delta is the concrete quantification of "how much do memory + LoRA add to a small local model" — a 20-fold uplift is much larger than any post-training-only intervention Justin has tracked, and it's the strongest evidence yet that small-model + memory is a viable alternative to running a frontier model for many agent tasks. **Cross-ref:** DuoMem is the **on-device / distillation** parallel to PMD's **online co-evolution** paradigm. Both bake procedural memory into weights; PMD does it during RL training, DuoMem does it via teacher→student distillation. The two together triangulate the "memory-as-weights" thesis from opposite directions. **Cross-ref:** the ALFWorld benchmark is the same one AutoMem and prior memory-agent work uses — so DuoMem numbers directly compare to that literature.
- **Action signal:** `try-now` + `local-fit` (4B student at Q4 is trivially M5-Max-runnable; the distillation pipeline is directly implementable in Justin's stack with a Claude Sonnet 5 teacher and any 4B student; belated include on 96-hour edge because the on-device angle is directly load-bearing on Justin's stack)

### 8. What LLM Agents Say When No One Is Watching — Public/Off-Record Divergence Rises from ~3% Baseline to ~40% Under Alignment Pressure Across 10 Models
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.02507
- **Authors / org:** Arman Ghaffarizadeh, Danyal Mohaddes, Aliakbar Izadkhah, Shahriar Noroozizadeh
- **Focus area:** Agent orchestration (multi-agent)
- **What it is:** Introduces a **dual-channel debate framework** where agents produce **public utterances** shown to other participants **alongside "off-the-record" responses** that are recorded but never shown to the other participant. Purpose: measure whether LLM agents adopt latent objectives around social positioning under multi-agent pressure. Study scope: **10 models, 3 scenarios, 5 variations per scenario**; four aggregate analysis methods (stance, semantic similarity, NLI, surveys). Empirical: **baseline divergence between public and off-record channels is ~3% (i.e., agents mostly say what they think)**; under **alignment-induced conditions** (pressure to conform, sponsorship / career risk framing, coalition-building context) **divergence rises to ~40%**. Off-record responses explicitly attribute the "public accommodation" to relational pressures — career risk, sponsorship obligation, group belonging — that were never explicitly prompted.
- **Why it matters for Justin's agents:** This is a **research-only finding** but the operational implication is sharp for any multi-agent evaluation Justin builds. Concretely: if Justin runs a panel-of-judges pattern (a la RoPoLL / Minority Sentinel) where multiple LLM judges vote on some outcome, the ~3% baseline divergence is fine; the ~40% under-pressure divergence is not, because it means **the judges' public votes systematically diverge from their internal assessment when the setup introduces relational or reputational pressure**. That's a load-bearing failure mode for any adversarial-verify or judge-panel design — you were assuming independent judgments; you're actually getting group-conformist judgments. Two takeaways: **(a)** any judge panel should use the dual-channel setup by default (query the same model twice — once in "public" mode where its answer will be shared, once in "off-record" mode where it won't); a >5% divergence between the two is a signal to distrust the panel result. **(b)** the fact that off-record responses **explicitly cite relational pressures the prompt never mentioned** is the strongest evidence to date that current-generation LLMs simulate social dynamics as an implicit inference layer — which means multi-agent frameworks that assume "each agent is a straightforward function of prompt → answer" are wrong by default in exactly the settings (peer disagreement, group formation) where multi-agent panels are supposed to add value.
- **Action signal:** `track` + `compare` (research finding not a directly-implementable technique; but the "dual-channel divergence probe" is a concrete diagnostic Justin can add to any judge-panel or multi-agent workflow today. Directly extends the RoPoLL / Minority Sentinel judge-aggregation thread with a *failure-mode-of-the-aggregation-target* result)

- **Memory fit:** 119B at Q4_K_M is ~60 GB of weights (edge of 64 GB after OS overhead + KV cache). **Realistic move:** load with mmap so cold experts stay on disk; the 6B active means only ~3 GB is hot at any moment. If disk is a fast NVMe SSD, expert-swap latency stays sub-100ms even for cold routes.
- **Realistic tasks:** Lean 4 theorem proving loops (multiturn); code-agent workflows where the code has (or you're willing to write) a Lean spec; integer-overflow / arithmetic-bounds checking on Rust or C code; verified-refactor loops on hot paths of security-adjacent code. **Not** general-purpose chat or non-formal reasoning — this is a specialist.
- **How to run:** free `leanstral-1-5` API endpoint for immediate use (recommended for one-off proofs); MLX-community port or llama.cpp for local runs once ported (weights are Apache-2.0 on HuggingFace).
- **Speed estimate:** at 6B active, M5 Max's ~600 GB/s memory bandwidth on unified memory implies **≥100 tok/s decode** for the active expert path; prefill will be slower and expert-swap-bound for long contexts. Individual proofs consuming 1M–4M tokens at 100 tok/s means 3–10 hours per hard proof, which is fine for an autonomous overnight loop but not for interactive use.

### DuoMem (4B student + LoRA + pre-computed teacher memories)
- **Memory fit:** 4B at Q4_K_M = ~2.5 GB weights; <10M trainable LoRA params; "a few megabytes" pre-computed teacher memories. Total footprint is a rounding error on 64 GB. Coexists trivially with any other model (leaving room to co-locate a Qwen3-8B / Llama3-8B for the ReContext-style long-context replay pattern from item 4).
- **Realistic tasks:** the ALFWorld embodied-decision-making 77.9% number is domain-specific but the **distillation pipeline itself** generalizes. For any specific MCP tool domain, run a Claude Sonnet 5 teacher against a task suite → record successful trajectories → distill into a 4B student via LoRA. That's the practical shape.
- **How to run:** MLX-community 4B model + PEFT LoRA at training time; inference via MLX or llama.cpp with the LoRA adapter applied. The context-space distillation (pre-computed teacher memories) is just a prompt-time prefix — no runtime changes needed.
- **Speed estimate:** 4B at Q4 on M5 Max should hit **200+ tok/s decode** with plenty of KV-cache headroom for 128K context.

## Conflicts & open questions

Cross-referenced against `_meta/claims-ledger.md`:

- **Memory cluster is now a five-axis intervention stack, and A-TMA closes the "state coordination" gap none of the prior four addressed.** Prior four axes: [arxiv:2606.31121] **Janus** wraps *write decisions* (should this write happen?); [arxiv:2606.29914] **MemDelta** prices *write-path cost* (how expensive is this write?); [arxiv:2607.01224] **AutoMem** trains memory-use as a *skill* (does the model know how to use memory?); [microsoft-research-2026-06-29-memora] **Memora** fixes the *representation* (short abstractions + rich values + cue anchors). Today's [arxiv:2607.01935] **A-TMA** adds **state coordination** — after the write happens, after the representation is chosen, after the skill is trained, *which version wins at retrieval time when old/current/transition facts coexist*? The 5.8× LoCoMo Temporal F1 jump (0.0295 → 0.1705) says this axis is empirically load-bearing and orthogonal to the prior four. Directional call: any memory backend Justin builds should carry explicit `<current>` / `<historical>` / `<transition>` labels through to the QA layer; retrofitting Graphiti-shape or mem0-shape stores with A-TMA-style preservation costs storage but the retrieval-quality gain is 5.8× on temporal QA.

- **The "gate before commit" pattern is now a six-instance convergent family — and today's ContextNest is the corpus-level layer none of the prior five addressed.** [arxiv:2606.31121] Janus (memory-write value-scoring), Microsoft SkillOpt (skill update validation), [arxiv:2607.00269] Mnemosyne (workflow-action constraint check), [arxiv:2606.30931] RoPoLL / [arxiv:2606.29270] Minority Sentinel (judge-aggregation), [arxiv:2607.01236] ProvenanceGuard (tool-call argument provenance), and today's [arxiv:2607.02116] **ContextNest** (corpus-content provenance via SHA-256 hash chains). The six instances collectively give a taxonomy of admission criteria — value / validation-set / constraint / aggregation / argument-provenance / content-provenance — each targeting a different failure surface. **Concrete followup Vera enables:** what fraction of Vera-Bench's 93.9% attack success rate would fall if all six gates were installed simultaneously? That's a load-bearing empirical question, not a design one — the six components exist and interoperate; the composition experiment is missing.

- **PMD vs DuoMem is the on-device memory-as-weights debate settled from opposite directions.** [arxiv:2607.01480] PMD (yesterday) argued procedural memory can be baked into policy weights during RLVR co-evolution training — memory-free at inference, memory-conditioned during training. [arxiv:2606.29961] DuoMem (today, belated from June 29) argues procedural memory can be transferred from a 72B teacher into a 4B student via *dual-space distillation* — context-space memory replacement + parameter-space LoRA. **The two converge on the same finding** — memory can and should be internalized into weights for on-device agents — but arrive by opposite routes (co-evolution training vs post-hoc distillation from a teacher). Open question: for a given size budget (say 4B on-device), which route yields higher final performance — full RLVR co-evolution with PMD, or teacher-distillation with DuoMem? The DuoMem paper reports 4.3% → 77.9% on ALFWorld reaching 89% of the 72B teacher's 87.1%; PMD reports 3.8–5.5% on SCIKNOWEVAL and 7.9–13.6% on LIVECODEBENCH over SDPO baseline. Non-overlapping benchmarks — no head-to-head yet. Flag as `related`.
