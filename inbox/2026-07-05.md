### 1. Steerability via Constraints — Substrate-Level Oversight for Coding Agents (Gemma 4 e4b: 54.5% → 90.9% Backdoor Recall)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.02389
- **Authors / org:** Thomas Winninger
- **Focus area:** Coding agents / tools & connectors / evaluation (safety)
- **What it is:** Direct attack on the "scalable oversight of coding agents" problem. Argues that the mechanisms already used to make human engineering teams safe — **access control, network policies, strict coding conventions enforced by tooling** — apply to LLM agents more cost-effectively than scaffolding. Concrete demonstration: give a **Gemma 4 e4b** reviewer model a Python codebase with **11 inserted backdoors**, then ask it to detect them under two configurations. **Unconstrained baseline: 54.5% recall.** **Constrained substrate + a ~200-line-of-code `docs` CLI: 90.9% recall.** Substrate and tools contribute **independently** to the improvement. Author picks Python deliberately because "substrate-level oversight gains are largest where the language gives the fewest guarantees by default."
- **Why it matters for Justin's agents:** This is the direct empirical response to yesterday's **[arxiv:2607.01793] Vera Framework 93.9% attack-success-rate on Claude Code and three peer frameworks**. The Vera finding said "current production agent frameworks are broadly exploitable"; today's Steerability paper says "the mitigation is not more agent scaffolding, it is substrate constraints + tooling." **Three concrete moves for Justin's stack: (a)** any MCP tool Justin builds should ship with an *access control layer* — enumerated allowed file paths, allowed network hosts, allowed shell subcommands — not a natural-language "please only touch X" prompt hint; the 90.9% vs 54.5% delta says this is worth ~35 percentage points of security-review recall. **(b)** the **~200-LoC CLI** is the operational shape — a small `docs`-style utility that the agent uses to structure its exploration, and it's **independent of the substrate constraint's contribution**, meaning both are worth implementing. **(c)** Gemma 4 e4b as the reviewer means the local-fit story is exceptional — Justin's M5 Max can host the reviewer *and* the tool substrate locally, and the security-adjacent MCP surface Justin cares about (his federal-data-engineer side) can be reviewed offline without shipping code to a frontier lab. **Cross-ref:** Composes directly with the six-instance gate-before-commit stack from yesterday's ContextNest note. The gate stack (Janus/SkillOpt/Mnemosyne/RoPoLL/ProvenanceGuard/ContextNest) is *what* to check; Steerability's substrate + tool CLI is *how* the checker is scaffolded. **Cross-ref:** the "tools contribution + substrate contribution are independent" property is the empirical justification for continuing to invest in MCP-tool authoring even in environments that already have strong substrate controls.
- **Action signal:** `try-now` + `local-fit` (200-LoC CLI is a one-day prototype; Gemma 4 e4b runs on M5 Max at Q4 in <4 GB; the 54.5% → 90.9% delta is a target Justin can measure)

### 2. PACE — 85% Pairwise Model-Ranking Accuracy on SWE-Bench / GAIA-Class Agentic Benchmarks at <1% of Full Eval Cost
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.02032
- **Authors / org:** Yueqi Song, Lintang Sutawika, Jiarui Liu, Lindia Tjuatja, Jiayi Geng, Yunze Xiao, Daniel Lee, Aditya Bharat Soni, Vincent Lo, Xiang Yue, Graham Neubig (CMU)
- **Focus area:** Evaluation
- **What it is:** Attacks the "SWE-Bench and GAIA cost $XXk to run per model" problem head-on. **PACE constructs proxy benchmarks by selecting instances from existing non-agentic evaluations whose aggregate scores most reliably predict model performances** on agentic benchmarks. Uses regression fitting + two instance-selection strategies to identify **atomic capabilities that correlate with agentic performance**. Empirical: **14 models × 4 agentic benchmark targets** (SWE-Bench, GAIA, and two others), leave-one-out cross-validation MAE < 4%, Spearman > 0.80, **pairwise model-ranking accuracy ~85%**, at **<1% of full evaluation cost**.
- **Why it matters for Justin's agents:** Justin's model-comparison surface is nontrivial — Claude Sonnet 5 for the planner tier, Opus 4.7 for the reasoning tier, local Qwen/Llama/Gemma variants for the executor tier, and any new open-weight release he wants to evaluate against those. Running SWE-Bench end-to-end on 4-6 models per week is not economical. PACE inverts the math: a proxy that gets 85% of the pairwise ranking right at <1% of the cost means Justin can screen 20+ candidate models per week and only pay the full SWE-Bench cost on the finalists. **The 85% pairwise accuracy is the key number** — not raw score correlation but *ranking* correlation, which is exactly what "should I use model A or model B?" reduces to. **Concrete integration:** wire PACE as an MCP tool that Claude Code can invoke to pre-screen candidate models before committing to a full agentic-benchmark run. **Cross-ref:** yesterday's [arxiv:2607.01793] Vera Framework contributes the *safety* half of the model shootout — 93.9% attack-success as a baseline; PACE contributes the *capability* half at 85% ranking accuracy. Together they define a two-axis pre-screening pipeline (capability + safety) that fits inside a single afternoon of eval time. **Cross-ref:** the 14-models sample size is not enormous — flag as an open question whether the ~85% pairwise accuracy holds on new models trained after PACE's regression fit was learned (i.e., is this a rolling benchmark or does it stale?).
- **Action signal:** `try-now` (proxy benchmark is directly usable; <1%-cost story means the payback on integration is immediate; 85% pairwise ranking accuracy is the concrete target)

### 3. CacheMerge (CanonicalMerge) — CvRDT-Based KV-Cache Composition for Multi-Agent Latent Reasoning: Byte-Identical Under Any Permutation
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.01308
- **Authors / org:** Carlos Baquero, Luís Brito
- **Focus area:** Agent orchestration / agent memory / context engineering
- **What it is:** Attacks a specific gap in multi-agent latent reasoning: **when N agents contribute KV-cache fragments into a shared latent space, the *order* in which fragments arrive determines the merged cache**, which means the system is order-sensitive (non-deterministic) and cannot be treated as a state to reason about. **CanonicalMerge** solves this by **ordering caches by mean K-norm at a middle layer**, which renders the merged cache **byte-identical under any input permutation**. Cast as a **CvRDT (Convergent Replicated Data Type) with set-union semantics** — the multi-agent latent-cache state is a set of content-addressed latent fragments, the merge is set union, and CanonicalMerge is the canonical serialization of the merged set. Verified on **Qwen 1.7B and 4B**. **Benchmark**: on partitioned-reasoning tasks, CanonicalMerge **matches the best BagMerge orderings across all regime-budget-ordering combinations without requiring ordering knowledge** — i.e., you don't need to know the "right" order because the merge is order-invariant by construction. **Limitation noted**: at k > 2 agents, the approach "transports and colocates latent traces but does not by itself compose them" — the ordering problem is solved but a separate composition problem remains at larger fan-outs.
- **Why it matters for Justin's agents:** This is a genuinely new primitive for the memory cluster. Prior memory-cluster interventions Justin has tracked all operate at a *single* agent's memory bank: representation (Memora), skill (AutoMem), write-gate (Janus), write-cost (MemDelta), state coordination (A-TMA, yesterday). CacheMerge introduces the **inter-agent** axis — how do multiple agents share latent state deterministically? The CvRDT framing is important because it's the same abstraction distributed systems has used to solve this class of problem for decades (Riak, distributed shopping carts, etc.), and it means the multi-agent latent-cache state can be reasoned about as a distributed data store rather than an ad-hoc blob. **Two operational implications: (a)** for any multi-agent workflow Justin builds where a planner and one or more executor agents share intermediate reasoning state (planner emits a partial plan → executor A refines → executor B refines → planner recomposes), the CanonicalMerge property means the final composed cache is deterministic — which means the workflow is *replayable*, which is what makes long-horizon multi-agent runs auditable. **(b)** Qwen 1.7B and 4B verification means the primitive is demonstrated on models Justin can run locally — the multi-agent latent-reasoning setup does not require frontier scale. **Cross-ref:** the "byte-identical under any input permutation" property complements yesterday's [arxiv:2607.02116] ContextNest deterministic-selectors (Jaccard 1.0 on repeated queries) at a different layer — ContextNest gives determinism at the *corpus retrieval* layer; CanonicalMerge gives it at the *latent state merge* layer. Together they close the "your multi-agent pipeline is non-deterministic and you didn't notice" failure mode from both sides. **Cross-ref:** the k > 2 composition limitation is the concrete open problem to watch — a followup showing composition at k = 3, 4 would make this a full solution.
- **Action signal:** `try-now` + `local-fit` + `compare` (implementable on top of any llama.cpp / MLX inference stack; Qwen 1.7B/4B verified means M5 Max can run the full multi-agent latent-reasoning setup locally; adds a new inter-agent axis to the memory cluster)

### 4. Maven — Evidence-State RL for Long-Context Reasoning (Llama + Qwen on LongBench v2, LongReason, RULER)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.02073
- **Authors / org:** Ya Gao, Pekka Marttinen (Aalto University)
- **Focus area:** Context engineering / reasoning & inference-time compute
- **What it is:** Attacks the same gap as yesterday's [arxiv:2607.02509] ReContext but from the RL-training side rather than the training-free wrapper side. **Maven maintains an editable evidence memory** during long-context reasoning and provides **granular rewards on intermediate actions**: (1) **add-via-marginal-gain** — reward for pulling in a new piece of evidence that improves the working state; (2) **link-via-synergy** — reward for connecting two evidence items that jointly support a claim; (3) **drop-via-improved-support** — reward for removing a distractor. Optimized inside **GRPO**, so evidence navigation is a *stateful* RL problem rather than a one-shot extraction. **Empirical:** on **Llama and Qwen** backbones across **LongBench v2, LongReason, RULER**, Maven "outperforms outcome-only RL and evidence-identification baselines" and produces **more sufficient evidence sets with lower distractor retention**.
- **Why it matters for Justin's agents:** This closes a specific gap in the training-free family. Yesterday's ReContext showed that a *wrapper* can lift long-context evidence utilization on frozen 4B/8B models; Maven shows that if you're willing to *train* the model with an evidence-state reward, you can bake the same behavior into the weights. The interesting property is that Maven's reward structure — add / link / drop — is **exactly the ontology ContextNest and A-TMA use for *representation* and *retrieval***, but at the RL-reward layer. That means: the same "evidence-graph" primitive can now be enforced at three levels of the stack — retrieval (ContextNest), state coordination (A-TMA), and now training reward (Maven) — which is a strong convergence signal that this is the right ontology. **Concrete integration for Justin:** for any small local model Justin wants to specialize as a long-context executor (Qwen 3-4B, Llama 3-8B), Maven's GRPO-with-evidence-rewards is the recipe to bake in the behavior. **Cross-ref:** open question raised — do the training-free wrapper (ReContext) and the RL-trained backbone (Maven) *compose*? If ReContext-shape recursive replay wrapped around a Maven-trained backbone gets larger deltas than either alone, the operational recommendation is "train once with Maven, deploy under ReContext." **Cross-ref:** the "add / link / drop" reward structure is close to the memory-cluster's write-gate (Janus) and write-cost (MemDelta) primitives, but applied to the *evidence buffer* rather than the persistent memory bank — an analog worth naming.
- **Action signal:** `try-now` + `local-fit` (implementable with GRPO on any Qwen 3-4B or Llama 3-8B; benchmarks are all publicly reproducible; expected to compose with ReContext)

### 5. kNNGuard — Training-Free Configurable LLM Guardrail from Hidden Activations: 2.7×–10× Faster, <10s Domain Adaptation
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.02072
- **Authors / org:** Mahmoud Abdelfattah, Hamid Nasiri, Peter Garraghan (Lancaster University)
- **Focus area:** Tools & connectors (safety) / local & open models
- **What it is:** Attacks the "adding a new safety rule to an agent requires fine-tuning a classifier" problem. **kNNGuard uses the activation space of an off-the-shelf LLM** — no fine-tuning — combined with a **small bank of ~50 safe and unsafe prompts** to define the safety rule. At inference time, it extracts multi-layer activations for the candidate prompt and runs **multi-layer k-nearest-neighbors classification** against the bank. Combines activation-space and embedding-space scores across layers. Empirical: **competitive or superior F1 vs fine-tuned SOTA guardrails**; **2.7× faster than the best comparable guardrail; 10× faster than a fine-tuned safety classifier**; **domain adaptation in <10 seconds** (author the 50 prompts, kNN is ready) — "several orders of magnitude faster than established guardrails." Evaluated across **six domains covering topical and security-related prompts**.
- **Why it matters for Justin's agents:** The **<10-second domain adaptation is the operational headline**. Every MCP tool Justin builds needs *some* safety layer — is this file access allowed, is this network host allowed, is this shell command benign. Today, adding a new rule to an fine-tuned classifier is a training run; with kNNGuard it's a 50-prompt authoring exercise. **Two concrete moves: (a)** wrap kNNGuard as an MCP tool that takes {LLM handle, 50 examples, target activation-layer set} and returns a live guardrail — Claude Code can then invoke it during any autonomous loop to gate a proposed action. **(b)** the **training-free-wrapper family is now three strong instances** — ReContext (context utilization), BlockSearch (attention dilution), kNNGuard (safety). The pattern is dense enough to write up: the training-free wrapper is the right abstraction for adding *any* behavior to a frozen model, not just safety. **Cross-ref:** composes with the six-instance gate-before-commit family — a Janus write-gate can use kNNGuard as its scoring function; a ProvenanceGuard argument check can use kNNGuard to score whether the argument content is dangerous; a ContextNest audit trace can invoke kNNGuard on the document. The gate says *when* to check, kNNGuard says *how* to check the specific "is this safe?" question. **Cross-ref:** the 50-prompt bank size means the setup cost is dominated by prompt-authoring quality, not compute — flag as an open question how sensitive the F1 is to bank-quality on adversarial-crafted rules (e.g., "no data exfiltration" is harder to specify with 50 examples than "no profanity").
- **Action signal:** `try-now` + `local-fit` (training-free wrapper on any local LLM; 50-prompt bank + kNN is a one-day prototype; <10s domain adaptation means iteration is nearly free)

### 6. Paper-Replication — Coding Agents Verify Scientific ML Claims via Workspace-Evidence Validation (158/158 Claims Matched Across 4 Papers × 12 Runs)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.02134
- **Authors / org:** Atharva Hans, Ilias Bilionis (Purdue)
- **Focus area:** Coding agents / evaluation
- **What it is:** Introduces **Paper-replication**, a structured coding-agent workflow that transforms a scientific ML paper's claims into **testable targets with documented evidence**. The agent runs the paper's method, records outputs against the claimed numbers, and produces a workspace where each claim is either **matched to evidence** or **flagged as unmet**. Crucially, **completion is validated by workspace evidence and predicate checks, not by the agent's final response** — the agent can't just claim success; the workspace has to contain the evidence. **Empirical:** across **four scientific ML papers with twelve independent runs each**: **all 12 workspaces cleared the completion validation gate; all 158 recorded claims matched with corresponding report coverage**. Runs varied on target decomposition, numerical accuracy, execution duration, and evidence acceptance thresholds.
- **Why it matters for Justin's agents:** Two things stack. **(a) The "completion is a workspace-state predicate, not a model self-report" primitive is the same evidence-grounded verifier pattern Vera Framework uses for safety.** It's now emerging as the *right* pattern for autonomous long-horizon agent evaluation — regardless of domain, if you're evaluating an agent's work, the pass/fail should be a code predicate over environment state, not an LLM's answer. **(b) 158/158 claim coverage across 12 runs is a strong empirical result on a task class (paper replication) that is notoriously flaky.** For Justin's federal-data-engineer work where reproducibility is table stakes, the Paper-replication workflow is directly transferable: an autonomous agent that takes a set of documented data-transformation claims and produces a workspace where each transformation is either matched to test evidence or flagged as unmet is exactly the shape of "verify this ETL pipeline actually does what the spec says." **Cross-ref:** the workspace-state predicate is the same primitive at the heart of yesterday's [arxiv:2607.01793] Vera Framework's *deterministic verification predicates* — this is the third pattern in the "verification is a code check, not an LLM check" family (Vera safety, Paper-replication coding, and earlier Mnemosyne workflow-action constraint checks). Emerging as a named vault primitive. **Cross-ref:** the "12 independent runs, 158/158 matched" is a *reliability* claim on a hard task; watch for a followup that scales the paper count from 4 to a larger sample — the 12-run reliability at 4 papers is convincing, but the generalization surface is small.
- **Action signal:** `try-now` + `compare` (transferable pattern: any coding-agent workflow Justin builds should adopt workspace-state predicate as completion gate; the 158/158 headline is a target to measure against on his own domain)

### 7. Multi-Agent Framework Ecosystem — Longitudinal Study of 15 Open-Source Frameworks: Star Counts Mislead, LangChain = 82.5% of Cross-Ecosystem Contributors
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.02453
- **Authors / org:** Xi Zhang, Papi Menon, Vivian Chu, Koray Cosguner (Cisco / Indiana University)
- **Focus area:** Agent orchestration / tools & connectors (meta)
- **What it is:** Empirical longitudinal analysis of **15 major open-source AI agent frameworks** — AutoGPT, LangChain, Pydantic-AI, MetaGPT, LangFlow, Openai-agents-python, and others — from **late 2022 through early 2026**. Corpus: **~808k stars, ~74k PRs, ~86k commits, ~1M user profiles**. **Three headline findings**: **(1) Star counts reflect hype cycles and inorganic activity, not ecosystem health** — AutoGPT hit 111,967 stars in one month with only **9 contributors per 1,000 stars (vs LangChain's 41)**, a metric they name "contributor density." **(2) LangChain attracted 82.5% of cross-ecosystem contributors** — i.e., of contributors who touched more than one framework, 82.5% touched LangChain, positioning it as **shared infrastructure** rather than "just another framework." **(3) Contributor retention drops most within the first 30 days, stabilizes near 90 days** — the newcomer-attrition curve is bimodal, so the "did this framework survive?" question really means "did anyone stick past 30 days?"
- **Why it matters for Justin's agents:** This is meta-level but operationally decisive when Justin is deciding which agent framework to invest in as a dependency. Concrete calls: **(a)** the **contributor-density metric** is the right adoption signal for Justin's MCP-tool ecosystem picks — if a MCP-adjacent framework is racking up stars but its contributor density is <20/1000, it's a hype cycle and the underlying maintenance risk is high. **(b)** the **LangChain-as-shared-infrastructure finding at 82.5%** means that if Justin builds a framework-agnostic MCP tool, targeting the LangChain shape is the highest-leverage move even if he doesn't personally use LangChain — the cross-ecosystem contributor pool converges there. **(c)** the **30-day retention cliff** is the concrete signal to track — a framework that shows a healthy 30-day-retention plot is a real ecosystem; a framework showing a cliff at 30 days is a hype spike, whatever the star count. **Cross-ref:** the "contributor density" primitive is the *ecosystem-health analog* of PACE's "proxy for capability at <1% cost" — both are cheap signals that predict expensive-to-measure ground truth (model capability / framework longevity). Meta-level pattern: 2026 is the year the AI-agent space stops running on marketing metrics. **Cross-ref:** this contradicts the implicit assumption in every "which agent framework should I pick" blog post that stars are a proxy for adoption — the 9-vs-41 contributor-density delta between AutoGPT and LangChain is the concrete refutation, and the 30-day retention cliff generalizes across all 15 frameworks studied.
- **Action signal:** `track` + `compare` (not directly implementable but the three metrics — contributor density, cross-ecosystem contribution, 30-day retention — are the framework-selection criteria Justin should apply on every MCP-adjacent dependency; refutes the star-count-as-adoption assumption)

### 8. DecompRL — Modular Code Generation via RL Learns Hierarchical Decomposition, Cuts GPU Token Cost ~50× on Hard Problems
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.02390
- **Authors / org:** Juliette Decugis, Fabian Gloeckle, Francis Bach, Taco Cohen, Gabriel Synnaeve (Meta / École Normale Supérieure / Inria)
- **Focus area:** Coding agents / reasoning & inference-time compute
- **What it is:** Attacks the "agent hits a hard coding problem → burns more inference-time compute on sampling → still fails" ceiling. **DecompRL trains a model via RL with verifiable rewards to decompose a hard problem into smaller, independently solvable sub-functions.** Once decomposed into **k implementations across n modules**, the composed solution space is **k^n candidates** — much larger than sample-N-and-vote at the same GPU cost, because module-implementation combinations are enumerated on CPU rather than sampled on GPU. **Reported to reduce GPU token cost by ~50× on hard problems.** **Empirical**: on **LiveCodeBench and CodeContests** with **Qwen 2.5 7B** and **Code World Model 32B**, DecompRL outperforms standard and diversity-optimized RL baselines when token budgets exceed **10^5 per problem**, and **solves problems that conventional generation methods cannot reach**.
- **Why it matters for Justin's agents:** Two operational implications. **(a) The 50× GPU-cost reduction on hard problems is exactly the class Justin cares about** — a coding subtask where Claude Sonnet 5 (or a local 7B/32B model) hits a wall on the first attempt and needs to escalate. DecompRL says: don't sample more times, decompose into modules and enumerate combinations. That fits directly into Justin's stack as an "escalation policy" when a subtask fails: the planner decomposes, the executor implements each module, the recombiner enumerates on CPU. **(b) Qwen 2.5 7B verification** means the pattern is demonstrated at a size class Justin can run locally, and the **10^5 per-problem token budget** is well within the range Justin's autonomous loops operate at. **Cross-ref:** DecompRL is the **coding-agent parallel to yesterday's [arxiv:2607.01942] ATG (Atomic Task Graph)** — ATG produces an *explicit* task-DAG at the planner layer for parallel execution and localized repair; DecompRL produces an *implicit* modular decomposition at the code-generation layer for k^n combinatorial coverage. Both attack the "monolithic plan / monolithic code" ceiling from different levels of the stack. Composition question: does an ATG-planned + DecompRL-executed coding agent stack the wins from both? **Cross-ref:** the "shift computation from GPU to CPU" property is the same efficiency argument Justin uses when picking small local models over frontier ones — DecompRL is the generalization of that principle to inference-time computation shape, not just model size.
- **Action signal:** `try-now` + `local-fit` (7B/32B model demonstrations are M5-Max-runnable; 50× GPU-cost reduction is a directly measurable target on Justin's coding loops; composes with ATG for planner+executor stack)

No paper has yet demonstrated the composition; this is a concrete followup Justin's stack could run.

- **The "verification is a code predicate, not an LLM check" family is now a three-instance convergent pattern.** [arxiv:2606.30931] Mnemosyne (workflow-action constraint check) → [arxiv:2607.01793] Vera Framework (safety verification via deterministic predicates) → today's [arxiv:2607.02134] Paper-Replication (coding-agent completion via workspace evidence + predicate checks). The three papers cover **workflow-action, safety, and correctness** — three different verification surfaces, all landing on the same primitive: *the pass/fail is a code check over environment state, not a model self-report.* This is dense enough to name as a vault primitive. **Concrete followup:** the fourth surface would be *reasoning-step verification* — a code predicate over an intermediate reasoning state. [arxiv:2607.01223] Theoria (from July 3) is the informal-reasoning-verification candidate; if Theoria's mechanism were reformulated as a deterministic predicate over reasoning-state fragments, it would close the four-corner pattern.

- **The training-free wrapper family is now a three-instance dense pattern.** [arxiv:2607.02509] ReContext (long-context evidence utilization) + [arxiv:2607.01538] BlockSearch (attention-dilution softmax fix) + today's [arxiv:2607.02072] kNNGuard (safety via hidden activations + kNN). All three are training-free wrappers over frozen LLMs; all three demonstrate on small (4B-8B) models Justin can run locally; all three could plausibly compose (kNNGuard on the input side, BlockSearch during attention, ReContext at the evidence-replay step). **Open composition question:** does a small local model wrapped in {kNNGuard, BlockSearch, ReContext} approach the capability of a frontier model on the same task? Justin's M5 Max is the natural test rig — all three wrappers implementable in a single week.

- **Maven vs ReContext is the RL-vs-training-free debate for long-context reasoning, and both work with the same underlying evidence ontology (add / link / drop).** [arxiv:2607.02509] ReContext (yesterday) said long-context utilization can be lifted with a training-free recursive-replay wrapper; today's [arxiv:2607.02073] Maven says RL with action-level evidence rewards bakes the same behavior into weights. **The convergence signal is that both papers use the same evidence-graph ontology** — add-evidence, link-evidence, drop-distractor — but at different layers of the stack. Open question: for a fixed compute budget on a small local model (say Qwen 3-4B), does the training-free wrapper or the RL-trained backbone yield higher long-context QA quality? Untested. Flag as an experimental gap Justin's local rig could close.
