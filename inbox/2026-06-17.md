# AI Research Digest — Wednesday, June 17, 2026

## TL;DR
June 16's arXiv batch lands a strong second-day echo of yesterday's User-as-Code thesis: **PreAct ([arxiv:2606.17929]) is by the same single author (Bojie Li) and applies the same "compile reasoning to an executable substrate" move to computer-using agents** — successful task runs are compiled into small state-machine programs that replay 8.5–13× faster without per-step LLM calls. Two-day Bojie-Li pattern: typed-code as the user-memory tier, state-machine programs as the action tier. Plus the first **MCP-specific factuality verifier** (ProvenanceGuard) and a coding model that turns the looped-transformer line into a real number (LoopCoder-v2: 7B / 18T tokens, SWE-bench Verified 43.0 → 64.4 by adding parallel loops).

- **PreAct ([arxiv:2606.17929], Bojie Li, June 16) extends yesterday's User-as-Code compile-to-executable thesis to the action tier.** UaC compiles user memory into typed Python; PreAct compiles successful task trajectories into **screen-state-machine programs** that check conditions and execute transitions without invoking the LLM. **8.5–13× faster replay**; guardrails verify screen state per action and return control to the agent on divergence; **only programs that pass independent verification on clean re-runs are stored**, blocking faulty-program accumulation. Across mobile / desktop / web benchmarks the validation pass added **1.75–2.6 tasks per benchmark vs no-guardrail baselines**. The interesting null: **prompt wording, runtime safeguards, and retrieval method (LM vs embedding) had minimal effect** — the leverage is the compile-and-verify primitive, not the surrounding configuration.
- **ProvenanceGuard ([arxiv:2606.18037], June 16) is the first MCP-specific factuality verifier.** Decomposes agent answers into atomic claims, routes each claim to source-specific evidence via the MCP trace, and verifies both factuality and proper source attribution. On 281 medical-domain MCP traces / 2,325 LLM-assisted labels: **Block F1 0.802, source accuracy 0.858** (40-trace held-out); **Block F1 0.846 on multi-source**; **100% detection on 50 controlled cross-source-conflation probes**. The novel failure mode it catches — **"cross-source conflation"** (claim is supported by evidence but attributed to the wrong source) — is exactly the silent-failure regime MCP-based products will hit at scale and aggregator UIs cannot currently surface.
- **OPD-Evolver ([arxiv:2606.17628], June 16) is the strongest agent-self-improvement number this week.** Two-loop architecture: a **fast loop** of agent ↔ four-level memory hierarchy (read / use / write / maintain), and a **slow loop** of outcome-calibrated memory attribution + privileged hindsight distillation back into the deployable policy. Reports **+11.5% over ReasoningBank**, **+5.8% over Skill0-class training methods**, and the headline cross-scale claim: **OPD-Evolver-9B challenges Qwen3.5-397B-A17B and Step-3.5-Flash on multi-domain benchmarks**. The 9B-beats-397B-A17B framing is the part that, if it reproduces, matters most for Justin's local stack.
- **LoopCoder-v2 ([arxiv:2606.18023], June 16) turns looped transformers into a deployable SWE number.** **Parallel Loop Transformers (PLT)** with cross-loop position offsets + shared-KV gated sliding-window attention — makes loop count a tunable inference-time-compute knob without the latency/KV-cache blow-up of sequential looping. **7B base trained on 18T tokens**: **SWE-bench Verified 43.0 → 64.4**, **Multi-SWE 14.0 → 31.0**. Critical methodological finding: **two loops is optimal; more loops yield diminishing returns**. For Justin's coding-agent stack the headline is that **a properly trained 7B with 2-loop test-time compute clears 60% on SWE-bench Verified** — that's the new floor for local-fit coding agents.
- **Verbal RL Feedback Loop ([arxiv:2606.17591], June 16) names the retention-forgetting dilemma.** Three-layer architecture — **Rules** (distilled experience), **Evidence** (per-rule reliability logs), **Skills** (governance over which rules apply, conflict resolution, abstention) — connected by a **feedback-driven curation loop**. Tested on financial forecasting (non-stationary world). The actionable finding is **bivalent**: *the same accumulated experience either degrades performance below the zero-shot baseline or dramatically improves accuracy depending on whether the curation loop is present*. This sharpens the GitOfThoughts null result one more notch — **memory hurts when uncurated, not because the substrate is wrong**.
- **SkillMigrator ([arxiv:2606.17645], June 16) is the cleanest answer to web-skill-portability.** Stores each skill paired with a **structural sketch of the page snapshot at induction time**, then at deployment retrieves skills via **layout similarity (not URL / instruction similarity)** and grounds references to the live page. **8–10% reduction in average LM-action count on successful trajectories** on WebArena + Mind2Web. The reusable insight: **skill keys should be the layout topology, not the site identity** — directly applicable to any browser-use stack Justin builds.
- **SEAGym ([arxiv:2606.17546], June 16) introduces the harness-improvement evaluation framework everyone in the self-evolving cluster needs.** Measures harness updates across training / validation / held-out / replay diagnostics / cost tracking. Tests three methods (ACE, TF-GRPO, AHE) on Terminal-Bench 2.0 + HLE and surfaces two findings the cluster has been ignoring: **(a) frequent updates may fail to improve held-out performance** (i.e., the self-evolving curves are partly overfitting to the recent update batch), and **(b) model backend can affect harness reliability** (i.e., a harness that works for one base model may not transfer). This is the eval lens the Self-Harness / RHO / OpenSkill / Socratic-SWE / OPD-Evolver papers should all be re-run through.

### 1. PreAct — computer-using agents that compile repeated tasks to state-machine programs (Bojie Li, day-two of the compile-to-executable thesis)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.17929
- **Authors / org:** Bojie Li (single-author, same as yesterday's User as Code [arxiv:2606.16707])
- **Focus area:** Long-running / autonomous loops + computer-use agents
- **What it is:** Computer-using agents typically re-solve repeated tasks from scratch — even tasks the agent has demonstrably succeeded at many times. PreAct compiles successful runs into **small state-machine programs** where states **check screen conditions** and transitions **execute UI actions**, then on subsequent runs **replays those programs directly without per-step LLM calls**. Safety primitives: (a) **screen-state verification before every action** — if conditions diverge from the recorded program's state machine, control is returned to the agent; (b) **independent verification on clean re-runs before storage** — programs are not added to the library unless they pass an independent re-run validation, blocking the accumulation of faulty programs that would compound replay errors over time. **Reported numbers**: 8.5–13× faster replay; across mobile + desktop + web benchmarks, the validation primitive (vs no guardrails) added **+1.75–2.6 solved tasks per benchmark**. **Key null finding**: prompt wording, runtime safeguards beyond the verification primitive, and retrieval method (LM vs embedding-based) showed minimal effect — **the leverage is the compile-then-verify pipeline, not the surrounding configuration**.
- **Why it matters for Justin's agents:** This is the second Bojie-Li paper in two days applying the same architectural move — *compile from observation to executable substrate, execute deterministically, fall back to the LLM only when execution diverges from substrate*. UaC did it for the **user-memory tier** (typed Python objects + functions, append-only log → typed-code checkpoint). PreAct does it for the **action tier** (state-machine programs over screen states). For Justin's MCP-tool and computer-using-agent products, the read-through is concrete: **for every repeated workflow your agent runs (logging into the same SaaS, exporting the same report, filling the same form), the right primitive is to compile to a deterministic program after the second or third success and only fall back to the LLM on screen divergence**. The 8.5–13× speedup is the number that matters for cost, but the **−1.75–2.6 tasks without the verification primitive** is the more important warning — programs that get into the library without independent re-run validation will degrade the agent net-net. This couples neatly with PROJECTMEM ([arxiv:2606.12329])'s pre-action gate primitive — both reject known-bad actions deterministically, just at different layers.
- **Action signal:** `try-now` — the compile-trajectory → state-machine + screen-state-verification primitive is straightforward to layer over any existing computer-use agent (Anthropic Computer Use, OpenAI Operator-class, Claude Code with browser MCP). Also `compare` — directly extends yesterday's [arxiv:2606.16707] UaC into the action tier; the Bojie Li author cluster is now a coherent two-paper thesis on **compile-to-executable substrate as the core agent primitive**.

### 2. ProvenanceGuard — first MCP-specific factuality + cross-source-conflation verifier
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.18037
- **Authors / org:** Ander Alvarez, Santhiya Rajan, Samuel Mugel, Román Orús
- **Focus area:** Tools & connectors (MCP-specific)
- **What it is:** Most factuality verifiers assume a single retrieval source; the MCP regime breaks that — answers compose claims drawn from multiple tools, multiple servers, multiple knowledge bases. ProvenanceGuard analyzes the **MCP trace itself**, decomposes the agent's answer into **atomic claims**, routes each claim to **source-specific evidence** (the tool call + server that produced it), and verifies both **factuality** (does the evidence support the claim) and **proper attribution** (is the claim correctly tied to the source that supports it). Names a novel failure mode: **"cross-source conflation"** — the claim is supported by *some* evidence in the trace, but attributed to the wrong source. **Reported numbers**: dataset of **281 medical-domain MCP agent traces**, 2,325 LLM-assisted claim labels (266-trace subset), 361 held-out human labels; on the 40-trace held-out split — **Block F1 0.802, source accuracy 0.858 across 260 source-eligible claims**; multi-source benchmark Block F1 0.846; and on **50 controlled clinical conflation probes — 100% detection rate**.
- **Why it matters for Justin's agents:** Cross-source conflation is the single hardest silent-failure mode for any multi-MCP-server product. Without something like ProvenanceGuard, the agent can confidently state "Patient X has a sulfa allergy per their EHR" when the allergy actually came from a different patient's chart that happened to be in the trace (or from a Wikipedia auto-fill). The current MCP UX surfaces tool calls but does **not** verify that the citations in the answer correctly map to the tool calls — and at scale this is the regime where MCP products get sued. For Justin's federal-data-engineer work, where claims-to-source attribution **is** the deliverable, this is the most directly applicable paper of the week. The 100% detection on controlled conflation probes is the headline; the 0.858 source-accuracy is the realistic operational ceiling. Worth designing the next MCP-server product so that **claim-decomposition + per-claim source verification** can be plugged in as a downstream module — not bolted on after a customer complaint. Pairs with [arxiv:2606.13715] WorkBench Revisited (2.5% irreversible-harm ceiling) and yesterday's [arxiv:2606.16813] GIST-CMTF (wrong-goal execution 19.4% → 2.5%) as the three-layer safety stack: **GIST-CMTF prevents wrong-goal commits, ProvenanceGuard prevents wrong-source claims, WorkBench Revisited sets the residual-harm ceiling**.
- **Action signal:** `try-now` — the MCP-trace-decomposition primitive is directly buildable on top of any logging-enabled MCP runtime; 281-trace medical dataset is small enough to extend with Justin's own domain. Also `track` — first MCP-specific factuality framework, expect rapid follow-ups.

### 3. OPD-Evolver — two-loop agent self-evolution; 9B challenges Qwen3.5-397B-A17B; +11.5% over ReasoningBank
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.17628
- **Authors / org:** Guibin Zhang, Xun Xu, Yanwei Yue, Zikun Su, Wangchunshu Zhou, Xiaobin Hu, Shuicheng Yan
- **Focus area:** Agent memory + reasoning
- **What it is:** Reframes agent self-improvement as a **two-loop control problem**. **Fast loop**: agent ↔ four-level memory hierarchy (read / use / write / maintain) — immediate adaptive evolution during deployment. **Slow loop**: **outcome-calibrated memory attribution + privileged hindsight distillation** — successful strategies discovered in the fast loop are distilled back into the deployable policy itself (not just the memory bank). The slow loop is the operationally important piece — it's the **mechanism by which fast-loop wins become permanent weights**, instead of remaining as accumulating context. **Reported numbers**: outperforms **ReasoningBank by up to 11.5%** and **Skill0-class training-based methods by ~5.8%**; **OPD-Evolver-9B challenges Qwen3.5-397B-A17B and Step-3.5-Flash on multi-domain benchmarks**.
- **Why it matters for Justin's agents:** The two-loop fast/slow split is the architectural move that separates "agent with growing context" from "agent that gets better." Most self-improving agent frameworks Justin has worked with (SkillsVote, CODESKILL, Self-Harness) operate at one timescale — either context-time or training-time, not both. OPD-Evolver's claim is that **the four-level memory hierarchy in the fast loop is the workspace, and outcome-calibrated hindsight distillation is the consolidation step that promotes useful fast-loop discoveries into the slow tier**. For Justin's indie-dev stack the 9B-challenges-397B-A17B claim is the load-bearing number: **if it reproduces, the right architecture for a personal-agent product may be a 9B base + the OPD-Evolver fast/slow stack, not a frontier-API call**. The +11.5% over ReasoningBank also closes one of the open questions from the memory cluster — that benchmark-style "memory bank + retrieval" was structurally one consolidation layer short. Slightly tempered: "challenges" is a careful framing; not the same as "beats on every benchmark." The hindsight-distillation step is also non-trivial to operate — there's an offline training-pass for every batch of slow-loop updates, which has its own ML-ops surface area.
- **Action signal:** `compare` — direct numerical successor to ReasoningBank-class memory architectures; sits adjacent to [arxiv:2606.16707] User as Code as **two different routes through the memory→reasoning bottleneck** (UaC: change the substrate; OPD-Evolver: change the loop structure). Also `local-fit` — 9B base is comfortably M5-Max-runnable; the slow-loop training step is the ops question, not the inference question.

### 4. LoopCoder-v2 — parallel-loop transformers turn looped reasoning into deployable SWE numbers (7B / 18T, SWE-bench Verified 43.0 → 64.4)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.18023
- **Authors / org:** Jian Yang, Shawn Guo, Wei Zhang, Tianyu Zheng, Yaxin Du, Haau-Sing Li, Jiajun Wu, Yue Song, Yan Xing, Qingsong Cai, Zelong Huang, Chuan Hao, Ran Tao, Xianglong Liu, Wayne Xin Zhao, Mingjie Tang, Weifeng Lv, Ming Zhou, Bryan Dai
- **Focus area:** Coding agents + reasoning / inference-time compute
- **What it is:** Sequential looped transformers scale latent computation by re-applying shared blocks, but each loop adds latency + KV-cache pressure linearly. **Parallel Loop Transformers (PLT)** address both: **cross-loop position offsets (CLP)** + **shared-KV gated sliding-window attention** make loop count a practical inference-time-compute knob without the runtime tax. **Reported numbers**: 7B base, **18T training tokens**; SWE-bench Verified **43.0 → 64.4** with PLT vs single-pass; Multi-SWE **14.0 → 31.0**. Methodological finding worth pinning: **two loops is optimal; more loops yield diminishing returns**.
- **Why it matters for Justin's agents:** Two consequences. First, the **64.4% SWE-bench Verified at 7B** number is the new local-fit ceiling for coding agents — Justin's M5-Max stack can run a 7B PLT model with two parallel loops at quality that was a 70B+ regime three months ago. Second, the **two-loops-is-optimal** finding is the practical guide: there's no value in continuing to climb the loop-count knob beyond 2 for the SWE regime, which sets a clean inference-time-compute budget per task. The 18T training tokens is unrealistic to reproduce, but the inference-side architecture (PLT + CLP + shared-KV gated SWA) is implementable as a fine-tune on top of an existing 7B base. Pairs with [arxiv:2606.17930] *How Inference Compute Shapes Frontier Evaluation* (today): if benchmark scores are protocol-dependent and **larger token budgets substantially improve performance**, PLT is one concrete way to spend that budget without ballooning user-facing latency.
- **Action signal:** `try-now` for the PLT architecture as an inference-time-compute knob on Justin's coding-agent stack; `local-fit` — 7B base + 2 loops + KV-shared SWA is well within M5 Max headroom. Also `compare` against [arxiv:2606.18206] Fixed-Point Reasoners (today's other looped-transformer paper, stability angle).

### 5. Verbal RL Feedback Loop — names the retention-forgetting dilemma in long-running agent memory
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.17591
- **Authors / org:** Yanwei Cui, Xing Zhang, Yulong Zhang, Li Shao, Xiaofeng Shi, Guanghui Wang, Peiyang He
- **Focus area:** Agent memory + context engineering
- **What it is:** "Training-free verbal reinforcement learning" — LLM agents learn from objective world feedback (task outcomes, market returns, demand forecasts) by **extracting verbal rules from experience and injecting them as context**, no parameter updates. The novel framing is the **retention-forgetting dilemma in non-stationary environments**: keeping outdated rules causes negative transfer; discarding them risks catastrophic forgetting when conditions return. The proposed architecture is three layers — **Rules** (distilled experience), **Evidence** (per-rule reliability logs across episodes), **Skills** (governance: which rules apply when, conflict resolution, abstention) — connected by a **feedback-driven curation loop** that manages knowledge lifecycle dynamically. **Reported finding**: tested on financial forecasting (naturally non-stationary), with the dramatic result that **the same accumulated experience either degrades performance below the zero-shot baseline or dramatically improves accuracy and risk-adjusted returns, depending on whether the curation loop is present**.
- **Why it matters for Justin's agents:** This is the most actionable framing of the memory-degradation problem in the recent cluster. The retention-forgetting dilemma is what every long-running agent eventually hits — Justin's companion-app products will absolutely encounter regimes where last month's correct rule is this month's wrong rule (user preferences shift, contexts return seasonally, deprecation cycles flip). The three-layer Rules / Evidence / Skills decomposition is **the right granularity to track per-rule reliability** without falling into either of the two failure modes. The headline empirical finding — **same experience can degrade or improve depending on curation** — is the strongest evidence yet that the GitOfThoughts null result ([arxiv:2606.14470]) is curation-bound, not substrate-bound: memory can structurally hurt if you don't have an evidence-per-rule layer with a governance step. For Justin's stack, the engineering implication is **don't ship a memory layer without a per-rule reliability log and an explicit governance step** — accumulation alone is a regression risk, not a feature.
- **Action signal:** `compare` — direct counter to "naive accumulation hurts" findings from [arxiv:2606.14470] GitOfThoughts and [arxiv:2606.14571] StreamMemBench; says **curation is the missing variable**. Also `try-now` — the three-layer rules/evidence/skills schema is implementable over any persistent memory layer Justin already runs.

### 6. SkillMigrator — layout-similarity-based skill transfer for web agents, 8–10% action reduction across sites
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.17645
- **Authors / org:** Shiqi He, Yue Cui, Feijie Wu, Xinyu Ma, Jiaheng Lu, Yaliang Li, Bolin Ding, Mosharaf Chowdhury
- **Focus area:** Tools & connectors / agent skills
- **What it is:** Prior skill libraries for web agents (SkillOS, SkillsVote, PREPING) keyed skills on **instruction similarity** or **site metadata** — both of which collapse the moment the agent encounters a new site with similar function but different identity. SkillMigrator stores each skill paired with a **Transferable Interaction Pattern (TIP)** — a **structural sketch of the page snapshot at the time the skill was induced** — and at deployment retrieves skills via **layout similarity** before grounding references to the live page. **Reported numbers**: **8–10% reduction in average LM-action count on successful trajectories** on WebArena + Mind2Web. The implicit win is on token consumption per task — fewer LM calls per action, fewer actions per task.
- **Why it matters for Justin's agents:** This is the cleanest answer yet to the question "why don't my browser-use agent's learned skills transfer to similar sites?" — the answer is that the retrieval key has been wrong. The shift from instruction-similarity to **layout-topology similarity** is the structural fix. For Justin's MCP-tool products that wrap browser-use workflows (the federal-data-engineer side especially: similar form layouts across different agency portals), the 8–10% LM-action reduction transfers directly. The deeper read is that **layout structure is the right abstraction at which skill transfer becomes practical** — a finding that should bias future skill-library designs across the cluster (CODESKILL, SkillOpt, Ratchet, SkillsVote) toward layout-or-AST-based retrieval keys rather than instruction-text retrieval keys. Pairs naturally with PreAct (item 1) — PreAct compiles trajectory → state machine over screen states; SkillMigrator stores trajectory → layout sketch + skill. The two together are a coherent layered store: **PreAct for "this exact workflow, replay deterministically"; SkillMigrator for "this kind of layout, adapt the steps."**
- **Action signal:** `try-now` — layout-sketch retrieval key is implementable on any existing browser-use stack with DOM inspection. Also `compare` — sharpens the SkillOS / SkillsVote / SkillOpt / CODESKILL cluster along the retrieval-key axis.

### 7. SEAGym — multi-view harness evaluation; surfaces that "frequent updates may fail to improve held-out performance"
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.17546
- **Authors / org:** Congjie Zheng, Chuanyi Xue, Bin Liang, Jun Yang, Changshui Zhang
- **Focus area:** Evaluation
- **What it is:** Evaluation framework specifically for **harness improvements** — the structured execution layer around a base model (prompts, memory, tools, middleware, runtime state, model-tool interaction loop). Measures updates across **training performance, validation results, held-out test metrics, replay diagnostics, operational costs** — explicitly designed to separate genuine improvements from overfitting / cost regressions / capability degradations. Comparison of three self-evolving methods (**ACE, TF-GRPO, AHE**) on Terminal-Bench 2.0 + HLE. Two findings worth pinning: **(a) frequent updates may fail to improve held-out performance** (i.e., much of what's being reported as self-evolving gain is partly overfitting to the recent update batch); **(b) model backend can affect harness reliability** (a harness that works on one base model may not transfer to another).
- **Why it matters for Justin's agents:** The cluster of self-evolving agent papers ([arxiv:2606.09498] Self-Harness, [arxiv:2606.05922] RHO, [arxiv:2606.07412] Socratic-SWE, today's [arxiv:2606.17628] OPD-Evolver) has been reporting striking gains without a shared evaluation lens that controls for the **overfit-to-recent-batch** failure mode. SEAGym is what should be re-run over those numbers. For Justin's own infra — anything resembling a continual-improvement loop on top of an MCP-tool stack — the headline-finding "frequent updates may fail to improve held-out" is a real warning: **the self-evolution curves you're looking at may not generalize**. The model-backend finding is similarly load-bearing: **a harness tuned against Claude Fable 5 may not produce gains against Opus 4.8 or against a local Qwen3.6**. For an indie dev product the cost-tracking view in SEAGym is also exactly the missing axis — most self-improvement papers don't report cost-deltas, just capability deltas. The right ops protocol is to run this kind of multi-view eval on every harness update, not just every base-model swap.
- **Action signal:** `track` for the framework; `compare` — direct methodological counter to recent self-evolution claims; the cluster needs a SEAGym-style re-evaluation before any single result becomes operationally trusted.

- **Memory fit:** ~4–5 GB at Q4, ~14 GB at FP16. PLT adds **shared KV** across loops — the KV-cache cost does **not** scale linearly with loop count, which is the architectural reason it's M5-Max-friendly at 2 loops. M5 Max + 64 GB has **enormous headroom** (~50 GB free even at FP16).

Practically, watch for a reference implementation; in the meantime the PLT mechanism can be approximated with a 2-pass dual-decoder setup on existing inference stacks for evaluation.
- **Speed estimate:** Not benchmarked for M5 Max specifically; for a 7B Q4 the single-pass decode is ~80–100 tok/s; 2-loop PLT should be **roughly 2× slower than single-pass at decode time** but with the per-task quality lift offsetting wall-clock.

- **Model:** OPD-Evolver-9B (memory-hierarchy + hindsight-distillation framework)
- **Memory fit:** ~5–6 GB at Q4, ~18 GB at FP16. M5 Max + 64 GB has plenty of room for either.
- **Realistic tasks:** Multi-domain agent tasks where the "challenges Qwen3.5-397B-A17B" claim holds — likely **structured reasoning, planning, and tool-use** rather than pure long-context retrieval. Cross-domain transfer specifically is the strength.
- **How to run:** Weights / training code not yet enumerated — the slow-loop hindsight-distillation step is ML-ops-heavy (requires offline training pass per update batch), so the deployable artifact will likely be the **policy after slow-loop consolidation** rather than the live fast/slow stack. Worth watching for the model release.
- **Speed estimate:** 9B Q4 on M5 Max is **70–90 tok/s decode** territory based on similar-scale MLX benchmarks. The four-level memory hierarchy adds ~1 retrieval op per turn but is CPU-side, not decode-side.

Also of note: **PreAct's compile-trajectory-to-state-machine primitive (item 1) is a CPU-side operation** — the state-machine programs themselves run without LLM calls. For Justin's M5 Max stack, this is the regime where wall-clock task time can drop from "tens of seconds" to "milliseconds" for the high-frequency repeated workflows, dramatically reducing the practical cost ceiling of running a personal-agent product on local inference.

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:

- **Bojie Li two-paper pattern: compile-to-executable-substrate** — `compare`, confirming. PreAct (today, [arxiv:2606.17929]) and User as Code (yesterday, [arxiv:2606.16707]) are by the same single author and both apply the same architectural move at different tiers — UaC at the **memory tier** (typed Python objects + functions as user memory, append-only log → typed-code checkpoint), PreAct at the **action tier** (state-machine programs over screen states as compiled workflows). Combined claim: the right primitive for personal-agent products is **compile to deterministic executable substrate; fall back to the LLM only on divergence**. **Open empirical question**: do the two compose cleanly? PreAct stores per-task state machines; UaC stores typed-code over user state. The natural integration is **UaC reads supply preconditions to PreAct programs** (e.g., "user has international trips" → triggers a PreAct program that opens the airline website state machine), but neither paper tests that composition. If it works, it's the cleanest blueprint for a fully deterministic-substrate personal-agent stack — a thesis worth testing on Justin's companion-app side.

- **Verbal RL Feedback Loop vs GitOfThoughts / StreamMemBench** — `compare`, partial reconciliation. GitOfThoughts ([arxiv:2606.14470]) and StreamMemBench ([arxiv:2606.14571]) both reported that **memory does not reliably help** under naive accumulation. Verbal RL ([arxiv:2606.17591]) sharpens that finding: **the same accumulated experience either degrades performance below the zero-shot baseline or dramatically improves it, depending on whether the curation loop is present**. The reconciliation is that the memory-cluster null result is a **curation null**, not a **substrate null** — and yesterday's User as Code ([arxiv:2606.16707]) added a substrate-side counter-claim (typed-code substrate makes aggregate reasoning 99% vs 6–43%). The full picture is now: **substrate matters (UaC) and curation matters (Verbal RL) — the GitOfThoughts naive-accumulation null is a corner of a 2D space, not the whole space**. **Open empirical question**: do Verbal RL's three-layer (Rules / Evidence / Skills) curation gains compose with a UaC-style typed-code substrate, or are they substrate-specific? The papers don't address this.

- **SEAGym vs the self-evolving agent cluster** — `compare`, methodological counter. SEAGym's finding that **frequent updates may fail to improve held-out performance** is a direct warning to OPD-Evolver (today, [arxiv:2606.17628]), Self-Harness ([arxiv:2606.09498]), RHO ([arxiv:2606.05922]), Socratic-SWE ([arxiv:2606.07412]), and the broader skill-curation cluster (SkillsVote / CODESKILL / Ratchet). None of those papers reports replay diagnostics or cross-backend transfer in the SEAGym sense. **Open empirical question**: how many of the self-evolving-agent improvement claims survive a SEAGym-style multi-view re-evaluation, controlling for overfit-to-recent-batch + cross-backend transfer?
