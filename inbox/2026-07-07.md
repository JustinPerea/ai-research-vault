### 1. LLM-as-a-Verifier — Verification as a First-Class Scaling Axis: Terminal-Bench V2 86.5% / SWE-Bench Verified 78.2%
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.05391
- **Authors / org:** Jacky Kwok, Shulu Li, Pranav Atreya, Yuejiang Liu, Yixing Jiang, Chelsea Finn, Marco Pavone, Ion Stoica, Azalia Mirhoseini
- **Focus area:** Evaluation / reasoning & inference-time compute
- **What it is:** Attacks the "our LLM judges give noisy discrete scores and don't scale like generators do" problem head-on. **Positions verification — the ability to determine correctness — as a new scaling dimension** alongside training and inference. Core mechanism: instead of eliciting a discrete grade token, **computes the expectation over the distribution of scoring token logits to produce continuous scores** — turning the judge into a smooth signal. Then scales verification across three axes: **(a) granularity** (step-level vs trajectory-level), **(b) repeated evaluation** (sample judges like you sample generators), **(c) criteria decomposition** (break rubric into orthogonal axes). Reports state-of-the-art on **Terminal-Bench V2: 86.5%**, **SWE-Bench Verified: 78.2%**, **RoboRewardBench: 87.4%**, **MedAgentBench: 73.3%** — plus RL improvements on robotics + math using the verifier as the reward signal. Ships as a "general-purpose verification framework" — the framing matters as much as the numbers.
- **Why it matters for Justin's agents:** Justin has been building verifier stacks piecemeal — outcome-only judges, sample-and-vote rubrics, LLM-as-judge with schemas. LLM-as-a-Verifier collapses these into one framework with three named scaling knobs. **Concrete moves: (a)** the **logit-expectation continuous score** is a small change (extract logits over grade tokens, compute expectation, cache) but eliminates most of the grader-noise problem that pushed Justin toward N-of-M voting; retrofit into any existing LLM-judge harness in an afternoon. **(b)** the **three scaling axes** (granularity + repeated eval + criteria decomposition) are the diagnostic vocabulary Justin has been missing when a judge underperforms — instead of "the judge is bad," you can say *which* axis is under-scaled. **(c)** **SWE-Bench Verified 78.2%** as the SOTA verification number resets the "how good is my code-review verifier" reference — anything below ~75% pass on SWE-Bench Verified means the verifier stack is under-scaled on one of the three axes. **(d)** **MedAgentBench 73.3%** ties directly to yesterday's [arxiv:2607.01470] World Feedback for Clinical Agents (18.2% pure RL vs 34.1% rule-based SFT) — the paper diagnoses *training-side* ceilings while this paper delivers *verification-side* SOTA on the same benchmark; together they define both ends of the clinical-agent stack. **Cross-ref:** the **three scaling axes** parallel yesterday's SkillCoach [arxiv:2607.01874] four-axis process-quality rubric — both papers explicitly resist "one number for judge quality" and decompose it. **Cross-ref:** **Pavone appears as coauthor here and on yesterday's [arxiv:2607.01520] KV Cache Compression minimax risk paper** — same author is contributing simultaneously to context-side and verification-side scaling frameworks; watch for a synthesis.
- **Action signal:** `try-now` + `compare` (logit-expectation continuous scoring is a same-day retrofit; three-axis scaling framework is the verifier-side vocabulary Justin's eval stack has been missing; direct SOTA numbers reset his internal reference)

### 2. SelfMem — Self-Optimizing Memory: Agents Learn Their Own Memory Strategy (41–49% BEAM Gain, 100K–1M Context)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.03726
- **Authors / org:** Shu Yang, Junchao Wu, Derek F. Wong, Di Wang
- **Focus area:** Agent memory
- **What it is:** Attacks the "we hardcoded a memory system and it doesn't fit our workload" problem with a paradigm shift. Rather than shipping a fixed memory mechanism (mem0-class semantic store; LangMem-class message summarization; entity graph; scratchpad), **provides the agent with memory tools + feedback signals and lets it explore, evaluate, and refine its own memory strategy** — the memory *policy* becomes learnable rather than baked in. Reports **41–49% improvements on BEAM benchmark vs established baselines across conversation lengths from 100K to 1M tokens**, with **effectiveness maintained across question types** and gains that grow with continuous model-guided refinement. The paper's meta-thesis: fixed memory mechanisms are the wrong abstraction — what should be optimized is the *policy over memory operations*.
- **Why it matters for Justin's agents:** This directly contradicts the design assumption behind every mem0/LangMem/Zep-class memory framework Justin has evaluated for his companion apps. Those frameworks ship an opinionated memory strategy (semantic recall + vector search + entity extraction, or whatever); SelfMem says: **the memory strategy is workload-dependent and should be learned, not chosen**. **Concrete moves: (a)** for Justin's companion-app memory stack, instead of picking one static memory framework, **wrap N memory tools (semantic, episodic, summary, scratchpad-file) as agent-callable tools + give the agent a scoring signal on recall quality**. The agent will learn a memory strategy specialized to the actual conversation shape. **(b)** the **41–49% BEAM delta at 100K–1M-token context** means SelfMem's payoff is largest exactly where Justin's autonomous loops live — long-running Claude Code sessions, multi-hour research runs, week-long companion conversations. **(c)** **BEAM as a benchmark** is worth adding to Justin's eval harness — it stresses memory across long contexts and diverse question types, which matches Justin's actual workload better than the standard needle-in-haystack. **Cross-ref:** this is the third convergent signal on "learnable strategy over static mechanism" in the past week: [arxiv:2607.02073] Maven evidence-state rewards (learn what evidence to write), [arxiv:2607.01874] SkillCoach self-evolving rubrics (learn what to score), now SelfMem (learn how to remember). Emerging pattern: **the agent should learn its own operational primitives, not inherit them from the framework author**. Name for the vault: **learn-your-primitive** pattern. **Cross-ref:** the **100K → 1M token range** overlaps with today's HiLS-Attention 64× extrapolation (item 3) — HiLS-Attention extends the *architectural* long-context capacity while SelfMem extends the *memory-strategy* capacity. Composable stack: HiLS-Attention for the underlying model + SelfMem for the memory policy above it.
- **Action signal:** `try-now` + `compare` (directly contradicts static memory-framework assumption; the "wrap N memory tools + score" implementation is 1–2 days; 41–49% delta at Justin's actual context lengths is the operational headline)

### 3. HiLS-Attention — Hierarchical Sparse Attention: 64× Training-Context Extrapolation at 90% Retrieval Accuracy via Lightweight Continued Pretraining
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.02980
- **Authors / org:** Xiang Hu, Xinyu Wei, Hao Gu, Minshen Zhang, Tian Liang, Huayang Li, Lei Zhu, Yan Wang, Sirui Han, Yushi Bai, Kewei Tu, Haitao Mi, Leo Liang
- **Focus area:** Context engineering / local & open models
- **What it is:** Attacks the "sparse attention loses accuracy vs full attention, so nobody deploys it" problem with a hierarchical design. **HiLS (Hierarchical Landmark Sparse) Attention** factorizes attention hierarchically and **learns chunk selection end-to-end through language modeling loss** — chunk selection is not a heuristic but a trainable subproblem inside the LM objective. Reports **>64× training-context extrapolation with 90% retrieval accuracy** — a model trained at 32K generalizes to >2M-token context at 90% retrieval; **matches or beats full attention on in-domain lengths**; **general long-context tasks improve while efficiency is preserved**. Critically: the method operates via **lightweight continued pretraining of existing models** — you don't rewrite the architecture, you patch it — which means any open-weights model can be extended.
- **Why it matters for Justin's agents:** Long-context extension for open-weights local models has been in a "pick your poison" state — either quality regressions (naive extension), a full retrain (not feasible), or expensive inference (full attention on 128K+). HiLS-Attention is the "patch existing models cheaply" recipe with a hard number attached. **Concrete moves: (a)** for Justin's Qwen3 / Llama3 M5 Max stack, HiLS-Attention is a candidate patch to extend context to 2M+ tokens without retraining — the lightweight continued pretraining fits inside a few days of M5 Max compute for a 7B–8B model. **(b)** the **90% retrieval accuracy at 64× extrapolation** is the number to compare against StreamingLLM / LongNet / RoPE-scaling / YaRN — HiLS is *end-to-end learned* rather than heuristic, so the retrieval number should be more robust to task shift. **(c)** the **hierarchical factorization** matches Justin's actual autonomous-loop workload: recent context (dense attention) + older reasoning trace (sparse chunk-level) — the same pattern as ContextNest [arxiv:2607.02116] and Kara [arxiv:2607.01237]. **Cross-ref:** **third convergent signal in the past week** on hierarchical / sparse / compressed attention as *the* solution to long-context inference: [arxiv:2607.01520] KV Cache Risk minimax framework (theory), [arxiv:2607.01237] Kara Token2Chunk variable-sized retention (production), now HiLS end-to-end learned chunk selection (training-time). The convergence is: **static long-context extensions are over; the frontier is learned or theoretically-grounded compression**. **Cross-ref:** pairs directly with SelfMem (item 2) — HiLS-Attention extends the architectural long-context capacity while SelfMem extends the memory-strategy layer above it.
- **Action signal:** `try-now` + `local-fit` (existing-model patch via lightweight continued pretraining; 64× extrapolation at 90% retrieval is a hard number to beat; composes with Kara + SelfMem as a three-layer long-context stack for local Qwen/Llama)

### 4. Natural Language Tools Replication — 14.9pp Accuracy Gain over Structured Function-Calling Across 14 Models × 8,560 Trials
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.03953
- **Authors / org:** Alexander Somma, Isabelle Plante, Fred Premji
- **Focus area:** Tools & connectors
- **What it is:** Attacks the "structured JSON-schema function-calling is obviously the right abstraction for tool use" assumption directly, with a large-N replication study. **14 models × 8,560 trials** comparing Natural Language Tools (NLT — describe tools in plain prose to the model, let the model reason in plain prose about which to call and with what arguments) vs standard structured function-calling. Headline: **62.3% NLT vs 47.4% structured = 14.9pp accuracy gain overall**. Additional numbers: **93% reduction in critical errors (51 vs 755)**; **+24.0pp to +43.1pp for models without native tool calling, reasoning models, and smaller models**; **25.2% token reduction**. The pattern: NLT gets its largest gains exactly where structured calling was already brittle — reasoning models, small models, models without a native tool-calling stack.
- **Why it matters for Justin's agents:** Justin's MCP-tool authoring workflow has been built on the JSON-schema function-calling contract since 2023 — MCP itself standardizes structured tool descriptions. This paper is a `compare` against that entire design lineage: **for models without native tool calling (which includes almost every local model Justin runs on M5 Max) and reasoning models (which is where Justin's stack is heading), NLT is 24–43 percentage points better**. **Concrete moves: (a)** for any local-model MCP integration Justin runs, ship a **prose-tool wrapper** alongside the JSON-schema tool — describe the tool in a paragraph, present it in-context, and parse the model's plain-text call. The 24–43pp gain is likely on-trend for local Qwen/Llama executors. **(b)** the **25.2% token reduction** is a second-order but real cost win — NLT avoids the JSON boilerplate overhead. **(c)** the **93% critical-error reduction** matters *more* than the accuracy delta for autonomous-loop use: a Claude Code session that malformats a tool call and burns the loop iteration is a failure mode NLT largely eliminates. **(d)** for MCP tool authoring going forward, **write the tool spec in prose first, then generate JSON schema from the prose**, not the reverse — this respects the actual failure mode. **Cross-ref:** contradicts the standard MCP tool-authoring guidance (schema-first) — this is the second `compare` signal against a foundational MCP assumption in the past week (yesterday's [arxiv:2606.31227] AI-Infra-Guard exposed the *security* gap in MCP; today's NLT paper exposes the *accuracy* gap in the structured tool-call contract). Emerging pattern: **MCP-as-shipped has real design gaps; watch for MCP v2-shaped proposals.** **Cross-ref:** the **reasoning-model gap** connects to the RLVR reward-granularity paper (item 8 below) — both papers converge on: **process-level and prose-level supervision beat outcome-level and schema-level supervision for capability-limited models**.
- **Action signal:** `try-now` + `compare` (14.9pp is a large delta; 93% critical-error reduction is even larger; prose-tool wrapper is a same-day change; the 24–43pp reasoning-model gain is the specific number for Justin's local stack)

### 5. VBQ Variable Bit-width Quantization — 69% of Weight Groups Want 1-Bit, 4.7× Apple Silicon Speedup at 9B, 3.7× Storage Compression
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.02893
- **Authors / org:** Hamish Ogilvy
- **Focus area:** Local & open models for Apple Silicon
- **What it is:** Attacks the "we quantize all layers to the same bit-width and hope" heuristic with a per-group learned-precision method. **VBQ**: each **contiguous group of 64 weights learns its own bit-width from {1, 2, 4, 8} via Gumbel-Softmax relaxation** at training time. The discovered allocation is highly heterogeneous: **69% of groups converge to 1-bit**; **LM head averages 1.09 bits** (near the extreme low end). Concrete deployment numbers: **131M model at 1.82 mean bits hits perplexity 4.2 on TinyStories at 3.8× less storage than 55M FP16**; **1.46B VBQ model matches 593M FP16 baseline at 3.7× less storage while carrying 2.5× more parameters**; **quality-per-byte efficiency = 3.9–8.4× vs FP16**. **Apple-silicon inference: 1.0B model = 1.9× faster; 9B model = 4.7× faster** (memory-bandwidth-bound decode, which is Justin's regime). The paper notes: **scaling the training-time search beyond 1.5B parameters remains open** — so 7B–9B VBQ models are being extrapolated rather than natively trained.
- **Why it matters for Justin's agents:** This is *the* local-fit number of the day for the M5 Max + 64 GB stack. Justin's decode-side bottleneck on M5 Max Q4 models is memory bandwidth (~600 GB/s), so **4.7× decode speedup on a 9B model translates directly to interactive-latency reasoning** — not "eventually finishes" but "response streams as fast as GPT-4o." **Concrete moves: (a)** if VBQ weights are released for any Qwen or Llama in the 7B–9B range, immediately benchmark on M5 Max Q4 vs VBQ at the same task set; the delta is expected to hold. **(b)** the **1.09-bit LM head** finding is a general insight (LM heads don't need FP precision) that applies even without VBQ — Justin can experiment with binarizing LM heads in existing GGUF/MLX conversions as a same-day exercise. **(c)** the **69% 1-bit / 31% higher-precision** allocation is the "quantization pattern" that a mixed-precision GGUF exporter should target — the current quant strategies (Q4_K_M, Q5_K_M) don't allocate this way. **(d)** the **"scaling beyond 1.5B is open"** caveat is the honesty in the paper — treat >1.5B VBQ numbers as extrapolated until confirmed. **Cross-ref:** the **memory-bandwidth-bound decode** framing is the M5 Max regime specifically; this paper is the first quantization-side release this cycle to directly benchmark on Apple silicon. Complements the *serving-side* KV cache work ([arxiv:2607.01237] Kara, today's HiLS-Attention) — VBQ compresses *weights*, the KV papers compress *cache*. Together they define both memory line-items on the M5 Max. **Cross-ref:** the **learned-per-group precision** pattern is another convergent instance of the **learn-your-primitive** meta-pattern named in item 2 (SelfMem) — instead of picking a bit-width heuristic (Q4_K_M), the model learns its own allocation.
- **Action signal:** `try-now` + `local-fit` (highest-signal local-model number of the day; 4.7× decode speedup on 9B is the interactive-latency threshold on M5 Max; LM-head binarization is a same-day experiment even without VBQ weights)

- **What it is:** Attacks the "our GUI agent works on desktop but falls over on mobile because the training data was single-platform" problem. Same primitive, different domain: multi-agent deliberation needs private evidence, multi-platform GUI agents need platform tokens. Add to vault: **conditioning-preserves-specificity** as a general pattern. **Cross-ref:** MobileWorld 12.0% ties to the general observation that mobile GUI agents remain the weakest deployment surface — the 3.2× gap between desktop and mobile in this paper is the number to track as the field converges.

### 7. PivoARL — Pivotal-Aware Self-Feedback Retry: 11.5% Pass@2/3 Gain, 45% Minesweeper, 42% Fewer Interaction Turns
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.03702
- **Authors / org:** Weiyang Guo, Zesheng Shi, Longhui Zhang, Zeen Zhu, Min Zhang, Jing Li
- **Focus area:** Agent orchestration / long-running loops
- **What it is:** Attacks the "our agent RL wastes budget re-doing correct early steps whenever a late step fails" problem. **PivoARL**: identify the **pivotal state** where the trajectory went wrong, then perform a **local retry from that pivotal state** rather than restarting the whole trajectory. Evaluates on **4 agent tasks + 7 search-based QA benchmarks**. Reports **~11.5% average Pass@2/3 gain over MetaRL across all tasks**, **consistent Pass@1 gains on >80% of tasks**, **>45% improvement over GiGPO on Minesweeper**, and **~42% fewer interaction turns vs full-retry methods**. The paper's meta-thesis: full trajectory resets are the wrong abstraction for agent RL; the pivotal-state retry is a fundamental primitive.
- **Why it matters for Justin's agents:** This is *directly* transferable to Justin's autonomous-loop stack. Justin's Claude Code sessions and long-running agent runs frequently fail at step N and today the recovery move is either "restart the task" or "let the human intervene." PivoARL's **pivotal-state retry** matches the actual failure structure — most of the trajectory was correct; only the specific decision point needs to be re-tried. **Concrete moves: (a)** for any autonomous-loop workflow with checkpointable state, implement pivotal-state retry: on failure, walk backwards through the trajectory to identify the earliest decision that led to divergence, restore state to *that* point, retry only forward from there. The 42% interaction-turn reduction translates directly to token cost. **(b)** the **>80% Pass@1 improvement rate** is the harder number: it means PivoARL isn't just efficient, it's more likely to solve the task at all — because the retry preserves the correct early context rather than re-doing it wrong. **(c)** the **45% Minesweeper gain over GiGPO** signals PivoARL is strongest on structured problems with clear branching decisions — which matches Justin's data-engineering workloads. **Cross-ref:** this is the *trajectory-side* companion to yesterday's [arxiv:2607.01415] Rollout Infrastructure Tax — that paper measured 110× cold-start variation across substrates; PivoARL reduces the *count* of full rollouts needed by using pivotal-state retry. Substrate + trajectory optimizations compose: for a coding-agent RL workload, both papers together define the "how to make this affordable" recipe. **Cross-ref:** pivotal-state retry is a specific instance of the **restart-cost-aware autonomous loop** pattern — matches Justin's own "self-pacing / heartbeat" design principles for long-running agents; PivoARL is the RL-training-time realization of what Justin has been building at inference time.
- **Action signal:** `try-now` (pivotal-state retry at inference time is directly implementable in any checkpointable autonomous-loop workflow; 42% turn reduction is a hard cost win)

### HiLS-Attention hierarchical sparse attention (item 3)
- **Model:** any open-weights model — HiLS operates via lightweight continued pretraining, not architectural rewrite.
- **Memory fit:** at 64× training-context extrapolation (32K → 2M), the KV cache dominates memory unless combined with Kara [arxiv:2607.01237] or ContextNest [arxiv:2607.02116] compression. Standalone, expect ~4–6 GB additional KV cache overhead per additional 256K tokens on an 8B model.
- **Realistic tasks:** long-form multi-file reasoning at 500K–2M tokens — codebases the size of a mid-sized repo, multi-document RAG without external retrieval, sustained autonomous-loop workspaces with weeks of history.
- **How to run:** apply HiLS continued pretraining to an existing local Qwen3-8B or Llama3-8B — the paper describes it as lightweight, so plan for ~1–2 days of M5 Max compute per model. Retrieval-accuracy target: 90% at 64× extrapolation.
- **Speed estimate:** at inference time HiLS is faster than full attention on long context because chunk selection reduces the attention compute. On M5 Max Qwen3-8B at 256K context, expect prefill 2–3× faster than full-attention baseline; decode similar to standard.

### SelfMem policy-learned memory (item 2)
- **Model:** any local reasoning model as the memory-policy learner + any local model as the underlying agent; on M5 Max the two can be the same 8B model or a small (0.5B–3B) memory policy layered over a larger executor.
- **Memory fit:** the memory-tool wrappers (semantic store + episodic store + scratchpad files) are file-backed and cheap; the memory-policy layer is a few-thousand-token prompt-time overhead. Fits comfortably.
- **Realistic tasks:** long-running companion conversations (weeks), autonomous-loop workspaces where the memory shape isn't known a priori, workloads where mem0-class static memory doesn't fit the traffic pattern.
- **How to run:** wrap Justin's existing memory tools as agent-callable primitives; add a scoring signal (recall-quality prompt or LLM-judge — LLM-as-a-Verifier from item 1 is the perfect fit); let the agent explore memory strategies via ReAct-style loops with the memory tools available.
- **Speed estimate:** memory-policy overhead is small (a few tool-calls per turn). On M5 Max Qwen3-8B: expect no material slowdown at short turns, ~10–15% overhead at long turns with many memory operations.

**The three items compose:** VBQ compresses weights → HiLS-Attention extends context → SelfMem learns memory policy above the extended context. This is a full local-agent stack on 64 GB with interactive latency + 2M-token context + learned memory.

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:
- **CONFLICT: NLT vs structured function-calling** [arxiv:2607.03953]: The 14.9pp NLT-vs-structured-calling gap contradicts the MCP-tool-authoring standard (which assumes JSON-schema function-calling is the correct abstraction). Cross-refs: yesterday's [arxiv:2606.31227] AI-Infra-Guard is the *security* critique of MCP; today's NLT paper is the *accuracy* critique. Two papers in two days flag the MCP-as-shipped design surface. Watch for MCP v2 proposals in Q3.
- **CONFLICT: SelfMem vs static memory frameworks** [arxiv:2607.03726]: The 41–49% BEAM gain over baselines contradicts the "pick a memory framework and configure it" design lineage (mem0, LangMem, Zep). Same pattern as yesterday's [arxiv:2607.01874] SkillCoach — **rubric-as-training-signal beats fixed rubrics** — and yesterday's [arxiv:2607.02073] Maven **evidence-state rewards beats fixed evidence policy**. Convergent claim: **learn-your-primitive beats pick-your-framework**. Name for the vault: **learn-your-primitive** meta-pattern.
- **CONFLICT: process rewards vs outcome rewards for capability-limited models** [arxiv:2607.02869]: The ~10pp process-vs-outcome gap on Qwen2.5-0.5B contradicts the RLHF/RLAIF lineage that ships outcome-only judges as the default. Same finding as yesterday's [arxiv:2607.01874] SkillCoach — **process-quality rubrics beat outcome scoring**. Two convergent papers → strong signal → treat outcome-only as the *legacy* setting for capability-limited models.

**Open empirical questions raised today:**
- LLM-as-a-Verifier's **three scaling axes** (granularity + repeated eval + criteria decomposition) — is there a natural composition law? If you double one axis is the payoff the same as doubling another?
- VBQ's **69% 1-bit / LM head 1.09-bit** allocation pattern — is it universal across model families, or an artifact of the specific training run? Waiting for VBQ replication on Qwen/Llama.
- HiLS-Attention's **90% retrieval at 64× extrapolation** — does this hold on tasks that need to reason across the whole extended context, not just retrieve from it? The retrieval number is strong; the reasoning number would be stronger.
