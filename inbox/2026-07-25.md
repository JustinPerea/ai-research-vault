### 2. Sample-Efficient Learning from Agent Experience (Experience Distillation)
- **Source:** arXiv / HF Daily Papers (8 upvotes)
- **Link:** https://arxiv.org/abs/2607.21051
- **Authors / org:** Chenhui Gou, Haoqin Tu, Yunhao Fang, Jianfei Cai, Hamid Rezatofighi
- **Submitted:** 23 Jul 2026
- **Focus area:** Agent memory (weight-level consolidation); reasoning & inference-time compute (turning ICL into permanent capability)
- **What it is:** Names and implements the problem of **Experience Distillation** — turning the in-context gains an agent gets from *its own past trajectories* into weight-level knowledge without any additional environment interaction beyond what was already collected. The recipe is straightforward: do in-context learning on the collected trajectory buffer first, then distill that improved context-conditional behavior into the base weights.
- **Numbers:**
  - **≥ 64.8%** of the in-context learning gains retained after context is removed (SWE tasks + text-adventure games)
  - **3.8%** — how much *supervised fine-tuning directly on the same trajectories* recovers (the naive baseline; the gap is the whole story)
  - **≥ 9.6× fewer environment samples** to match classical RL baselines
  - Evaluated on **749 curated software-engineering tasks** and **six text-adventure games**
- **Why it matters for Justin's agents:** This is the missing weight-side complement to the vault's **SEED (2607.14777)** on-policy skill mining and **AgentBrew (2607.16851)** teacher-note synthesis. SEED and AgentBrew produce *artifacts* the runtime carries into the next session; Experience Distillation converts the same trajectory buffer into *model weights* — the two are stackable. For a scheduled routine like Justin's daily digest, this means: log every day's session buffer, do occasional distillation, and the agent quietly gets better at the task without any RL infrastructure. The 3.8% naive-SFT number is the important negative — plain "fine-tune on trajectories" is roughly *nothing*, and the whole trick is doing ICL first as the demonstration surface.
- **Action signal:** `track` — no code link on the abstract, but the recipe is simple enough to prototype against any base model with a trajectory buffer. `compare` — pairs with **ReOPD** (2607.04763, Jul 6, teacher trajectories as replayed prefixes, ≥4× faster per rollout, zero tool calls during training) as two "turn expensive agent-environment interaction into reusable offline signal" answers: ReOPD reuses a *teacher's* trajectories under student-selected steps; Experience Distillation reuses the *student's own* trajectories via a two-stage ICL→distill pipeline.

### 3. Autonomous Topology Mutation: Safe Runtime Restructuring for Multi-Agent LLM Systems (ATM)
- **Source:** arXiv (cs.MA)
- **Link:** https://arxiv.org/abs/2607.20488
- **Authors / org:** Bronislav Sidik, Chaya Levi, Nizzan Kimhi
- **Focus area:** Agent orchestration (dynamic topology); autonomous loops (self-restructuring)
- **What it is:** The first named mechanism for **runtime team restructuring** in multi-agent LLM systems — most current frameworks fix their topology at boot and cannot factorize an overloaded agent into specialists mid-run. ATM detects overload via a six-signal **Bottleneck Index** (queue depth, context thrash, tool-error rate, role entropy, retry-loop rate, cross-agent wait time) calibrated during a warmup window. When the threshold trips for multiple consecutive ticks, ATM **factorizes** the overloaded agent into specialized sub-agents and **hot-swaps the parent into a coordinator role while preserving its external identity**. Structural changes are gated by three invariants: **capability monotonicity** (children maintain or exceed parent capability), **state-routing completeness** (every memory atom either routes to a permitted child or is logged as dropped with a reason), and **shadow-before-live validation** (candidate topologies handle mirrored traffic before serving real users).
- **Numbers:** 720 DeepSeek-V3-driven task runs across 4 ablation conditions × 3 workloads with deterministic tool stubs.
  - Code-task success: **3.3% → 61.7%** after factorization
  - High-privacy memory exposure (regex classifier): **2.0 → 0.0** events per task
  - Runtime overhead: **< 500 µs p99** on the agent hot path
  - External-validity check: small live-tool probe with real Python execution
  - Implementation, benchmark harness, traces open-sourced
- **Why it matters for Justin's agents:** The Claude Code + MCP loop today has *no* built-in mechanism for factorizing an overloaded subagent — the closest thing is Justin manually noticing that a subagent has drifted and reissuing with a narrower prompt. ATM's contribution is the **operationalization**: (1) a concrete overload signal set worth wiring into any harness (queue depth + tool-error rate + role entropy would already move most current MCP setups from "the user notices" to "the harness notices"), and (2) the **state-routing-completeness invariant**, which forces the topology change to explicitly account for every memory atom rather than silently dropping context. Composes directly with **Shippy's Soul + Skills + Config** artifacts (2026-07-18): ATM is the *reflex layer* under Shippy's *organism layer*.
- **Action signal:** `track` — arxiv date recorded on the abstract page reads **4 Jun 2026** (~7 weeks old) but the paper does not appear in the vault; likely a June submission surfaced by a cs.MA cross-listing. Worth transplanting the six-signal Bottleneck Index into a session-hook prototype regardless of when it was formally published.

### 4. Workload-Aware Caching for Multi-Agent Systems
- **Source:** arXiv (cs.MA / cs.AI)
- **Link:** https://arxiv.org/abs/2607.20495
- **Authors / org:** Anas Mohamed, Kaizan Haque, Azal Ahmad Khan, Chetan Sharma, Shuwen Ge, Ali Anwar
- **Focus area:** Context engineering (system-level caching); agent orchestration (multi-agent DAGs)
- **What it is:** Caches **intermediate agent outputs in DAG-structured multi-agent workflows** (not KV cache and not tool results — the outputs of *specialized agent operations* that get reused across queries). The eviction policy is a unified score combining three signals: **recomputation cost** (expense of regenerating the entry), **DAG dependency count** (how many downstream operations depend on this entry), and **agent invocation frequency** (how often the producing agent is called).
- **Numbers:**
  - **Up to 64.7%** latency reduction vs uncached baseline
  - **Average 31.1%** latency reduction over the next-best finite-capacity baseline
  - Accuracy parity with competing methods, approaches unbounded-cache performance under capacity constraints
- **Why it matters for Justin's agents:** The daily digest and PR-watcher patterns both re-invoke the same "read the state file, dedup against processed IDs, extract summary" agent operations on every run — currently every invocation re-computes from scratch. This paper's contribution isn't a specific implementation, it's the **eviction formula**: cost × dependency-count × frequency is the right composite signal for agent-DAG caching, and it beats access-frequency-only LFU/LRU by 31.1% on average. That formula is portable to any MCP transport layer with a memoization decorator. Extends the vault's KV cache stack (**JoLT / Jet-Long / KV grafting / C²KV / PReM**) up one layer — instead of caching attention states, cache *agent-output artifacts*.
- **Action signal:** `try-now` — the formula is small enough to implement as a decorator around MCP tool handlers. `compare` — sits above **C²KV** (2607.17715, non-prefix KV library) as agent-output-level to token-level caching. Together they define a two-tier cache: token-level below, agent-output-level above.

### 5. MKEvolve: A Modular Multi-Agent Framework for Kernel Code Generation
- **Source:** arXiv (cs.LG / cs.MA)
- **Link:** https://arxiv.org/abs/2607.20501
- **Authors / org:** Jason Yoo, Rajarshi Saha, Shaowei Zhu, Tao Yu, Wei Tang, Youngsuk Park
- **Focus area:** Coding agents (kernel synthesis); agent orchestration (co-evolution)
- **What it is:** Iteratively co-evolves the **modular decomposition** of complex PyTorch modules and the **LLM-generated Triton kernel** for each submodule. The decomposition itself refines by splitting and fusing across iterations; each submodule kernel is independently improved via LLM-driven beam search. Resulting kernels are programmatic compositions of independently verified subkernels — **configurable** (subkernels swappable), **interpretable** (errors and speedups traceable to specific subkernels), and **adaptable** to related model architectures.
- **Numbers:** Improves both **correctness and speedup** over end-to-end direct-synthesis baselines on KernelBench L2 and L3 (multi-operator sequences and full model architectures); reduces LLM token usage **up to 35%**.
- **Why it matters for Justin's agents:** Kernel synthesis isn't Justin's daily surface, but the **decomposition-plus-synthesis co-evolution shape** is exactly what the harness-engineering thread has been converging on for higher-level agent work — MKEvolve is a domain-specific instantiation of the same primitive appearing in **Compound RELAI-VCL / SEED / MSCE / PRO-LONG**. The specific novelty is the **traceability property**: errors and speedups map back to individual subkernels, which is a cheap version of **Proof-or-Stop-style receipts** (2607.14890) attached to compositional outputs.
- **Action signal:** `track` — pattern is transplantable to any code-generation-with-verification loop (test synthesis, migration scripts) where "swappable subcomponent with error attribution" beats monolithic regeneration.

### 6. POCKET-35B: Sub-2-bit Sparse MoE for CPU / Apple Silicon Inference
- **Source:** Hugging Face Blog (FINAL-Bench, 2026-07-23)
- **Link:** https://huggingface.co/blog/FINAL-Bench/pocket
- **Authors / org:** FINAL-Bench (community release; base is Darwin-36B-Opus, Qwen3.5-family MoE)
- **Focus area:** Local & open models for Apple Silicon (M5 Max, 64 GB)
- **What it is:** A **34.66B sparse MoE (~3B active per token)** post-processed with **MoE-aware mixed-precision quantization** — attention and shared-expert layers stay at high precision while routing experts are pushed to sub-2-bit. That combination reportedly cuts English-perplexity degradation from **+81% to +36%** relative to uniform quantization at the same total size. Runs unmodified on llama.cpp / LM Studio / Ollama / MLX; Apache-2.0.
- **Numbers (measured by authors):**
  - **Q4_K_M:** 21 GB weights, needs 32 GB RAM
  - **Q2_K:** 13 GB weights, runs in **16–24 GB RAM**, **~20 tok/s on 12-core AMD CPU**
  - **IQ1_M:** 8.2 GB weights, 16 GB RAM, **27.0 tok/s on Xeon (16 threads)**
  - **H100:** 197 tok/s generation (but 0.41× Bonsai-27B Q1_0 on prefill — honest caveat)
  - **MacBook M3 Pro 18 GB:** tested with Metal (numbers not surfaced in blog)
  - vs Bonsai-27B Q1_0: **2.69× faster** CPU generation, **2.22× faster** H100 generation, quality tie on HellaSwag (61.0% vs 60.0%)
  - **iPhone / Android:** authors explicitly state "not yet measured by us" — headline is aspirational
- **Why it matters for Justin's agents:** The M3 Pro 18 GB test with Metal is a *lower bound* — M5 Max at 64 GB will handle **Q4_K_M** comfortably with ~40 GB headroom for KV cache and MCP scratch buffers, which lands POCKET-35B squarely in the "leave it resident all day" category for local Claude Code MCP subagents. Realistic tasks: RAG over the vault, tool-call orchestration where latency matters more than raw quality, and a local fallback for the digest routine when the API is degraded. The **MoE-aware mixed precision** insight is the reusable primitive — attention layers need precision, routed experts don't, and the perplexity gap between uniform-quant and MoE-aware-quant (+36% vs +81%) is worth a `local-fit` note independent of this specific model.
- **Action signal:** `local-fit` — download **Q4_K_M (21 GB)** to the M5 Max, run it under MLX or llama.cpp/Metal, and time a real MCP subagent handoff against `claude-opus-5` on the same task. `track` — watch for a proper Apple-Silicon-specific benchmark from the FINAL-Bench team; M3 Pro 18 GB isn't enough to characterize M5 Max 64 GB behavior.

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:

- **Claude Opus 5's headline gains vs the "static benchmarks undercount capability gaps" convergence.** The Anthropic-reported numbers on ARC-AGI 3 (3×) and Frontier-Bench v0.1 (>2×) are exactly the kind of *headline-only, single-source* frontier-model claim the vault's four-paper convergence from 2026-07-24 (**AppWorld-UL / LLMs-Get-Lost-in-Evolving-Intent / ICAE-Bench / WorkBuddy Bench**) argues should be discounted until confirmed on **multi-turn, evolving-intent, or user-agent-simulated** variants. This is an open empirical question — not a refutation of Opus 5, but a warning against updating priors from the release post alone. First cross-check: watch for the **AA Coding Agent Index** (mentioned in the release) or **WorkBuddy Bench** to post independent Opus 5 numbers.
- **Experience Distillation vs "auto-authored skills don't beat fixed prompting" (Ray/Goyal, 2607.20668, 2026-07-24).** The Ray/Goyal negative was specifically about *policies distilled from agent experience via textual optimization (GEPA-family)* — Experience Distillation is a **weight-level** distillation of the ICL context, not a text policy. These are compatible and possibly complementary: Ray/Goyal shows that trying to squeeze self-authored *text* out of agent trajectories fails without external validation; Experience Distillation shows that squeezing self-authored *weights* out of the same trajectories works if you use ICL as the demonstration surface first. **Sharpens** the Ray/Goyal claim to "auto-authored text policies fail; auto-authored weight updates via ICL bootstrap succeed."
- **Open empirical question raised today:** ATM's six-signal Bottleneck Index (queue depth / context thrash / tool-error rate / role entropy / retry-loop rate / cross-agent wait time) is the most concrete named signal set for "when should an agent factorize itself." Does any of it survive as a useful *single-agent* self-monitoring signal, i.e. before there is even a second agent to factorize into? If yes, it's a cheap self-diagnostic to bolt onto a scheduled routine like this one.
