# AI Research Digest — Monday, May 04, 2026

## TL;DR
- **Tool-calling decisions are quantifiable**: a new framework (arXiv:2605.00737) shows LLMs misjudge when to invoke tools, and lightweight hidden-state probes can outperform self-perceived need.
- **Multi-agent web search hit a step change**: Web2BigTable's bi-level orchestrator + parallel workers reports a **7.5× lift** on WideSearch (Avg@4 success 38.50 vs. 5.10).
- **Coding agents got two useful signals**: Mistral Medium 3.5 (dense 128B, 256k ctx) claims **77.6% SWE-bench Verified**, and AEM's entropy-modulation RL adds **1.4 pp** on top of a SOTA SWE-bench baseline.
- **Local sweet spot updated**: IBM Granite 4.1 (Apache 2.0) ships 3B/8B/30B dense with **512K context** on 8B/30B and strong tool-calling (BFCL v3 at 73.7 for 30B). Comfortable on M5 Max at FP8 or Q4.
- **Eval cost is the new bottleneck**: HF/EvalEval shows agent benchmarks resist compression (only 2–3.5× vs. 100–200× for static), and a credible k=8 reliability run on HAL costs ~$320K — flag for anyone shopping benchmarks.

## Items

### 1. To Call or Not to Call: A Framework to Assess and Optimize LLM Tool Calling
- **Source:** arXiv (cs.AI)
- **Link:** https://arxiv.org/abs/2605.00737
- **Authors / org:** Wu, Das, Amani, Nag, Lee, Gummadi, Ravichander, Zafar (MPI-SWS et al.)
- **Focus area:** Tools & connectors / Agent orchestration
- **What it is:** Decision-theoretic framework that scores tool calls by **necessity, utility, and affordability**, contrasting normative (optimal allocation) with descriptive (model's self-perception) views. Across 3 tasks × 6 models, models' self-perceived need diverges from true need; lightweight estimators trained on hidden states beat the model's own gating.
- **Why it matters for Justin's agents:** Direct lever for any MCP-tool-rich agent — instead of letting the model decide when to call `web_search` / `read_file` / etc., probe the hidden state. Should compose with Claude tool use today via a small classifier on logits/activations.
- **Action signal:** `try-now` — the "lightweight estimator on hidden states" pattern is reproducible and cheap to bolt onto an agent loop.

### 2. Web2BigTable: A Bi-Level Multi-Agent LLM System for Internet-Scale Information Search and Extraction
- **Source:** arXiv (HF Daily Papers, #2 trending today)
- **Link:** https://arxiv.org/abs/2604.27221
- **Authors / org:** Huang, Chen, He, Chen, Lee, Zhou, Luo, Fang, Wang
- **Focus area:** Agent orchestration / Tools
- **What it is:** Upper-level orchestrator decomposes web-research tasks; lower-level workers solve sub-problems in parallel through a shared workspace that reconciles conflicting evidence and adapts to coverage gaps. Reports **WideSearch Avg@4 = 38.50 (7.5× the 5.10 second-best)**, Row F1 63.53 (+25.03), Item F1 80.12 (+14.42), and 73.0 on XBench-DeepSearch.
- **Why it matters for Justin's agents:** Concrete supervisor/worker architecture with measured deltas — useful template if any companion-app feature involves aggregating across many entities (research, comparisons, monitoring). The shared-workspace pattern is what makes the parallelism non-redundant.
- **Action signal:** `track` — implementation isn't released yet from what I can see; revisit if code/repo lands.

### 3. AEM: Adaptive Entropy Modulation for Multi-Turn Agentic Reinforcement Learning
- **Source:** arXiv (cs.AI, submitted May 1)
- **Link:** https://arxiv.org/abs/2605.00425
- **Authors / org:** Zhao, Zhang, Zhou, Yau, Zhang, Tian, Zhu, Huang, Zeng, Gu, Dong, Wu
- **Focus area:** Coding agents / Reasoning & inference-time compute
- **What it is:** Supervision-free credit assignment for multi-turn agent RL. Modulates entropy at the **response level** (not token level) using advantage-weighted response surprisal, naturally moving from exploration to exploitation. Tested 1.5B–32B; **+1.4 pp on SWE-bench Verified** when bolted onto a SOTA baseline.
- **Why it matters for Justin's agents:** If/when fine-tuning a coding agent locally, response-level entropy control is a cheap addition to GRPO-style pipelines. The 1.4 pp on Verified is a real number on a hard benchmark; not headline-grabbing but real.
- **Action signal:** `track` — useful technique to file under "agent post-training tricks."

### 4. AgentFloor: How Far Up the tool-use Ladder Can Small Open-Weight Models Go?
- **Source:** arXiv (cs.AI)
- **Link:** https://arxiv.org/abs/2605.00334
- **Authors / org:** Karmakar, Chatterjee
- **Focus area:** Evaluation / Local & open models
- **What it is:** A **30-task, six-tier capability-ladder** benchmark covering instruction following, tool use, multi-step coordination, long-horizon planning. 16 open-weight models (0.27B–32B) plus GPT-5; 16,542 scored runs. Finding: best open-weight matches GPT-5 on short-horizon structured tool use; gap remains on long-horizon planning where neither category is reliable.
- **Why it matters for Justin's agents:** Maps directly onto the question "which tier of agent work needs Claude vs. can run on a local 8–32B?" Useful for routing decisions in mixed-cost agent stacks (e.g., supervisor on Claude, sub-tasks on local Granite/Qwen).
- **Action signal:** `local-fit` — explicitly grades small models on the work Justin's agents actually do.

### 5. Are Tools All We Need? Unveiling the Tool-Use Tax in LLM Agents
- **Source:** arXiv (cs.AI)
- **Link:** https://arxiv.org/abs/2605.00136
- **Authors / org:** Zhang, Xiong, Zhong, Jiang, Yuan, Li, Lin
- **Focus area:** Tools & connectors
- **What it is:** Argues tool-augmented reasoning **does not always beat native CoT** under semantic distractors, and isolates a "tool-use tax" — performance degradation from the tool-calling protocol itself, separate from formatting overhead. Proposes G-STEP, an inference-time gate that gives partial recovery.
- **Why it matters for Justin's agents:** Counterpoint to item #1's framing. If both hold, the right design is: (a) hidden-state need estimator + (b) protocol-aware gating, since even *needed* tool calls leak performance. Worth testing on any agent that aggressively uses MCP tools on noisy inputs.
- **Action signal:** `compare` — extends item #1 with the additional claim that tool-calling has intrinsic protocol cost; flagged in claims ledger.

### 7. IBM Granite 4.1 (3B / 8B / 30B dense)
- **Source:** Hugging Face Blog (ibm-granite, Apr 29, 2026)
- **Link:** https://huggingface.co/blog/ibm-granite/granite-4-1
- **Authors / org:** IBM Granite team
- **Focus area:** Local & open models / Tools
- **What it is:** Three dense decoder-only models (3B/8B/30B), GQA + RoPE + SwiGLU + RMSNorm, **Apache 2.0**. **Standard 4K, extended to 512K** (8B/30B) via Phase 5 long-context training (80% books + 20% code repos). Reported instruct numbers: GSM8K 86.9/92.5/94.2, HumanEval pass@1 79.3/87.2/89.6, MMLU-Pro 49.8/56.0/64.1, **BFCL v3 tool-calling 60.8/68.3/73.7**, RULER@128K 58.0/73.0/76.7. FP8 quantized variants ship via vLLM (~50% memory savings). The 8B "consistently matches or outperforms" the prior Granite 4.0-H-Small (32B MoE / 9B active).
- **Why it matters for Justin's agents:** BFCL v3 of 73.7 + 512K context + Apache 2.0 makes 30B a legitimate candidate for local MCP-tool agents. 8B at Q4 is a likely default for fast in-loop use; 30B for quality passes.
- **Action signal:** `local-fit` — see Local-model corner below for M5 Max sizing.

### 8. AI Evals Are Becoming the New Compute Bottleneck (HF / EvalEval)
- **Source:** Hugging Face Blog (evaleval, Apr 29, 2026)
- **Link:** https://huggingface.co/blog/evaleval/eval-costs-bottleneck
- **Authors / org:** Ghosh, Mai, Channing, Choshen (EvalEval Coalition)
- **Focus area:** Evaluation
- **What it is:** Quantitative case that **eval compute, not training compute, gates assessment of frontier agents**. Static benchmarks compress 100–200× (HELM aggregate ~$100K → tinyBenchmarks); agent benchmarks only 2–3.5×. Single GAIA run on a frontier model: **$2,829**. Holistic Agent Leaderboard: $40K for 21,730 rollouts; **k=8 reliability rerun ≈ $320K**. 33× cost spread on identical tasks depending on scaffold. Recommends: standardized log schema (`evaleval/EEE_datastore`), Pareto-frontier leaderboards, mid-difficulty (30–70% pass) filtering for agent benches.
- **Why it matters for Justin's agents:** When picking a benchmark to track for an agent product (memory, coding, etc.), the cost-vs-rank-fidelity tradeoffs here are the most concrete numbers I've seen. The "**pass^k consistency** drops from 60% → 25% across 8 runs" point is the honest version of "our agent works most of the time."
- **Action signal:** `track` — methodology reference, not an integration.

### 9. Anthropic — BioMysteryBench: evaluating Claude on bioinformatics research
- **Source:** Anthropic Research (Apr 29, 2026)
- **Link:** https://www.anthropic.com/research/Evaluating-Claude-For-Bioinformatics-With-BioMysteryBench
- **Authors / org:** Anthropic
- **Focus area:** Frontier models / Evaluation
- **What it is:** 99-question benchmark grounded in **objective, verifiable signals** in real datasets (validated by notebook before inclusion). Models access NCBI/Ensembl, can install software. Reported scores: **Opus 4.6 ~77% / Sonnet 4.6 ~66%** on 76 human-solvable tasks; **Opus 4.6 ~24% / Sonnet 4.6 ~13% / "Claude Mythos Preview" 30%** on 23 human-difficult tasks. Mythos solved problems experts couldn't, but many wins on hard set are "brittle" — succeed inconsistently across 5 attempts.
- **Why it matters for Justin's agents:** The brittle-wins finding reinforces the same eval-reliability point as #8 — single-run accuracy oversells durable agent capability. Also the first public number on "Claude Mythos Preview," which is worth tracking as an unannounced model handle.
- **Action signal:** `track` — flagged in claims ledger as the first public Mythos signal.

## Local-model corner

**Model:** IBM Granite 4.1-30B-Instruct (dense, Apache 2.0)
- **Memory fit (M5 Max, 64 GB unified):**
  - FP16 weights: ~60 GB → tight; KV headroom too small for any meaningful context.
  - **FP8 (vLLM-style): ~30 GB** weights → leaves ~30 GB for KV cache and OS. Realistic ctx ~64K–128K with GQA.
  - **Q4 (GGUF/MLX): ~17–18 GB** weights → comfortable. ~40 GB for KV; full 512K reachable in theory but you'll be memory-bound long before then in practice. Realistic ctx ~128K.
- **Realistic tasks:** Tool-calling agent loops (BFCL v3 73.7 is genuinely competitive for an open 30B), structured extraction, code completion (HumanEval 89.6 / MBPP 83.3), long-document QA up to ~128K. **Not** a substitute for Claude on long-horizon planning or open-ended research — AgentFloor (#4) shows that gap is still real.
- **How to run:** Easiest path is **MLX** via mlx-lm once a community Q4 conversion lands (likely within days given Apache 2.0 + HF availability). Until then, **llama.cpp Q4_K_M GGUF** is the practical default; Ollama wraps it cleanly. vLLM FP8 path exists but the M5 Max isn't its target.
- **Speed estimate:** No M5-Max-specific Granite 4.1 numbers published yet. Memory-bandwidth ceiling on M5 Max (~600 GB/s) for a Q4 30B (~18 GB) puts the bandwidth-bound upper bound around **30–35 tok/s**; in practice expect **18–28 tok/s** for short outputs at modest context, dropping with context length. **Treat as an estimate — verify with a local benchmark before quoting.**

**Also worth a Q4 try:** Granite 4.1-8B-Instruct (~4–5 GB Q4) — likely **70–110 tok/s** on M5 Max, BFCL v3 68.3, runs alongside Claude in agent supervisor/worker setups.

## Conflicts & open questions

Cross-referenced against `_meta/claims-ledger.md` (empty — first run):

- **Tool-use framing tension (item #1 vs. item #5):** Wu et al. (#1, arXiv:2605.00737) frame tool-call quality as a *decision* problem solvable with a hidden-state estimator over necessity/utility. Zhang et al. (#5, arXiv:2605.00136) argue there is also a *protocol-induced* tax — even correctly-decided tool calls degrade performance. Not a direct contradiction; they're orthogonal axes (when-to-call vs. cost-of-calling). Worth tracking whether anyone composes the two: estimator-gated calls + protocol-aware re-prompting.
- **Open empirical question:** Mistral's 77.6% SWE-bench Verified for a 128B dense — does this hold under independent reproduction? Vendor numbers on Verified have a track record of slipping ~3–8 points in third-party runs.
- **Open empirical question:** What is "Claude Mythos Preview"? Anthropic's own BioMysteryBench post is the first public reference; no model card or release notes accompany it.
