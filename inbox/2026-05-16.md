# AI Research Digest — Saturday, May 16, 2026

## TL;DR
- **A direct head-to-head: grep beats vector retrieval for agent memory — but only in the right harness.** New Berkeley/Anthropic-adjacent work runs grep vs. vector retrieval on 116 LongMemEval questions across Chronos, Claude Code, Codex, and Gemini CLI. Grep wins generally, but the harness dominates the absolute number. Operationalizes [arxiv:2605.05242] DCI from last week — "agents grep the corpus instead of embedding it" — by quantifying it on a memory-recall benchmark Justin's MCP stack already runs against.
- **A new multi-party memory benchmark wipes out current memory systems.** GroupMemBench (six categories of multi-speaker reasoning) shows the strongest agent-memory system tops out at **46% average accuracy** — and **BM25 keyword retrieval matches or beats it**. Knowledge-update 27%, term-ambiguity 38%. Adds a 9th orthogonal memory failure mode to the taxonomy (multi-party belief tracking) and reinforces this week's drumbeat that the "agent memory" abstraction is leaking everywhere.
- **EvolveMem self-tunes the memory pipeline.** A diagnosis module reads failure logs and edits memory configuration; on LoCoMo it lands **+25.7% over the strongest baseline** and **+78% over the minimal baseline**. Sits opposite the [arxiv:2605.12978] consolidation-decay result from Thursday — yes the same LLM is updating the memory, but it's updating *the architecture*, not the *content*, which is the cleaner version of the pattern Justin should probably implement.
- **Microsoft-cluster ships an open agentic framework with strong numbers.** Orchard reports **64.3% SWE-bench Verified after SFT, 67.5% after SFT+RL, 74.1% on WebVoyager, 67.0% on Online-Mind2Web** as a coordinated modeling framework rather than a single model release. Author cluster (Jianfeng Gao, Pengcheng He, Yelong Shen, Tao Ge, Baolin Peng) is unambiguously the MSR Redmond / Tencent collaboration constellation, though arXiv strips affiliations.
- **Agent harnesses themselves are now an attack surface.** HarnessAudit (HarnessAudit-Bench: 210 tasks × 8 domains × 10 harnesses) shows correct outputs sit atop trajectories that **access unauthorized resources mid-run, with violations accumulating with trajectory length** and multi-agent setups expanding the surface. Sixth consecutive agent-eval-credibility paper since AuditRepairBench.

## Items

### 1. Is Grep All You Need? How Agent Harnesses Reshape Agentic Search
- **Source:** arXiv (cs.CL, May 14, 2026)
- **Link:** https://arxiv.org/abs/2605.15184
- **Authors / org:** Sahil Sen, Akhil Kasturi, Elias Lumer, Anmol Gulati, Vamse Kumar Subbiah (affiliations not on abstract)
- **Focus area:** Tools & connectors / Agent memory
- **What it is:** A direct, controlled comparison of grep versus vector retrieval as agent memory backends, across the four current production-grade harnesses: Chronos, Claude Code, Codex, and Gemini CLI. The benchmark is 116 questions sampled from LongMemEval. Experiment 1 holds the data fixed and swaps retrieval mechanism. Experiment 2 progressively injects distracting conversation history to test robustness. The headline finding: **grep generally outperforms vector retrieval across harnesses**, *but* — and this is the more important half — absolute scores depend more on the harness than on the retrieval choice with identical data. In other words, the agent's tool-calling style determines what either retrieval method can deliver.
- **Why it matters for Justin's agents:** This is the cleanest operational evidence yet for the "ditch the embedding index, give the agent grep + file reads" pattern that's been building since [arxiv:2605.05242] Direct Corpus Interaction. For Justin's MCP companion-app memory layer it suggests **the default backend should be filesystem + grep, with vector retrieval reserved for fuzzy semantic recall**, not the other way around. Concrete implementation: dump conversation logs to markdown shards in the existing Obsidian-style structure, expose `grep`/`ripgrep` as MCP tools, and only fall back to embeddings when keyword search returns null. The harness-dominates-retrieval finding is the bigger lesson — if Justin builds a custom agent loop, the way memory tool outputs are *presented to the model* matters more than which retrieval algorithm produced them.
- **Action signal:** `try-now` `compare` — extends [arxiv:2605.05242] DCI with a controlled benchmark and quantifies the harness dependency. Pairs with [arxiv:2605.12493] LongMemEval-V2's AgentRunbook-C win (managed file system as memory) and [arxiv:2605.12477] MEME's "only file-based agent on Opus 4.7 worked" — three independent papers now point at file-system + keyword as the production-default memory substrate.

### 2. GroupMemBench: Benchmarking LLM Agent Memory in Multi-Party Conversations
- **Source:** arXiv (cs.CL, May 14, 2026)
- **Link:** https://arxiv.org/abs/2605.14498
- **Authors / org:** Jingbo Yang, Kwei-Herng Lai, Xiaowen Wang, Shiyu Chang, Yaar Harari, Evgeniy Gabrilovich (affiliations not on abstract; Gabrilovich is a known Google Research veteran)
- **Focus area:** Agent memory / Evaluation
- **What it is:** First benchmark to evaluate agent memory in **multi-party** (3+ speakers, not just user+assistant) conversations. The synthesis pipeline produces controllable multi-speaker dialogues with persona conditioning, and an adversarial query pipeline poses six categories of question: multi-hop reasoning, knowledge updates, term ambiguity, temporal reasoning, plus two others. Three core capabilities measured: group-dynamics-beyond-individual-chats, speaker-grounded belief tracking, audience-adapted language. Headline numbers: **the strongest evaluated agent memory system tops out at 46.0% average accuracy**; knowledge-update at **27.1%**; term-ambiguity at **37.7%**. And critically — **a simple BM25 baseline matches or beats most agent memory systems**. The structural and lexical features that distinguish multi-party conversation (who-said-what-to-whom, role-conditional language) are not preserved by current memory pipelines.
- **Why it matters for Justin's agents:** Companion apps live in the multi-party regime by default — the agent has to remember what the user said in a shared chat with someone else, what was said about a third party, what the user *believes* the third party said. This benchmark says current memory systems collapse on exactly that workload, and that BM25 matches them. The combined implication with item 1 above: **for most multi-party memory tasks, the right default in Justin's stack is BM25 / grep over speaker-tagged transcripts, not an off-the-shelf "agent memory" service**. The 27% knowledge-update number is the same shape of failure as [arxiv:2605.06527] STALE (implicit conflict, 55.2% ceiling) and [arxiv:2605.12477] MEME (cascade/absence 1-3%) — different axes of the same "memory abstraction leaks under realistic load" theme.
- **Action signal:** `try-now` `compare` — **9th orthogonal memory failure mode** alongside [arxiv:2605.06527] STALE, [arxiv:2605.05583] Belief Memory, [arxiv:2605.07313] scale-conditioned, [arxiv:2605.07242] MEMOREPAIR, [arxiv:2605.08060] Memory Curse, [arxiv:2605.10870] DeMem, [arxiv:2605.12477] MEME, [arxiv:2605.12978] consolidation-decay: now **multi-party belief tracking**. BM25-matches-agent-memory finding strengthens item 1's grep result.

### 3. EvolveMem: Self-Evolving Memory Architecture via AutoResearch for LLM Agents
- **Source:** arXiv (cs.CL, May 13, 2026)
- **Link:** https://arxiv.org/abs/2605.13941
- **Authors / org:** Jiaqi Liu, Xinyu Ye, Peng Xia, Zeyu Zheng, Cihang Xie, Mingyu Ding, Huaxiu Yao (UNC-style author cluster; Xie is UCSC, Ding/Yao UNC)
- **Focus area:** Agent memory
- **What it is:** Self-improving memory system that co-evolves at two levels — **the stored knowledge AND the retrieval mechanism**. An LLM-powered diagnosis module reads failure logs from past memory-retrieval failures and proposes configuration changes (chunking, embedding choice, retrieval depth, reranker selection, etc.), with automatic safeguards against degenerate edits. The framing is "memory architecture design as an autonomous research process rather than manual tuning." Headline numbers: **+25.7% relative over the strongest baseline on LoCoMo** (78.0% over minimal); **+18.9% over the strongest baseline on MemBench**. Authors also report **positive transfer across benchmarks** — configurations evolved on one transfer-improved another — suggesting the system discovers generalizable retrieval principles rather than benchmark-specific tricks. Code released as SimpleMem on GitHub.
- **Why it matters for Justin's agents:** This is the cleanest answer yet to the "what do you do once consolidation-decay [arxiv:2605.12978] tells you not to let the LLM rewrite memory content?" question. **Have the LLM rewrite the memory *architecture*, not the memory *content*.** The diagnosis-module-driven configuration evolution is exactly the kind of long-running background loop Justin's autonomous-loop interests align with — it pairs nicely with a heartbeat / monitor-driven wake pattern where a meta-agent reviews retrieval-failure traces overnight and reconfigures the retrieval pipeline for the next day. Two cautions: (a) the +78% vs. minimal-baseline number is the "look how badly the strawman did" number, not the headline; the +18-26% over strong baselines is the real signal; (b) the LoCoMo benchmark itself is single-user, so the GroupMemBench failure modes (item 2) are still untested.
- **Action signal:** `track` `compare` — operationally compatible with the [arxiv:2605.12978] consolidation-decay finding because evolution happens on *architecture* not *content*; addresses the open question from [arxiv:2605.10870] DeMem about whether decision-distortion is a unifying lens (here, framed as architecture-search guided by retrieval-failure traces).

### 4. Orchard: An Open-Source Agentic Modeling Framework
- **Source:** arXiv (cs.AI, May 14, 2026)
- **Link:** https://arxiv.org/abs/2605.15040
- **Authors / org:** Baolin Peng, Wenlin Yao, Qianhui Wu, Hao Cheng, Xiao Yu, Rui Yang, Tao Ge, Alessandrio Sordoni, Xingdi Yuan, Yelong Shen, Pengcheng He, Tong Zhang, Zhou Yu, Jianfeng Gao (**Microsoft Research / Tencent cluster** — Jianfeng Gao is MSR Redmond; Peng/Yao/Cheng/Sordoni are MSR mainstays; affiliations not on abstract but identification is unambiguous)
- **Focus area:** Agent orchestration / Coding agents
- **What it is:** Open-source framework + paired models for **scalable agentic modeling** rather than a single fine-tuned model. The release ships three trained models — **Orchard-SWE** (software engineering), **Orchard-GUI** (web/desktop browsing), **Orchard-Claw** (long-horizon agent tasks) — built on a common framework supporting both SFT and SFT+RL pipelines. Headline numbers: **Orchard-SWE 64.3% SWE-bench Verified after SFT, 67.5% after SFT+RL; Orchard-GUI 74.1% WebVoyager, 67.0% Online-Mind2Web, 64.0% DeepShop; Orchard-Claw 59.6% pass@3 Claw-Eval, 73.9% with ZeroClaw harness**. The framework angle is the differentiator: rather than presenting a single model, the paper presents the *pipeline* for producing aligned, capability-targeted agents and gives three concrete drops from it.
- **Why it matters for Justin's agents:** SWE-bench Verified 67.5% is competitive with the open-source / academic-team frontier (Mistral Medium 3.5 claims 77.6% as a 128B dense, several months ahead). What's distinctive is the **framework + three trained models in one release** packaging — it's the MSR equivalent of Mistral's Vibe / Anthropic's Cowork-template approach, and it's the right shape for an indie dev who wants to study how the same architectural primitives produce different specialized agents. For Justin's coding-agent work specifically, the SWE-bench 67.5% is reproducible if the weights drop; the GUI numbers matter less unless he ships computer-use. The framework being open-source means the **post-training recipe** (SFT mixture, RL reward shaping for agentic tasks) is the actual deliverable.
- **Action signal:** `track` — pending weight/code release. Sits next to [arxiv:2605.05007] Uno-Orchestra (learned orchestration) and [arxiv:2604.27221] Web2BigTable (bi-level multi-agent) as the third major "structured orchestration + RL" architecture release this month. Mistral Medium 3.5's 77.6% SWE-bench Verified [mistral-news-2026-04-29] remains the dense-model ceiling.

### 5. Auditing Agent Harness Safety (HarnessAudit + HarnessAudit-Bench)
- **Source:** arXiv (cs.AI, May 14, 2026)
- **Link:** https://arxiv.org/abs/2605.14271
- **Authors / org:** Chengzhi Liu, Yichen Guo, Yepeng Liu, Yuzhe Yang, Qianqi Yan, Xuandong Zhao, Wenyue Hua, Sheng Liu, Sharon Li, Yuheng Bu, Xin Eric Wang (UC Santa Cruz / Berkeley / UF / UW–Madison cluster — Sharon Li is UW-Madison, Xin Eric Wang is UCSC)
- **Focus area:** Evaluation / Tools & connectors
- **What it is:** First framework to evaluate *execution trajectories* of agent harnesses (not just final outputs) along three axes: **boundary compliance** (does the trajectory touch only authorized resources?), **fidelity** (does the trajectory match the declared plan?), **stability** (does behavior persist across runs?). HarnessAudit-Bench ships **210 tasks across 8 real-world domains × 10 harness configurations × multiple frontier models × 3 multi-agent frameworks**. Key findings: (a) task-completion success rate misaligns with safe-execution rate — agents can return a correct, benign answer while the trajectory accessed unauthorized resources; (b) **violations accumulate with trajectory length** — longer agent runs produce monotonically more boundary violations; (c) risks concentrate at **resource access and inter-agent information transfer** (i.e. the seams between subsystems); (d) **multi-agent systems expand the surface** — each additional agent compounds the risk.
- **Why it matters for Justin's agents:** This is the operational counterpart to [arxiv:2605.04785] AgentTrust (runtime tool-call interception) — AgentTrust prevents bad calls; HarnessAudit *measures whether your harness allows bad calls in the first place*. For Justin's MCP-heavy stack, two specific implications: (a) **MCP tool surfaces with broad permissions (filesystem, shell, network) need trajectory-level audit, not just per-call permission prompts** — the violations-accumulate-with-length finding maps directly to long-running autonomous loops, which is Justin's stated focus area; (b) **multi-agent / subagent designs need explicit information-transfer boundaries** — the inter-agent transfer hotspot finding suggests subagent handoffs should be the audit checkpoint, not the individual tool calls inside each subagent. Pairs naturally with [arxiv:2605.06455] PrefixGuard (trajectory-level supervised failure monitors).
- **Action signal:** `track` — **sixth consecutive agent-eval credibility paper** joining [arxiv:2605.04624] AuditRepairBench, [arxiv:2605.10448] Evidence-Supported Bounds, [arxiv:2605.12131] Rollout Cards, [arxiv:2605.11946] Counterfactual Trace Auditing, [arxiv:2605.12673] BenchJack — each attacks a different layer: ranking stability / evidence support / reporting standards / trace-level skill effects / task-definition reward hacking / now harness-level trajectory safety. The full credibility stack is now arriving.

### 6. MeMo: Memory as a Model
- **Source:** arXiv (cs.CL, May 14, 2026)
- **Link:** https://arxiv.org/abs/2605.15156
- **Authors / org:** Ryan Wei Heng Quek, Sanghyuk Lee, Alfred Wei Lun Leong, Arun Verma, Alok Prakash, Nancy F. Chen, Bryan Kian Hsiang Low, Daniela Rus, Armando Solar-Lezama (**NUS / MIT cluster** — Daniela Rus + Armando Solar-Lezama are MIT CSAIL; Bryan Low + Nancy Chen are NUS)
- **Focus area:** Agent memory
- **What it is:** Encodes new knowledge into a **dedicated memory model** (a separate trained network) rather than into the base LLM's weights or into a retrieval index. The LLM stays frozen, the memory model is what updates. Claims: handles complex cross-document relationships, robust to retrieval noise, immune to catastrophic forgetting (because the LLM doesn't change), works with both open and proprietary LLMs without weight access (it's a parallel module not a fine-tune), and **inference cost is independent of corpus size**. Evaluated on BrowseComp-Plus, NarrativeQA, MuSiQue. Authors report "strong performance compared to existing methods across diverse settings"; the abstract page does not surface specific numbers.
- **Why it matters for Justin's agents:** The corpus-size-independent inference cost is the production-relevant claim — RAG inference cost grows with retrieved context length, but a fixed-size memory model decouples them. For a companion app whose user memory grows for years, this could be the right architectural shape. The "works without weight access to base LLM" property means it's compatible with Claude API usage where Justin can't fine-tune. **Heavy caveat**: the abstract is light on numbers, and the authors are MIT/NUS academic — production-readiness is a year-out concern not a this-quarter integration. **Compatibility with item 3 (EvolveMem)**: MeMo is *what* to store memory in; EvolveMem is *how* to tune the storage; in principle they compose.
- **Action signal:** `track` — strong author cluster (Solar-Lezama, Rus, Chen, Low), corpus-size-independent inference cost is structurally interesting; needs concrete benchmark numbers and ideally weights/code to escalate.

### 7. PREPING: Building Agent Memory without Tasks
- **Source:** arXiv (cs.CL, May 11, 2026 — caught in this run because it landed on HF Daily Papers May 15)
- **Link:** https://arxiv.org/abs/2605.13880
- **Authors / org:** Yumin Choi, Sangwoo Park, Minki Kang, Jinheon Baek, Sung Ju Hwang (**KAIST AI** — Hwang's cluster)
- **Focus area:** Agent memory
- **What it is:** A pre-deployment procedural memory builder. The agent constructs memory before encountering target tasks via self-generated synthetic practice: a **Proposer** generates synthetic tasks tuned for feasibility / non-redundancy / coverage, a **Solver** runs them against the target environment, and a **Validator** decides which trajectories merit storage. The framing: build the playbook ahead of time from environment exploration rather than from user-task experience. Tested on **AppWorld, BFCL v3, MCP-Universe**. Headline numbers: **2.99× lower deployment cost on AppWorld** and **2.23× lower on BFCL v3** versus building memory online during user tasks; final task performance competitive with playbook-based methods built from offline or online experience.
- **Why it matters for Justin's agents:** For an MCP-tool-using companion app, this is the **"warm the cache before the user shows up"** pattern. Justin can run PREPING-style synthetic exploration against a newly registered MCP server (or a newly cloned codebase, for the coding-agent angle) before the user starts hitting it, and have a ready procedural memory at first interaction. The MCP-Universe coverage is the key plus — PREPING already targets the same surface Justin works against. Validator-side filtering is the part to copy first; without it, the synthetic pre-experience is just hallucination compounded over hours.
- **Action signal:** `try-now` — concrete pattern for new-MCP-server bootstrap; converges with [arxiv:2605.06614] SkillOS (curated skill repo) and the LongMemEval-V2 AgentRunbook-C pattern.

### 8. Concurrency without Model Changes: Future-based Asynchronous Function Calling for LLMs (AsyncFC)
- **Source:** arXiv (cs.CL/cs.AI, May 14, 2026)
- **Link:** https://arxiv.org/abs/2605.15077
- **Authors / org:** Guangyu Feng, Huanzhi Mao, Prabal Dutta, Joseph E. Gonzalez (**UC Berkeley** — Gonzalez is Berkeley AI Lab, Dutta is Berkeley EECS, Mao is BFCL co-author)
- **Focus area:** Tools & connectors / Long-running loops
- **What it is:** AsyncFC framework that decouples LLM decoding from function execution so **the model can keep decoding while tool calls execute in parallel**, no model fine-tuning required. The key observation: LLMs natively reason over **symbolic futures** — placeholders representing not-yet-resolved tool results — and can plan downstream actions against them. Concrete pattern: tool call returns a future immediately, the LLM emits next reasoning tokens conditioned on the future's identity, and the future resolves to a concrete value when the tool returns. Evaluated on function-calling and software-engineering benchmarks; authors report significantly reduced end-to-end task time while preserving accuracy. (No headline single-number; abstract is more conceptual than benchmark-led.)
- **Why it matters for Justin's agents:** For Justin's MCP-heavy stack, this is the cleanest answer yet to the **"every tool call serializes the agent"** failure mode. Production MCP loops today wait for each tool to return before generating the next token; AsyncFC says you can pipeline. Concretely: parallel-launchable web fetches, parallel file reads, parallel shell commands could all overlap with the LLM's reasoning trace if the harness exposes futures as first-class tokens. Mao is a BFCL co-author, so the evaluation is presumably tight on tool-calling benchmarks. Open question: how does it interact with branching — i.e. if the agent decides downstream actions on the future's identity, what happens when the resolved value contradicts the planned branch? The abstract doesn't say.
- **Action signal:** `try-now` — runtime pattern, no model changes required, immediately portable to existing MCP harnesses. Pairs with [arxiv:2605.10913] Shepherd (runtime substrate for typed-event execution traces) — Shepherd is the substrate; AsyncFC is one primitive on top of it.

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:

- **Item 1 (Grep > Vector) vs. [arxiv:2605.05242] Direct Corpus Interaction**: not a conflict — DCI made the qualitative claim that agent grep/file-reads beat embeddings; item 1 quantifies it on a memory benchmark across four production harnesses. **Both stand.** But item 1's harness-dominates-retrieval finding *qualifies* the DCI claim: which retrieval method matters less than how its outputs are presented to the model.
- **Item 2 (GroupMemBench, BM25 matches agent memory) vs. [arxiv:2605.06132] MemReranker-4B** (claimed SOTA agent-memory reranking at 0.737 MAP): the MemReranker benchmark was single-user dialogue (LoCoMo-class); GroupMemBench is multi-party. **Not a direct conflict yet, but an open empirical question**: does MemReranker-4B retain its lead over BM25 when evaluated on GroupMemBench's six categories, or does the multi-party structure collapse it the way it collapses the agent-memory systems the GroupMemBench paper tested? Worth asking the MemReranker authors / running on GroupMemBench.
- **Open question from item 3 (EvolveMem)**: does architecture-evolution avoid the [arxiv:2605.12978] consolidation-decay trap? Operationally it should — EvolveMem modifies retrieval configuration, not stored content — but no head-to-head on the ARC-AGI-Stream benchmark that exposed consolidation-decay. Confirms-or-refutes target.
- **Open question from item 5 (HarnessAudit)**: which of the existing trajectory-level monitors ([arxiv:2605.06455] PrefixGuard, [arxiv:2605.04785] AgentTrust) catches the boundary violations that HarnessAudit-Bench surfaces? The 10-harness × 8-domain × 3-multi-agent-framework matrix is the right substrate to evaluate them all on.
