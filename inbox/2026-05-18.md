# AI Research Digest — Monday, May 18, 2026

## TL;DR
- **Memory consolidation rethought twice in one drop:** RecMem (2605.16045) gates LLM-based extraction on observed recurrence (-87% token cost vs. three SOTA memory systems while *improving* accuracy); DimMem (2605.15759) reaches 81.4% LoCoMo / 78.2% LongMemEval-S with a Qwen3-4B fine-tune. Both directly attack the "MEME found memory only works at ~70× cost on Opus 4.7" pain point.
- **Population-broadcast memory** (FORGE, 2605.16233): self-evolving textual memory without weight updates wins 1.7–7.7× over zero-shot on CybORG CAGE-2 across Gemini / Grok / Llama / Qwen — model-agnostic enough to drop into existing harnesses.
- **Argus moves the deep-research SOTA bar by ~25 points:** 86.2 BrowseComp with 64 parallel Searchers + a Navigator that maintains a shared evidence graph (vs. LongSeeker 61.5, OpenSeeker-v2 46.0). Compute-heavy but reproducible recipe with a 35B-A3B backbone.
- **Coding-agent context pruning lands a usable recipe:** LaMR (2605.15315) decomposes relevance into semantic-evidence + dependency-support rubrics; wins 12/16 multi-turn head-to-heads on SWE-Bench Verified / SWE-QA / LCC / LongCodeQA with 31% token savings.
- **Two foundational caveats:** RoPE provably can't preserve both locality and token discriminability in long contexts (2605.15514); and best computer-use agents end-to-end-complete <4% of professional SaaS workflows on the new SaaS-Bench (2605.15777).
- **Local-fit:** Darwin-28B-Opus (Qwen3.6-27B evolutionary merge, Apache 2.0) hits 88.89% on GPQA Diamond — but only via Stage-3 adaptive ensemble (~20× compute); single-shot is 74.75%. Quants available; M5 Max-friendly at Q4–Q6.

## Items

### 1. RecMem: Recurrence-based Memory Consolidation for Long-Running LLM Agents
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2605.16045
- **Authors / org:** Zijie Dai, Shiyuan Deng, Sheng Guan, Yizhou Tian, Xin Yao, Xiao Yan, James Cheng
- **Focus area:** Agent memory
- **What it is:** Memory pipeline that stores incoming turns in a "subconscious" embedding layer and only fires the LLM extractor when *sustained recurrence* of semantically similar interactions is observed (i.e., when a stable cluster forms). A semantic refinement pass recovers fine-grained facts the extractor would otherwise lose.
- **Why it matters for Justin's agents:** Eager LLM consolidation is exactly the bottleneck MEME measured at ~70× baseline cost on Opus 4.7. RecMem reports -87% token cost while *exceeding* the accuracy of three SOTA memory systems — directly applicable to companion-app memory loops where every consolidation call is real money. Pairs cleanly with mem0-class stacks if the recurrence trigger can be exposed as a config knob.
- **Action signal:** `try-now` (if code lands) / `compare` — sharpens [arxiv:2605.12477] MEME and [arxiv:2605.12493] LongMemEval-V2 by attacking the cost axis instead of the recall axis.

### 2. FORGE: Self-Evolving Agent Memory With No Weight Updates via Population Broadcast
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2605.16233
- **Authors / org:** Igor Bogdanov, Chung-Horng Lung, Thomas Kunz, Jie Gao, Adrian Taylor, Marzia Zaman
- **Focus area:** Agent memory / long-running autonomous loops
- **What it is:** Population-based protocol that converts failed agent trajectories into reusable textual memory (rules and/or few-shot examples), then broadcasts the best-performing memory across the population between stages. No gradient updates.
- **Why it matters for Justin's agents:** 1.7–7.7× over zero-shot, 29–72% over isolated Reflexion, major-failure rate driven to ~1% on a 30-step CybORG CAGE-2 network-defense task — replicated across four model families (Gemini, Grok, Llama, Qwen). Rules representation reportedly uses ~40% fewer tokens than alternatives. The model-agnostic story is the headline: this could sit on top of an MCP-tool stack without retraining and without commitment to any single backbone.
- **Action signal:** `track` (no code link surfaced); `compare` — population-broadcast adds a 10th memory-mechanism axis alongside SkillOS curated repo, Belief Memory, Constant-Context Skill Learning, etc.

### 3. DimMem: Dimensional Structuring for Efficient Long-Term Agent Memory
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2605.15759
- **Authors / org:** Wentao Qiu, Haotian Hu, Fanyi Wang, Jinwei Kong, Yu Zhang
- **Focus area:** Agent memory / local models
- **What it is:** Represents memories as "atomic, typed, self-contained" units with structured metadata fields, enabling dimension-aware retrieval and selective recall instead of raw-history storage.
- **Why it matters for Justin's agents:** 81.43% LoCoMo-10 / 78.20% LongMemEval-S with a 24% per-query token reduction on LoCoMo. The key data point: a fine-tuned **Qwen3-4B** runs the system above LightMem with GPT-4.1-mini on both benchmarks — strong evidence a 4B model is enough to drive structured-memory production loops if the storage schema does the lifting. Code released. Pairs naturally with grep-style retrieval per [arxiv:2605.15184].
- **Action signal:** `try-now` / `local-fit` — Qwen3-4B fits in <8 GB at Q4 on M5 Max and is the most credible "memory-driver" local-model story this week.

### 4. LaMR — Context Pruning for Coding Agents via Multi-Rubric Latent Reasoning
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2605.15315
- **Authors / org:** Jingjing Wang, Xiwen Chen, Wenhui Zhu, Huayu Li, Zhengxiao He, Feiyang Cai, Ana S. Carreon-Rascon, Xuanzhao Dong, Feng Luo
- **Focus area:** Context engineering / coding agents
- **What it is:** Decomposes "is this code relevant?" into two interpretable rubrics — *semantic evidence* and *dependency support* — and uses specialized CRFs + MoE gating to decide which sections to keep. Multi-rubric labels derived via AST analysis so no extra human annotation.
- **Why it matters for Justin's agents:** Wins 12/16 head-to-head multi-turn comparisons across SWE-Bench Verified / SWE-QA / LCC / LongCodeQA with **up to 31% token savings** on multi-turn tasks and **+3.5 Exact Match** single-turn. Concrete pattern for any Claude Code-style harness: AST-derived rubrics are auditable, MoE-gated relevance is cheap at inference, and the dependency-support signal is exactly what file-retrieval heuristics currently miss.
- **Action signal:** `try-now` (if released) / `compare` — orthogonal to [arxiv:2605.15184] "Is Grep All You Need?" — grep dominates on memory backend, but LaMR-style structured pruning still wins when the harness has to choose *which files* to load.

### 5. Argus: Evidence Assembly for Scalable Deep Research Agents
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2605.16217
- **Authors / org:** Zhen Zhang, Liangcai Su, Zhuo Chen, Xiang Lin, Haotian Xu, Simon Shaolei Du, Kaiyu Yang, Bo An, Lidong Bing, Xinyu Wang
- **Focus area:** Agent orchestration / reasoning
- **What it is:** Two-role architecture — Searcher (ReAct evidence-gatherer) and Navigator (maintains a shared evidence graph, verifies what's still missing, dispatches more Searchers). Navigator trained via RL; Searcher trained as standard ReAct. Scales 1 → 64 parallel Searchers without retraining; 35B-A3B MoE backbone.
- **Why it matters for Justin's agents:** Reports **86.2 BrowseComp** with 64 Searchers (vs. [arxiv:2605.05191] LongSeeker 61.5, [arxiv:2605.04036] OpenSeeker-v2 46.0, Tongyi DeepResearch 43.2) — claimed to surpass every proprietary deep-research agent benchmarked. Navigator context stays **under 21.5K tokens** even at 64 Searchers because the evidence graph is the shared substrate, not chat history. This is the cleanest implementation to date of the planner-as-graph-manager pattern.
- **Action signal:** `compare` — large leap over prior open-source SOTA; awaits independent reproduction at the 64-Searcher scale (the headline number is compute-heavy). Flagged below.

### 6. RoPE Distinguishes Neither Positions Nor Tokens in Long Contexts, Provably
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2605.15514
- **Authors / org:** Yufeng Du, Phillip Harris, Minyang Tian, Eliu A Huerta, Srikanth Ronanki, Subendhu Rongali, Aram Galstyan, Hao Peng
- **Focus area:** Context engineering (foundational)
- **What it is:** Theoretical proof that as context grows, RoPE-based attention loses both (a) locality bias — failure probability approaches 0.5 (random) — and (b) consistency in token-relevance ranking. Increasing the RoPE base parameter trades token discriminability for positional discriminability and *cannot preserve both*. Multi-head, multi-layer architectures are shown insufficient to overcome this.
- **Why it matters for Justin's agents:** Mechanistic foundation for the empirical decays already in the ledger ([arxiv:2605.12922] "Channel-transition" / GAR, [arxiv:2605.10828] "First Drop of Ink", [arxiv:2605.12978] consolidation-decay). Practical takeaway: stop expecting long-context to "just work" because the model nominally supports 1M tokens — RoPE-based models lose the ability to *find* the relevant span, not just to reason over it. Reinforces the case for compaction + grep + periodic goal re-anchoring over raw context dumping.
- **Action signal:** `track` — informs harness design choices (when to compact, when to re-anchor) rather than directly actionable.

### 7. SaaS-Bench: Can Computer-Use Agents Leverage Real-World SaaS to Solve Professional Workflows?
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2605.15777
- **Authors / org:** Kean Shi, Zihang Li, Tianyi Ma, Zengji Tu, Jialong Wu, Xinbo Xu, Qingyao Yang, Ruoyu Wu, Weichu Xie, Ming Wu, Jason Zeng, Michael Heinrich, Elvis Zhang, Liang Chen, Kuan Li, Baobao Chang
- **Focus area:** Evaluation / tools / computer-use agents
- **What it is:** 106 tasks across **23 deployable SaaS systems** in six professional domains; multimodal long-horizon execution with verification checkpoints measuring both task completion and partial progress.
- **Why it matters for Justin's agents:** Strongest evaluated model completes **fewer than 4% of tasks end-to-end**, with failure modes concentrated in planning, state tracking, cross-application context maintenance, and error recovery. Sharpens the picture from [arxiv:2605.10787] ComplexMCP (top frontier <60% on 300+ tools) and [arxiv:2605.12481] ToolCUA (46.85% OSWorld-MCP) by moving to *real* SaaS apps — and the gap widens. Honest baseline for anyone shipping CUA-style agents into actual enterprise workflows.
- **Action signal:** `track` — useful expectation-setting for federal-data-engineer use cases where the agent has to drive real tooling.

### 8. Darwin Family — MRI-Trust-Weighted Evolutionary Merging for Training-Free Reasoning Scaling
- **Source:** arXiv + Hugging Face blog
- **Link:** https://arxiv.org/abs/2605.14386 (paper) · https://huggingface.co/FINAL-Bench/Darwin-28B-Opus (model card)
- **Authors / org:** Taebong Kim, Youngsik Hong, Minsik Kim, Sunyoung Choi, Jaewon Jang, Junghoon Shin, Minseo Kim (VIDRAFT / FINAL-Bench)
- **Focus area:** Local models / frontier models / reasoning
- **What it is:** Training-free evolutionary weight-space merging of existing checkpoints. Three contributions: 14-dimensional adaptive merge genome (component-level + block-level), MRI-Trust Fusion that weights per-layer importance via learnable trust parameters, and an Architecture Mapper that allows Transformer × Mamba SSM crossover. Apache 2.0.
- **Why it matters for Justin's agents:** Darwin-28B-Opus is built on **Qwen3.6-27B with hybrid linear/full attention** (64 layers, 3:1 linear:full). Per the model card: GPQA Diamond **74.75% single-shot greedy → 83.84% majority-vote@8 → 88.89% adaptive ensemble (~20× compute)** — the headline 88.89% is real, but it's a Stage-3 ensemble result, not raw model capability. Single-shot 74.75% is still meaningfully above its Qwen3.6 parent and arrives without a single gradient step, which makes it the most credible "open-source merge keeps up with training" data point in months.
- **Action signal:** `local-fit` / `try-now` — see Local-model corner below.

## Local-model corner
**Model:** Darwin-28B-Opus — 27.6 B params, BF16 base (Qwen3.6-27B hybrid linear/full attention, 64 layers).

**Memory fit on M5 Max 64 GB:**
- BF16 native ~55 GB → too tight (no KV cache room).
- Q8_0 ~28 GB → comfortable with long-context KV headroom.
- Q5_K_M ~20 GB → ample headroom for 128K+ context KV cache.
- Q4_K_M ~16 GB → trivially fits, leaves room for a second small model alongside.
- 3 community quants already linked from the model card; GGUF flow via llama.cpp / Ollama / LM Studio / Jan is supported. Explicit MLX-format weights not yet listed — convert from BF16 with `mlx_lm.convert` if you want native MLX.

**Realistic tasks (not marketing):**
- Single-shot reasoning at the level of a strong non-frontier model (74.75% GPQA Diamond single-shot is roughly Qwen3.6-32B Thinking territory). Good drop-in for a local "second opinion" subagent in a Claude Code harness.
- Adaptive-ensemble mode (~20× compute) gets to 88.89% GPQA Diamond, but at ~20 tok/s expected on M5 Max for Q5 inference that's minutes per question — only worth it for offline batch reasoning (analysis pipelines, eval grading), not interactive coding.
- Hybrid linear/full attention should give it noticeably better long-context throughput than a pure-attention 27B at the same quant — practical implication: you can hold a longer codebase in-context before throughput collapses.
- Not a tool-use specialist by default — pair with [arxiv:2605.07112] Switchcraft-style router or [arxiv:2605.15315] LaMR context pruning before using it as the primary coding agent.

**How to run:**
- llama.cpp via Ollama (`ollama pull` once a community Q5_K_M GGUF is registered) — easiest path.
- LM Studio for GUI + KV-cache monitoring; useful for checking the long-context behavior the RoPE paper above predicts will degrade.
- For MLX-native speed, convert BF16 → MLX (Q5 quant) locally; expect ~10–15% throughput uplift vs. llama.cpp on M5 Max based on recent Qwen3.6 community benchmarks.

**Speed estimate:** No M5 Max-specific number published yet. Extrapolating from M4 Max community numbers on Qwen3.6-27B at Q5_K_M (~22 tok/s decode), expect **~28–35 tok/s decode / ~250+ tok/s prefill** on M5 Max for Darwin-28B-Opus at Q5_K_M. Reasoning-mode generation halves this in practice.

**Bonus local-fit:** the DimMem (item 3) Qwen3-4B fine-tune is the kind of "small specialist beside the big model" pattern Darwin-28B is begging for — Qwen3-4B at Q5 fits in <4 GB and could run the memory-driver loop while Darwin handles reasoning.

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:

- **Argus 86.2 BrowseComp vs. prior open-source SOTA** — [arxiv:2605.16217] reports **86.2** with 64 Searchers + Navigator on a 35B-A3B backbone, surpassing the previously tracked open-source frontier of [arxiv:2605.05191] LongSeeker (61.5 BrowseComp) and [arxiv:2605.04036] OpenSeeker-v2 (46.0 BrowseComp), and claimed to surpass every proprietary agent benchmarked. The mechanism (Navigator-managed evidence graph + parallel Searcher dispatch with Navigator context <21.5K tokens) is novel rather than a scale-only argument — but the 64-Searcher headline is compute-heavy and the open-source comparison points were typically run at much lower parallelism. **Status:** flag as `compare`; awaits independent reproduction at matched compute budgets. Sources: https://arxiv.org/abs/2605.16217 vs. https://arxiv.org/abs/2605.05191 vs. https://arxiv.org/abs/2605.04036.

- **Open empirical questions raised today:**
  - Does RecMem's recurrence-triggered consolidation evade the [arxiv:2605.12978] *consolidation-decay* failure mode, or does it just defer it? (RecMem only consolidates clusters, but it still consolidates.)
  - Does DimMem's typed-memory schema survive the [arxiv:2605.14498] multi-party / GroupMemBench failure mode where structural multi-speaker features get lost? (DimMem reports LoCoMo, not GroupMemBench.)
  - Do FORGE-style population-broadcast updates inherit the [arxiv:2605.08060] "Memory Curse" — i.e., does broadcasting the best-performing memory erode cooperative intent in multi-agent settings?
  - Darwin Family's headline 88.89% requires ~20× compute (adaptive ensemble). Is the single-shot 74.75% the honest comparable number for production deployment?
  - Does the RoPE provable-failure result imply any RoPE-based "long-context" model evaluation should report a *retrieval baseline* alongside its long-context number, the way KV-eviction work already does?
