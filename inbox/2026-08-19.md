## Items

### 1. Demystifying Agent Skills: Why They Work-Until They Don't
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.14036
- **Authors / org:** Zhiyuan Jiang / Fangrui Huang / Hanwen Xing / Xander Wu / Yipeng Gao / Rui Cao / Mengdi Wang / Shilong Liu / Yijiang Li — UC San Diego (HF org)
- **Focus area:** Agent skills + retrieval vs format
- **What it is:** Isolates representation, outcome annotation, retrieval difficulty, and cross-framework robustness. 8,135 trial records; 238 unique labels from 240 open-coded records; taxonomy of three categories / twelve skill-use modes. Skills beat Workflow Memory by **6.06 points** in matched comparisons. Procedural anchoring **65.7%** of skill cases vs explicit knowledge injection **4.5%**. Retrieval: pool 5→100, actual-use precision **29.6% → 3.3%**. Confusable distractors hurt offline identification, yet downstream success stays stable; exact ground-truth invocation is neither sufficient nor necessary. Skills fail under brittle assumptions, incompatible contexts, or insufficient adaptation. Submitted Aug 14; HF Daily Aug 19; abs verified this run. Code: github.com/zhiyuanjiang04/demystify-agent-skills
- **Why it matters for Justin's agents:** Direct counterweight to WikiSkill [arxiv:2608.27454] (Friday 08-28 digest). WikiSkill eval *injects* the skill; this paper shows that once the agent has to *find* it, precision collapses. Mitamaton / Claude Code skill files should be short procedural checklists, not knowledge dumps, and skill-pool growth needs a retrieval/gating layer — CaSKG [arxiv:2608.25500] is a candidate, not a solved problem. Outcome labels during skill creation matter once failures enter the pool.
- **Action signal:** `try-now` — rewrite 2–3 live SKILL.md files as procedural anchors; do not grow the skill pool without a retrieval test.

### 2. Agentic ESOpt: Fine-Tuning Long-Horizon LLM Agents with Minimal GPU Requirements
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.17310
- **Authors / org:** Zhi Zheng / Rongsheng Chen / Yunpeng Ba / Zhenkun Wang / Yee Whye Teh / Wee Sun Lee — NUS + Oxford
- **Focus area:** Agentic RL without backprop
- **What it is:** Evolution strategies as full-parameter agent FT at inference-level GPU memory. Black-box reward interface composes with prompt-space evolution (skill optimization, test-time compute). Trajectory-level parameter attribution, no reward decomposition across horizons. WebArena-Lite: full-parameter Qwen-3.5-27B **+6.69%** over the No Skill baseline. Test-time automatic heuristic design: online prompt–parameter co-evolution improves the matched baseline in **28 of 36** settings. Cosine decay on perturbation scale σ. Code: github.com/zz1358m/Agentic-ESOpt. Submitted Aug 18 (v2 Aug 21); abs verified.
- **Why it matters for Justin's agents:** Backprop-free agent training at inference GPU memory is the 64GB-class path if you ever want to specialize a local agent without a GRPO cluster. The Trace2Skill / SkillOpt family is the prompt-space half; ESOpt is the weight-space optimizer that can sit next to it. Not a drop-in on M5 Max (NVIDIA GPU numbers), but the "compose ES with skill evolution" recipe is portable.
- **Action signal:** `compare` — against OpenForgeRL / Agent Lightning if you ever train a local policy; skip until you have a reward.

### 3. FreeToken: Efficient Edge-Native MoE Serving with Bandwidth-Adaptive Execution
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.16157
- **Authors / org:** Shuo Yang / Xiaoze Fan / Melissa Pan / Haocheng Xi / Zhe Wang / Shanlin Sun / Kurt Keutzer / Song Han / Matei Zaharia / Chenfeng Xu / Ion Stoica — UC Berkeley
- **Focus area:** Local / on-device MoE serving
- **What it is:** Edge-native MoE stack that treats a personal machine as a unified elastic inference platform (layout, expert residency, CPU–GPU execution, agentic state reuse, runtime memory). Continuously remaps computation and model state onto whatever CPU/GPU/bandwidth is actually there. **>20 MoE models** plus real coding/tool agents; hardware from an **8 GB laptop GPU** (35B) to a gaming desktop (**284B**) to a workstation GPU (**753B GLM-5.2**). Released at flashml.ai / github.com/FlashML-org/FreeToken. Submitted Aug 17; abs verified.
- **Why it matters for Justin's agents:** Headline 2026 local-MoE existence proof — but **designed for discrete NVIDIA GPU + host DRAM, not Apple unified memory / MLX**. Do not swap llama.cpp/MLX on the M5 Max for it. Compare the bandwidth-adaptive expert residency and agentic state-reuse ideas against MLX-LM paging; the 8 GB laptop result is the existence proof that 35B-class MoE can be interactive on modest VRAM if the runtime is right.
- **Action signal:** `try-now` on the ideas (state reuse at tool-call boundaries); `compare` before touching the Mac serving stack.

### 4. Agent Lightning v1.0: Towards Harnessed Agentic RL
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.17528
- **Authors / org:** Zhiyuan He / Siwei Zhang / Zhiwen Zhou / Yuqing Yang / Yu Kang / Yuge Zhang / Luna K. Qiu / Tin Yan Tsui / Jiahang Xu / Chong Luo — Microsoft
- **Focus area:** Harnessed agentic RL (production cousin of OpenForgeRL)
- **What it is:** ~**3,500 LOC** framework for harnessed agentic RL: the deploy-time harness owns the environment loop; the trainer sees only LLM request–response pairs. Challenges called out: retokenization, sample merging, advantage, loss normalization, backend scheduling. Coding: Qwen3.5-9B SWE-bench Verified **41.8% → 56.4% (+14.6)** on **6K** training examples. Also instruction-following and search agents; complete reproducible coding-agent RL pipeline. Docs: microsoft.github.io/agent-lightning/stable/. Submitted Aug 18; abs verified.
- **Why it matters for Justin's agents:** The production cousin of OpenForgeRL [arxiv:2607.21557]. If you ever train a Mitamaton / Claude Code skill policy, the unit of RL is the *harnessed rollout*, not a single completion. 3500 LOC is small enough to read. Complements ESOpt (item 2): Lightning is the harness-native trainer; ESOpt is the backprop-free optimizer.
- **Action signal:** `compare` — read the 3500 LOC before inventing a trainer; do not run RL this week.

### 5. Harness the Memory: A Holistic Evaluation of Memory Substrates in Memory Agents
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.15008
- **Authors / org:** Wei-Chieh Huang / Weizhi Zhang / Yuchen Wu / Yankai Chen / Eric Hanchen Jiang / Wooseong Yang / Yiwei Yang / Henry Peng Zou / Hanrong Zhang / Ying Nian Wu / Haolun Wu / Kai-Wei Chang / Philip S. Yu / Xue Liu / Aylin Caliskan
- **Focus area:** Agent memory substrates
- **What it is:** Controlled harness eval of dense/sparse indices, text records, structural stores, hierarchical stores, refinement-based memories, parametric updates, and activation-compatible context. Three backbones × four benches × **26** metrics. **No single substrate consistently dominates.** Broad retrieval helps long-context factual QA; excessive retrieval **hurts sequential decision-making** by shifting attention away from action-critical context. Substrates that win at moderate history can become costly or brittle at longer horizons. Motivates **substrate routing**. Submitted Aug 15; abs verified.
- **Why it matters for Justin's agents:** Direct design constraint for Mitamaton's notebook. Calendar/QA retrieval wants read-broad memory; day-admin *action* wants write-deep distilled strategies. Dumping more context into the agent loop is the wrong default — this is the quantitative version of "notebook as curated state, not append-only log." Pairs with MemTrapBench (Friday) on the "retrieved memory can hurt" axis.
- **Action signal:** `compare` — route substrates per regime rather than picking one memory product.

### 6. HarnessRisk: A Lifecycle-Oriented Benchmark for Agent Harness Safety
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.17597
- **Authors / org:** Yajing Bai / Jinhao Duan / Jie Peng / Xianfeng Wu / Sijia Liu / Song Wang / Tianlong Chen
- **Focus area:** Agent / MCP harness security
- **What it is:** Six operational phases: Harness Configuration, Capability Extension, Runtime Operation, State Persistence, Action Control, Incident Recovery. **128** sandboxed cases; benign user objective + adversarial instruction in an untrusted workflow artifact. Metrics: Utility, ASR, Persistence, Detection. Three harnesses × six models × 14 configs: ASR **12.6%–80.9%**, Utility still **75.0%–97.6%**. **Harness Configuration is the most vulnerable phase on every harness.** Explicit risk recognition does not imply safe action (some configs detect in >90% of runs while retaining substantial ASR). Code: github.com/Baiyajing/HarnessRisk. Submitted Aug 18; abs verified.
- **Why it matters for Justin's agents:** MCP / Claude Code / OpenClaw stack is the attack surface, not just the model. SARA [arxiv:2608.27146] (08-28 digest) is observation-authorization; HarnessRisk says **config is the hole**. Treat harness YAML, MCP allow-lists, and skill-install paths as the security boundary. Detection dashboards will lie.
- **Action signal:** `compare` — audit Mitamaton / Claude Code config and MCP allow-lists as the first security pass.

## Conflicts & open questions
- **Skills vs WikiSkill eval protocol.** 2608.14036: retrieval precision collapses (29.6% → 3.3% at pool 100) and exact GT invocation is neither sufficient nor necessary. WikiSkill [arxiv:2608.27454] eval *injects* the skill. Both can be true — evolution helps when the skill is in context; retrieval is the unsolved half. CaSKG [arxiv:2608.25500] is a retrieval candidate, not a proof that retrieval is solved.
- **HarnessRisk vs SARA.** HarnessRisk: config is the hole, detection ≠ safety. SARA: observation-authorization. Complementary layers, not competing papers — flag so the vault does not collapse "agent security" into one mechanism.
