### 2. LongMINT: Evaluating Memory under Multi-Target Interference in Long-Horizon Agent Systems
- **Source:** arXiv (cs.CL, submitted May 18, 2026)
- **Link:** https://arxiv.org/abs/2605.18565
- **Authors / org:** Hyunji Lee, Justin Chih-Yao Chen, Joykirat Singh, Zaid Khan, Elias Stengel-Eskin, Mohit Bansal (**UNC Chapel Hill cluster** — Mohit Bansal is UNC; Stengel-Eskin and Chen are also UNC Bansal-group; affiliations not on abstract but cluster signature is clear)
- **Focus area:** Agent memory / Evaluation
- **What it is:** Memory benchmark targeting **multi-target interference under fact revision**. **15.6k QA pairs across contexts averaging 138.8K tokens (up to 1.8M)**, four domains: state tracking, multi-turn dialogue, Wikipedia revisions, GitHub commits. Two question types: single-target recall + multi-target aggregation. Tests 7 systems (vanilla long-context LLMs, RAG, memory-augmented agent frameworks). Headline: **avg 27.9% accuracy** across systems, **degradation strictly increases with number of intervening updates**, and **failures attribute to retrieval and memory construction, not reasoning capacity**.
- **Why it matters for Justin's agents:** Two specific implications. (a) **The interference axis is now formally tested** — prior memory benchmarks tested implicit conflicts (STALE 55.2%), multi-party belief tracking (GroupMemBench 46%), scale-induced usability loss (Qwen3-8B exceeds budget), consolidation-decay (54% prior wins lost). LongMINT adds **fact-gets-revised-then-asked-about-with-intervening-noise** as orthogonal failure mode 11. For Justin's companion app where users update preferences and goals across sessions, the 27.9% number is a concrete reliability ceiling. (b) **The "retrieval + construction, not reasoning" attribution** sharpens the production fix: don't pay for a bigger model, fix the memory write path. Pairs cleanly with [arxiv:2605.15184] (grep > vector on memory recall) and [arxiv:2605.12493] LongMemEval-V2 AgentRunbook-C (file-based memory 72.5% vs RAG 48.5%) — the three together argue that **the write path needs to record raw revision history, not consolidated state**, exactly the [arxiv:2605.12978] consolidation-decay fix.
- **Action signal:** `track` `compare` — **11th orthogonal memory failure mode** in the May 2026 taxonomy. Should be the next eval target after Justin's app supports preference updates across sessions.

### 3. EvoMemBench: Benchmarking Agent Memory from a Self-Evolving Perspective
- **Source:** arXiv (cs.CL, submitted May 18, 2026)
- **Link:** https://arxiv.org/abs/2605.18421
- **Authors / org:** Yuyao Wang, Zhongjian Zhang, Mo Chi, Kaichi Yu, Yuhan Li, Miao Peng, Bing Tong, Chen Zhang, Yan Zhou, Jia Li (affiliations not on abstract; cluster signature suggests HKUST / China industry mix; code released)
- **Focus area:** Agent memory / Evaluation
- **What it is:** Meta-benchmark for agent memory. Organizes the eval space along two orthogonal axes: **memory scope (in-episode vs cross-episode) × memory content (knowledge-oriented vs execution-oriented)**. Evaluates **15 memory methods** plus long-context baselines. Three headline findings: (a) **no single memory approach excels universally** across all four cells; (b) **retrieval-based methods are best for knowledge-intensive tasks**, **procedural / long-term memory works better for execution-oriented tasks when experience aligns with task structure**; (c) **long-context baselines remain highly competitive**, especially on in-episode tasks.
- **Why it matters for Justin's agents:** This is the cleanest decomposition we have for choosing a memory architecture for a real agent product, and it explicitly says "stop picking one global memory system." Concrete design pattern for Justin's stack: **route memory operations by axis before retrieval**. Cross-episode + knowledge → vector / RAG (or grep, per [arxiv:2605.15184]); cross-episode + execution → procedural skill library ([arxiv:2605.06614] SkillOS, [arxiv:2605.18401] SkillsVote — see item 5); in-episode + anything → long-context with goal re-anchoring ([arxiv:2605.14457] InsightReplay). The "no universal winner" finding **partially confirms** the implicit message of [arxiv:2605.13941] EvolveMem (architecture itself should be evolved per task), but argues a simpler static-routing approach captures most of the value if the route is right.
- **Action signal:** `compare` `try-now` — operational rubric for memory architecture decisions in any new agent. Pairs with the May 2026 memory-failure-mode taxonomy as the "what do I actually build?" companion to the "where does it break?" papers.

### 4. SocialMemBench: Are AI Memory Systems Ready for Social Group Settings?
- **Source:** arXiv (cs.CL, submitted May 18, 2026)
- **Link:** https://arxiv.org/abs/2605.17789
- **Authors / org:** Olukunle Owolabi (single-author; affiliation not on abstract; first publication under this name in this thread)
- **Focus area:** Agent memory / Evaluation
- **What it is:** Multi-party memory benchmark structured around five **social archetypes** (close friends, family, recreational groups, interest communities, acquaintances) × three size tiers (4–30 members). **430 personas, 7,355 conversation turns, 1,031 QA pairs.** Five named failure modes: single-stream conflation, temporal-state overwrite, entity merging at scale, missing cross-persona knowledge, **norm-individual conflation** (the new one). Headline numbers: **Gemini 2.5 Flash full-context: 0.721 on small networks**; **open-source frameworks Mem0 / LangMem / Graphiti / Cognee: 0.12–0.18**; **uncompressed retrieval: 0.345**. Two failure modes are addressed via research probes; three remain open.
- **Why it matters for Justin's agents:** Direct overlap with [arxiv:2605.14498] GroupMemBench from May 16, but with two important new angles. (a) **Social archetypes (not just speaker count)** — family vs acquaintance memory expectations differ substantially in failure modes; for Justin's companion-app product, this maps directly to the "the agent remembers who is in the user's inner circle vs outer circle" capability. (b) **The 0.12–0.18 number for Mem0/LangMem/Graphiti/Cognee is a hard floor on the current OSS memory layer for social use cases** — these are the same frameworks every indie companion-app builder is using as a default. Combined with GroupMemBench's "BM25 matches/beats most agent memory systems" finding from three days ago, the operational conclusion is: **don't ship a vector-based memory backend for social group features**. Use raw retrieval over file-based history or invest in custom architecture.
- **Action signal:** `compare` `try-now` — **12th orthogonal memory failure mode** in May taxonomy (norm-individual conflation specifically); reinforces [arxiv:2605.14498] GroupMemBench BM25-matches-most finding with a 6× wider performance gap.

### 5. SkillsVote: Lifecycle Governance of Agent Skills from Collection, Recommendation to Evolution
- **Source:** arXiv (cs.AI, submitted May 18, 2026)
- **Link:** https://arxiv.org/abs/2605.18401
- **Authors / org:** Hongyi Liu, Haoyan Yang, Tao Jiang, Bo Tang, Feiyu Xiong, Zhiyu Li (**Memtensor Research Group** — same cluster that has been publishing on agent-memory governance for the past few months)
- **Focus area:** Agent orchestration / Coding agents
- **What it is:** Three-stage governance framework for reusable agent skills. **Stage 1 — Collection & Curation:** profiles open-source code repos to assess environment requirements, quality metrics, verifiability before adding to skill library. **Stage 2 — Pre-Execution:** searches structured skill library for contextual guidance. **Stage 3 — Post-Execution:** decomposes trajectories into subtasks, attributes outcomes to skill use vs environment factors, evidence-gated updates. Headline numbers: **+7.9 pp on Terminal-Bench 2.0 (offline evolution, GPT-5.2)**; **+2.6 pp on SWE-Bench Pro (online evolution)**. 44 pages with 7 figures + 5 tables.
- **Why it matters for Justin's agents:** Direct sharpening of [arxiv:2605.06614] SkillOS (frozen executor + trainable skill curator with Markdown SkillRepo) along the **credit-attribution + evidence-gating** axis. The SkillOS pattern was "let the curator decide what goes in the repo"; SkillsVote constrains this with three governance gates that explicitly answer **what counts as evidence that a skill works**. For Justin's MCP companion app or coding-agent work, this is the practical recipe for letting the agent accumulate reusable skills without falling into the [arxiv:2605.12978] consolidation-decay trap — the evidence-gated update gate is exactly the missing piece. The +7.9 pp on Terminal-Bench 2.0 is the right ballpark of expected improvement for adding a governed skill layer to an existing harness.
- **Action signal:** `try-now` — concrete pattern reusable in any MCP harness with trajectory logging. Composes naturally with [arxiv:2605.13880] PREPING (pre-deployment synthetic-practice memory) — PREPING fills the initial library, SkillsVote governs its evolution.

### 6. Model-Adaptive Tool Necessity Reveals the Knowing-Doing Gap in LLM Tool Use
- **Source:** arXiv (cs.AI, submitted May 13 / revised May 17, 2026)
- **Link:** https://arxiv.org/abs/2605.14038
- **Authors / org:** Yize Cheng, Chenrui Fan, Mahdi JafariRaviz, Keivan Rezaei, Soheil Feizi (**University of Maryland cluster** — Soheil Feizi is UMD; per HF Daily attribution)
- **Focus area:** Tools & connectors
- **What it is:** Decomposes LLM tool use into two stages — **internal cognition** (does the model recognize a tool is needed?) and **execution** (does it actually invoke?) — and measures the gap between them. Hidden-state probing across four models. Headline numbers: **26.5–54.0% cognition-vs-execution mismatch on arithmetic tasks**, **30.8–41.8% on factual QA**. Mechanistic finding: **both cognition and execution signals are linearly decodable from hidden states, but their probe directions become nearly orthogonal in the late-layer / last-token regime** — meaning the model "knows" it should call but the late layers route around the call.
- **Why it matters for Justin's agents:** Direct mechanistic extension of [arxiv:2605.07990] (tool calling is linearly readable + steerable from logits). That paper said you could read tool *choice* from a single unit vector; this paper says you can also read tool *necessity* from earlier layers, and the bug is that necessity and choice live in nearly-orthogonal subspaces near the output. Two concrete operational implications. (a) **A pre-call hook that reads the cognition probe and reissues with an explicit tool-required system prompt is a free reliability gain** — 26.5–54% of arithmetic queries are currently in this gap. (b) **Hidden-state probes can serve as a runtime confidence signal** for whether the model is going to skip a needed tool call, similar to [arxiv:2605.06455] PrefixGuard but earlier in the pipeline. Pairs with [arxiv:2605.15041] CAST (when-to-reason-deeply from trajectory history) and [arxiv:2605.07112] Switchcraft (cross-model routing) as a third independent angle on the tool-use accuracy frontier.
- **Action signal:** `track` `compare` — mechanistic complement to [arxiv:2605.07990]; immediate research direction is whether the orthogonality gap closes with fine-tuning or whether it requires architectural changes.

### 7. EnvFactory: Scaling Tool-Use Agents via Executable Environment Synthesis and Robust RL
- **Source:** arXiv (cs.CL / cs.LG, submitted May 18, 2026)
- **Link:** https://arxiv.org/abs/2605.18703
- **Authors / org:** Minrui Xu + 14 collaborators (affiliations not on abstract)
- **Focus area:** Tools & connectors / Agent orchestration
- **What it is:** Pipeline that autonomously **explores and verifies stateful executable tool environments** from authentic resources, then synthesizes multi-turn conversations with **implicit user intents via topology-aware sampling**. Two design contrasts vs prior work: (a) verified executable environments instead of mocked sandboxes; (b) intent-conditioned trajectories instead of over-specified instruction sequences. From only **85 verified environments × 7 domains**, generates **2,575 training trajectories**. Headline numbers: **+15% on BFCLv3, +8.6% on MCP-Atlas, +6% on τ²-Bench / VitaBench** vs strong baseline.
- **Why it matters for Justin's agents:** Two operationally important features for Justin's MCP work. (a) **The "85 environments → 2,575 trajectories" yield ratio** is the right shape for indie-scale agent training: not "scrape the internet," but "verify a small set of high-quality environments and synthesize aggressively from them." Justin could plausibly verify 10-20 MCP servers manually and use a synthesis pipeline like EnvFactory to produce a fine-tuning corpus for a specialized local model. (b) **Topology-aware sampling produces intent-driven (not instruction-driven) queries** — this is exactly the failure mode that has made prior tool-use SFT data useless for production. The +15% BFCLv3 number is competitive with anything in the May 2026 tool-use literature without an order-of-magnitude data difference.
- **Action signal:** `try-now` `compare` — pairs directly with [arxiv:2605.13880] PREPING and [arxiv:2605.18401] SkillsVote on the "warm the agent before it sees a user" pattern. EnvFactory generates the trajectories; PREPING bootstraps the memory; SkillsVote governs the resulting skill library.

### 8. EPIC: Preference-Aligned Memory Construction for On-Device RAG ("From Volume to Value")
- **Source:** arXiv (cs.CL, submitted May 18, 2026 — ICML 2026)
- **Link:** https://arxiv.org/abs/2605.18271
- **Authors / org:** Changmin Lee, Jaemin Kim, Taesik Gong (affiliations not on abstract — cluster signature suggests Korean academic, code/data public)
- **Focus area:** Agent memory / Local & open models
- **What it is:** On-device RAG optimization for personal AI agents. **Core idea:** treat user preferences as compact personal context and aggressively prune memory storage around them, rather than storing all conversational history. Headline numbers across four benchmarks (conversations, debates, explanations, recommendations): **2,404× indexing-memory reduction**, **+20 pp preference-following accuracy**, **33× faster retrieval latency**, **<1 MB memory footprint**, **29.35 ms streaming-mode query latency**. Code + data released.
- **Why it matters for Justin's agents:** Most directly local-fit item of the day. The **<1 MB memory footprint + 29.35 ms latency** numbers mean this entire memory layer fits comfortably alongside any model on M5 Max — even a 70B Q4 model leaves ~64 GB - 40 GB = 24 GB headroom, and EPIC's index sits below the rounding error. For Justin's companion-app product, the **+20 pp preference-following accuracy at 2,404× less memory** is exactly the curve a local-first design needs: more memory was never the bottleneck, knowing what to keep was. Pairs operationally with [arxiv:2605.12357] δ-mem (8×8 online associative state) and [arxiv:2605.10870] DeMem (decision-centric rate-distortion forgetting) — three independent rate-distortion-flavored memory designs all landing within 10 days, each picking a different axis (δ-mem = generation-time corrections; DeMem = decision-conflict-triggered partition refinement; EPIC = preference-anchored compression at write time).
- **Action signal:** `try-now` `local-fit` — directly usable for M5 Max companion-app prototype; ICML 2026 acceptance signal raises confidence in reproducibility.

### 9. ZEDA: Post-Trained MoE Can Skip Half Experts via Self-Distillation
- **Source:** arXiv (cs.LG, submitted May 18, 2026)
- **Link:** https://arxiv.org/abs/2605.18643
- **Authors / org:** Xingtai Lv + 14 collaborators (**Tsinghua University** per HF Daily attribution)
- **Focus area:** Local & open models for Apple Silicon
- **What it is:** Post-training adaptation that converts already-trained static MoE models into **dynamic-active variants** — i.e. lets you serve at half the active experts without retraining from scratch. Two-stage self-distillation. Evaluated on **Qwen3-30B-A3B and GLM-4.7-Flash** across **11 benchmarks (math, code, instruction-following)**. Headline numbers: **>50% reduction in active compute with marginal accuracy loss**; **~1.20× end-to-end inference speedup** vs original; outperforms prior dynamic-MoE methods at the same accuracy. Conceptually similar to [hf-blog-2026-05-08-allenai-emo] EMO's "serve at 12.5% of experts" finding but applied post-hoc to existing models rather than requiring pretraining-time pooling.
- **Why it matters for Justin's agents:** Direct local-fit win for M5 Max. **Qwen3-30B-A3B at half active experts** drops effective inference compute roughly proportionally, and the ~1.20× speedup applies on top of any quantization. For Justin's M5 Max + 64 GB setup: Qwen3-30B-A3B Q4 sits at ~18 GB weights; ZEDA-adapted version doesn't change weights (so memory footprint identical) but cuts active-expert compute per token. Expected speedup on M5 Max sustained: Qwen3-30B-A3B Q4 today ~35-40 tok/s → ZEDA-adapted ~42-48 tok/s. Composable with [arxiv:2605.09649] learnable KV cache eviction. **The combination "ZEDA + KV cache eviction + InsightReplay [arxiv:2605.14457]" is now the production-frontier stack for long-context local coding agents on Apple Silicon** — three independent harness-side optimizations that each apply on top of the same Q4 weights.
- **Action signal:** `try-now` `local-fit` — waiting on weights/checkpoint release for Qwen3-30B-A3B-ZEDA, then directly runnable via MLX or llama.cpp.

## Conflicts & open questions

Cross-referenced against `_meta/claims-ledger.md`:

- **Item 4 (SocialMemBench) vs [arxiv:2605.14498] (GroupMemBench)**: not a conflict — overlapping but complementary. GroupMemBench tested 3+ speaker conversations with general queries (best agent memory 46%, BM25 matches/beats); SocialMemBench tests five social archetypes specifically (Mem0/LangMem/Graphiti/Cognee 0.12–0.18 vs full-context Gemini 2.5 Flash 0.721 — note different metric ranges). Operational conclusion is the same direction in both papers: **the OSS agent memory frameworks are substantially worse than uncompressed retrieval for multi-party / social settings**. Open empirical question: does Belief Memory [arxiv:2605.05583] or MemReranker [arxiv:2605.06132] close any of the SocialMemBench gap?

- **Item 3 (EvoMemBench "no universal winner") vs [arxiv:2605.13941] EvolveMem ("self-evolving architecture beats baselines")**: complementary, not contradictory. EvolveMem's argument is that the *configuration* should adapt; EvoMemBench's finding is that no *static configuration* is universally best. These compose — EvoMemBench provides the rubric (4-cell scope × content matrix) that EvolveMem's diagnosis loop could route across.

- **Open empirical question (items 2, 3, 4 combined)**: with three independent memory benchmarks landing in a single day — interference (LongMINT), meta-evaluation (EvoMemBench), social-archetypes (SocialMemBench) — and the prior accumulation of 10+ orthogonal failure modes in the May taxonomy, the next-meta-question is whether **any of the May 2026 memory-aware methods** ([arxiv:2605.05583] Belief Memory, [arxiv:2605.13941] EvolveMem, [arxiv:2605.15156] MeMo, [arxiv:2605.06614] SkillOS, [arxiv:2605.18401] SkillsVote, [arxiv:2605.18271] EPIC) move the LongMINT 27.9% or the SocialMemBench 0.12–0.18 numbers. None of the May memory papers have been run against either benchmark. The cross-evaluation matrix is the obvious next paper.

- **Item 1 (Anthropic acquires Stainless) vs prior MCP coverage**: not a conflict — vertical-integration signal that strengthens the operational case for committing to MCP as Justin's primary tool-connection layer. No prior ledger entry on the MCP business / ownership layer.

- **Items 6, 7 (knowing-doing gap + EnvFactory) vs [arxiv:2605.07990], [arxiv:2605.07112], [arxiv:2605.15041]**: all consistent and stack on the tool-use efficiency frontier. Five orthogonal angles now: pre-call cross-model routing (Switchcraft), logit-gap runtime monitor ([arxiv:2605.07990]), within-call reasoning-depth control (CAST), training-data synthesis (EnvFactory), and cognition-execution gap diagnosis (item 6).
