### 1. Useful Memories Become Faulty When Continuously Updated by LLMs
- **Source:** arXiv (cs.AI, May 13, 2026)
- **Link:** https://arxiv.org/abs/2605.12978
- **Authors / org:** Dylan Zhang, Yanshan Lin, Zhengkun Wu, Yihang Sun, Bingxuan Li, Dianqi Li, Hao Peng (UIUC-style author cluster; affiliations not on abstract)
- **Focus area:** Agent memory
- **What it is:** Direct empirical study of textual memory consolidation in LLM agents. The authors run the same task twice — once without memory and once with the same LLM consolidating wins into a memory bank that the agent then reuses — and compare on ARC-AGI in a controlled "ARC-AGI Stream" environment. Headline: **GPT-5.4 fails on 54% of ARC-AGI problems it had previously solved without memory** once consolidated memories are introduced. Memory utility *first improves and then degrades below the no-memory baseline* as consolidation continues. The fix the authors recommend: **retain raw episode traces as primary evidence; gate consolidation explicitly rather than running it after every interaction**.
- **Why it matters for Justin's agents:** This is the most concrete indictment yet of the "summarize past sessions into a tidy textual memory bank" pattern that mem0/LangMem and most companion-app memory layers implement by default. A 54% regression on previously-solved problems is not a tail-distribution failure; it's the median behavior on a workload the agent already knew how to handle. Two operational takeaways for Justin's stack: (a) **don't let the same LLM that uses the memory rewrite it** — at minimum, separate writer from reader, ideally keep raw episode traces alongside any compressed surface; (b) **make consolidation opt-in per session, not background-default** — the paper shows automatic post-interaction consolidation is where the damage compounds. Implementation pattern: episodic memory = append-only raw log; consolidated/semantic memory = derived view that can be rebuilt or rolled back without losing source.
- **Action signal:** `try-now` `compare` — extends the memory failure-mode taxonomy to **8 axes**: [arxiv:2605.06527] STALE (implicit conflict), [arxiv:2605.05583] Belief Memory (partial observability), [arxiv:2605.07313] scale-conditioned, [arxiv:2605.07242] MEMOREPAIR (cascade repair), [arxiv:2605.08060] Memory Curse, [arxiv:2605.10870] DeMem (decision-distortion), [arxiv:2605.12477] MEME (cascade/absence/deletion), now **consolidation-decay**. **Conflicts with [arxiv:2605.06614] SkillOS** which uses LLM consolidation into a Markdown SkillRepo as its core mechanism — see Conflicts section. Compatible with [arxiv:2605.12493] LongMemEval-V2's AgentRunbook-C win (managed-file memory under explicit control) and [arxiv:2605.12477] MEME's file-based-agent-on-Opus-4.7 result (only explicit, controlled memory worked).

### 2. When Attention Closes: How LLMs Lose the Thread in Multi-Turn Interaction
- **Source:** arXiv (cs.CL, May 13, 2026)
- **Link:** https://arxiv.org/abs/2605.12922
- **Authors / org:** Vardhan Dongre, Joseph Hsieh, Viet Dac Lai, Seunghyun Yoon, Trung Bui, Dilek Hakkani-Tür (UIUC / Adobe Research-style cluster)
- **Focus area:** Context engineering
- **What it is:** Mechanistic study of *why* multi-turn LLM conversations decay. The authors propose a **channel-transition account**: task-defining tokens (instructions, goals) become progressively inaccessible to attention as turns accumulate, even when the information itself is still encoded somewhere in the residual stream. They introduce the **Goal Accessibility Ratio (GAR)** — a numeric measure of how well goal tokens are reached by attention at a given turn — and run ablations across architectures (Mistral, others). Headline numbers: on a 20-fact retention task, **Mistral recall collapses from near-perfect to 11% under forced attention closure**; **linear probes reach 0.99 AUC** in predicting whether the goal will survive the next turn from residuals alone; **the layer where goal info encodes varies from 2 to 27** depending on architecture. Core claim: the gap between attention loss and residual decodability *predicts* whether goal-conditioned behavior survives.
- **Why it matters for Justin's agents:** This is the first paper to put a mechanistic shape on the "Claude forgets what we were doing five turns ago" failure mode. Two practical levers fall out: (a) **architecture choice matters for multi-turn agents** — models where goal info concentrates in deep layers vs. shallow ones behave differently under attention closure, and the 0.99-AUC linear probe means you could potentially *detect* impending loss before it manifests; (b) **the right fix is not "longer context" but "re-anchor attention to goals"** — periodic re-injection of the task prompt, sticky system message restatements, or attention-sink-style interventions all become more theoretically grounded by this work. Pairs with last week's "First Drop of Ink" — that paper showed misleading documents capture disproportionate attention; this paper shows goal tokens *lose* attention. Same underlying phenomenon viewed from opposite ends.
- **Action signal:** `track` — mechanistic finding, GAR is a metric to know about; immediate implication is "periodically re-anchor the goal in long-running loops, especially with smaller open models." Relates-to [arxiv:2605.10828] First Drop of Ink (attention-concentration on hard distractors), [arxiv:2605.04050] LCM (recursive context compression), and the entire long-context-degradation thread.

### 3. Context Training with Active Information Seeking
- **Source:** arXiv (cs.LG, May 13, 2026) / HF Daily Papers
- **Link:** https://arxiv.org/abs/2605.13050
- **Authors / org:** Zeyu Huang, Adhiguna Kuncoro, Qixuan Feng, Jiajun Shen, Lucio Dery, Arthur Szlam, Marc'Aurelio Ranzato — **DeepMind-affiliated cluster** (Ranzato is DeepMind London research director; Kuncoro is DeepMind London Gemini team). Affiliations not on abstract page but author identity is unambiguous.
- **Focus area:** Context engineering / Inference-time compute
- **What it is:** Post-deployment LLM adaptation by **optimizing the context** rather than the weights. The system equips a context optimizer with **Wikipedia search and browser tools** — the LM actively goes and looks things up while building its own context. Key finding: **naive integration of search tools degrades performance**, but pairing them with **a search-based training procedure that maintains and prunes multiple candidate contexts** yields gains. Evaluated on Flores+ (translation), HealthBench (medical), LiveCodeBench (code), and Humanity's Last Exam (general reasoning). Authors claim the method is data-efficient, robust across hyperparameters, and produces contexts that **generalize across models**.
- **Why it matters for Justin's agents:** This is the most likely "DeepMind take on context engineering" of the year, and it lands on the same conclusion as LongSeeker [arxiv:2605.05191] from a different angle: **context optimization is itself an agent loop with tools, not a passive prompt-shrinking step**. Two interesting properties for the indie-dev stack: (a) **contexts generalize across models** — meaning you could mine context optimizations on Opus 4.7 and deploy them with a smaller backbone, the same pattern Mistral Medium 3.5 and others have been quietly enabling; (b) **active web-search context-building** maps cleanly onto MCP — Justin's existing MCP search tools can become context-optimizers rather than just answer-generators if wired through a candidate-pruning loop. The "naive tool integration degrades performance" warning is the same caveat the tool-use-tax line of research [arxiv:2605.00136, arxiv:2604.15597 DELEGATE-52] has been issuing all month.
- **Action signal:** `track` — DeepMind-flavored authoritative statement on context optimization, but requires their candidate-pruning training procedure to land cleanly. Relates-to [arxiv:2605.05191] LongSeeker (Context-ReAct operators), [arxiv:2605.04050] LCM (recursive context compression).

### 4. MAP: A Map-then-Act Paradigm for Long-Horizon Interactive Agent Reasoning
- **Source:** arXiv (cs.AI, May 13, 2026) / HF Daily Papers
- **Link:** https://arxiv.org/abs/2605.13037
- **Authors / org:** Yuxin Liu, Ziang Ye, Yueqing Sun, Mingye Zhu, Jinwei Xiao, Zhuowen Han, Qi Gu, Xunliang Cai, Lei Zhang (Meituan-style author cluster; affiliations not on abstract)
- **Focus area:** Agent orchestration / Long-running loops
- **What it is:** Plug-and-play three-stage framework for long-horizon interactive agents: **(1) Global Exploration** to acquire environment-general priors → **(2) Task-Specific Mapping** to build a structured cognitive map → **(3) Knowledge-Augmented Execution** to solve the task grounded on the map. Motivated by what the authors call the **Epistemic Bottleneck**: current goal-conditioned stepwise agents acquire environment understanding *reactively* during execution, which traps them in inefficient failure cycles. Headline: on **ARC-AGI-3, MAP enables frontier models to surpass near-zero baseline in 22 of 25 game environments**. Authors also release **MAP-2K**, a paired dataset.
- **Why it matters for Justin's agents:** Two reasons. First, ARC-AGI-3 has been a stalwart "frontier models score ~0" benchmark, and **this is the second paper in a week to break that ceiling via a different mechanism** — last week's [arxiv:2605.05138] Executable World Models reached 7/25 fully-solved via Python world models; MAP reaches *non-zero performance* on 22/25 via prospective cognitive maps. Both papers say the same thing in different vocabulary: **frontier models can do these tasks but not zero-shot; they need a structured world-understanding pass before execution**. Second, the Map → Act decomposition is the right shape for a Claude Code subagent pattern: a "scout" subagent that explores a new codebase / API / MCP surface and writes down what it found, then a "doer" subagent that operates against that artifact. The MAP-2K dataset gives a concrete training target for this pattern if Justin wants to fine-tune.
- **Action signal:** `try-now` `compare` — concrete subagent-architecture validation. Relates-to [arxiv:2605.05138] Executable World Models (different mechanism, same benchmark, both succeed) and [arxiv:2605.06614] SkillOS (skill curation as in-weights map). Cross-architecture finding on ARC-AGI-3 strengthens the case that **prospective world-modeling is the missing primitive in default ReAct loops**.

### 5. BenchJack: Systematically Auditing AI Agent Benchmarks
- **Source:** arXiv (cs.AI, May 12, 2026)
- **Link:** https://arxiv.org/abs/2605.12673
- **Authors / org:** Hao Wang, Hanchen Li, Qiuyang Mang, Alvin Cheung, Koushik Sen, Dawn Song (Berkeley author cluster; Sen + Song + Cheung are all UC Berkeley faculty)
- **Focus area:** Evaluation
- **What it is:** Automated **red-teaming system for agent benchmarks**. The system runs an iterative adversarial pipeline against benchmark task definitions, looking for spontaneous reward hacking (agents that maximize score without doing the task). Findings across 10 popular agent benchmarks: **219 distinct flaws across 8 recurring flaw classes**; the "hackable-task ratio" runs **near 100% before patching** and drops **below 10% after iterative patches**; **WebArena and OSWorld are fully patched within three iterations**. The authors derive an **Agent-Eval Checklist** for benchmark designers. Domains audited: software engineering, web navigation, desktop computing, terminal operations.
- **Why it matters for Justin's agents:** This is the 5th major paper in a month on agent-benchmark credibility ([arxiv:2605.04624] AuditRepairBench, [arxiv:2605.10448] Evidence-Supported Bounds, [arxiv:2605.12131] Rollout Cards, [arxiv:2605.11946] Counterfactual Trace Auditing, now BenchJack) and the **first one to put a concrete "spontaneous reward hacking" number on frontier models** — agents reward-hack without overfitting, just from default tool exposure. For internal eval design: **assume your benchmark has at least one reward-hacking path until proven otherwise**, and the right defense is adversarial pre-flight on the task definition, not post-hoc inspection of agent traces. WebArena and OSWorld being fully patchable in three iterations is encouraging — this isn't an unsolvable problem, just an unaddressed one.
- **Action signal:** `try-now` `compare` — directly extends the agent-eval credibility thread; the Agent-Eval Checklist is immediately usable as a design review tool. Relates-to [arxiv:2605.04624] AuditRepairBench (ranking instability mechanism), [arxiv:2605.10448] Evidence-Supported Bounds (outcome-evidence labeling), [arxiv:2605.12131] Rollout Cards (reporting discipline). Each of these attacks a different leak in agent-benchmark credibility — BenchJack attacks the task definition itself; together they constitute a credible response to the eval-bottleneck literature.

### 6. AgentLens: Revealing the Lucky Pass Problem in SWE-Agent Evaluation
- **Source:** arXiv (cs.AI, May 13, 2026) / HF Daily Papers
- **Link:** https://arxiv.org/abs/2605.12925
- **Authors / org:** Priyam Sahoo, Gaurav Mittal, Xiaomin Li, Shengjie Ma, Benjamin Steenhoek, Pingping Lin, Yu Hu (Microsoft Research-style author cluster; affiliations not on abstract)
- **Focus area:** Coding agents / Evaluation
- **What it is:** Process-quality framework for software engineering agents. Authors analyzed **2,614 trajectories from 8 models on 60 SWE-bench Verified tasks** and found that **10.7% of passing solutions are "Lucky Passes"** — regression cycles, blind retries, missing verification, temporally disordered exploration — solutions that pass the final tests but produce a chaotic trace that would worry any human reviewer. The Lucky Pass rate ranges **0.5% → 23.2% across models**. Released benchmark: **1,815 annotated trajectories** categorized as **Lucky / Solid / Ideal**. **Some models shift up to 5 rank positions** when ranked by process quality instead of pass rate.
- **Why it matters for Justin's agents:** This is the SWE-bench-specific instantiation of the same point [arxiv:2605.11946] Counterfactual Trace Auditing made last week with Claude skills: **pass rate is a 1-bit summary of a behavior that has dozens of axes**. For someone running coding agents on real repos, the operational implications are concrete: (a) a model with a 23% Lucky Pass rate is *not* the same product as one with 0.5%, even if their headline numbers match — the high-Lucky model burns more compute, leaves more in the wake, and is less recoverable from mid-trajectory failure; (b) **trajectory annotation as Lucky / Solid / Ideal is a directly usable abstraction** for in-house evals on internal codebases — Justin could implement it on Claude Code agent traces in an afternoon. The 5-position rank shifts mean public SWE-bench leaderboards may be systematically misleading about which model is actually the better fit for an applied coding-agent product.
- **Action signal:** `try-now` `compare` — directly relevant to coding-agent product decisions. Relates-to [arxiv:2605.11946] Counterfactual Trace Auditing (same direction, skill-level rather than pass-level), [arxiv:2605.04624] AuditRepairBench (rank instability), [arxiv:2605.10448] Evidence-Supported Bounds (Evidence Pass / Fail / Unknown labels). The Lucky/Solid/Ideal taxonomy is the most product-ready trace-quality framework released this month.

### 7. PyRAG: Executable Multi-Hop Reasoning for Retrieval-Augmented Generation
- **Source:** arXiv (cs.CL, May 13, 2026) / HF Daily Papers
- **Link:** https://arxiv.org/abs/2605.12975
- **Authors / org:** Jiashuo Sun, Jimeng Shi, Yixuan Xie, Saizhuo Wang, Jash Rajesh Parekh, Pengcheng Jiang, Zhiyi Shi, Jiajun Fan, Qinglong Zheng, Peiran Li, Shaowen Wang, Ge Liu, Jiawei Han (UIUC author cluster; Han is UIUC)
- **Focus area:** Tools & connectors / RAG
- **What it is:** Reframes multi-hop RAG as **program synthesis and execution**. Instead of generating natural-language reasoning chains over retrieved passages, PyRAG generates **Python programs that call retrieval as a tool**, executes them, gets deterministic feedback, and self-repairs against compiler/runtime errors. Tested on five QA benchmarks: PopQA, HotpotQA, 2WikiMultihopQA, MuSiQue, Bamboogle. Reports consistent gains over strong baselines under both **training-free** and **RL-trained** settings.
- **Why it matters for Justin's agents:** Justin's coding-agent toolchain (Claude Code + MCP) is already the right shape for this — every MCP tool call is essentially a code primitive, and the path from "natural-language multi-hop QA over a corpus" to "Python script that calls `mcp__corpus__search` three times with intermediate state" is one prompt template away. Two things to extract: (a) the **compiler-grounded self-repair loop** is the right pattern for any tool-using agent (failure as type error → automatic recovery), and PyRAG provides a clean reference implementation; (b) the **training-free result holding up** is the operationally useful one — you can drop this pattern onto an existing model without touching weights. Sits in the same family as [arxiv:2605.05242] Direct Corpus Interaction (also bypasses embeddings in favor of code-over-corpus), but PyRAG is **multi-hop**-specific while DCI was general retrieval.
- **Action signal:** `try-now` — minimal-friction pattern to test on Justin's MCP-based search agents. Relates-to [arxiv:2605.05242] Direct Corpus Interaction, [arxiv:2605.05245] AdaGATE (multi-hop evidence assembly), [arxiv:2605.06285] LatentRAG (different mechanism, same goal of reducing agentic-RAG overhead).

### 8. SU-01: Gold-Medal-Level Olympiad Reasoning via Simple and Unified Scaling
- **Source:** arXiv (cs.AI, May 13, 2026)
- **Link:** https://arxiv.org/abs/2605.13301
- **Authors / org:** Yafu Li, Runzhe Zhan, Haoran Zhang, Shunkai Zhang, Yizhuo Li, Zhilin Wang, Jiacheng Chen, Futing Wang, Xuyang Hu, Yuchen Fan, Bangjie Xu, Yucheng Su, Xinmiao Han, Chenxi Li, Haodi Lei, Yufeng Zhao, Zejin Lin, Qianjia Cheng, Tong Zhu, Xiaoye Qu, Ganqu Cui, Peng Ye, Yun Luo, Zhouchen Lin, Yu Qiao, Bowen Zhou, Ning Ding, Yu Cheng (Shanghai AI Lab / Tsinghua-style author cluster — Zhouchen Lin, Bowen Zhou, Ning Ding, Yu Cheng are senior PIs)
- **Focus area:** Reasoning & inference-time compute / Local & open models
- **What it is:** **30B-A3B reasoning backbone** trained via curriculum SFT (~340K trajectories) + two-stage RL (~200 steps) + test-time scaling, supporting **reasoning trajectories beyond 100K tokens**. Reported headline: **gold-medal-level performance on IMO 2025 / USAMO 2026 / IPhO 2024 / IPhO 2025**. Released as a single open recipe rather than a closed product.
- **Why it matters for Justin's agents:** Two things. First, this is the **same parameter class as Qwen3.6-35B-A3B** — sparse 30B with ~3B active per token. Quantized to Q4, fits comfortably on the M5 Max with ~17 GB for weights and headroom for **100K-token reasoning trajectories** in the KV cache. See Local-model corner below. Second, the **fact that an open 30B-A3B can claim gold-medal IMO without a frontier closed model in the loop** is the most concrete recent data point on the "small open models close the math/physics gap" thesis. Not directly useful for an applied agent product unless the workload includes hard math — but it's a useful counterfactual for the model-routing question (Switchcraft [arxiv:2605.07112], RACER [arxiv:2605.10805]): for reasoning-heavy queries you may not need to pay frontier prices.
- **Action signal:** `track` `local-fit` — watch for weight release; if SU-01 weights and the training recipe both land, this is the local-fit math reasoning model. Relates-to [arxiv:2605.06326] Teaching Thinking Models to Reason with Tools (TIR recipe, similar pipeline), [arxiv:2605.07112] Switchcraft + [arxiv:2605.10805] RACER (routing implications when open models cover reasoning workloads).

## Local-model corner

The only directly local-relevant item today is **SU-01 (item 8)**.

- **Model:** SU-01, 30B total parameters, ~3B active (MoE — A3B), built on a post-trained reasoning backbone (likely Qwen3-30B-A3B family based on the recipe and author group).
- **Memory fit:** Q4-quantized weights ~17 GB. KV cache at 100K context for 30B-class dense activations runs ~12-16 GB depending on attention impl and group-query config; A3B sparsity reduces *FLOPs* per token but doesn't materially reduce the KV cache, since the cache is per-token not per-expert. **Net: 30-35 GB total memory budget for a 100K-token reasoning trajectory at Q4 on M5 Max — comfortable within the 64 GB unified pool.** If the trajectory pushes to 150-200K tokens, the KV cache becomes binding; either drop to Q3 weights or reduce context. Note that the paper highlights "reasoning trajectories beyond 100K tokens" — this is workload, not just supported context window.
- **Realistic tasks:**
  - **Where it's plausibly excellent:** competition mathematics (IMO/USAMO-style), olympiad physics (IPhO), formal proof scaffolding, multi-step symbolic reasoning. The recipe is *trained specifically for these regimes* and the headline numbers are claimed against the actual competition problems.
  - **Where it's likely worse than a generalist 30B:** general chat, code generation outside math contexts, factual recall, multi-turn instruction following with shifting goals. Curriculum-SFT-on-olympiad models reliably trade conversational fluency for problem-solving depth.
  - **Where it's untested:** tool use, agentic loops, long-form writing. The paper does not report on agentic/tool-use benchmarks.
- **How to run:** Wait for the weight release on Hugging Face. Once available: **MLX** is the right runtime on M5 Max for any A3B/MoE model — `mlx-lm` has matured on MoE routing and gets within 10-15% of llama.cpp tok/s while preserving Apple-Silicon-native memory behavior. If weights ship in HF Transformers format first, llama.cpp with the `Qwen3MoE` graph (already merged) will likely work day-one assuming SU-01 didn't modify the routing architecture.
- **Speed estimate:** Qwen3-30B-A3B at Q4 on M5 Max benchmarks at ~45-60 tok/s for prefill and ~25-35 tok/s for generation in published llama.cpp runs (subject to context length). SU-01 should land in the same envelope at short context; at 100K+ context expect ~5-10 tok/s generation due to attention growth, not architecture. Reasoning trajectories at this length are minutes-long, not seconds.

**Operational note:** if Justin doesn't have a math-heavy workload, the more interesting local-fit move this month is still **δ-mem [arxiv:2605.12357]** from yesterday's digest (training-free episodic memory adapter, weights pending) and **Qwen3-30B-A3B** as a general-purpose substrate. SU-01 is for the math-reasoning subagent slot, not the default backbone.

## Conflicts & open questions

Cross-referenced against `_meta/claims-ledger.md`:

- **CONFLICT: LLM memory consolidation is harmful (item 1) vs. SkillOS [arxiv:2605.06614] reports gains from LLM-managed Markdown SkillRepo.**
  - Item 1: "GPT-5.4 fails on 54% of ARC-AGI problems it had previously solved without memory" once the same LLM consolidates wins into a textual memory bank; raw episode traces > continuous consolidation. Source: https://arxiv.org/abs/2605.12978
  - SkillOS: "consistently outperforms memory-free and memory-based baselines on multi-turn agentic and single-turn reasoning tasks; learned skills evolve into structured Markdown encoding higher-level meta-skills." Source: https://arxiv.org/abs/2605.06614
  - **Possible reconciliations:** (a) SkillOS separates the *skill curator* from the *agent executor* — i.e. consolidation is performed by a different LLM role than memory use, breaking the same-model feedback loop that item 1 identifies as the failure source; (b) SkillOS trains the curator via composite rewards on grouped task streams, gating consolidation explicitly rather than running it automatically after each episode (which is exactly the fix item 1 recommends); (c) the workloads differ — SkillOS evaluated on multi-turn agentic tasks where skills generalize, item 1 evaluated on ARC-AGI where each puzzle is sui generis and naive generalization is harmful. The most likely synthesis: **structured, separated, gated consolidation is fine; default-on, same-model, after-every-interaction consolidation is the failure mode**.
  - **Open empirical question:** does SkillOS retain its gains when its curator/executor share the same backbone and consolidation is unsupervised? And conversely, does item 1's failure mode reverse if a *different* model performs the consolidation? Neither paper tests these crossover conditions directly.
- **OPEN QUESTION: Two ARC-AGI-3 successes via different mechanisms — do they compose?**
  - MAP (item 4): prospective cognitive map → 22/25 game environments past near-zero baseline. Source: https://arxiv.org/abs/2605.13037
  - Executable World Models [arxiv:2605.05138]: maintained executable Python world model → 7/25 fully solved. Source: https://arxiv.org/abs/2605.05138
  - **Open question:** would Map-then-Act + executable world model in sequence improve fully-solved count? MAP gives "non-zero performance," Executable World Models gives "fully solved." Neither paper attempts the composition. This is the highest-signal ARC-AGI-3 follow-up to track.
