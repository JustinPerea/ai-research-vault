# AI Research Digest — Monday, August 10, 2026

## TL;DR
- **DCAS** [arxiv:2608.06113] explains a failure Justin will hit the first time he fine-tunes an open model on OpenHands trajectories and then runs it under Claude Code: scaffold-specific *planning structure* is what overfits. Untrained bases do not show the gap. DCAS is a backend-substitution layer that routes any CLI scaffold ↔ any model without editing the scaffold. A small set of DCAS-collected planning-aware trajectories, trained under *one* scaffold, transfers to the others; explicit vs implicit planning are separable in the data.
- **Evo-Bench** [arxiv:2608.09096] is the sibling of HarnessOpt-Bench (Fri) focused on *intrinsic* harness-evolving capability across Search / Office / General. Construction uses auxiliary-task evolution to keep only tasks that actually move with the harness, then sensitivity-aware splits. Nine models: top absolute gains **+16.6**, approaching human-engineered baselines. Autonomous evolution beats a hand harness on General, excels on Search, **struggles on Office**. Early saturation is common; evolved harnesses transfer to other policy models.
- **SWE-Bench ProMax** [arxiv:2608.09802]: 170 expert-curated multilingual refactoring instances (Py / Java / TS / Go / C / C++ / Rust), mean **11.4 files / 261.6 LOC**, issue text rewritten from scratch, tests hand-reviewed against the "60% of unsolved SWE-bench Verified tests are flawed" audit. Best frontier + scaffold: **41.2%** resolve. Unsaturated. Dataset: huggingface.co/datasets/swe-bench-promax/SWE-Bench-ProMax.
- **Macaron-V1** [arxiv:2608.09819] (Mind Lab) is the open-weight drop: Mixture-of-LoRA on a frozen base, one LoRA per turn (chat / agent / coding / GenUI). Flagship **Venti** = 744B GLM-5.2 + 4 LoRAs (~748B). **Tall** = Qwen3.6-35B-based **50B**, aimed at local deployment. Recursive model–harness co-design under an external contract; compounding continual-learning gains still an open question. Local-model corner: Tall is the 64 GB candidate, not Venti.

## Items

### 1. DCAS: Decoupling CLI Agent Scaffolding to Internalize Planning across Scaffolds
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.06113
- **Authors / org:** Kishanthan Thangarajah / Boyuan Chen / Ahmed E. Hassan
- **Focus area:** CLI coding agents + scaffold transfer
- **What it is:** Open coding-agent post-training has converged on OpenHands trajectories. Models fine-tuned there score well under OpenHands and drop under any other scaffold; untrained bases do not show that split, so the gap is fine-tuning-induced. Load-bearing hypothesis: planning structure — *explicit* (pre-execution plan as a first-class artifact) and *implicit* (conventions that shape the loop). DCAS is a backend-substitution interception layer: any CLI scaffold ↔ any backend, scaffold unmodified, for cross-scaffold eval and planning-aware data collection. Plan-source intervention: planning quality is high-leverage, gains exceed the cross-scaffold drops. A model fine-tuned on a small DCAS-collected planning-aware set under one scaffold gains on the non-training scaffolds; the two senses of planning are separable in the training data.
- **Why it matters for Justin's agents:** If a local Qwen / GLM is trained on OpenHands (or any one scaffold) and then dropped under Claude Code, DCAS predicts a silent regression that the base model would not have shown. Two uses: (1) **do not fine-tune the 30B-A3B on a single-scaffold corpus** without a DCAS-style cross-scaffold check, (2) if you *do* train, collect trajectories that force explicit planning rather than OpenHands conventions. DCAS as a piece of infra is also how you A/B Claude Code vs OpenCode vs Pi without rewriting any of them.
- **Action signal:** `compare` — before any local-model SFT on coding-agent traces, run the same 10 tasks under Claude Code and one other scaffold; if the SFT model drops and the base does not, you have the DCAS gap.

### 2. Evo-Bench: Can Language Models Improve Agent Harness?
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.09096
- **Authors / org:** Lisheng Huang / Chen Yang / Hao Zhou / Huatong Song / Zongchao Chen / Ran Le / Yang Song / Wayne Xin Zhao / Tao Zhang
- **Focus area:** Harness evolution (capability benchmark)
- **What it is:** Isolates harness-evolving ability from base-model strength and from task-specific overfitting. Harness-guided construction: auxiliary-task evolution finds tasks that actually move when the framework improves; sensitivity-aware stratified split for cross-suite generalization. Domains: Search, Office, General. Nine frontier + open-weight models. Top models: absolute gains up to **16.6**, approaching human-engineered baselines. Autonomous evolution outperforms a hand harness on General and does well on Search; **Office** (specific processing workflows) is the failure mode. Temporal anomalies include early saturation. Synthesized harnesses transfer as reasoning structures to other policy models.
- **Why it matters for Justin's agents:** Office is Mitamaton's world (calendar, docs, mail). The paper's own split says that is where autonomous harness evolution *loses*. So: let Claude Code evolve Search / coding harnesses; keep Office / day-admin harnesses human-edited and evaluation-gated (HarnessOpt-Bench protocol). The transfer result is the optimistic half — a harness evolved on one model can be dropped onto local Qwen.
- **Action signal:** `compare` — run one Office-like Mitamaton skill through an autonomous edit loop *and* a human edit; expect the paper's Office failure to show up.

### 3. SWE-Bench ProMax: Benchmarking Agents on Large-Scale Multilingual Code Refactoring
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.09802
- **Authors / org:** Yuling Shi / Jinghan Xu / Kelin Fu / Wenhao Zeng / Shilin He / Lei Zhang / Yue Liu / Zelin Zhao / Terry Yue Zhuo / Jialun Cao / Siyu Ye / Tianyu Liu / Kai Cai / Shing-Chi Cheung / Xiaodong Gu
- **Focus area:** Coding-agent evaluation (refactoring)
- **What it is:** Response to SWE-bench saturation + the audit that ~60% of unsolved Verified instances have flawed tests (too narrow or too broad) and that frontier models can reproduce gold patches from training data. 170 expert-curated refactoring instances from real commits, seven languages. Issue descriptions rewritten from scratch; tests hand-reviewed; low-complexity / single-file work filtered. Mean **11.4 files, 261.6 lines** per instance. Two agent scaffolds × frontier models: best resolve rate **41.2%**. Dataset: https://huggingface.co/datasets/swe-bench-promax/SWE-Bench-ProMax
- **Why it matters for Justin's agents:** This is the honest Claude Code eval once SWE-bench Verified stops moving. Refactoring (behavior-preserving, many files) is closer to "clean up this module" than to "fix this fail." 41.2% ceiling means a personal 10-instance refactoring set will not saturate this quarter. Use it when claiming a harness or model swap "won."
- **Action signal:** `compare` — replace or supplement SWE-bench Verified with a 10-instance ProMax-shaped personal set (multi-file, tests you trust) for Claude Code A/Bs.

### 4. Macaron-V1: Towards Open Continual Learning with Self-Improvement and Mixture-of-LoRA
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.09819
- **Authors / org:** Mind Lab (Vin Bo, Asher Cai, Jingwei Cao, Song Cao, et al.)
- **Focus area:** Open agent models + local Mixture-of-LoRA
- **What it is:** Open agent-model family for experiential intelligence. Two system goals. **Adaptation:** recursive improvement of versioned model–harness pairs, experience evaluated under an external contract, successor built from that. **Collaboration:** Mixture-of-LoRA — freeze the base, compose specialist LoRAs, pick one LoRA per user turn. Macaron-V1-Venti: 744B GLM-5.2 + four LoRAs (chat / agent / coding / GenUI), ~748B. Macaron-V1-Tall: Qwen3.6-based **50B**, same design, aimed at local deployment. Supporting stack: UI4A GenUI harness, stateful action substrate, versioned Harness Context Protocol contract, MindForge agentic RL, MinT post-training, LongStraw long-context RL. Evaluated on Personal Intelligence, GenUI, and general benchmarks vs frontier baselines. Authors flag compounding continual-learning and collective-intelligence gains as still open.

#### Local-model corner
Tall (50B, Qwen3.6 base + 4 LoRAs, one active per turn) is the 64 GB-class object; Venti is not. MoL is the interesting local primitive: keep a frozen Qwen3 / GLM local base and swap a small adapter per turn rather than loading a 50B specialist each time. Do not treat the paper as a measured "Tall beats Qwen3-30B-A3B on Mitamaton" result — those numbers are not in the abstract we verified.

- **Why it matters for Justin's agents:** Pattern, not a download-tonight mandate: **frozen local base + turn-routed LoRAs + versioned harness contract.** That is a cleaner 64 GB story than one ever-growing merged model. The external-contract evaluation is the PAST-Bench / HarnessOpt-Bench lesson applied to weight updates. Wait for independent Tall numbers on a personal set before displacing Qwen3-30B-A3B.
- **Action signal:** `track` — watch for Tall weights + a Personal Intelligence score that names the baseline; the MoL routing idea is stealable now without their checkpoint.

## Conflicts & open questions
- **Conflict flagged:** Evo-Bench's "autonomous harness evolution wins on General/Search, loses on Office" is the scope condition HarnessOpt-Bench (Fri) and HSI (Sun) did not draw. Using those Friday/Sunday gains as a reason to auto-evolve Mitamaton's *day-admin* harness would be a misread. Office stays human-gated.
- **Convergent with DCAS + Replay Gap (Sat):** both say the eval/training *scaffold* is load-bearing. DCAS is about training-scaffold lock-in; Replay Gap is about eval-scaffold fantasy. Together: train and eval live, on more than one harness.
- **Open question vs Macaron:** Mixture-of-LoRA "one adapter per turn" vs Claude Code's "one skill retrieved per turn" — same routing idea at different layers. Uncompared.
