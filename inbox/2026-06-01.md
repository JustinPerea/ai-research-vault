# AI Research Digest — Monday, June 1, 2026

## TL;DR
- **Two-pronged push on the "context-and-memory-as-policy" axis.** **[arxiv:2605.31075] TaskMem** (ByteDance Seed) introduces a learnable *task-focused memorization policy* on a streaming Qwen3-VL-30B-A3B backbone — two-phase training (Phase 1 = how to memorize, Phase 2 = post-deployment adapter learning what to memorize). **+6.3% / +7.0% / +5.3% VQA on streaming-reformulated VideoMME / EgoLife / EgoTempo** where the agent must answer using only memory, not raw video. **[arxiv:2605.30785] AdaCoM** (Renmin / Alibaba) trains an *external* LLM via end-to-end RL to manage a **frozen agent's context** through flexible modification actions — the first paper to treat context management as a *separable, portable* policy rather than something baked into the agent itself. Surfaces a structural "Fidelity-Reliability Trade-off": higher-performing agents benefit from higher-fidelity preservation, lower-performing ones need aggressive compression to stay in the reasoning regime.
- **First multi-step trojan attack benchmark for local agentic harnesses.** **[arxiv:2605.31042] ClawTrojan + DASGuard** documents a new attack class: an injection planted in a file or tool output, *written by the agent into workspace state*, then read and executed in a later session — no individual step is malicious in isolation. **95.5% ASR on GPT-5.4 in an OpenClaw-style simulated workspace vs. near-zero ASR for existing single-turn prompt-injection attacks**. DASGuard mitigates by scanning control-like text in sensitive local files and tracing origin to a trusted source. Directly relevant to anyone running Claude Code / Cursor / Aider over a persistent workspace.
- **MAVEN turns lightweight verification into the agentic-tool-calling cost story.** **[arxiv:2605.30738]** is a symbolic reasoning scaffold (structured decomposition + intermediate verification + adaptive tool orchestration) that **lifts GPT-OSS-120b from 48% → 71% accuracy on MAVEN-Bench without any training**, and reports competitive results with frontier proprietary models at ~10% the cost on BFCL v3 / TauBench / Tau2Bench / AceBench. Open-weight + scaffold + verification > closed-weight model is now a repeatable recipe.
- **Two new pieces of evidence that long-horizon agent reliability degrades non-trivially with turn count and tools don't paper over it.** **[arxiv:2605.30434] LongDS-Bench** (Ant Group) — 68 Kaggle-derived data-analysis tasks across 2,225 turns; **best model 48.45% accuracy, a 47-point drop from early to late turns, 52–69% of all failures are long-horizon errors, additional agent steps do not improve performance**. **[arxiv:2605.30824] DecomposeR** (planner-centric RL with typed-DAG plans) adds **+5.1–8.0 points on deep-research benchmarks with a Qwen3-8B backbone** by making the plan itself the unit of reward. The LongDS finding directly extends the DELEGATE-52 (May 10) + tool-use-tax (May 4) cluster — third independent confirmation that the bottleneck is *state maintenance*, not interaction budget or tool count.
- **Reasoning-trace economics gets a sharper knob.** **[arxiv:2605.30832] SLAT** (Segment-Level Adaptive Trimming) shows CoT inefficiency *concentrates in high-probability segments with low marginal utility* — token-uniform penalties suppress useful reasoning alongside redundancy. RL-trained segment-level trimming gives **50% reasoning length reduction at competitive accuracy** and a superior accuracy-efficiency Pareto frontier. Mechanistic refinement of the response-level AEM (May 4) and milestone-level BEACON (May 8) axes.

### 1. TaskMem — Task-Focused Memorization Policy for Multimodal Agents
- **Source:** arXiv (submitted May 29, 2026)
- **Link:** https://arxiv.org/abs/2605.31075
- **Authors / org:** Tao Zou, Yichen He, Tian Qiu, Yuan Lin, **Hang Li** (ByteDance Seed)
- **Focus area:** Agent memory / Local & open models for Apple Silicon
- **What it is:** A reinforcement-learning framework that treats memory *generation* (deciding what to write down from a streaming observation feed) as a learnable policy rather than a fixed rule. **Two-phase training paradigm:** Phase 1 = "learns *how* to memorize" by optimizing memory quality under fidelity requirements; Phase 2 = post-deployment, on-device — "learns *what* to memorize" by tuning an adapter on the base MLLM, using recent environment tasks to define a reward model that pulls the memorization policy toward task-relevant content. **Eval setup:** authors reformulate VideoMME, EgoLife, EgoTempo into streaming benchmarks where the agent processes observations online and must answer questions **using only its memory, with no access to raw video** — this isolates memory quality from retrieval-from-source. **Numbers:** built on **Qwen3-VL-30B-A3B**, TaskMem improves VQA accuracy by **+6.3% (VideoMME), +7.0% (EgoLife), +5.3% (EgoTempo)** over the appropriate fidelity-only baselines.
- **Why it matters for Justin's agents:** (a) **Phase 2 is the operationally interesting half** — it's *post-deployment adapter training* whose reward signal comes from the agent's actual environment, not a static dataset. For a companion-app or always-on assistant, this is the architectural pattern that lets the memory policy adapt to the user's actual usage patterns rather than guessing what's universally important. (b) Pairs structurally with **[arxiv:2605.21463] Mem-π** ("Adaptive Memory through Learning When and What to Generate", May 21) — Mem-π attacked the same when-and-what axis for single-agent text; TaskMem extends it to *multimodal streaming*. Two independent groups in 11 days argue that **memory write policy should be learned, not engineered** — the "what to memorize" question is becoming the central design lever, displacing the "how to retrieve" question that dominated 2024-2025 memory research. (c) Cross-references to a tension worth flagging: **[arxiv:2605.08060] Memory Curse** (May 11) found expanded accessible history *degrades* cooperation in 18 of 28 model-game settings. TaskMem's defense is precisely *selective retention* of task-relevant content, which is the right architectural answer to the Curse — but the paper does not test on the Memory Curse benchmark. **Open question for the ledger:** does a learned task-focused memorization policy actually neutralize the Curse, or only on cooperative-task subsets? (d) The base model — **Qwen3-VL-30B-A3B** (30B total, ~3B active MoE) — sits squarely in the M5 Max comfort zone (see Local-model corner).
- **Action signal:** `try-now` `compare` `local-fit` — Phase 1 weights are reproducible from public Qwen3-VL-30B-A3B + the streaming-benchmark recipe; Phase 2 adapter is a straightforward on-device RL loop. Cross-reference with [arxiv:2605.21463] Mem-π and [arxiv:2605.08060] Memory Curse in the claims ledger as the emerging *write-policy-as-learned-thing* cluster.

### 2. AdaCoM — Learning Agent-Compatible Context Management for Frozen Agents
- **Source:** arXiv (submitted May 29, 2026)
- **Link:** https://arxiv.org/abs/2605.30785
- **Authors / org:** Lu Yi, Runlin Lei, **Liuyi Yao**, Yuexiang Xie, Yuyang Li, Wenhao Zhang, **Zhewei Wei**, **Yaliang Li**, Jian-Yun Nie (Renmin University of China + Alibaba — Yaliang Li / Liuyi Yao = Alibaba Tongyi / AgentScope lineage)
- **Focus area:** Context engineering / Agent orchestration
- **What it is:** Reframes context management as an **external** policy problem. Prior work (LongSeeker, LCM, Context-ReAct, Constant-Context Skill Learning) all assume you can fine-tune the agent itself — which doesn't work for closed-source agents (Claude Code, Cursor) and bakes in a one-size-fits-all assumption. AdaCoM trains an **external LLM via end-to-end RL** to manage the context of a **frozen agent** through flexible modification actions (the abstract names "preserving task constraints and progress while pruning stale content" as the learned behavior). **Headline empirical finding — the Fidelity-Reliability Trade-off:** agents with higher vanilla ReAct performance benefit from *higher-fidelity* context preservation; lower-performing agents need *more aggressive* compression to stay within a reliable reasoning regime. Transfer experiments show AdaCoM "generalizes most effectively across agents with similar capability (measured by vanilla ReAct performance)" — i.e., one context manager per capability tier is a viable factoring.
- **Why it matters for Justin's agents:** (a) **This is the structurally cleanest answer to "how do I manage context for an agent I don't own,"** which describes every MCP / Claude Code / external-API deployment in Justin's stack. The external-policy framing means the *context manager* becomes a reusable component you can train once and slot in front of any frozen executor — analogous to how a router model sits in front of a frozen LLM. (b) The **Fidelity-Reliability Trade-off** is a publishable empirical finding in its own right and has a counter-intuitive implication: **swapping in a stronger executor without re-tuning the context manager can hurt you**, because the manager's compression aggressiveness was calibrated to the weaker model's tolerance. For a Claude Code 4.7 → 4.8 swap or a Sonnet → Opus swap, this means the harness's context management heuristics should be re-checked, not assumed to scale. (c) Pairs with the May 7–10 context-mgmt cluster — **[arxiv:2605.05191] LongSeeker** (5 atomic context operators trained *into* the agent), **[arxiv:2605.04050] LCM/Volt** (recursive compression *inside* a coding agent), **[arxiv:2605.05413] Constant-Context Skill Learning** (procedural context in the *weights*), and **[arxiv:2605.23296] Parallel Context Compaction** (May 25). AdaCoM is the **first to make context management explicitly external + transferable** — the cluster now has agent-side, weights-side, and externalized variants, but no published head-to-head benchmark. (d) The implementation pattern (small external LLM as context manager in front of a large frozen executor) is **directly the M5-Max-runs-the-manager-while-Claude-runs-the-task** architecture — a small local Qwen / Gemma context manager in front of remote Claude Code is the natural prototype.
- **Action signal:** `try-now` `compare` — the external-policy framing is implementable today as a wrapper around any harness; cross-reference with the existing context-management cluster in the ledger as the externalized-manager variant.

### 3. ClawTrojan + DASGuard — Persistent Multi-Step Trojan Attacks on Local Agent Harnesses
- **Source:** arXiv (submitted May 29, 2026)
- **Link:** https://arxiv.org/abs/2605.31042
- **Authors / org:** Jiejun Tan, **Zhicheng Dou**, Xinyu Yang, Yuyang Hu, Yiruo Cheng, Xiaoxi Li, **Ji-Rong Wen** (Renmin University — Dou + Wen, classical-IR-and-RAG cluster moving into agent security)
- **Focus area:** Tools & connectors / Coding agents / Long-running autonomous loops
- **What it is:** Defines a new attack surface specific to **local agentic harnesses** (Claude Code, OpenClaw, Cursor, etc.) where the agent has read/write access to files, tools, and persistent workspace state across sessions. **The attack:** the adversary embeds a prompt injection inside a file or tool output; the agent reads it during one task, stores it in workspace state (e.g., writes it to a notes file, scratchpad, or generated artifact), and then executes the planted instruction in a *later, unrelated* session. **No individual step is overtly malicious** — the attack only exists as a sequence — so step-isolated defenses miss it. **Benchmark:** ClawTrojan in an OpenClaw-style simulated workspace. **Numbers:** **95.5% Attack Success Rate on GPT-5.4** with multi-step trojan vs. **near-zero ASR for existing single-turn prompt-injection attacks on the same model**. **Defense — DASGuard:** scans control-like text in *sensitive local files*, traces its origin, and removes control content that does not originate from a trusted source. Reported to achieve "strong dynamic defense by combining runtime attack blocking with sanitized commits to the workspace."
- **Why it matters for Justin's agents:** (a) **This is the most actionable agent-security paper this month for anyone running coding agents over a persistent workspace.** The 95.5%-vs-near-zero gap shows existing prompt-injection defenses — Llama Guard 3, in-prompt instructions, AgentTrust-style call-level interceptors — are structurally blind to *write-now-read-later* attacks because every step inspects only the current call. The fix isn't a better single-step detector; it's an *origin-tracing* layer over workspace writes. (b) The attack model is **exactly the failure mode Anthropic Skills / MCP server configs are exposed to** — if Claude reads a malicious Skill description from a community repository and writes it into a local CLAUDE.md or settings file, the next session inherits the injection automatically. The threat exists today; ClawTrojan is the first benchmark that measures how reliably current defenses miss it. (c) Pairs cleanly with the **May 27 Redpanda Agentic Data Plane** ([arxiv:2605.29082]) — Redpanda's out-of-band metadata channel is the *infrastructure*-side answer (governance the agent cannot see); DASGuard is the *runtime*-side answer (origin tracing on file writes). The two are complementary layers, not competitors — origin tracing catches what the metadata channel doesn't enforce, and vice versa. (d) **Implementation:** DASGuard-style origin tagging on every file write is a small wrapper around any agent harness that writes to disk — annotate the write with the source URL / tool call that produced the content, refuse to execute control-like text whose origin is not on a trust allowlist. This is a one-week change in Justin's MCP-server stack.
- **Action signal:** `try-now` `compare` — implement origin-tagging on file writes in the MCP harness today. Add to claims ledger; cross-reference with [arxiv:2605.29082] Redpanda Agentic Data Plane (out-of-band governance) and [arxiv:2605.04785] AgentTrust (call-level interception) as the three-layer agent-security cluster.

### 4. MAVEN — Verification-Scaffolded Tool Calling Lifts Open-Weight Past Frontier at 1/10 Cost
- **Source:** arXiv (submitted May 29, 2026)
- **Link:** https://arxiv.org/abs/2605.30738
- **Authors / org:** Omkar Ghugarkar, Vishvesh Bhat, Muhammad Ahmed Mohsin, Asad Aali
- **Focus area:** Tools & connectors / Coding agents
- **What it is:** A **lightweight symbolic-reasoning scaffold** for agentic tool calling — three coupled mechanisms: **structured decomposition** (break a tool-use task into subtask graph), **adaptive tool orchestration** (route subtasks to tools), and **intermediate verification** (check each tool output against a typed expectation before committing). **Eval surface:** BFCL v3, TauBench, Tau2Bench, AceBench, **plus a new MAVEN-Bench for multi-step math/physics tool composition**. **Headline number:** on MAVEN-Bench, the scaffold **lifts GPT-OSS-120b from 48% → 71% accuracy with no fine-tuning** — purely an inference-time scaffold change. Reports "competitive results with proprietary frontier models" on the public benchmarks at **~10% the cost** using the open-weight backbone.
- **Why it matters for Justin's agents:** (a) **23 percentage points without fine-tuning is the right scale of result for the "scaffold > model" thesis** that's been gathering evidence all month (Switchcraft, PrefixGuard, AgentTrust, CONCAT, ATOM). MAVEN's specific contribution is the **intermediate-verification axis** — most scaffold papers attack routing (Switchcraft), monitoring (PrefixGuard), or topology (CONCAT). MAVEN attacks the *commit step* — don't pass a tool output forward until a typed check passes. This is the closest thing to a *type system for tool use* that's been published. (b) The **GPT-OSS-120b backbone** is the load-bearing detail. OpenAI's GPT-OSS-120b is a 120B-parameter open-weight model released this winter; MAVEN's claim is that this *specific open-weight backbone* plus scaffold matches Claude / GPT-5.4-class frontier on BFCL / TauBench / Tau2Bench. If reproduced independently, this is the strongest evidence yet that **the next-step in agentic-tool-calling capability lives at the scaffold layer, not the model layer**. (c) **The 1/10 cost number is the operationally interesting one** — for an MCP-driven companion app where tool calls dominate per-message cost, a verification-scaffold-over-open-weight architecture moves the unit economics from "frontier-API-bound" to "GPU-rental-bound." (d) Limitation: GPT-OSS-120b doesn't fit on M5 Max (>80GB at Q4), so the *local-inference* version of this result would need a smaller backbone — Qwen3-30B-A3B or Gemma-4-26B-A4B class. Whether the scaffold transfers to 30B-active or only to 100B-class is the next experiment.
- **Action signal:** `try-now` `compare` — implement the structured-decomposition + intermediate-verification primitives on top of an existing MCP harness; cross-reference with [arxiv:2605.07112] Switchcraft (routing), [arxiv:2605.04785] AgentTrust (call-level), and [arxiv:2605.06455] PrefixGuard (trajectory) as the four-axis scaffold cluster.

### 5. LongDS-Bench — Long-Horizon Data Analysis Fails at 48% Best, "More Steps Don't Help"
- **Source:** arXiv (submitted May 28, 2026)
- **Link:** https://arxiv.org/abs/2605.30434
- **Authors / org:** Kewei Xu, Xiaoben Lu, Shuofei Qiao, Zihan Ding, Haoming Xu, Lei Liang, **Ningyu Zhang** (Ant Group + Zhejiang — the same Zhejiang cluster behind MMPO and Meta-Team)
- **Focus area:** Evaluation / Long-running autonomous loops
- **What it is:** Real-world data analysis is iterative — explore, transform, plot, re-transform, model, iterate. Most existing agent benchmarks evaluate this as isolated short tasks. **LongDS-Bench** sources **68 multi-turn tasks from Kaggle notebooks** across six domains (Geoscience, Business, Education, others), totaling **2,225 interaction turns**. Tasks are specifically curated to require **state-evolution** — the average dependency span is **11.3 turns** between an action and the action that depends on it. **Numbers:** best frontier model reaches **48.45% accuracy**; performance declines by **~47 points from early-turn to late-turn questions**; **long-horizon errors account for 52–69% of total failures**; and crucially, **"additional agent steps do not necessarily improve performance"** — the bottleneck is maintaining correct analytical state, not interaction budget.
- **Why it matters for Justin's agents:** (a) **Third independent confirmation of "long-horizon reliability degrades non-trivially with turn count, and more tools/steps don't paper over it"** — joins **[arxiv:2604.15597] DELEGATE-52** (May 10: 25% content corruption in long delegated document edits; "tool use does NOT improve performance") and **[arxiv:2605.06635] AST-parser citation-eval** (May 8: factual accuracy drops ~42% as tool-call depth scales 2 → 150). Three different task domains (delegated editing / cited deep research / data analysis), three different benchmarks, same conclusion: **the late-turn collapse is the dominant frontier-agent failure mode**. (b) The "additional steps don't help" finding **directly contradicts the implicit assumption in autonomous-loop / heartbeat-pattern literature** — extending agents' runtime and giving them more tool calls is not a free lunch; without explicit state-maintenance machinery (memory write policies, structured plans, external context managers — see items 1, 2, 6), more steps means more drift, not more progress. (c) For Justin: this is the eval to run against any in-house long-running analysis agent. The Kaggle-notebook task structure is closest in shape to the federal-data-engineering use case — exploratory queries with state evolution across turns. (d) The **state-maintenance bottleneck framing** gives a sharper hypothesis than DELEGATE-52's "interaction length and distractor files worsen results" — LongDS specifies *which axis* matters most (dependency-span, not raw turn count or document size).
- **Action signal:** `try-now` `compare` — when code lands, run the in-house data agent on LongDS-Bench to get a baseline. Update claims ledger to extend the DELEGATE-52 / citation-decay cluster with LongDS as the third confirmation; flag the "additional steps don't help" as a quantified counter to naive heartbeat-pattern extensions.

### 6. DecomposeR — Planner-Centric RL with Typed-DAG Plans Adds 5.1–8.0 pts to Deep Research
- **Source:** arXiv (submitted May 29, 2026)
- **Link:** https://arxiv.org/abs/2605.30824
- **Authors / org:** Mustafa Anis Hussain, Xinle Wu, Yao Lu
- **Focus area:** Agent orchestration / Reasoning & inference-time compute
- **What it is:** Argues that flat-trajectory RL (the dominant deep-research training paradigm) can't credit-assign *plan structure* — only the final answer gets reward, so the planner's decomposition quality is rewarded only indirectly. DecomposeR represents research plans as **typed directed acyclic graphs**, where node types describe operation kinds (search, summarize, compare, etc.) and edges encode dependencies. **Two-stage training:** (1) optimize graph structure + query decomposition under a structure-aware reward; (2) train execution + synthesis conditioned on the produced plan. **Numbers:** **+5.1–8.0 points over comparable open-source baselines on long-form deep-research benchmarks** with a **Qwen3-8B backbone**.
- **Why it matters for Justin's agents:** (a) **First paper to make the plan itself the reward target, not just the answer** — this is the planner-side counterpart to the "answer-vs-trace" credibility cluster ([arxiv:2605.29087] Trace-Answer Dissociation, May 31; [arxiv:2605.12925] AgentLens Lucky Pass). Plan accuracy and answer accuracy are different things; rewarding only the answer is exactly the same epistemic mistake as judging only the answer in faithfulness evals. (b) **The typed-DAG framing is portable** — it's basically a structured logging schema for what a deep-research agent should be doing. Even without the RL training step, instrumenting an existing harness to emit typed-DAG plan traces gives you a *separable* signal you can score (and later RL against) independently from the final report. For Justin: a one-week harness-side change to emit DAG traces from any of his deep-research loops sets up future fine-tuning without committing to the full DecomposeR recipe. (c) The Qwen3-8B backbone is small enough to **run + fine-tune the planner locally** on M5 Max (8B at FP16 ≈ 16GB, leaves 48GB for KV + activations + optimizer state). (d) Pairs with **[arxiv:2604.27221] WideSearch** (May 4: bi-level orchestrator + parallel workers + shared workspace, 7.5× over second-best), **[arxiv:2605.05007] Uno-Orchestra** (May 7: learns decomposition depth + worker model + budget jointly), **[arxiv:2605.06642] StraTA** (May 9: top-down strategy abstraction). The four-paper cluster on structured / learned planning hasn't been head-to-head benchmarked yet — the next paper prediction is a unified deep-research orchestration benchmark that separates plan-structure quality from final-answer quality.
- **Action signal:** `try-now` — instrument deep-research loops to emit typed-DAG plan traces today; full DecomposeR RL recipe is `track` until code is released.

### 7. SLAT — Segment-Level Adaptive Trimming Halves CoT Length at Pareto-Optimal Quality
- **Source:** arXiv (submitted May 29, 2026)
- **Link:** https://arxiv.org/abs/2605.30832
- **Authors / org:** Jian Yao, Xiongcai Luo, **Ran Cheng**, **Kay Chen Tan** (Hong Kong PolyU / SUSTech evolutionary-computation lineage)
- **Focus area:** Reasoning & inference-time compute / Context engineering
- **What it is:** Existing CoT-length-reduction recipes use *token-uniform penalties* — a single global penalty per token, applied across the trace. SLAT's theoretical contribution: this is wrong because **inefficiency concentrates in high-probability segments with low marginal utility** (i.e., low-information confident filler — "let me think step by step…", "therefore we have…", etc.), while informative segments live in lower-probability higher-utility regions that token-uniform penalties indiscriminately punish. SLAT proposes a segment-level RL framework that **identifies and targets high-prob low-utility segments** specifically. **Numbers:** **50% relative reduction in reasoning length** at competitive accuracy; "superior accuracy-efficiency Pareto frontier" on standard reasoning benchmarks.
- **Why it matters for Justin's agents:** (a) **Mechanistically distinct from the response-level and milestone-level axes already in the ledger** — **[arxiv:2605.00425] AEM** (May 4: response-level entropy modulation, +1.4 pp SWE-bench) and **[arxiv:2605.06078] BEACON** (May 8: milestone-segmented temporal reward shaping, 92.9% ALFWorld) both operate at coarser granularity. SLAT's segment-level *information-theoretic targeting* (high-prob × low-utility) is a sharper knob that should *compose* with AEM and BEACON, not replace them. (b) **50% CoT length reduction matters at the unit-economics level** for any thinking-mode loop — a Claude Opus 4.8 think-mode session that emits 50% fewer reasoning tokens at the same answer accuracy is a direct 2× reduction in per-message cost on think-mode-dominated workloads. The same logic applies to local MLX inference on M5 Max where output-token throughput is the binding constraint. (c) Cross-references with **[arxiv:2605.09649] Learnable KV Cache Eviction** (May 12) — both attack the "reasoning produces too many tokens" problem, but at different layers (SLAT: which segments to *generate*; KV eviction: which generated tokens to *keep in cache*). Composable. (d) Limitation: the abstract doesn't name the specific benchmarks or model sizes tested, so the "50% reduction at competitive accuracy" headline is provisional until the PDF is read; the theoretical characterization (high-prob × low-utility = inefficiency) is the durable contribution either way.
- **Action signal:** `track` `compare` — strong theoretical framing; magnitude of practical win provisional pending benchmark specifics. Cross-reference with AEM, BEACON, and KV-eviction in the ledger as the four-axis CoT-economics cluster.

## Local-model corner

The two memory items above are directly relevant for M5 Max + 64 GB.

- **Model:** **Qwen3-VL-30B-A3B** (TaskMem base; ByteDance Seed)
- **Memory fit:** 30B total / 3B active parameters. At Q4_K_M GGUF, weights are ~17–18 GB; the multimodal vision encoder adds a few GB. KV cache for a long-context vision agent (~32K tokens, 30B class) lands in the 6–12 GB range under MLX. **Total: ~30–35 GB of unified memory**, leaving 25–30 GB headroom for OS + applications. Fits comfortably with budget for a context-management policy and a local-MCP-server alongside.
- **Realistic tasks:** **streaming-observation memory** (multimodal video / screen capture / sensor logs into selectively-retained text+image entries), **embodied or always-on companion agents** that need to keep "what the user is doing" state without re-watching raw footage. NOT a frontier-coding-agent base — Qwen3-VL-30B-A3B is comparable to Qwen3-30B-A3B on text but the value here is the vision-language pre-training, not the raw reasoning quality.
- **How to run:** **MLX** is the natural choice — `mlx-vlm` has Qwen3-VL pipeline support; the MoE layer benefits from MLX's unified-memory routing. `llama.cpp` GGUF is the fallback for systems without the vision-language path wired in.
- **Speed estimate:** Qwen3-30B-A3B text-only on M5 Max benchmarks in the **70–90 tok/s decode** range at Q4 on recent MLX builds; the Vision-Language variant adds image-token decode overhead but the active-parameter count (3B) keeps decode latency similar for text tokens.
- **Pairing with AdaCoM (item 2):** AdaCoM's *external* context-manager LLM is a natural fit for a smaller local Qwen3-4B or Gemma-4-E4B running on M5 Max in front of a remote Claude Code / Opus 4.8 executor — the manager edits context locally before forwarding to the cloud agent. This is the cleanest "local context manager + remote executor" architecture published this month. No code yet; harness-level prototype is implementable today.

**Cosmos 3 (NVIDIA, May 31)** is open-weight under OpenMDW 1.1 on Hugging Face but is **off-axis for Justin's agent work** — it's a physical-AI / robotics omnimodel (text/image/video/audio/action) for synthetic-data generation and robot policy training, not an LLM agent base. Parameter counts not yet listed; "Super" and "Nano" variants released, "Edge" coming. Worth tracking for the open-omnimodel benchmark direction (ranked first on Artificial Analysis, Physics-IQ, R-Bench, PAI-Bench), not for runnable use on M5 Max today.

TaskMem does not test against the Memory Curse benchmark. **Open question:** does a learned task-focused memorization policy actually move the Memory Curse number (cooperation degradation under expanded history), or only on the cooperative-task subset where its reward signal is well-defined? This is the highest-value unrun experiment in the current memory cluster — the Memory Curse, TaskMem, BeliefMemory ([arxiv:2605.05583]), and BeliefTrack ([arxiv:2605.30219]) are now four papers in the cluster with no head-to-head measurement.

- **Open empirical question (the four-axis tool-calling scaffold cluster):** **[arxiv:2605.30738] MAVEN** (intermediate verification) joins **[arxiv:2605.07112] Switchcraft** (routing across backends), **[arxiv:2605.04785] AgentTrust** (call-level interception), and **[arxiv:2605.06455] PrefixGuard** (trajectory-level supervised monitor) as four mechanistically distinct scaffold-layer interventions. None of the four are ablated against each other. The MAVEN claim (open-weight + scaffold ~ frontier-model at 1/10 cost) is the strongest argument yet that **the scaffold layer is doing most of the work in 2026 agentic tool-calling capability**, but the empirical decomposition — how much each of routing / interception / monitoring / verification contributes — has not been published. Next-paper prediction: a unified scaffold-cost benchmark.
