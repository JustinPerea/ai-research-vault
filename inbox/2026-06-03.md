## TL;DR
- **The "pedagogical paradox" — weaker code agents are better teachers.** **[arxiv:2606.03461] Terminal-Lego** (Huawei Noah's Ark + HKU + PolyU) finds **Qwen3-32B fine-tuned on DeepSeek-V3.2 trajectories generalizes substantially better than the same student trained on Claude Opus 4.6 trajectories**, despite Opus scoring higher standalone on Terminal-Bench 2.0. Mechanically distinct from this season's write/manage/decay memory cluster (TaskMem / AdaCoM / UCE / eMoT) — Sleep operates on the *parameters* layer, not the *external context store*; the two layers compose.

The first credible argument that the LLM-as-memory-compressor design (Mem0, LangMem-class systems) was solving a problem that didn't need an LLM.
- **Two production-grade local CUA + memory releases for M5 Max.** **Hcompany Holo3.1** (HF blog, June 2) ships a **0.8B / 4B / 9B / 35B-A3B-MoE** family with **Q4 GGUF for Apple Silicon** and the 35B-A3B variant hitting **79.3% AndroidWorld** (vs. Holo3 67%); the 4B/9B both hit 72%. **Holo3.1-9B Q4 + DMF (item 3) on a single M5 Max** is now a plausible production stack for private companion-app CUA. ### 1. Terminal-Lego — The Pedagogical Paradox & Harness Engineering (Qwen3-32B 24.3% Terminal-Bench 2.0 from 15.3k Trajectories)
- **Source:** arXiv (submitted June 2, 2026)
- **Link:** https://arxiv.org/abs/2606.03461
- **Authors / org:** Sidi Yang, Chaofan Tao, Jierun Chen, Tiezheng Yu, Ruoyu Wang, Yuxin Jiang, Yiming Du, Wendong Xu, Jing Xiong, Taiqiang Wu, **Lifeng Shang**, Xiaohui Li, **Ngai Wong**, **Haoli Bai** (Huawei Noah's Ark + HKU + HK PolyU — Lifeng Shang and Haoli Bai are Noah's Ark agent-systems leads)
- **Focus area:** Coding agents / Evaluation
- **What it is:** Investigates the standard assumption that a stronger code agent makes a better teacher for post-training, and finds it's wrong. The team builds **Terminal-Lego**, a scalable pipeline that converts multi-domain real-world issues into environment-verified agentic tasks, then runs a controlled comparison: same student (**Qwen3-32B**), same harness, same budget, two teachers — **Claude Opus 4.6** (higher standalone Terminal-Bench 2.0 score) vs. **DeepSeek-V3.2** (lower standalone). **Students fine-tuned on DeepSeek-V3.2 trajectories show significantly stronger generalization than students trained on Claude Opus 4.6 trajectories.** The attributed mechanism is **Environment-Grounded Supervision (EGS)** — trajectories that explicitly expose *inspect-act-verify* behaviors through harness-visible interactions teach robust problem-solving routines rather than fragile action sequences. Scaling result: **24.3% on Terminal-Bench 2.0 with only 15.3k trajectories**, matching prior SOTA that used **30× more data**. Framing: "Harness Engineering" — systematic design of environment-grounded interaction structures — is the new frontier for agent post-training, not outcome-matching against the strongest teacher.
- **Why it matters for Justin's agents:** (a) **Direct counter to a default heuristic in the field.** "Distill from the strongest model" has been the default cookbook for 18 months across SWE-bench distillations and CUA bootstraps. Terminal-Lego is the first head-to-head in a controlled harness showing this defaults to *worse* students on the generalization axis. The implication is the teacher-model spend (Opus distillation runs at $20–$50/M tokens) was buying you the wrong thing. (b) **The harness-visibility property is the actionable lever.** If you can either (i) instrument the harness so the model's *think → call → read → next-think* loop is recorded as explicit text (not just inputs/outputs), or (ii) prompt the teacher to verbalize the inspect-act-verify cycle, you capture the EGS pedagogical signal without changing the underlying teacher. For Justin's coding-agent work, this is a one-day instrumentation change on the Claude Code harness that should materially improve any distillation pipeline. (c) **15.3k trajectories on Qwen3-32B is M5-Max-tractable for inference, and budget-tractable for fine-tuning rentals.** 15.3k Terminal-Bench-grade traces × ~30k tokens each ≈ 460M tokens of supervision — a single overnight LoRA fine-tune on a rented 8×H100. For a federal-data-engineering domain, the implication is that a private domain-specific terminal/SWE agent is a sub-$5k project at this data efficiency. (d) **Composes with yesterday's [arxiv:2606.02031] OpenWebRL.** OpenWebRL = 0.4K SFT + 2.2K RL → 67% Online-Mind2Web at 4B. Terminal-Lego = 15.3K SFT → 24.3% Terminal-Bench 2.0 at 32B. Same data-efficiency thesis on two distinct agent substrates (web; terminal) from different research groups (Microsoft; Huawei) — pointing at: *small open-recipe post-training at 4B–32B beats throwing 50K-500K trajectories at the same base*. The 2026 CUA/SWE training curve has bent.
- **Action signal:** `try-now` `compare` — instrument any Claude Code distillation harness to emit the inspect-act-verify reasoning steps as visible text in the trajectory; cross-reference with [arxiv:2606.02031] OpenWebRL as the second small-recipe data-efficiency point.

### 2. Language Models Need Sleep — Knowledge Seeding + Dreaming as a Memory-Consolidation Paradigm
- **Source:** arXiv (submitted June 2, 2026)
- **Link:** https://arxiv.org/abs/2606.03979
- **Authors / org:** **Ali Behrouz**, **Farnoosh Hashemi**, **Vahab Mirrokni** (Google — Behrouz is the Titans / TTT-as-fast-weights / longer-memory line; Mirrokni is the long-running Google Research large-scale-ML PI)
- **Focus area:** Agent memory / Reasoning & inference-time compute
- **What it is:** Treats LLMs' lack of a continual-learning loop as the central memory failure, and introduces a **Sleep** paradigm that distills short-term in-context fragile memories into long-term parametric knowledge with replay, and recursively self-improves through a **Dreaming** loop. Two stages: (1) **Memory Consolidation via Knowledge Seeding** — an *upward distillation* process that combines on-policy distillation with RL-based imitation learning, taking the memories of a *smaller-self* and distilling them into a *larger network* with more capacity while preserving the knowledge. The directionality is the key novelty — most existing distillation pipelines move teacher → student, smaller; Knowledge Seeding moves accumulated experience → larger student, with the smaller self acting as the experience source. (2) **Dreaming** — the model uses RL to generate a curriculum of synthetic data to rehearse new knowledge and refine existing capabilities, *without human supervision*. Reported gains on long-horizon, continual learning, knowledge incorporation, and few-shot generalization tasks. The abstract does not report magnitude numbers (PDF-only), so the headline contribution is paradigmatic, not benchmark-headline, at this stage.
- **Why it matters for Justin's agents:** (a) **This is the parameter-layer memory paper the external-context-layer cluster has been missing.** TaskMem (write-time policy), AdaCoM (external manager), UCE (typed externalization), eMoT (utility-decay self-curation) — every one of the four recent memory primitives operates on an *external* store. Sleep operates on the *weights*. The two layers don't compete; they compose into the same architectural split as L1/L2 cache vs. RAM. (b) **The directionality of Knowledge Seeding (smaller-self → larger-student) is operationally relevant.** It's the *correct* shape for the small-local-LLM-as-memory-manager + remote-frontier-executor pattern — the small local LLM accumulates personal/task experience, and Knowledge Seeding distills that experience upward into your frontier-class fine-tune. For Justin's companion-app stack on M5 Max, this is the first published paradigm that gives a principled answer to "what should the personalization layer of a frontier-routed companion app actually do." (c) **Dreaming as RL-generated rehearsal data is the structural analog of constitutional self-play.** Where Anthropic's principle-based training uses 3M Difficult-Advice tokens + constitutional documents to align Claude (see [anthropic-research-2026-05-08-teaching-claude-why]), Dreaming uses RL-generated curricula to *self-improve*. The two share a substrate: model-generated training data, gated by reward. (d) Caveat: the abstract is mechanism-heavy and benchmark-light. PDF read needed before any claim about *magnitude* of continual-learning gains. Behrouz's Titans line has historically delivered the empirics, so the magnitudes will likely arrive in the report — but treat the headline as a paradigm contribution not a SOTA claim until verified.
- **Action signal:** `track` `compare` — fetch the PDF when accessible; cross-reference with TaskMem / AdaCoM / UCE / eMoT in the ledger as the **parameter-layer** entry in the now five-mechanism memory primitive cluster (write / manage / decay / type / consolidate).

### 3. DMF — Deterministic Memory Framework (5×–242× Fewer Tokens vs. Mem0, No LLM in the Loop)
- **Source:** arXiv (submitted June 2, 2026)
- **Link:** https://arxiv.org/abs/2606.03463
- **Authors / org:** **Matteo Stabile**, **Enrico Zimuel** (Elastic — production-search-engineering lineage)
- **Focus area:** Agent memory / Context engineering
- **What it is:** A CPU-first memory layer for conversational agents that **eliminates LLM calls from the memory management loop entirely**. Three primitives: (1) a **Survival Score Ω** computed from deterministic content signals (lexical/structural features), conversational cues (turn role, recency, reference density), and structured provenance, combined through a **logistic projection**; (2) an **interaction-count decay law Ω_eff(Δn)** that governs relevance evolution as a function of *conversation turns*, not wall-clock time — the relevance of a memory unit decays based on how many turns have elapsed since it was last accessed, not how long it has sat there; (3) a deterministic write/retrieve/evict pipeline that runs entirely on CPU. **Evaluated on LoCoMo + LongMemEval + a purpose-built benchmark, against Mem0 as baseline:** comparable accuracy, **zero tokens spent on memory preparation, 5× to 242× fewer tokens across the entire conversation** depending on conversation length and density.
- **Why it matters for Justin's agents:** (a) **This is the first principled argument that LLM-driven memory compression (the design at the heart of Mem0, LangMem, Letta, and the "memory MCP" cluster) was solving the wrong problem.** The DMF claim is that conversational memory has enough lexical/structural/provenance signal that a deterministic scorer matches a neural compressor on accuracy *and* is free at inference. If this reproduces, the entire memory-as-LLM-pipeline category collapses to a CPU service. (b) **The cost math is genuine production relief.** For Justin's companion-app stack, every conversation that runs through Mem0-like memory pays ~20-50% token overhead for memory write + retrieve summarization calls. A 5×-242× reduction at parity converts that line item to ~0. On the M5 Max, deterministic-memory + DMF + a local 9B inference model is a fully on-device agent loop with no frontier-model dependency for memory operations. (c) **The interaction-count decay law (Ω_eff(Δn)) is the mechanistic answer to the "memory curse" problem ([arxiv:2605.08060]: expanded accessible history degrades cooperation).** A turn-count decay is exactly the eviction policy that limits accessible history to the working span — and unlike heuristic eviction caps, the decay rate is parameter-tunable per Survival-Score component. (d) **Composes with eMoT (yesterday's item 7 — memory corrosion via utility decay).** eMoT does utility-decay self-curation on *reasoning* traces; DMF does interaction-count decay on *conversational* memory. Both papers independently argue: **decay-as-first-class-primitive**, parameterized by the right scalar (utility / interaction-count), beats time-based or LLM-judged eviction. The decay-time axis of the memory primitive cluster is now multi-paper.
- **Action signal:** `try-now` `compare` — implement DMF as a memory-layer alternative in any Mem0-backed companion app; record token-cost delta and retrieval accuracy on LoCoMo; cross-reference with eMoT in the ledger as the second decay-axis paper.

### 4. NovelAPIBench — Diagnosing Knowledge Gaps in LLM Tool Use (Usage Examples = Strongest Standalone Signal)
- **Source:** arXiv (submitted June 2, 2026)
- **Link:** https://arxiv.org/abs/2606.03657
- **Authors / org:** Jinnuo Liu, Yue Peng, Jinhan Niu, Hongyi Wen (affiliations not listed in the abstract page)
- **Focus area:** Tools & connectors / Coding agents / Evaluation
- **What it is:** Most "novel API" benchmarks are static, use synthetic APIs that don't reflect real library evolution, or score with coarse pass/fail. **NovelAPIBench** is a **fully automated dynamic benchmark** that, for any base model and target library, (1) discovers novel APIs not in the base model's pretraining, (2) extracts decomposed knowledge bundles for each API — *signatures*, *module paths*, *I/O contracts*, *semantics*, *executable usage examples*, *mechanism descriptions* — (3) generates executable coding tasks, and (4) assigns failed samples to **six diagnostic categories**. Scale: **~1.9K tasks × 4 base models × 5 domains**. Headline findings: (i) **knowledge components are not interchangeable** — *usage examples* are the **strongest standalone signal**; the best two-component setting pairs *signatures* with either *mechanisms* or *examples* depending on domain and backbone; (ii) **adding more context, especially source code, can hurt** by increasing import-path errors; (iii) **parametric adaptation (fine-tuning) does not replace retrieval** once external knowledge is removed — fine-tuning mainly teaches models *how* to use provided bundles, and this *procedural integration* skill transfers to held-out libraries.
- **Why it matters for Justin's agents:** (a) **Sharpens the MCP-server-design playbook.** Every MCP server that exposes a tool to a model is, structurally, presenting a *novel API*. NovelAPIBench's finding that usage examples > signatures > mechanisms as standalone signals means: **the highest-leverage edit to any MCP server is moving from "type-signatures-only" to "executable usage examples in the tool description."** For Justin's MCP work, this is a one-week refactor across his published MCP servers with a measurable accuracy delta. (b) **"More context can hurt" is the counterintuitive finding worth instrumenting.** The temptation when an agent fails on a new tool is to dump more docs / source code into the prompt. NovelAPIBench reports this *increases* import-path errors — the model conflates module paths from the dumped code with the target API. The corollary: prune tool descriptions aggressively; prefer 2-3 verified usage examples to 50 lines of source. (c) **Fine-tuning teaches *procedural integration* but doesn't replace retrieval.** This is the principled answer to "should I fine-tune a small local model to use my MCP servers" — yes, but the fine-tune buys you the procedural skill (when-to-call, how-to-chain), not the API content (which still has to be retrieved fresh at inference). This is structurally aligned with [arxiv:2605.30785] AdaCoM's *frozen actor + learned external manager* split — fine-tune the procedural integrator, retrieve the volatile content. (d) **Pairs with [arxiv:2605.30738] MAVEN.** MAVEN's intermediate-verification scaffold lifts GPT-OSS-120b 48% → 71% on tool-use math/physics — orthogonal to NovelAPIBench's finding about *what should be in the tool description in the first place*. MAVEN improves *post-call verification*; NovelAPIBench improves *pre-call comprehension*.
- **Action signal:** `try-now` `compare` — audit all published MCP servers; ensure each tool description contains ≥2 executable usage examples (not just type signatures); cross-reference with MAVEN as the second tool-use scaffold axis (pre-call comprehension vs. post-call verification).

### 5. StepFinder — Lightweight Failure Attribution Without LLM in the Loop (79% Faster than LLM Methods)
- **Source:** arXiv (submitted June 2, 2026)
- **Link:** https://arxiv.org/abs/2606.03467
- **Authors / org:** Taiyu Zhu, Yifan Wu, Weilin Jin, **Ying Li**, **Gang Huang** (Peking U — Ying Li and Gang Huang are PKU systems-of-AI leads)
- **Focus area:** Evaluation / Agent orchestration / Long-running autonomous loops
- **What it is:** Failure-attribution methods that rely on LLMs to reason over full execution trajectories incur expensive inference and suffer from interference by redundant/noisy logs. **StepFinder** uses an LLM **only once, at feature-construction time**, to encode execution logs into **temporal semantic sequences**; the actual attribution then runs through a **parameter-efficient temporal-modeling + attention module** that captures sequential evolution and cross-step dependencies. The step-level error score is refined via **multi-scale differences + position bias** for precise root-cause identification. **Evaluated on the Who&When benchmark:** outperforms LLM-based methods on step-level attribution and achieves **79% inference-time reduction vs. the fastest LLM-based baseline**, with zero text-generation overhead.
- **Why it matters for Justin's agents:** (a) **The failure-attribution-as-primitive line is consolidating fast.** Three days, three papers: **[arxiv:2606.02060] DRIFT** (June 1: claim-centric audit, +30 pts span localization), **[arxiv:2605.29087] Trace-Answer Dissociation** (May 31: 50% latent-correct in think-mode, GPT-4o judge agrees 86%), now StepFinder. Mechanistically distinct: DRIFT extracts claims and checks support (semantic); Trace-Answer Dissociation measures answer/trace decorrelation (probability); StepFinder encodes once then runs a fast temporal scorer (operational). All three converge on: *post-hoc trajectory analysis is the missing layer in the agent eval stack*. (b) **StepFinder is the runtime-feasible variant.** DRIFT's +30 pts and Trace-Answer Dissociation's per-instance latent-correct measure are both expensive offline analyses. StepFinder's 79% inference-time reduction and zero text-gen overhead make it the only one of the three that's plausibly an *online monitor* for a long-running agent loop — you can run StepFinder *during* a trajectory and intervene early. (c) **For Justin's long-running companion-app loops:** instrument the heartbeat with a StepFinder-style temporal encoder so failure attribution runs continuously, then trigger DRIFT-style claim-centric audit only on flagged windows. The cost split (cheap continuous monitor + expensive on-demand audit) is the right architecture. (d) **Who&When is a smaller benchmark than DRIFT's 2,790-trajectory suite** — magnitude comparison requires same-benchmark eval, which doesn't exist yet. Open empirical question: head-to-head DRIFT vs. StepFinder on the same trajectory corpus to determine the cost-quality Pareto frontier.
- **Action signal:** `try-now` `compare` — implement temporal-semantic-sequence encoding + temporal+attention scorer as a heartbeat-runtime monitor in the agent harness; cross-reference with DRIFT in the ledger as the second axis (cheap online vs. expensive offline) of the failure-attribution cluster.

### 6. SkillPyramid — Hierarchical Skill Consolidation (+38.0% Avg Reward, −27.7% Steps)
- **Source:** arXiv (submitted June 2, 2026)
- **Link:** https://arxiv.org/abs/2606.03692
- **Authors / org:** Yuan Xiong, Ziqi Miao, Qian Chen, **Lijun Li**, **Yequan Wang**, **Shizhu He**, **Jun Zhao**, **Kang Liu** (BAAI + Institute of Automation CAS — Yequan Wang at BAAI; Kang Liu's CAS NLP lab is a long-running agent-systems group)
- **Focus area:** Agent memory / Agent orchestration
- **What it is:** A **hierarchical skill consolidation framework** for self-evolving agents — skills are organized into a *pyramid topology* (bottom = primitive actions, mid = composite skills, top = strategy-level abstractions) with explicit self-evolution mechanisms that promote / merge / refine skills across levels as the agent encounters new tasks. **Evaluated across ALFWorld + WebShop + ScienceWorld with four different backbone models.** Aggregate: **+38.0% average reward** and **−27.7% execution steps** over baselines. (Per-environment / per-backbone numbers are PDF-only — the abstract reports the aggregate, not the cluster split.)
- **Why it matters for Justin's agents:** (a) **Joins the ALFWorld-near-90% cluster as the fifth mechanism.** Prior members: **[arxiv:2605.05413] CC-Skill** (89.6%, in-weights procedural memory), **[arxiv:2605.06078] BEACON** (92.9%, milestone-segmented reward shaping), **[arxiv:2605.06642] StraTA** (93.1%, top-down strategy abstraction), **[arxiv:2606.02304] UCE** (96.3%, gradient-free typed externalization). SkillPyramid contributes the *hierarchical-topology* axis — skills aren't a flat library, they're stratified by abstraction level with explicit promotion/merge mechanics. **Open empirical question:** the per-environment ALFWorld split isn't in the abstract; whether SkillPyramid touches the 96.3% UCE ceiling is unverified until the PDF is read. (b) **The hierarchical topology aligns with UCE's typed-knowledge schema (Memory / Strategy / Workflow / Skill).** UCE types by *kind* of knowledge; SkillPyramid stratifies by *level of abstraction*. The two are orthogonal — a fully populated cell of the (type × level) grid is the next-step memory architecture. (c) **Cross-backbone evaluation (four different models) is the right rigor.** A lot of agent-memory papers report on one backbone, leaving cross-model transfer unknown. Four backbones across three environments is enough evidence that the gain attaches to the *mechanism*, not the backbone — which is the property Justin needs to build a memory layer that survives the year's model swaps. (d) The −27.7% execution-step reduction is the latency-relevant headline — same task, fewer environment interactions — which translates to a tool-call / API-cost reduction for any agent that bills per call.
- **Action signal:** `track` `compare` — add SkillPyramid as fifth mechanism in the ALFWorld near-90% cluster with the (type × level) cross-product as the open architecture question; fetch the PDF for the ALFWorld-specific number before promoting to `try-now`.

### 7. EvoDS — Self-Evolving Autonomous Data Science Agent (+28.9% on 4 Benchmarks, KDD 2026)
- **Source:** arXiv (submitted June 2, 2026; KDD 2026 accepted)
- **Link:** https://arxiv.org/abs/2606.03841
- **Authors / org:** Zherui Yang, **Fan Liu**, Yansong Ning, **Hao Liu** (HKUST — Hao Liu's USAIL group, prior data-science-agent lineage)

KDD 2026 acceptance signals the data-science-systems community has reviewed and endorsed the architecture.
- **Why it matters for Justin's agents:** (a) **EvoDS sits at the intersection of three focus areas — autonomous loops, memory, and coding agents — and supplies the multi-benchmark validation that yesterday's UCE / TaskMem / AdaCoM / eMoT cluster mostly hasn't.** Most memory papers this season report on one or two benchmarks; +28.9% across four data-science benchmarks is a stronger transfer signal. (c) **For Justin's federal-data-engineering hat:** the relevant production analogue is *internal-data-portal navigation + analysis* agents — which is structurally the same shape as EvoDS's task distribution (multi-source data, multi-step analysis, durable skill reuse). The KDD-camera-ready release with associated repo (`usail-hkust/EvoDS`) is directly clone-and-adapt-able. (d) **Pairs with [arxiv:2605.30434] LongDS-Bench** (May 31: 48.45% best-frontier on multi-turn data-analysis, ~47-point early-to-late decline). LongDS-Bench documented the late-turn collapse; EvoDS proposes (skill acquisition + IB-based compression) as the mitigation. **Open empirical question:** EvoDS's +28.9% is reported on its training distribution; LongDS-Bench would be the harder transfer test.
