# AI Research Digest — Thursday, May 28, 2026

## TL;DR
- **The ZJU memory group shipped a diagnosis + cure pair on the same day:** MemTrace turns memory pipelines into "executable memory evolution graphs" to attribute failures to operation-level root causes (+7.62% end-task via auto fault-correction), while FluxMem reframes memory as a continuously evolving connectivity graph and claims SOTA on LoCoMo/Mind2Web/GAIA. FluxMem's "continuous evolution helps" thesis sits in direct tension with this month's consolidation-decay finding — flagged below.
- **Reliability is now being measured as an aging curve, not a snapshot:** AgingBench (Your Agents Are Aging Too) frames dependability as a *lifespan property of the full harness* and names four decay mechanisms (compression / interference / revision / maintenance aging). Behavioral tests stay green while factual precision quietly decays — the longitudinal extension of the harness-as-primitive thread.
- **Output tokens are the energy line item:** Long Live the Librarian measures that an output token costs 30–1,000× an input/cached token in multi-agent SWE, and a persistent search sub-agent that suppresses redundant repo re-exploration cuts per-episode GPU energy up to 25% on SWE-Bench Verified with no performance loss.
- **Search agents are mostly verifying what they already know:** LiveBrowseComp shows agents answer up to 44.5% of BrowseComp without tools and collapse below 2% closed-book on genuinely fresh questions — search benchmark scores are inflated by parametric knowledge.
- **Local-fit signal is strong today:** ITBench-AA's SRE leaderboard has all frontier models below 50%, with **Gemma 4 31B (37%, $0.14/task) beating Gemini 3.1 Pro (30%, $2.23/task)** — a 31B dense model that fits comfortably on the M5 Max and is a credible local IT-triage agent. LearnWeak separately specializes 7–8B computer-use agents for +11 pp on OSWorld.

## Items

### 1. MemTrace — operation-level error attribution for memory systems
- **Source:** arXiv (HF Daily, 24 upvotes)
- **Link:** https://arxiv.org/abs/2605.28732
- **Authors / org:** Xinle Deng, Ruobin Zhong, Yunzhi Yao, Jizhan Fang, Buqiang Xu, … Ningyu Zhang (18 authors; Zhejiang University / zjunlp)
- **Focus area:** Agent memory
- **What it is:** A framework that transforms memory pipelines into *executable memory evolution graphs*, enabling fine-grained tracing of how information flows and corrupts. Ships MemTraceBench (derived from Long-Context, RAG, Mem0, and EverMemOS systems) plus an automated attribution method that traces operation subgraphs to root-cause a failure. Headline finding: memory failures are *systematic and operation-level*, not random; attribution-guided auto fault-correction yields up to **+7.62%** end-task performance. Code promised at `zjunlp/MemTrace`.
- **Why it matters for Justin's agents:** This is the first tool that treats "why did my memory layer give the wrong answer" as a debuggable graph instead of a black box. For a vault/companion-app memory stack, the operation-graph framing means you can instrument *which* step (write, consolidate, retrieve, rerank) introduced the error and patch that step — directly usable as a guardrail/observability pattern over Mem0-class systems.
- **Action signal:** `compare` — constructive counterpart to the 11+ orthogonal memory-failure-mode papers tracked this month (STALE, MEMOREPAIR, DeMem, MEME, LongMINT, consolidation-decay [arxiv:2605.12978]); MemTrace is the first to make those failures attributable rather than merely catalogued.

### 2. FluxMem — memory as continuously evolving connectivity
- **Source:** arXiv (HF Daily, 9 upvotes)
- **Link:** https://arxiv.org/abs/2605.28773
- **Authors / org:** Jizhan Fang, Buqiang Xu, Xinle Deng, … Ying Wei, Huajun Chen, Ningyu Zhang (Zhejiang University; same group as MemTrace)
- **Focus area:** Agent memory
- **What it is:** Argues dynamic agent environments need memory whose *structure* adapts, not static storage. Models memory as a heterogeneous graph refined in three stages — initial connection formation, feedback-driven refinement, and consolidation — that "repairs missing links, prunes interference, aligns abstraction granularity, and distills recurrent successful trajectories." Claims SOTA across LoCoMo, Mind2Web, and GAIA.
- **Why it matters for Justin's agents:** Pairs naturally with MemTrace (diagnose with one, restructure with the other). The "evolve the connectivity, not the stored text" stance is the design Justin would want if he wants memory that gets better with use without the documented risk of LLM re-writes corrupting stored facts.
- **Action signal:** `compare` — see Conflicts: FluxMem's "continuous evolution improves memory" claim must be reconciled with the consolidation-decay result [arxiv:2605.12978] and aligns with EvolveMem's "evolve architecture, not content" resolution [arxiv:2605.13941].

### 3. Your Agents Are Aging Too — lifespan engineering & AgingBench
- **Source:** arXiv (cs.MA)
- **Link:** https://arxiv.org/abs/2605.26302
- **Authors / org:** Jianing Zhu, Yeonju Ro, John Robertson, Kevin Wang, Junbo Li, Haris Vikalo, Aditya Akella, Zhangyang Wang (UT Austin cluster)
- **Focus area:** Long-running / autonomous loops
- **What it is:** Introduces AgingBench, a *longitudinal* reliability benchmark, and reframes reliability as "a lifespan property of the full agent harness, not only a snapshot property of the base model." Categorizes degradation into four mechanisms — compression aging, interference aging, revision aging, maintenance aging. Across 7 scenarios, 14 models, and 400+ runs spanning 8–200 sessions: **behavioral tests can remain clean while factual precision decays**, and derived-state tracking can collapse sharply within a single model.
- **Why it matters for Justin's agents:** This is the missing temporal axis for his durable/long-running companion agents. The actionable warning: the smoke tests that look green are exactly the ones that won't catch slow factual rot — you need longitudinal precision probes, not just behavioral assertions. The four aging mechanisms map cleanly onto his stack (compression aging ≈ compaction loss, interference aging ≈ accumulating facts, revision aging ≈ stale memory).
- **Action signal:** `compare` — longitudinal extension of the harness-as-primitive thesis [arxiv:2605.26112] Scaling the Harness, and a clean temporal complement to DELEGATE-52's degradation-over-20-iterations [arxiv:2604.15597].

### 4. Long Live the Librarian — energy-efficient persistent search sub-agent
- **Source:** arXiv (cs.MA)
- **Link:** https://arxiv.org/abs/2605.27787
- **Authors / org:** Seunghyuk Cho, Sunghyun Choi, Jaeseung Heo, Youngbin Choi, Saemi Moon, MoonJeong Park, Dongwoo Kim (POSTECH-affiliated)
- **Focus area:** Agent orchestration / coding agents
- **What it is:** Per-token energy attribution for multi-agent SWE reveals a sharp asymmetry — **an output token consumes 30–1,000× the energy of an input or cached token** — and multi-agent systems inflate output because agents repeatedly re-explore overlapping repo regions. "Librarian" is a persistent search sub-agent that tracks repository-search history, suppresses redundant exploration across agents, and returns short references to file regions instead of full file excerpts. On SWE-Bench Verified it cuts per-episode GPU energy **up to 25%** with task performance preserved.
- **Why it matters for Justin's agents:** This is a directly portable Claude Code pattern. The insight — output tokens dominate cost/energy and subagents waste them re-grepping the same files — argues for a shared, persistent "what's already been searched" memory across subagents that hands back file:line references rather than re-pasting code. Cheaper, greener, no quality hit.
- **Action signal:** `try-now` — the reference/index-instead-of-excerpt pattern is implementable today on top of Claude Code subagents + an MCP search-history store.

### 5. LiveBrowseComp — are search agents searching or just verifying?
- **Source:** arXiv (HF Daily, 8 upvotes)
- **Link:** https://arxiv.org/abs/2605.28721
- **Authors / org:** HuiMing Fan, Xiao Wang, Zheng Chu, Qianyu Wang, Zhuoyao Wang, Ming Liu, Bing Qin, et al. (HIT-affiliated)
- **Focus area:** Tools & connectors / evaluation
- **What it is:** Diagnoses "Intrinsic Knowledge Dependence" in search agents: they answer **up to 44.5% of BrowseComp questions without tools**, generate **more than half of their search queries from internally produced hypotheses** rather than retrieved evidence, and underperform closed-book baselines when supporting evidence is unavailable. Introduces LiveBrowseComp — 335 human-authored questions requiring information published within 90 days, excluding widely-known events. Result: **all evaluated agents fall below 2% closed-book accuracy**, and search-augmented scores drop **25–40 points** relative to BrowseComp.
- **Why it matters for Justin's agents:** A blunt reality check for any deep-research / MCP-search agent he builds: the benchmark wins are partly the model recalling training data, not the retrieval pipeline working. For genuinely fresh queries (the actual use case for a research agent), current search agents are near-useless closed-book — so retrieval quality and freshness, not model size, is the lever.
- **Action signal:** `compare` — empirically confirms the tool-necessity / knowing-doing gap [arxiv:2605.14038, arxiv:2605.00737, arxiv:2605.00136] and the benchmark-validity thread [arxiv:2605.10448 evidence-bounds, arxiv:2605.07161 SREGym]: static search benchmarks systematically over-credit parametric knowledge.

### 6. ITBench-AA — frontier models below 50% on agentic enterprise IT (SRE)
- **Source:** Hugging Face blog (Artificial Analysis × IBM Software Innovation Lab)
- **Link:** https://huggingface.co/blog/ibm-research/itbench-aa
- **Authors / org:** Ayhan Sebin, Saurabh Jha, Rohan Arora, et al. (Artificial Analysis + IBM)
- **Focus area:** Evaluation
- **What it is:** First entry in a benchmark series for agentic enterprise IT, built on IBM's ITBench via an open-source shell-access harness ("Stirrup"). The SRE track has 59 tasks (40 public + 19 held-out): Kubernetes incident response requiring agents to read logs, trace dependencies, and identify root-cause entities under a 100-turn cap, scored on average precision at full recall. **All frontier models score below 50%** — Claude Opus 4.7 (Max effort) 47% at $5.38/task, GPT-5.5 (xhigh) 46%, Qwen3.7 Max 42%, GLM-5.1 40% (best open-weights), down to Gemini 3.1 Pro Preview 30%. Two findings stand out: **more turns ≠ better answers** (over-investigation surfaces false positives), and **open-weights models win on cost** — Gemma 4 31B hits 37% at $0.14/task, beating Gemini 3.1 Pro on both score and cost. Dataset, harness, and leaderboard are public.
- **Why it matters for Justin's agents:** As a federal data engineer, SRE-style root-cause-on-live-systems is squarely in scope. The "over-investigation hurts" finding argues for turn-budgeting and early-stop heuristics, not max-effort loops. And the Gemma 4 31B result is the headline local-fit signal of the day (see Local-model corner).
- **Action signal:** `try-now` — public dataset + open harness; usable as an internal SRE-agent eval immediately.

### 7. LearnWeak — annotation-free specialization for small computer-use agents
- **Source:** arXiv (HF Daily, 22 upvotes)
- **Link:** https://arxiv.org/abs/2605.28775
- **Authors / org:** Suji Kim, Kangsan Kim, Sung Ju Hwang (KAIST-affiliated)
- **Focus area:** Tools & connectors / local & open models
- **What it is:** Deploying a separate large expert per software domain is expensive; small open computer-use agents are the practical specialization target but are weaker and fail unevenly. Naive large-scale synthetic data gives only marginal gains. LearnWeak uses a stronger *reference* agent to identify the student's weaknesses in the target domain, synthesize targeted tasks, and build supervision automatically (no human annotation), plus an error-aware objective that disentangles **planning vs execution errors**. On OSWorld across eight domains: **+11.6 pp (EvoCUA-8B)** and **+11.1 pp (OpenCUA-7B)**.
- **Why it matters for Justin's agents:** The 7–8B base models run trivially on the M5 Max, and the recipe is a blueprint for turning a cheap local computer-use agent into a domain specialist (e.g., a single app or workflow) using a frontier model only as the offline "teacher." The planning-vs-execution error split is a useful diagnostic frame even outside CUAs.
- **Action signal:** `local-fit` — EvoCUA-8B / OpenCUA-7B are local-runnable; LearnWeak is the specialization method to apply on top.

### 8. HRBench — unified benchmark for thinking-mode switching
- **Source:** arXiv (HF Daily, 10 upvotes)
- **Link:** https://arxiv.org/abs/2605.28398
- **Authors / org:** Yansong Ning, Mianpeng Liu, Jingwen Ye, Weidong Zhang, Hao Liu (HKUST-GZ-affiliated)
- **Focus area:** Reasoning & inference-time compute
- **What it is:** Hybrid-reasoning LLMs expose explicit controls over reasoning effort, but adaptive thinking-mode selection methods have been evaluated under incomparable setups. HRBench unifies the design space along two axes — three switching-strategy families (prompt-based selection, external routing, speculative execution) × four training regimes (training-free, SFT, offline RL, online RL) = 12 settings — evaluated across 6 LLMs (Qwen3.5-2B → Kimi-K2.5-1.1T) and 5 reasoning benchmarks, reimplementing 12+ prior methods in one pipeline. Findings: prompt-based methods give favorable token-accuracy trade-offs; routing gives more stable cost reduction; speculative methods buy accuracy at higher token cost; the best strategy varies with model scale and task domain.
- **Why it matters for Justin's agents:** Direct cost-control guidance for when to dial reasoning effort up or down. The practical takeaway — there is no universally best switcher; pick per model-scale and task — means his routing logic should be tuned per-model rather than copied wholesale. Reference implementations are released.
- **Action signal:** `track` — useful as a methodology reference for effort-routing; revisit if a clear default strategy emerges.

### 9. Coding Agents in the Social Sciences (Anthropic Economic Research)
- **Source:** Anthropic
- **Link:** https://www.anthropic.com/research/coding-agents-social-sciences
- **Authors / org:** Thomas Lyttelton, Maxim Massenkoff, Nathan Wilmers (Anthropic)
- **Focus area:** Coding agents (adoption)
- **What it is:** A survey of 1,260 quantitative social scientists (early 2026) on coding-agent adoption. While 81% have tried AI chatbots, only **20% regularly use coding agents**. Adoption is uneven (researchers with typically male names adopt at ~2× the rate of female-named peers; top-25-university researchers are 40% more likely). Among coding-agent users, 97% use them to generate analysis code; early users start ~25% more projects and post ~50% more working papers, but show no difference in journal submissions. The authors are explicit that this is descriptive baseline data for an ongoing randomized experiment, not causal.
- **Why it matters for Justin's agents:** Not a technical artifact, but a primary-source read on how the tool he builds with (Claude Code-class agents) is actually diffusing — and the productivity asymmetry (more starts, same finished output) is a useful signal that the bottleneck is downstream of code generation. Relevant context for anyone shipping agent products to a research/analyst audience.
- **Action signal:** `track` — adoption/economic data, no methodology to integrate; useful market context.

## Local-model corner

Two genuinely local-relevant signals today, both runnable on M5 Max (64 GB).

**Primary: Gemma 4 31B (Reasoning) — from the ITBench-AA SRE leaderboard**
- **Model:** Gemma 4 31B, dense, reasoning variant.
- **Memory fit:** At Q4 (~4.5 bpw) ≈ **17–18 GB** of weights; at Q8 ≈ **31 GB**. Even with a generous KV cache for 100-turn SRE trajectories (a few GB at 32–64K context with GQA), it sits comfortably inside 64 GB with room for the OS and an MCP server. No offload needed.
- **Realistic tasks:** Credible **IT triage / SRE root-cause** agent — it scored **37% on ITBench-AA SRE, beating Gemini 3.1 Pro Preview (30%) at ~16× lower cost ($0.14 vs $2.23/task)**. That makes it a defensible *local, zero-marginal-cost* first-pass triage agent for Kubernetes-style log reading and dependency tracing, escalating to a frontier model only when it stalls. Less suited to tasks needing the absolute top of the leaderboard (still <50%).
- **How to run:** MLX (`mlx-community` Gemma 4 31B build) is the cleanest path on Apple Silicon; llama.cpp/GGUF via Ollama or LM Studio also work. Pair with a turn budget — ITBench-AA shows over-investigation *hurts* precision, so cap the loop rather than letting it run to 100 turns.
- **Speed estimate:** No M5-Max-specific Gemma 4 31B benchmark located. Back-of-envelope: a 31B dense model at Q4 (~17.5 GB) against ~600 GB/s unified bandwidth is memory-bound around a **~30 tok/s ceiling**, realistically **~20–28 tok/s** decode in MLX — adequate for an agent loop, not for bulk generation. Treat as an estimate, not a measured figure.

**Secondary: EvoCUA-8B / OpenCUA-7B — small computer-use agents (from LearnWeak)**
- **Memory fit:** 7–8B at Q4 ≈ **4–5 GB**; trivial on 64 GB, leaves headroom for a screen-capture / accessibility-tree pipeline.
- **Realistic tasks:** OSWorld-style computer-use within a *narrow* specialized domain after applying the LearnWeak recipe (+11 pp). Out-of-the-box they're weak generalists; their value is as cheap, fast, domain-specialized local actors.
- **How to run:** MLX or llama.cpp; the bottleneck is the perception/grounding loop, not raw decode.

## Conflicts & open questions

Cross-referenced against `_meta/claims-ledger.md`:

- **FLAGGED — continuous memory evolution: help or harm?** FluxMem [arxiv:2605.28773] claims that *continuously* evolving memory connectivity (with a consolidation stage that "distills recurrent successful trajectories") yields SOTA on LoCoMo/Mind2Web/GAIA. This is in tension with the consolidation-decay finding [arxiv:2605.12978] ("Useful Memories Become Faulty When Continuously Updated by LLMs"): GPT-5.4 re-failed 54% of ARC-AGI problems it had previously solved *after* consolidating wins into a textual memory bank, with consolidation named as the core failure source. The likely reconciliation is the one the ledger already noted for EvolveMem [arxiv:2605.13941]: evolving memory *structure/connectivity* is safe, whereas LLM-driven rewriting of stored *content* is what corrupts. Open empirical question: does FluxMem's consolidation stage operate on connectivity only, or does it re-write content — and if the latter, why doesn't it inherit the consolidation-decay penalty? Neither paper runs the other's stress test (FluxMem isn't evaluated on an ARC-AGI-Stream-style re-solve protocol).

Open empirical questions raised today:
- **MemTrace × the failure-mode catalogue:** MemTrace [arxiv:2605.28732] claims memory failures are "systematic and operation-level." If true, the 11+ separately-named memory failure modes tracked this month may collapse into a smaller set of underlying *operation* faults (bad write, lossy consolidation, mis-rerank). Worth testing whether MemTraceBench's attribution categories subsume the existing taxonomy.
- **AgingBench vs. snapshot evals:** AgingBench [arxiv:2605.26302] shows behavioral tests stay clean while factual precision decays over 8–200 sessions. This implies most current agent benchmarks (single-session) structurally cannot detect the failure mode that matters most for deployed durable agents. Does any existing memory benchmark (LongMINT, EvoMemBench) actually probe far enough into a session lifespan to catch revision/interference aging?
- **LiveBrowseComp generalization:** The "<2% closed-book on fresh questions" result is on 335 hand-authored items; does the intrinsic-knowledge-dependence effect hold at the scale and noise of production web-search traffic, and does AKBE-style [arxiv:2605.26952] dual-path training reduce it?
