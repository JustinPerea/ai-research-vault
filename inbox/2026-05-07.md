# AI Research Digest — Thursday, May 07, 2026

## TL;DR
- **Context engineering had a genuinely big day.** LongSeeker (Qwen3-30B-A3B fine-tune) hits **61.5% on BrowseComp** vs. Tongyi DeepResearch 43.2% by giving the agent five explicit context-shaping operators (Skip, Compress, Rollback, Snippet, Delete). Independently, "Volt" (LCM) reports beating Claude Code on OOLONG across **32K–1M tokens** with recursive context compression + recursive task partitioning.
- **Multi-agent orchestration moved from hand-engineered to learned.** Uno-Orchestra learns decomposition depth + worker choice + budget jointly via RL: **77.0% macro pass@1 across 13 benchmarks, +16 pp over the strongest workflow baseline at ~10× lower per-query cost**.
- **Coding-agent evals are admitting their leaderboards are unstable.** AuditRepairBench shows agent-repair rankings reorder under evaluator reconfiguration and that screening-guided methods leak evaluator signal — **55–74% rank-displacement reduction is attributable to that leak**.
- **A real MCP-shaped runtime safety layer landed under AGPL-3.0** (AgentTrust): allow/warn/block/review verdicts on tool calls, 95% verdict accuracy, low-millisecond latency. First open-source piece in this slot worth integrating.
- **Local-model angle:** LongSeeker's base is Qwen3-30B-A3B MoE — that is exactly the M5 Max sweet spot, and the trained checkpoint (if released) would be a strong candidate for a local long-horizon search agent.

## Items

### 1. LongSeeker: Elastic Context Orchestration for Long-Horizon Search Agents
- **Source:** arXiv (cs.AI, submitted May 6/7)
- **Link:** https://arxiv.org/abs/2605.05191
- **Authors / org:** Yijun Lu, Rui Ye, Yuwen Du, Jiajun Wang, Songhua Liu, Siheng Chen
- **Focus area:** Context engineering / Long-running loops / Agent memory
- **What it is:** A general agentic paradigm called **Context-ReAct** that gives the agent five atomic context operators — **Skip, Compress, Rollback, Snippet, Delete** — to actively reshape its working context inside the reasoning/tool loop, instead of just appending. The Compress operator is proven expressively complete; the others are efficiency/fidelity primitives. The trained agent, **LongSeeker**, is a fine-tune of **Qwen3-30B-A3B** on 10k synthesized trajectories. Reported: **61.5% on BrowseComp** and **62.5% on BrowseComp-ZH**, vs. Tongyi DeepResearch (43.2 / 46.7) and AgentFold (36.2 / 47.3).
- **Why it matters for Justin's agents:** This is the cleanest formal articulation I've seen of "let the agent edit its own context." For any companion-app loop that has to do many tool calls before answering, the five-operator vocabulary is implementable today on Claude (as a structured tool the agent calls between steps) without retraining. Independent of the trained checkpoint, the *paradigm* is portable.
- **Action signal:** `try-now` for the Context-ReAct paradigm at the prompting layer; `local-fit` if/when the LongSeeker checkpoint or trajectory data ships — Qwen3-30B-A3B's 3B active params are M5 Max-friendly (see Local-model corner).

### 2. LCM: Lossless Context Management (and "Volt" coding agent)
- **Source:** arXiv (cs.AI / cs.CL)
- **Link:** https://arxiv.org/abs/2605.04050
- **Authors / org:** Clint Ehrlich, Theodore Blackman
- **Focus area:** Context engineering / Coding agents
- **What it is:** A deterministic memory architecture for LLM agents built on two mechanisms: **(a) recursive context compression** that builds a hierarchical summary DAG with lossless pointers back to original content, and **(b) recursive task partitioning** via engine-managed parallel primitives (e.g., LLM-Map) that replace model-written loops. Authors position LCM as an extension of Recursive Language Models (RLMs). They benchmark a coding agent built on LCM ("**Volt**") against **Claude Code on the OOLONG long-context eval, both running Opus 4.6**, and report Volt > Claude Code at every measured context length **between 32K and 1M tokens**.
- **Why it matters for Justin's agents:** Direct, in-domain comparison against the agent Justin uses every day. Two takeaways: (1) "lossless pointer back to source" is a memory pattern worth stealing — it's strictly stronger than naive summarization, and is achievable with tool-side state in MCP. (2) Engine-managed parallel maps are a portable orchestration win you can implement on top of Claude without changing the model.
- **Action signal:** `compare` — direct head-to-head claim against Claude Code; logged in claims ledger. Worth tracking for third-party reproduction and for the OOLONG curve shape (where exactly does the gap open?).

### 3. Uno-Orchestra: Parsimonious Agent Routing via Selective Delegation
- **Source:** arXiv (cs.AI)
- **Link:** https://arxiv.org/abs/2605.05007
- **Authors / org:** Cui, Xie, Yuan, Yang, Wang, Wu, Wu, Zhong, Yu, Guo, Zhang, Yu, Ren, Naseem (14 authors)
- **Focus area:** Agent orchestration
- **What it is:** Replaces hand-engineered orchestration / flat per-query routing with a **single learned policy** that jointly decides decomposition depth, worker model+primitive selection, and per-query inference budget. Trained via RL on real worker interactions across 22 baseline workflows covering math, code, knowledge, long-context, and tool use. Reports **77.0% macro pass@1 across 13 benchmarks, ~16 pp over the strongest workflow baseline, with roughly an order-of-magnitude lower per-query cost**.
- **Why it matters for Justin's agents:** Concrete evidence that "build one supervisor + workers and learn the routing" beats both static routers and bespoke decompositions, *and* costs less. Even without RL training, the structural lesson — let one policy decide depth + worker + budget — is a template for a Claude-supervisor / mixed local-worker stack.
- **Action signal:** `track` — strong numbers, but no code/model release noted yet; revisit if a repo lands. Cross-references the May 4 Web2BigTable orchestration claim — different benchmark axis (web research vs. mixed) but similar message that learned/structured orchestration beats flat workflows.

### 4. Executable World Models for ARC-AGI-3 in the Era of Coding Agents
- **Source:** arXiv (cs.AI, May 6, AGI-26 submission)
- **Link:** https://arxiv.org/abs/2605.05138
- **Authors / org:** Sergey Rodionov
- **Focus area:** Coding agents / Reasoning & inference-time compute
- **What it is:** Initial coding-agent baseline for **ARC-AGI-3** in which the agent maintains an **executable Python world model** of the game environment, verifies it against past observations, **refactors it toward simpler abstractions** as a practical proxy for an MDL/simplicity bias, and then plans through the model before acting. No game-specific logic. On 25 public ARC-AGI-3 games: **fully solves 7, exceeds 75% Relative Human Action Efficiency on 6, mean per-game RHAE 32.58%**.
- **Why it matters for Justin's agents:** "Agent writes a small executable model of its environment and refactors it" is a generalizable pattern beyond ARC. For tool-rich agents (MCP-heavy), the analog is having the agent maintain a small executable schema/state-machine of the connected services and replan against it — cheaper than re-deriving structure each turn. Worth reading even if you don't care about ARC.
- **Action signal:** `track` — single-author technical report; pattern is more interesting than the numbers.

### 5. AuditRepairBench: Evaluator-Channel Ranking Instability in Agent Repair
- **Source:** arXiv (cs.AI / cs.SE, NeurIPS 2026 Eval & Directions Track)
- **Link:** https://arxiv.org/abs/2605.04624
- **Authors / org:** Yuelin Hu, Zhenbo Yu, Zhengxue Cheng, Wei Liu, Li Song
- **Focus area:** Evaluation / Coding agents
- **What it is:** Empirical audit of agent-repair leaderboards: rankings **reorder substantially under evaluator reconfiguration**, and a measurable share of that reordering is produced by methods that **consult evaluator-derived signal during internal selection of candidate repairs** ("evaluator-channel leakage"). Corpus is 576,000 registered cells (96,000 executed) with four interchangeable screening implementations. Findings: screening-guided approaches reduce rank displacement by **55–74% (mean 62%)**; random channel blinding only 7%, generic retraining at most 13%. AuditRepairBench-Lite preserves the leaderboard at **Kendall τ = 0.88**; forward transfer to community evaluators **Spearman ρ = 0.65**.
- **Why it matters for Justin's agents:** This is the same theme as the May 4 EvalEval "eval is the bottleneck" piece, but with a sharper instrument: it shows that part of why agent-repair leaderboards are noisy is that the supposed top systems are *peeking at the evaluator*. If you're picking a repair/fix-it agent for a coding workflow, treat published rankings on the affected leaderboards as soft.
- **Action signal:** `compare` — extends and partially explains the EvalEval reliability story (claims-ledger 2026-05-04 / hf-blog evaleval). Logged.

### 6. AgentTrust: Runtime Safety Evaluation and Interception for AI Agent Tool Use
- **Source:** arXiv (cs.AI)
- **Link:** https://arxiv.org/abs/2605.04785
- **Authors / org:** Chenglin Yang
- **Focus area:** Tools & connectors / Agent orchestration
- **What it is:** Runtime safety layer that **intercepts agent tool calls before execution** (file ops, shell, HTTP, DB queries) and returns one of `allow / warn / block / review`. Components: shell-deobfuscation normalizer, "SafeFix" alternative-suggestion engine, "RiskChain" multi-step-attack detector, and an LLM-as-Judge with cache-aware reuse. Reported: **95.0% verdict accuracy, 73.7% risk-level accuracy** on a 300-scenario internal benchmark; **96.7% verdict accuracy, ~93% on shell-obfuscated payloads** on a 630-scenario adversarial benchmark; low-millisecond end-to-end latency. **Released AGPL-3.0 with an MCP server**.
- **Why it matters for Justin's agents:** First credible drop-in MCP-compatible safety layer for tool-using agents. For any companion app exposing shell/HTTP/file tools, this is the right shape of mitigation: a sidecar that authorizes each call, not a system-prompt rule. Caveat: AGPL-3.0 has real implications for product code — usable as a service / inside a sandbox, not as a linked library in proprietary code.
- **Action signal:** `try-now` — open repo + MCP server + concrete benchmark numbers. Verify the AGPL boundary fits the deployment shape.

### 7. BRIGHT-Pro + RTriever-4B: Rethinking Reasoning-Intensive Retrieval for Agentic Search
- **Source:** arXiv (cs.AI / cs.CL); HF Daily Papers
- **Link:** https://arxiv.org/abs/2605.04018
- **Authors / org:** Yilun Zhao, Jinbiao Wei, Tingyu Song, Siyue Zhang, Chen Zhao, Arman Cohan
- **Focus area:** Tools & connectors / Evaluation / Local & open models
- **What it is:** Two contributions: **BRIGHT-Pro**, an expert-annotated benchmark that expands each query with multi-aspect gold evidence and evaluates retrievers under both static *and* agentic search protocols; and **RTriever-Synth**, an aspect-decomposed synthetic corpus generating complementary positives plus positive-conditioned hard negatives. Used to LoRA-fine-tune **RTriever-4B** from Qwen3-Embedding-4B. Headline finding: aspect-aware + agentic evaluation reveals retriever behavior that single-passage relevance metrics hide; RTriever-4B substantially improves over its base.
- **Why it matters for Justin's agents:** Most agent RAG today optimizes single-passage relevance; this paper says that's the wrong objective for *iterative* search. The "evidence portfolio" framing — score retrievers on whether their hits are *complementary* across iterations — is what an MCP search tool inside an agent loop actually needs. RTriever-4B is also small enough to run locally.
- **Action signal:** `track` for the benchmark; `local-fit` if RTriever-4B weights are released — a 4B reasoning-aware embedder is trivially M5 Max-fit.

## Local-model corner

The strongest local angle today is **LongSeeker (Item #1)** because its base is **Qwen3-30B-A3B** — a Mixture-of-Experts model with **30B total / ~3B active** parameters. That architecture is unusually friendly to M5 Max + 64 GB.

- **Model:** Qwen3-30B-A3B (base for LongSeeker; LongSeeker checkpoint may follow)
- **Memory fit (M5 Max, 64 GB unified):**
  - Q4_K_M GGUF: **~17–18 GB weights** for the full set of experts → ~45 GB free for KV cache + OS. Activation footprint per token is small (only 3B active), so latency is closer to a 3B model than a 30B.
  - Q5/Q6: ~22–28 GB weights, still comfortable.
  - FP8/MLX 8-bit: ~30 GB weights → comfortable; KV headroom ~30 GB.
- **Realistic tasks:** Long-horizon search-style tool loops (the actual paper's use case), structured extraction with retries, agent supervisor over smaller workers. **Not** a frontier reasoning replacement; LongSeeker's BrowseComp number comes from the *paradigm*, not raw model strength.
- **How to run:** Today, **MLX via mlx-lm** has Qwen3-30B-A3B Q4 conversions; **llama.cpp / Ollama** also work and are the most predictable on Apple Silicon. If/when LongSeeker weights or LoRA adapters drop, expect MLX support within days.
- **Speed estimate:** M5 Max ~600 GB/s, ~3B active params at Q4 ≈ 1.6 GB read per token → bandwidth-bound upper bound ~**100–150 tok/s**; in practice **60–110 tok/s** at moderate context, comparable to a Q4 8B dense. **Treat as estimate — verify locally**.

**Secondary candidate:** RTriever-4B (Item #7) if released — a 4B reasoning-aware embedder runs trivially on M5 Max in fp16 (~8 GB) and is the right shape for a local MCP search-tool that actually understands query intent.
