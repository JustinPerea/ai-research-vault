### 1. Connect the Dots — Training LLMs as Long-Lifecycle Agents via End-to-End RL on Task + Context-Update Rollouts
- **Source:** arXiv (cs.LG, 2026-06-18)
- **Link:** https://arxiv.org/abs/2606.20002
- **Authors / org:** Yanxi Chen, Weijie Shi, Yuexiang Xie, Boyi Hu, Yaliang Li, Bolin Ding, Jingren Zhou (Alibaba)
- **Focus area:** Agent memory / long-running autonomous loops / reasoning
- **What it is:** End-to-end RL recipe that trains the LLM itself to develop a **meta-capability** for long-lifecycle deployment. Each training rollout contains **two phases** chained together: a task-solving phase and a **context-updating phase** in which the agent edits its own working environment (notes, scratchpads, distilled summaries) so that subsequent tasks become easier. A **GRPO variant with fine-grained credit assignment** propagates reward signals back through both phases. Custom environments are purpose-built to elicit and isolate the meta-capability, not to reward domain-specific skill. The paper reports successful generalization across domains and **from Connect the Dots tasks to "Ralph-loop" settings** — i.e., the trained meta-skill transfers to general long-running agent loops, not just the synthetic training task. Code released on GitHub; paper marked work-in-progress.
- **Why it matters for Justin's agents:** This is the training-side complement to the cluster of *frozen-LLM* memory-self-evolution mechanisms covered the past five days — **MATM** [arxiv:2606.19911] (raw-trajectory sharing), **MAA** [arxiv:2606.20475] (cross-batch signed-evidence accumulator), **AtomMem** [arxiv:2606.19847] (atomic facts + temporal profiles), **OPD-Evolver** [arxiv:2606.17628] (fast/slow loop). Those operate as *wrappers* over a fixed model; Connect the Dots bakes the meta-capability into the weights themselves. For Justin's companion-app and MCP-tool pipelines, the practical implication is: **the next generation of base models will arrive pre-trained to use scratchpads, daily-note vaults, and edit-their-own-context patterns as first-class behaviors** rather than emergent prompt-engineering tricks. If the generalization-to-Ralph-loops claim reproduces under independent eval, the long-running autonomous loop problem moves from "instrument a wrapper" to "pick a model trained for the regime."
- **Action signal:** `track` — watch for: (a) base-model checkpoints trained with this objective released by Alibaba (Qwen successor likely), (b) whether MAA's EMA accumulator and Connect the Dots' end-to-end RL **compose at inference time** (MAA refines the operation weights of an agent whose base model has already learned the meta-skill — should be additive but no one has tested it). Verify the cross-domain generalization claim before betting product roadmap on it.

### 2. GateMem — Memory Governance Benchmark for Multi-Principal Shared-Memory Agents
- **Source:** arXiv (cs.AI / cs.MA, 2026-06-17, HuggingFace Daily Papers featured 2026-06-22)
- **Link:** https://arxiv.org/abs/2606.18829
- **Authors / org:** Zhe Ren, Yibo Yang, Yimeng Chen, Zijun Zhao, Benshuo Fu, Zhihao Shu, Bingjie Zhang, Yangyang Xu, Dandan Guo, Shuicheng Yan (Bytedance affiliations indicated in HF)
- **Focus area:** Agent memory / evaluation / tools & connectors
- **What it is:** First benchmark that **assumes multiple users (principals) sharing common memory pools** — hospitals, workplaces, campuses, households — instead of the single-user default of every prior memory benchmark. Three dimensions evaluated jointly: **utility** (legitimate long-horizon recall under state updates), **access control** (authorization boundaries across roles), **active forgetting** (reliable deletion on explicit request). Multi-party episodes across four domains; structured per-dimension scoring. **Headline finding:** *"no method simultaneously achieves strong utility, robust access control, and reliable forgetting."* Long-context prompting wins on governance but at high compute cost. Retrieval and external-memory approaches reduce cost but **still leak unauthorized or deleted information**. Code + dataset released (GitHub + Hugging Face).
- **Why it matters for Justin's agents:** Justin's vault is currently single-principal but his companion-app and federal-data work intersect multiple users with different access scopes. GateMem formalizes the failure mode that everyone hand-codes around: **a shared memory store is not a memory system; it's a memory system + a governance system, and the governance system has to be deletion-correct or it's a liability.** The "long-context wins governance, RAG wins cost but leaks" trade-off is the same one Justin already faces in his vault-as-memory pattern; the explicit benchmark numbers (once code is read) will let him pick where on that frontier he wants to sit. Pairs with **WUPHF** [gh:nex-crm/wuphf] (June 21 digest, per-agent MCP scoping + private notebooks vs shared wiki) at the implementation level — WUPHF's notebooks/wiki split is precisely the access-control primitive GateMem would test.
- **Action signal:** `try-now` — clone the benchmark, run it against Justin's current vault-as-memory pattern (vault = shared wiki, daily-note inbox = per-agent scratchpad) to measure utility / access-control / forgetting on a stack that's already deployed. Reproduce the "RAG leaks deleted information" finding locally before shipping any product feature that involves user-requested deletion of agent-stored data.

### 3. VibeThinker-3B — 3B Dense Reasoning Model Claiming Frontier-Tier Math/Code Numbers
- **Source:** arXiv (cs.CL, 2026-06-15; HuggingFace Daily Papers featured 2026-06-22)
- **Link:** https://arxiv.org/abs/2606.16140
- **Authors / org:** WeiboAI
- **Focus area:** Local & open models for Apple Silicon / reasoning / frontier models
- **What it is:** 3B-parameter dense model trained via **Spectrum-to-Signal post-training paradigm** — curriculum-based SFT + multi-domain RL + offline self-distillation. Reported benchmarks: **AIME26 94.3 (97.1 with test-time scaling), LiveCodeBench v6 80.2 Pass@1, LeetCode contests 96.1% acceptance on unseen problems, IFEval 93.4**. The authors claim performance "matches or exceeds flagship models that are orders of magnitude larger, such as DeepSeek V3.2, GLM-5, and Gemini 3 Pro," and propose a **Parametric Compression-Coverage Hypothesis** — verifiable reasoning compresses into small models while general knowledge requires broader parameter coverage. Code/model availability not specified in the abstract (verify on HF).
- **Why it matters for Justin's agents:** If the AIME26 94.3 + LCB-v6 80.2 numbers reproduce, **a 3B model fits trivially in the M5 Max's 64 GB unified memory** (≤2 GB at Q4) and clears headroom for a 30K-context KV cache and concurrent tool calls. That makes it the candidate **verifier / planner** in a Claude-as-executor + local-as-verifier pattern — outsource expensive deliberation to the local model. The Compression-Coverage Hypothesis is the testable claim: if verifiable reasoning genuinely fits in 3B, the right local-agent topology is **a small reasoning model + a small retrieval-tuned model + a base model for general dialogue**, not a single monolithic 30B+ model. **Caveat:** WeiboAI benchmark claims need independent confirmation — recent small-model-beats-frontier announcements (Spectrum series, RAGEN-Mini) have often failed to replicate cross-decoder. Wait for HF leaderboard cross-check before swapping it into a pipeline.

### 4. OpenAI Codex Record & Replay — Workflow Capture → Reusable macOS Skills
- **Source:** OpenAI Developers (product launch, 2026-06-18; first surfaced via Releasebot 2026-06-19)
- **Link:** https://developers.openai.com/codex/record-and-replay
- **Authors / org:** OpenAI Codex team
- **Focus area:** Tools & connectors / coding agents / agent memory
- **What it is:** macOS-only feature that **observes a user's GUI workflow + window content** during a recording session, then **drafts a reusable Skill** describing when to use the workflow, what inputs it needs, the steps to execute, and verification criteria. The Skill becomes reusable context for Codex on subsequent tasks; Codex executes against **Computer Use, browser actions, and connected plugins**. Best-practice docs recommend short demonstrations with realistic inputs and refining the auto-generated skill to capture preferences (naming conventions, decision criteria). Requires Computer Use enabled; initially unavailable in EEA / UK / Switzerland. Team plans support sharing recorded skills broadly.
- **Why it matters for Justin's agents:** This is the **first production-deployed implementation of demonstration-to-skill induction** at general-purpose scope. Compare against **SkillMigrator** [arxiv:2606.17645] (June 17, layout-similarity skill retrieval), **CODESKILL** [arxiv:2605.25430], and the SKILL.md auto-mining paper [arxiv:2606.20363] (which found pure trajectory-mining + GRPO underperforms frequency priors). Record & Replay sidesteps the auto-mining failure mode by **keeping the human in the demonstration loop and letting the LLM draft the skill text**, not learn the policy. For Justin's federal-data-engineer work where the same multi-step UI workflow (e.g., a specific agency portal submission flow) repeats across data sources, this is the cleanest tooling fit on the market — assuming OpenAI's Computer Use is acceptable. **Architectural lesson** that generalizes regardless of provider: the demonstrate → LLM-drafted-skill-text → runtime-uses-skill-as-context pattern is what works, while raw trajectory mining without human-in-the-loop does not.
- **Action signal:** `try-now` — if Justin has a Codex / Computer Use seat, record one canonical workflow (e.g., the daily-digest publication flow) and inspect the auto-drafted Skill. Even without Codex, copy the skill-format pattern into a Claude Code Skill — the demonstration → LLM-drafted Skill text approach is provider-agnostic.

### 5. Recall — Deterministic Local Project Memory for Claude Code (TF-IDF + TextRank, No LLM API)
- **Source:** GitHub (Hacker News, 96 points, 2026-06-21)
- **Link:** https://github.com/raiyanyahya/recall
- **Authors / org:** Raiyan Yahya
- **Focus area:** Agent memory / tools & connectors / local inference
- **What it is:** Claude Code plugin that captures session activity (prompts, responses, files touched, commands run) into an append-only `.recall/history.md` log, then on demand regenerates `.recall/context.md` — a ~1–2K-token compact digest containing goal, status, next steps, and recent git info. **Summarization is deterministic via TF-IDF + TextRank**, *not* an LLM call — no network, no API key, no token cost. On session start, the plugin surfaces prior context and asks whether to resume. Treats `context.md` as untrusted reference data, fenced in the transcript. MIT-licensed, Python stdlib core (NumPy optional). Distributed via the Claude Code plugin marketplace.
- **Why it matters for Justin's agents:** Recall implements the **episodic-memory layer** Justin's vault currently does manually — `history.md` is the daily-note inbox, `context.md` is the consolidated note. Two things make it interesting beyond a one-shot tool: **(a) Deterministic summarization** dodges the **consolidation-decay** failure mode from [arxiv:2605.12978] (54% of ARC-AGI wins regressed after LLM consolidation) — TF-IDF/TextRank is monotonic, idempotent, and incapable of hallucinating new "facts." It trades retrieval *recall* for *correctness*. **(b) Zero token cost** for memory consolidation means Justin can run it on every session boundary on every project without budget anxiety. It composes with **WUPHF** [gh:nex-crm/wuphf] (June 21 digest) as the *single-developer* equivalent of WUPHF's multi-agent wiki, and with **MATM** [arxiv:2606.19911] as a no-LLM consolidator that wouldn't corrupt raw trajectories. Open question: does the deterministic-summary digest survive the GateMem [arxiv:2606.18829] forgetting test (i.e., when the user asks Recall to forget X, does TF-IDF actually re-weight to remove X's terms from `context.md`, or do they persist)?
- **Action signal:** `try-now` — `npx /plugin install recall@recall` against Justin's existing vault, run for a week alongside the current daily-digest workflow, compare `context.md` against the human-curated daily notes on retrieval accuracy. If signal is positive, the digestion routine itself could swap from LLM-synthesized to TextRank-synthesized to reduce per-day token spend.

### 7. Think Again or Think Longer? — Selective Verification Beats Always-Verify on Budget
- **Source:** arXiv (cs.CL, 2026-06-18)
- **Link:** https://arxiv.org/abs/2606.19808
- **Authors / org:** Sajib Acharjee Dip, Dawei Zhou, Liqing Zhang (Virginia Tech affiliations indicated)
- **Focus area:** Reasoning & inference-time compute / evaluation
- **What it is:** Introduces **SEVRA (Selective Verification for Reasoning Allocation)**, which decides per-example whether to verify a model's initial answer or accept it. Diagnoses that **extra reasoning is not uniformly valuable**: it can repair failed attempts, waste compute on already-correct answers, **or introduce harmful answer changes** (verifier-induced regressions). On **MATH-500**, selective verification achieves 76.3% accuracy while cutting post-generation tokens 26.8%. On **GSM8K transfer**, the selective policy **verifies only 3% of examples**, improves accuracy from 93.4% → 94.5%, and **reduces verification tokens 91.2%**. The paper's main recommendation is to **tune the initial reasoning budget first**, then apply selective recovery only "when explicit checks, bounded retries, auditability, or regression-risk control matter."
- **Why it matters for Justin's agents:** Composes directly with **GRACE** [arxiv:2606.19354] (granularity-regulated verification) and the broader May 2026 inference-time-compute cluster. The actionable finding is the **91.2% token reduction with accuracy gain** — the right verifier composition is gated on a cheap predictor, not always-on. For Justin's product loops where each call has real cost (companion-app per-message budget, batch processing for federal data), the gate is the win, not the verifier itself. Also a useful warning: **verifier-induced regressions exist** — a follow-up reasoning pass can flip a correct answer to incorrect. This is the same regression-from-extra-thinking failure mode as **consolidation-decay** [arxiv:2605.12978] (54% of ARC-AGI wins regressed after LLM consolidation) but at a finer time scale (single-call instead of cross-session). The pattern repeats across the stack: **adding more LLM compute is not monotonically improving on already-correct outputs.**
- **Action signal:** `compare` — see Conflicts. Watch for SEVRA code release; the gating predictor is the load-bearing component and the paper's value depends on whether it generalizes off-distribution.

## Conflicts & open questions

Cross-referenced against `_meta/claims-ledger.md`:

- **Compounding-or-competing? — Connect the Dots vs. the frozen-LLM memory-self-evolution cluster.** Today's [arxiv:2606.20002] **Connect the Dots** trains the *base LLM* via end-to-end RL on rollouts that include explicit context-updating phases — i.e., the meta-capability lives in the weights. The June 17–20 cluster — **MATM** [arxiv:2606.19911], **MAA** [arxiv:2606.20475], **AtomMem** [arxiv:2606.19847], **OPD-Evolver** [arxiv:2606.17628], plus May's SkillsVote / Ratchet / EvolveMem — wraps a *frozen* LLM with post-hoc memory or skill-evolution machinery. The two layers should compound: an LLM pre-trained to *use* a context-updating scratchpad ought to derive more value from a MATM-style trajectory store or a MAA-style cross-batch accumulator. But nobody has tested it. **Open empirical question:** does a Connect-the-Dots-trained model + MAA accumulator beat (a) Connect-the-Dots alone, (b) MAA wrapping a stock base model, (c) the sum of (a) + (b) in additive terms? If pre-training the meta-capability subsumes the wrappers' gains, the post-hoc-memory cluster loses much of its production-time justification; if they compound, the operational stack is "pick a Connect-the-Dots-class base model + layer MAA / MATM / AtomMem on top." Need to track upcoming Qwen-series checkpoints for Connect-the-Dots-style training mentions.

- **Open question — GateMem applied to Recall.** [arxiv:2606.18829] **GateMem** says no current memory system jointly achieves utility + access control + forgetting. **Recall** [gh:raiyanyahya/recall] uses **deterministic TF-IDF + TextRank** for summarization. Deterministic summarization should make forgetting **easier than LLM-based consolidation** (when the user asks Recall to forget X, simply re-running TF-IDF on a corpus with X removed should produce a `context.md` with X-related term weights at zero). But the *history* file is append-only — i.e., raw mentions persist. Empirical test: install Recall, log a session containing PII, run `/recall:save`, ask Recall to forget the session, then re-render `context.md` and grep for the PII terms. Reports the actual deletion guarantee Recall provides, which is the load-bearing question for any production deployment.

- **Open question — VibeThinker-3B reproducibility.** WeiboAI claims AIME26 **94.3** and LCB-v6 **80.2** at **3B parameters** matching **Gemini 3 Pro / DeepSeek V3.2 / GLM-5**. The Parametric Compression-Coverage Hypothesis is a strong testable claim — verifiable reasoning compresses into small models, general knowledge does not. Open empirical questions: (a) do the numbers reproduce on an independent eval harness (HuggingFace Leaderboard equivalent or a HarnessAudit-Bench [arxiv:2605.14271] re-eval), (b) does the model degrade on tasks requiring **broad world knowledge** (the hypothesis predicts it should — non-verifiable knowledge needs coverage), (c) does the **TTS gain (94.3 → 97.1)** indicate verifier-induced regression of the kind SEVRA [arxiv:2606.19808] just documented, or genuine refinement?

- **Open question — Connect the Dots' generalization-to-Ralph-loops claim.** The paper reports generalization "from Connect the Dots scenarios to Ralph-loop settings" but the specifics are deferred to the work-in-progress status. The Ralph-loop pattern is roughly *"agent that repeats a tool-using task at intervals, learning across runs"* — which is operationally the form Justin's autonomous routines (digest pipeline, monitor wake-ups) actually take. If generalization holds, base-model selection for those routines starts to depend on training objective, not just size/family. If it fails on the kind of long-tail tool-call distribution Justin's MCP stack produces, the meta-capability is benchmark-specific.
