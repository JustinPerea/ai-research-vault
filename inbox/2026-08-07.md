# AI Research Digest — Friday, August 7, 2026

## TL;DR
- **Activity Frames** [arxiv:2608.05784] compiles passively captured screen activity into agent memory *with no model in the loop*: typed frames (app, site, timing, input volume, evidence pointers), byte-identical and auditable. On one professional's 128,756 frames / 51 days it compresses a day **86× in 68 ms**; an agent reading the block answers day-questions at **98.4%** vs **66–80%** for an LLM summary of the same capture — and a mid-tier model matching a frontier one. Also the first demand-side measurement of Routine Overhead Ratio **R = 60–343×** and delegable recurrence **~8–9%**. Schema + compiler are open. Closest "what I actually did" memory primitive for Mitamaton.
- **HarnessOpt-Bench** [arxiv:2608.06301] finally makes "can the model improve the harness" a protocol: optimizer LLM + coding harness, seed harness, graded feedback, fixed eval budget, held-out test, trusted execution boundary. 5 frontier optimizers × shared vs native harnesses × 4 tasks, 111 scored runs. **Optimizer model separates more than the coding harness**; native harnesses are not consistently better; gains vary wildly by task and seed. Large headroom.
- **SkillProx** [arxiv:2608.07449] is the first skill-evolution recipe that treats *deletion* as a first-class consolidator, not a generic edit. Forward stage: diagnosis-driven edits, rollback on regression. Backward stage: leave-one-out utility audit of knowledge units, then validation-gated keep / demote / remove. **+3.0pp** average accuracy over the strongest gradient-based baseline, in- and out-of-distribution, multiple backbones.
- **Agent Memory Distillation** [arxiv:2608.07169] (KAIST) is the local-fit paper: training-free hierarchical teacher memory (Workflow / Subtask / Function) from a large teacher's successful traces into 4B–8B students. GPT-5-mini teacher. Average gains **+27.2 / +11.2 / +3.4pp** on AppWorld / BFCL V3 / ToolSandbox; 4B students benefit most; Function memory is retrieved only on tool-call errors.

## Items

### 1. Activity Frames: Deterministic Screen-Activity Compilation for Agent Memory and Replay
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.05784
- **Authors / org:** Nossa Iyamu (independent)
- **Focus area:** Agent memory from *what the user did* (not what they said)
- **What it is:** Zero-model compiler over a local screen-capture stream. Segments into typed activity frames — bounded episodes with application, site, timing, input volume, and pointers back to raw rows. Output is deterministic, cacheable, mechanically auditable. Single-user corpus: 128,756 frames, 51 active days. A day of raw capture → prompt-ready block **86× smaller in 68 ms**. Agent + compiled block: **98.4%** accuracy on day-questions (Wilson 95% CI 91.7–99.7%) vs 66–80% for an LLM summary of the same capture; mid-tier model matches frontier when both read the block. Demand-side cost instrument: Routine Overhead Ratio R (modeled upper bound) **60–343×**; delegable recurrence 9.0% in-sample / 7.7% out-of-sample; realistic all-fleet token ceiling near 8%. A compiled routine replays deterministically with the model out of the loop (live demo, zero model tokens, guard-matched hit). Schema, compiler, eval harness open.
- **Why it matters for Justin's agents:** Mitamaton's memory today will be notes and chat. This paper says the high-value memory is **the compiled day** — which apps, which sites, how long, how much typing — and that an LLM *summary* of that day is the wrong compression. Two experiments: (1) if Justin already has any screen/window telemetry (or even RescueTime-like logs), compile it into frames and ask yesterday-questions against the block vs against a Claude summary; (2) treat recurring compiled frames as replayable routines instead of re-prompting Opus to "do what I did Tuesday." Privacy: this is local, deterministic, and auditable — a better fit for a 64 GB Mac than a cloud "memory manager."
- **Action signal:** `try-now` — even a thin version (app + time-bucket + URL host, no pixels) is enough to test the 98% vs 66–80% claim on a week of Justin's own logs.

### 2. HarnessOpt-Bench: Evaluating LLMs at Harness Optimization
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.06301
- **Authors / org:** Varun Ursekar / Apaar Shanker / Yash Maurya / Shehab Yasser / Vijay S. Kalmath / Veronica Chatrath / Yuan Xue
- **Focus area:** Harness evolution (eval protocol)
- **What it is:** Common protocol for "the model edits the harness." Optimizer = LLM + coding harness; input = target agent's seed harness + graded feedback + fixed target-eval budget; output = nominated candidate scored by normalized gain over seed on a held-out test partition the optimizer never sees. Trusted execution environment enforces the eval boundary, meters resource use, versions candidates. 5 frontier LLMs as optimizers, shared coding harness *and* each model's native harness, 4 downstream tasks, 111 scored runs. Findings: optimizer models separate more than the coding harnesses they act through; native harnesses are not consistently superior; gains vary substantially across tasks and seed regimes. Harness optimization is measurable, discriminative, and far from solved.
- **Why it matters for Justin's agents:** The vault already believes "harness > weights" (Writer Harness Effect, PILOT, WikiSkill). This is the first shared *yardstick* for the claim that a model can *edit* that harness. Practical use: if Justin lets Claude Code rewrite its own prompts / tool wrappers / Mitamaton skills, run the edit against a held-out personal set and report normalized gain — not "the agent said it got better." Native-vs-shared result: do not assume Claude Code's own harness is the best optimizer environment.
- **Action signal:** `compare` — wrap one Mitamaton skill-edit loop in this protocol (seed / budget / held-out) before trusting auto-evolution.

### 3. SkillProx: Self-Evolving Agent Skills via Proximal Textual Gradient Descent
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2608.07449
- **Authors / org:** Mingxuan Zheng / Yujin Zhou / Chuxue Cao / Boqin Yin / Yuyao Zhang / Jiapeng Sun / Shuaishuai Gong / Sirui Han et al.
- **Focus area:** Agent skill evolution (deletion as consolidator)
- **What it is:** Skills as textual artifacts loaded into context, no weight updates. Prior loops diagnose and edit but treat deletion as just another patch. SkillProx: proximal-gradient-inspired forward–backward. Forward: re-execute diagnosis-driven edits on the same batch, roll back regressions, feed measured outcomes into the next diagnosis. Backward: decompose the skill into auditable knowledge units, frozen leave-one-out utility audit, then validation-gated consolidation / demotion / removal. +3.0pp average accuracy vs strongest gradient-based baseline on ID and OOD, multiple backbones. Ablations: closed-loop diagnosis and proximal refinement are complementary.
- **Why it matters for Justin's agents:** WikiSkill [arxiv:2608.27454] never rolls the wiki back and gates on val score. SkillProx's distinctive move is **unit-level deletion**. A `SKILL.md` that accretes workarounds needs a leave-one-out pass. Weekend shape: split a bloated skill into bullets, drop one at a time against a 10-task set, demote the ones that do not pay for their tokens. Complements SkillJack (yesterday): deletion is also how you retire a poisoned unit — if you can find it.
- **Action signal:** `compare` — run a leave-one-out delete pass on the three longest Claude Code skills before writing new ones.

### 4. Agent Memory Distillation: Empowering Small LLM Agents with Hierarchical Teacher Memory
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2608.07169
- **Authors / org:** Taeil Kim / Kangsan Kim / Sung Ju Hwang — KAIST
- **Focus area:** Local / small-agent memory (training-free distillation)
- **What it is:** Training-free transfer of structured knowledge from a large teacher agent to a 4B–8B student via hierarchical memory. Three types from successful teacher trajectories: **Workflow** (task-level strategies), **Subtask** (concrete behavioral examples), **Function** (per-function calling conventions + pitfalls). Workflow + Subtask injected proactively at task start; Function retrieved reactively on tool-call errors. Four student models (4B–8B), GPT-5-mini teacher, three tool-use benchmarks. Average accuracy gains **+27.2pp AppWorld, +11.2pp BFCL V3, +3.4pp ToolSandbox**, beating existing memory baselines. Subtask memory contributes the largest gains; teacher effectiveness depends on teacher capability *and* student compatibility; 4B students benefit most.
- **Why it matters for Justin's agents:** This is the local 64 GB recipe the vault has been circling: **evolve / succeed on a cloud teacher (Opus / GPT), ship markdown memory to Qwen3-4B / 8B, retrieve Function memory only on error.** Do not fine-tune the 4B to imitate the teacher — give it the teacher's *structured* traces. The 4B-benefits-most result matches WikiSkill's "small model + good skills can beat a bigger model with none," with the added routing split (proactive vs on-error).
- **Action signal:** `try-now` — from a handful of successful Claude Code sessions, write one Workflow + two Subtask notes for a Mitamaton tool, and a Function note that only injects on that tool's error.

## Conflicts & open questions
- **Convergent:** Activity Frames + Agent Memory Distillation + PAST-Bench (2026-08-04) all say memory quality is about *structure and pathway*, not "store more text." They disagree on the source: screen frames (what you did), teacher trajectories (what a stronger agent did), or the agent's own retained experience (what *it* did). Unrun experiment: which single source moves Mitamaton.
- **Open question vs WikiSkill / SkillProx:** WikiSkill never rolls the wiki back; SkillProx's backward pass exists to delete. If both are right, the wiki layer should be append-only *patterns* and the skill layer should be deletion-aware *units*. Do not collapse them.
- **No conflict flagged** against HarnessOpt-Bench — it is a protocol, not a method claim. Evo-Bench [arxiv:2608.09096, Mon] is the sibling benchmark; compare then.
