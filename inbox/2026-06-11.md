# AI Research Digest — Thursday, June 11, 2026

## TL;DR
- **Memory layer for coding agents lands as a working repo.** PROJECTMEM (arxiv:2606.12329) ships an **MCP-served, append-only, plain-text event log** that gates an agent before it repeats a failed debugging attempt or edits a fragile file — explicit "memory-as-governance" framing. Two-month self-study across 10 projects, 207 logged events, claimed **5–20k tokens saved per session**. Three-dependency Python package, github.com/riponcm/projectmem — closest thing to a drop-in for the Fable 5 / Opus 4.8 file-based-memory pattern Justin would actually run today.
- **Hierarchical "file-system" memory keeps making numerical gains.** HORMA (arxiv:2606.11680) organizes experience as a hierarchy that links summarized data to detailed trajectories, then trains a small RL navigator to pull *minimal sufficient* context; **token usage drops to 22.17% of baseline on long conversations** while ALFWorld / LoCoMo / LongMemEval scores improve. Same broad direction as Infini Memory (2026-06-10) and MAGE / HORMA-style tree memory cluster — file-system metaphor is winning over flat vector stores.
- **An autonomous-research agent beats Claude Code on six research tasks.** Arbor (arxiv:2606.11926, 18-author RUC NLPIR + collaborators) pairs a **long-lived coordinator + short-lived executors + Hypothesis Tree Refinement** linking hypotheses → artifacts → evidence → insights; **2.5× the average relative held-out gain over Codex and Claude Code**, **86.36% Any Medal on MLE-Bench Lite with GPT-5.5**. Frames hypothesis-tree-as-persistent-state — direct continuation of [arxiv:2606.06448] systems-level memory taxonomy applied to research workflows.
- **Multi-turn compression keeps composing.** Doc-to-Atom (arxiv:2606.12400) emits **per-document micro-LoRA adapters with retrieval keys**, lets a lightweight router select+combine atoms at inference (continues the LatentSkill / Code2LoRA hypernetwork-LoRA-as-context line — third modality in two weeks); C-DIC (arxiv:2606.12411, ICML 2026) treats dialogue history as **revisable interleaved threads** with TBPTT for cross-turn dependencies.
- **Governance / orchestration formalism is maturing fast.** Five-Plane Reference Architecture (arxiv:2606.12320, 65 pages) — reasoning plane + 4 enforcement planes (network/identity/endpoint/data), six interruption primitives, **single-digit-microsecond adjudication**, foreclosure of seven production-agent threats. Pairs with [arxiv:2606.04306] OCL and [arxiv:2606.04896] CADVP from earlier this week to triangulate the **synchronous-gate execution-boundary cluster**.
- **Self-distillation gets a turn-level supervision signal.** HERO (arxiv:2606.11559) converts each environment observation into a compact diagnostic ("was this action necessary, valid, why did it fail") rather than relying on terminal outcomes; outperforms environment-feedback-only baselines and GRPO on **TauBench and WebShop** under limited-rollout budgets.

## Items

### 1. PROJECTMEM — Local-First, Event-Sourced Memory and Judgment Layer for AI Coding Agents
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.12329
- **Authors / org:** Ripon Chandra Malo, Tong Qiu (affiliation not stated; code at github.com/riponcm/projectmem)
- **Focus area:** Agent memory; Tools & connectors (MCP); Coding agents
- **What it is:** A **local-first, offline-first, append-only plain-text event log** (issues, attempts, fixes, decisions, notes) projected deterministically into compact AI-readable summaries over **14 MCP tools + 19 CLI commands**. Includes a **memory-as-governance** layer — a deterministic pre-action gate that warns the agent before it repeats a failed fix or edits a known-fragile file. Two-month self-study: 10 projects, 207 logged events, **5,000–20,000 tokens saved per session**. Three-dependency Python package, CC BY 4.0.
- **Why it matters for Justin's agents:** This is the most immediately deployable artifact in today's batch. Justin already runs Claude Code + MCP heavily and pulls notes into Obsidian — PROJECTMEM is structurally a **per-project event journal that MCP exposes back to Claude**, exactly the "compact persistent memory across sessions" gap that Fable 5's file-based memory release implicitly assumes you'll fill at the application layer. The append-only log is auditable, diff-friendly, and survives outside the IDE — fits the way the AI research vault itself is structured. The pre-action governance gate is the more novel piece: it operationalizes "don't repeat the bug you already failed to fix" as a *deterministic check* rather than relying on the model's recall of prior context. Worth a single-evening integration trial on one of his agent products.
- **Action signal:** `try-now`

### 2. HORMA — Organize then Retrieve: Hierarchical Memory Navigation for Efficient Agents
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.11680
- **Authors / org:** Hao-Lun Hsu, Nikki Lijing Kuang, Boyi Liu, Zhewei Yao, Yuxiong He (Zhewei Yao + Yuxiong He are DeepSpeed/Microsoft DeepSpeed-era infra leads)
- **Focus area:** Agent memory; Context engineering
- **What it is:** Two-stage memory framework: (1) structured construction that **distinguishes information gaps from misleading / overloaded context** before storing, (2) **navigation-based retrieval via a lightweight RL-trained navigator** that traverses a file-system-like hierarchy linking summaries to detailed trajectories. No lossy compression — summaries are *pointers* into raw trajectory blocks. Headline: **token usage reduced to at most 22.17% of baseline on long conversations** while improving accuracy on ALFWorld, LoCoMo, LongMemEval; generalizes to unseen tasks.
- **Why it matters for Justin's agents:** Continues the **file-system / tree memory** convergence that's run through MAGE ([arxiv:2606.06090] state tree), SegTreeMem ([arxiv:2606.04555] temporal tree), PersonaTree ([arxiv:2606.04780] lifecycle tree), and now Infini Memory + HORMA in the past week. HORMA's distinctive piece is the **summary-as-pointer** design — no information loss at storage, only at retrieval *selection*; this is the right architecture if you ever need to recover detail you previously thought irrelevant (common in agent debugging). The RL navigator is cheap-to-host (small policy net), so the whole stack composes cleanly with Justin's existing Claude-as-executor + small-controller pattern.
- **Action signal:** `track` (waiting for code; if released, immediately `try-now` for companion-app long-conversation memory)

### 3. Arbor — Toward Generalist Autonomous Research via Hypothesis-Tree Refinement
- **Source:** arXiv (Hugging Face Daily Papers #3, 31 upvotes)
- **Link:** https://arxiv.org/abs/2606.11926
- **Authors / org:** Jiajie Jin et al. (18 authors, RUC NLPIR Lab + collaborators)
- **Focus area:** Agent orchestration; Long-running / autonomous loops; Coding agents
- **What it is:** Autonomous-research agent framework with three coupled pieces — **long-lived coordinator + short-lived executors in isolated environments + Hypothesis Tree Refinement (HTR)** that links hypotheses ↔ artifacts ↔ evidence ↔ distilled insights across time. Introduces an **Autonomous Optimization (AO) evaluation setting** where agents iteratively improve research artifacts. Headlines: **>2.5× average relative held-out gain over Codex and Claude Code** across six research tasks (model training, harness engineering, data synthesis); **86.36% Any Medal on MLE-Bench Lite with GPT-5.5** (strongest in their comparison). Long-lived/short-lived split echoes Justin's existing supervisor + executor pattern.
- **Why it matters for Justin's agents:** This is the **planner-executor split with persistent state pattern** Justin is already using, written up at frontier-research scale. Two specific transferable pieces: (a) the **hypothesis tree as persistent connective tissue** between long-lived and ephemeral agents — solves the "the coordinator forgot what executor #4 found" failure mode; (b) the **AO evaluation setting** (artifact-improvement-under-iteration) as an internal benchmark template for any agentic dev tool he ships. Note the explicit *beats-Claude-Code* claim — this lands in a week when Claude Code coding-agent results are otherwise dominant (Fable 5 SWE-Bench-Pro 80.3%); the difference is research/optimization workload vs SWE-Bench-style bug-fix workload. Flagged below in conflicts.
- **Action signal:** `compare` — extends and contradicts a recent claims-ledger thread

### 4. DeNovoSWE — Scaling Long-Horizon Environments for Generating Entire Repositories from Scratch
- **Source:** arXiv (Hugging Face Daily Papers, 21 upvotes)
- **Link:** https://arxiv.org/abs/2606.10728
- **Authors / org:** Jiale Zhao, Guoxin Chen, Fanzhe Meng, Wayne Xin Zhao, Ruihua Song, Ji-Rong Wen, Kai Jia
- **Focus area:** Coding agents; Local & open models for Apple Silicon
- **What it is:** Large-scale **whole-repository-generation dataset**: 4,818 high-quality instances each requiring a complete repo from documentation. Built via a sandboxed agentic workflow (divide-and-conquer per-capability decomposition + iterative critic-repair to fix omissions/inconsistencies in the generated docs) with difficulty-aware trajectory filtering — **no human annotation**. Headline result: **fine-tuning Qwen3-30B-A3B on DeNovoSWE lifts BeyondSWE-Doc2Repo from 5.8% → 47.2%** (≈8× improvement).
- **Why it matters for Justin's agents:** Two reasons. First, **Qwen3-30B-A3B is the M5-Max sweet spot model** — 30B-param MoE with 3B active fits comfortably in 64 GB unified memory under MLX, runs at usable tok/s. The DeNovoSWE dataset is the missing ingredient if Justin wants to LoRA-tune a *local* coding agent for whole-repo-bootstrap workloads (his federal-data-engineer side hits "scaffold a new repo" tasks regularly). Second, the data-construction pipeline itself (sandboxed agentic workflow → critic-repair → difficulty filter, all annotation-free) is reusable — applies to any "agent learns from synthetic-but-verifiable trajectories" loop he wants to set up. Composes with [arxiv:2606.04703] Rethinking Continual Experience Internalization (principle-level granularity, off-policy distillation) as a *what-to-train-on* counterpart to *how-to-train*.
- **Action signal:** `local-fit` (the Qwen3-30B-A3B base is the runnable piece) + `track` (dataset release)

### 5. HERO — Hindsight-Enhanced Reflection from Environment Observations for Agentic Self-Distillation
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.11559
- **Authors / org:** Haoran Liu, Yuwei Zhang, Xiyao Li, Bohan Lyu, Jingbo Shang (UCSD style affiliations)
- **Focus area:** Agent orchestration; Reasoning & inference-time compute
- **What it is:** Self-distillation framework for multi-turn agents. The problem it names: most self-distillation uses **privileged terminal feedback** (succeeded? final score?) which is misaligned with the *local* context of any given decision. HERO converts each environment observation into a **compact turn-level diagnostic** ("was this action necessary, was it valid, why did it fail") — dense, locally-aligned supervision. Beats environment-feedback-only baselines and GRPO on **TauBench and WebShop**, especially under limited-rollout budgets where successful trajectories are scarce.
- **Why it matters for Justin's agents:** The locally-aligned-supervision insight is more important than the specific HERO architecture. Every long-horizon agent Justin builds will eventually want to learn from its own runs — the standard "terminal reward + GRPO" recipe fails on the workloads where successful runs are rare (which is exactly federal-data-engineer territory: rare success + lots of partial-progress signal). HERO's "per-turn local diagnostic from environment observations" is reusable as a **labeling primitive** even outside RL — e.g., for trace-mining experience replay or for trajectory filtering before context injection.
- **Action signal:** `track`

### 6. Doc-to-Atom — Learning to Compile and Compose Memory Atoms
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.12400
- **Authors / org:** Xingjian Diao, Wenbo Li, Yashas Malur Saidutta, Avinash Amballa, Lazar Valkov, Srinivas Chappidi
- **Focus area:** Agent memory; Context engineering
- **What it is:** Document internalization via **semantically typed knowledge atoms**, each compiled into an **independent micro-LoRA adapter** with retrieval keys. A lightweight router selects + combines only the relevant atoms at inference. End-to-end trained with multi-objective distillation. Outperforms Doc-to-LoRA baselines on six QA benchmarks while reducing the memory cost of document internalization.
- **Why it matters for Justin's agents:** This is the **third hypernetwork-LoRA-as-context paper in 14 days** — after [arxiv:2606.06087] LatentSkill (skill descriptions → LoRA via hypernet) and [arxiv:2606.06492] Code2LoRA (per-repository LoRA from code state). Doc-to-Atom completes the triangle with **document-level atoms**, and adds the key refinement: *one LoRA per atom*, not per document. The router-over-atoms primitive is what makes this composable with memory architectures like HORMA or PROJECTMEM — the atom set IS the retrieval index, and the LoRA *is* the retrieved content. Convergence signal: per-X-LoRA is no longer a one-off trick, it's becoming the third memory substrate alongside vector stores and KV cache.
- **Action signal:** `track`

### 7. Five-Plane Reference Architecture for Runtime Governance of Production AI Agents
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.12320
- **Authors / org:** Krti Tallam (single-author position/architecture paper, 65 pages)
- **Focus area:** Agent orchestration; Tools & connectors
- **What it is:** Architectural blueprint for production-agent governance. Decomposes the runtime into **one reasoning plane + four enforcement planes (network, identity, endpoint, data)** with four composable primitives: **stop-anywhere mediation, composite principals with capability attenuation, structured audit substrate, six interruption primitives generalizing allow/deny**. Defines four formal correctness invariants. Threat coverage: seven production-agent threats across five concrete workflows foreclosed. Quantitative claims: **single-digit-microsecond adjudication**, attenuation correctness validated on every trial, evidence reconstructability consistent.
- **Why it matters for Justin's agents:** Governance is the layer that turns a working demo into something a federal data engineer can actually deploy. The **six interruption primitives** (generalizing allow/deny) and **composite principals with capability attenuation** are the most directly portable concepts — both apply to MCP server design where Justin already controls how a tool's authority is delegated to sub-tools. Pairs naturally with the synchronous-gate cluster ([arxiv:2606.04306] OCL, [arxiv:2606.04896] CADVP, [research-google-blog-2026-06-05] Sufficient Context Agent): OCL guards execution, CADVP guards cross-agent memory writes, Sufficient Context Agent guards retrieval, and Five-Plane is the **outer scaffold** that says where those gates plug in.
- **Action signal:** `track`

### 8. Agentic Environment Engineering for LLMs — Survey
- **Source:** arXiv (Hugging Face Daily Papers #1, 40 upvotes)
- **Link:** https://arxiv.org/abs/2606.12191
- **Authors / org:** Jiachun Li et al. (15-author survey, Chinese Academy of Sciences style)
- **Focus area:** Agent orchestration; Evaluation
- **What it is:** 63-page systematic survey of **environments for LLM agents**. Frames the lifecycle as Modeling → Synthesis → Evaluation → Application. Categorizes environments across 8 attributes × 8 application domains; introduces **symbolic vs neural synthesis paradigms** with paired evaluation; identifies **four agent-environment co-evolution pathways** (memory-centric experience evolution, orchestration-centric workflow evolution, trajectory-centric offline evolution, exploration-centric online evolution); proposes three environment-evolution models (neural-driven, difficulty-driven, scaling-driven) and three forward-looking framings (Environment-as-a-Service, Multi-agent Environments, Neural-Symbolic Environments).
- **Why it matters for Justin's agents:** Surveys are usually `track`-not-`try-now`, but this one is worth keeping in the vault as a *map of the territory* the past two months of digests have been independently mapping piecewise. The four co-evolution pathways — especially **memory-centric experience evolution** and **orchestration-centric workflow evolution** — are the clean axes along which the AutoMEM / Vortex / RHO / AutoLab / Socratic-SWE / MLEvolve / Arbor papers from the last 14 days actually divide. Useful as the reference outline for any longer-form post Justin writes about how he architects his agents.
- **Action signal:** `track`

## Local-model corner
Today's only directly local-runnable item is the **base model used in DeNovoSWE fine-tuning** — Qwen3-30B-A3B. PROJECTMEM is local-first by design (no inference, just an event log), so it doesn't need a model-fit math entry.

- **Model:** Qwen3-30B-A3B (30B-param MoE, ~3B active params per token)
- **Memory fit:** ~16–18 GB at Q4 (Q4_K_M GGUF or MLX 4-bit), leaves ~45 GB headroom for KV cache + system → comfortably supports 64k–128k context windows with room to spare; at Q5/Q6 ~22–28 GB, still fits with 32k+ KV
- **Realistic tasks:** light-to-medium agentic coding (file edits, multi-step toolcalls), Python/TypeScript completion, structured tool-result synthesis, *experimental* whole-repo bootstrap if you fine-tune on DeNovoSWE-style data (5.8% → 47.2% on BeyondSWE-Doc2Repo is for the fine-tuned variant; the stock base will be much weaker on doc→repo). Not a replacement for Fable 5 / Opus 4.8 on hard SWE-Bench / Terminal-Bench tasks.
- **How to run:** `mlx_lm.server` with the official Qwen3 MLX repo (best on M5 Max), or `llama.cpp` with the Q4_K_M GGUF if you want broader tool ecosystem support (Ollama / LM Studio both wrap it cleanly). MLX path expected to give noticeably better tok/s on M5 Max specifically.
- **Speed estimate:** No published M5 Max benchmark yet; based on Qwen3-30B-A3B numbers reported on M4 Max 64 GB (~55–70 tok/s at Q4 via MLX-LM), **M5 Max should sit in the 70–95 tok/s range at Q4** given the ~30–40% memory-bandwidth uplift and IPC improvements. Drop to ~40–55 tok/s at Q6.

For Justin specifically: if you want a local *coordinator* for the planner-executor pattern (Arbor item #3, HORMA item #2), Qwen3-30B-A3B at Q4 is the right size — fast enough to drive a tight reasoning loop while leaving Fable 5 / Opus 4.8 for the heavy executor calls.

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:

- **Arbor's "2.5× over Claude Code on six research tasks" vs the Fable 5 frontier-coding-agent narrative.** Anthropic's June 9 release ([anthropic-news-2026-06-09-claude-fable-5-mythos-5]) anchors Fable 5 at 80.3% SWE-Bench Pro (+11 over field) and 88.0% Terminal-Bench 2.1 — i.e., Claude Code is at its strongest position on **bug-fix / terminal / SWE-Bench-style** workloads. Arbor's claim is on **research/optimization workloads** (model training, harness engineering, data synthesis) where the workload structure is open-ended hypothesis search rather than localized code change. **These are not in direct contradiction** — they're measuring different things — but the gap is worth tracking: if "agent that beats Claude Code on research" generalizes back into coding-adjacent work, that's a real shift. Compare with [arxiv:2606.06453] Vortex (agents author their own sparse-attention algorithms), [arxiv:2606.06473] MLEvolve (beats AlphaEvolve on math optimization), [arxiv:2606.05922] RHO — Arbor is the *fourth* recent agent-improves-its-own-stack result that beats a named frontier baseline on a non-SWE-Bench task. The cluster is now too large to dismiss as cherry-picked.

- **Open question:** HORMA's 22.17% baseline-token reduction is on LoCoMo / LongMemEval / ALFWorld — the same benchmark suite where EMBER ([arxiv:2606.05894] 71% relative F1 gain at 8192 tokens) and MRAgent ([arxiv:2606.06036] +23% on LoCoMo) and MAGE ([arxiv:2606.06090] +7.8–20.4pp / −55.1% tokens on MemoryArena) all post results. **No head-to-head comparison** yet exists across these four — and they each define "memory" differently (constrained retention vs reconstructed graph walk vs state tree vs file-system hierarchy). The field needs a unified eval where the same scaffolding swaps memory backends.

- **Open question:** PROJECTMEM's "5,000–20,000 tokens saved per session" is from a 2-month / 10-project self-study by the authors. The token-saving claim is plausible but the **selection effect is severe** (authors using their own tool, choosing what to log). Would want a third-party replication on a single benchmarked workload (e.g., SWE-Bench Verified with vs without the MCP layer) before treating the number as authoritative.
