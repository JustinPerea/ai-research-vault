## Items

### 1. PM-Bench: Evaluating Prospective Memory in LLM Agents
- **Source:** arXiv (COLM 2026)
- **Link:** https://arxiv.org/abs/2607.12385
- **Authors / org:** Genglin Liu, Saadia Gabriel
- **Focus area:** Agent memory (prospective / working)
- **What it is:** First LLM adaptation of cognitive science's Virtual Week paradigm — agents must execute an intention (e.g., "remind X when Y happens") at a *future* cue while running unrelated activities across a simulated 7-day horizon. Tests 8 frontier LLMs under varied memory strategies (no memory, scratchpad, structured episodic, retrieval).
- **Why it matters for Justin's agents:** "Deferred intent" is the load-bearing feature for always-on companion agents and long-running MCP loops — "notify me when the deploy finishes," "email X when the report is ready," "when the CI turns green, unpin the PR." The gap between top score (65.1% F1) and useful (~95%) is a real product wall, and *no single strategy dominates across models* — so plug-and-play mem0 wrappers won't rescue you; strategy must be co-designed with the base model. Third data point in the vault this week that **memory eval is fracturing along a dimension axis** (PM-Bench = prospective; MemOps = lifecycle ops; LightMem-Ego = egocentric streams).
- **Action signal:** `track` — no code released with abstract yet; watch for the eval harness so we can score our own companion-app loops against it. Also `compare` — extends the growing memory-benchmark cluster (LoCoMo, LongMemEval, Mem-Gallery) into a new time-deferred dimension.

### 2. MemOps: Benchmarking Lifecycle Memory Operations in Long-Horizon Conversations
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.12893
- **Authors / org:** Xixuan Hao, Zeyu Zhang, Zehao Lin
- **Focus area:** Agent memory (evaluation methodology)
- **What it is:** Reframes conversational memory as a sequence of *lifecycle operations* — remember, forget, update, reflect — rather than static facts. Structured traces include trigger, target, scope, state transitions, and evidence. Six operation-level probe categories under two evidence settings (adjacent vs. long-context).
- **Why it matters for Justin's agents:** Moves memory eval from "did the agent produce the right final answer" to "did the *update* op fire when it should have, on the right target, with the right scope?" That's exactly the debugging surface you actually need when a mem0-class store misbehaves in production. Findings that (a) session-level retrieval beats turn-level, and (b) long-context models struggle to reconstruct ordered memory-state trajectories, both cut against the "just paste history" default. Companion to Shared Selective Persistent Memory below — one gives you the eval, the other gives you a policy that scores well on it.
- **Action signal:** `track` — hoping for released probes so we can drop them into our own memory-store CI. Adopt the operation vocabulary in the memory-primitive doc.

### 3. Shared Selective Persistent Memory for Agentic LLM Systems
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.09493
- **Authors / org:** Sanjana Pedada, Aditya Dhavala, Neelraj Patil
- **Focus area:** Agent memory (semantic, shared)
- **What it is:** Argues code-generating agents shouldn't start from zero each session. Retains four reusable categories — task specs, data schemas, tool configs, output constraints — while discarding session-specific reasoning traces. Adds role-based access so the memory is shareable across users, with git-versioned artifacts. Zero-token refresh mechanism reloads the persistent slice without re-injecting raw content.
- **Why it matters for Justin's agents:** **96% task completion with the 4-category store vs 79% no-memory vs 71% dumping full history** is the cleanest published evidence yet that "just give it everything you have" is worse than "give it the right things." 14× task-time reduction from zero-token refresh, 97× per-invocation token savings vs raw injection. Direct blueprint for what to persist between Claude Code sessions and MCP-tool invocations — the four categories (specs / schemas / tool configs / output constraints) are copy-pastable as a memory schema for indie agent stacks.
- **Action signal:** `try-now` — implement the four-category persistent-slice pattern in one of the vault's MCP loops; measure token deltas. Also `compare` — flips the "more context = better" naive intuition (full-history 71% < no-memory 79%). Add to claims ledger as an "over-context penalty" data point.

### 4. A JoLT for the KV Cache: Near-Lossless KV Cache Compression via Joint Tucker and JL-Residual Allocation
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.12550
- **Authors / org:** Rahul Krishnan, Volker Schulz
- **Focus area:** Context engineering (KV cache, long-context serving)
- **What it is:** Treats the KV cache as a third-order tensor; partial Tucker decomposition on token/feature axes only, then restores truncated energy with a Johnson-Lindenstrauss rotated low-bit residual. One Lagrangian dual jointly allocates per-layer-group Tucker ranks *and* residual bit-widths, separately for K and V, under a single byte budget. FlashJoLT kernel makes compression 5–13× faster than the reference implementation.
- **Why it matters for Justin's agents:** **2–3× near-lossless compression on Mistral-7B-v0.3 and LLaMA-2-13B**, relative Frobenius error 0.009 (K) / 0.006 (V) at 2× — an order of magnitude below cross-layer SVD and 4-bit KV quant baselines. Perplexity, GSM8K, and RULER all preserved. For a 64 GB M5 Max serving a 32B-A3B or 70B-Q4 model with a big KV footprint, this is the difference between 32K and 64K–96K comfortable context — pure operational headroom with no weight touching.
- **Action signal:** `local-fit` — track for MLX and llama.cpp ports; the FlashJoLT throughput number (9,125 tok/s) suggests it's realistic on Apple Silicon once GGUF-side kernels land. Also `compare` — extends the running KV-cache thread (Jet-Long, TokenSelect, prior Tucker+bitwidth papers) with the first joint allocation.

### 5. StructAgent: Harness Long-horizon Digital Agents with Unified Causal Structure
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.11388
- **Authors / org:** Wenyi Wu, Sibo Zhu, Kun Zhou
- **Focus area:** Agent orchestration + long-running loops (computer-use)
- **What it is:** State-centered computer-use framework: replaces raw interaction history with a compact, verifiable *task-progress state* plus a structured workflow of verifier-backed transitions. Explicit progress checkpointing, evidence-driven completion criteria, and targeted failure-recovery paths.
- **Why it matters for Justin's agents:** OSWorld-Verified numbers are dramatic — Qwen3.5-9B **27.0 → 46.9%**, Qwen3.5-27B **31.6 → 62.2%**, MiniMax-M3 **78.9% (new open-source SOTA)**. The wrapper is doing more work than the backbone swap. Direct architectural template for any MCP tool that drives a UI — the checkpoint / verify / repair loop is the same shape as our gate-before-commit family, just applied to GUI actions instead of code commits.
- **Action signal:** `track` (with strong `compare`) — the "state + verifier-backed transitions" primitive is the *eleventh* convergent gate-before-commit instance in the vault this quarter. Update the family doc and cross-reference to StructAgent's specific formulation of the task-progress state.

### 6. Speculate with Memory: Lossless Acceleration for LLM Agents
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.12236
- **Authors / org:** Yu Li, Qinyuan Ye, Prafulla Kumar Choubey
- **Focus area:** Agent orchestration + agent memory (speculative execution)
- **What it is:** Turns the (usually stateless) speculator that pre-launches an agent's next step into a *memory-augmented predictor* with three online stores — a contrastive transition table for action-sequence statistics, episodic memory for similar past segments, and a confusion tracker to suppress recurring mistakes. All speculation runs during environment idle time (waiting on tools), so it's wall-clock-free and lossless.
- **Why it matters for Justin's agents:** Free latency win for any tool-calling MCP agent — the speculator fires during the seconds you're already waiting on the tool call. **19–39% relative action-prediction accuracy gain, up to 2.5× on observation prediction** in repetitive action spaces, across six benchmarks. Gains grow monotonically with accumulated memory, so deployment time compounds the benefit — same design intuition as skill-library maturation but at the speculation layer.
- **Action signal:** `try-now` — the pattern (contrastive transitions + episodic recall + confusion tracker, all fed by idle-time speculation) can be prototyped in a Claude Code MCP loop without waiting for the paper's code drop.

### 7. Function-Aware Fill-in-the-Middle Mid-Training for Coding Agents
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2607.12463
- **Authors / org:** Yubo Wang, Jiarong Liang, Yuxuan Zhang
- **Focus area:** Coding agents (repo-scale, SWE-bench)
- **What it is:** Observation: the action–observation–continuation loop of a coding agent is isomorphic to a function call site. Exploits that with a self-supervised FIM objective that masks functions selected by program-dependency-graph analysis under a complexity–inferability criterion. Mid-training on 2.6B decontaminated tokens from 968 GitHub repos.
- **Why it matters for Justin's agents:** SWE-Bench-Verified **+2.8 / +3.0 / +3.2 pp** on Qwen2.5-Coder 7B/14B and Qwen3-8B; SWE-Bench-Lite **+3.7 / +4.0 / +5.4 pp**. Also mitigates the capability erosion agentic post-training typically induces on LiveCodeBench, τ-bench, and BFCL — rare evidence that the collateral damage is *addressable* and not intrinsic. For anyone maintaining a local coding-agent stack (Qwen3-Coder derivatives on M5 Max), this is a clean mid-training recipe that stacks cleanly on top of R2E-Gym or SWE-Smith post-training.
- **Action signal:** `track` for now (mid-training compute is nontrivial); watch for HF checkpoint releases. Also `compare` — first paper this quarter to demonstrate an SFT/mid-training intervention that *undoes* the LiveCodeBench regression from agentic RL, which is a live open question in the coding-agent cluster.

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:

- **Over-context penalty vs "just paste more history"** — Shared Selective Persistent Memory (2607.09493) reports **full-history 71% < no-memory 79% < selective-persistent 96%** task completion. Directly extends and sharpens the "context dilution" thread already tracked via SLEUTH (2607.12267), Agentic Context Learning / PSCI [arxiv:2607.09794], and the broader long-context-degradation literature. **Recommend claims-ledger entry** for over-context penalty as a first-class primitive: the naive-full-history baseline is now empirically *worse than nothing* in this domain. Open question: at what context length does the crossover happen for tool-calling MCP loops specifically (vs code-gen loops in the paper)?
- **Wrapper vs backbone in computer-use** — StructAgent (2607.11388) doubles Qwen3.5-9B on OSWorld-Verified (27.0→46.9%) with pure orchestration changes, no backbone swap. Extends the eleventh convergent gate-before-commit instance and reinforces the ongoing theme that *harness design is often higher-leverage than base-model swap* for agent tasks (see also UniClawBench [arxiv:2607.08768] framing capability × harness as joint variance).
- **Open empirical question** — PM-Bench's finding that "no single memory strategy dominates across 8 models" implies the correct memory design is *model-specific*. That cuts against the mem0/LangMem framing of memory-as-portable-library. Is there a diagnostic (like the MemOps operation-level probes) that predicts which strategy pairs best with which base model? Nothing published yet — flagging as an open thread to watch.
