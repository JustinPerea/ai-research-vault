# AI Research Digest — Saturday, June 06, 2026

## TL;DR
- **Serving infra is now the agent story.** Two papers in 48h (Vortex, Tangram) reframe sparse attention and KV cache as agent-serving primitives rather than batch-decoding tricks; Vortex even uses agents to discover sparse attention programs.
- **Sub-agent dispatch keeps composing.** SkillComposer (4B composer raises a 27B executor by +4.5 on agent tasks across τ²-Bench / LiveCodeBench / AppWorld) extends the small-local-as-controller pattern from yesterday's TMEM/Mellum2/AdaCoM cluster — composer-as-skill-engineer is a third axis.
- **Google ships agentic-RAG as production architecture.** Gemini Enterprise Agent Platform's five-component pipeline (Orchestrator / Planner / Query Rewriter / Search Fanout / Sufficient Context Agent) hits 90.1% on FramesQA cross-corpus by *iterating until enough context accumulates*, not by one-shot retrieval — first frontier-lab production reference of a gate-before-generate sub-agent.
- **Coding-agent infra splits along the codebase-evolution axis.** Code2LoRA generates per-repo LoRA adapters from a hypernetwork (+5.2pp on the evolution track of RepoPeftBench, 215K training / 87K test tasks) — repo context becomes a parameter not a prompt.
- **Adaptive-planning eval finally measures hidden constraints.** AdaPlanBench (307 household tasks, dual world/user constraints surfaced only on violation, 10 frontier LLMs benched, **top model 67.75%**) puts a number on the gap between static plan-and-execute and constraint-revealing environments.
- **Execution-boundary governance gets benchmarked.** Organizational Control Layer drops unsafe executions from 88% → near-zero (12% → 96% valid success) on adversarial buyer-seller negotiation without modifying the LLM — first numerical anchor for the "intercept before execute" cluster.

## Items

### 1. Vortex — Programmable Sparse Attention Serving for AI Agents (3.46× throughput vs full attention, 4.7× on MLA-based GLM-4.7-Flash)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.06453
- **Authors / org:** Zhuoming Chen, Xinrui Zhong, Qilong Feng, Ranajoy Sadhukhan, Yang Zhou, Michael Qizhe Shieh, Zhihao Jia, Beidi Chen
- **Focus area:** Context engineering (serving infrastructure)
- **What it is:** Python-embedded frontend language over a **page-centric tensor abstraction** for expressing sparse-attention algorithms, paired with an LLM-serving backend. Up to **3.46× throughput over full attention** with accuracy preserved, **4.7× throughput on MLA-based GLM-4.7-Flash**, and **1.37× speedup on 229B-parameter MiniMax-M2.7 on B200**. Critically, AI agents themselves use Vortex to **autonomously generate and refine sparse-attention algorithms** — the system is co-designed for human researchers and for agent-driven kernel discovery.
- **Why it matters for Justin's agents:** First sparse-attention infra explicitly built around the *agent-as-author* loop — pairs with [arxiv:2606.05922] RHO (yesterday: self-supervised harness optimization without external graders) and [arxiv:2606.05080] AutoLab (engineering-persistence as dominant predictor). For a companion app whose KV cache grows linearly with session length, a programmable sparse-attention layer where the agent can ablate its own policy on its own conversation is the missing primitive between Vortex-style serving (this paper) and TaskMem-style write-time policies. Strong direction for the long-horizon companion stack.
- **Action signal:** `track` — wait for code release / benchmark on a Qwen/Llama family before promoting.

### 2. Tangram — Non-Uniform KV Cache for Efficient Multi-Turn LLM Serving (2.6× throughput, accuracy preserved)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.06302
- **Authors / org:** Hyungmin Kim, Minsoo Kim, Hongseok Kim, Jungwook Choi
- **Focus area:** Context engineering (KV cache management)
- **What it is:** Three coupled techniques for multi-turn serving: **deterministic budget allocation per attention head**, **grouped page management for heads with similar demand**, and **static load balancing**. Reports **up to 2.6× throughput over existing serving systems** while preserving model accuracy on multi-turn workloads.
- **Why it matters for Justin's agents:** Multi-turn is exactly the regime an agent companion runs in. Tangram's per-head budget allocation is mechanistically distinct from [arxiv:2606.04628] RAMPART's prompt-block registry (yesterday: position-engineering at the prompt layer) — Tangram operates *inside* the serving stack on KV pages, RAMPART operates *outside* on prompt blocks. Composable: RAMPART decides what enters the prompt, Tangram decides which KV pages survive in cache. Both are deterministic, both avoid extra LLM calls. The pair is the cleanest "no LLM in the memory loop" stack alongside [arxiv:2606.03463] DMF.
- **Action signal:** `track` — abstract reports the 2.6× number but no head-to-head against vLLM PagedAttention / SGLang RadixAttention; needs that comparison before promoting.

### 3. SkillComposer — 4B Composer Lifts a 27B Executor +4.5 on Agent Tasks (τ²-Bench / LiveCodeBench v6 / AppWorld)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.06079
- **Authors / org:** Qi Zhang, Zhaopeng Feng, Xiaonan Shi, Xiaomeng Hu, Chu Liu, Pengjun Xie, Xiaobin Wang, Jieping Ye, Bryan Hooi, Haobo Wang, Junbo Zhao (under review)
- **Focus area:** Agent orchestration (small composer + large executor)
- **What it is:** Decomposes agent-skill construction into **three learnable operations** — create, improve, merge — trained via rejection sampling and deployable offline / online / hybrid. **A 4B SkillComposer paired with a 27B executor delivers +4.5 on agent tasks and +3.4 on code tasks** over the 27B alone; demonstrated transfer to unseen domains.
- **Why it matters for Justin's agents:** Third axis of the small-local-as-controller cluster — [arxiv:2606.04536] TMEM (yesterday) writes LoRA fast-weights within an episode, [hf-blog-2026-06-02-jetbrains-mellum2-launch] Mellum2 12B/2.5B-A MoE compresses context for a frontier executor, AdaCoM trains an external context-manager for a frozen agent. SkillComposer is fourth-axis-distinct: it engineers the *skill library* the executor draws on, not the executor's prompt or memory. With Bryan Hooi co-author (same lead on Tuesday's MRAgent) this completes a "composer / context-manager / fast-weight / memory-graph" four-corner small-local-controller architecture in 7 days. The composer is the cheapest of the four to host on M5 Max.
- **Action signal:** `try-now` — under-review preprint; check author repos for the 4B checkpoint and rejection-sampling recipe.

### 4. Gemini Enterprise Agentic RAG — Five-Agent Pipeline With Sufficient Context Agent, 90.1% on FramesQA Cross-Corpus
- **Source:** Google Research blog
- **Link:** https://research.google/blog/unlocking-dependable-responses-with-gemini-enterprise-agent-platforms-agentic-rag/
- **Authors / org:** Cyrus Rashtchian, Da-Cheng Juan (Google Research)
- **Focus area:** Agent orchestration (frontier-lab production reference)
- **What it is:** Five specialized agents — **Orchestrator** (delegates tasks), **Planner** (maps information pathways), **Query Rewriter** (expands into multiple targeted queries), **Search Fanout** (distributes queries to retrieval sources), and a novel **Sufficient Context Agent** that **validates whether retrieved context is enough before generation** and emits feedback for the next search round. On **FramesQA (824 multi-hop queries, 2,676 documents, 4 candidate corpora)** the cross-corpus agentic-RAG configuration answers **90.1%** correctly; standard RAG markedly lower.
- **Why it matters for Justin's agents:** First public frontier-lab reference architecture that names the *gate-before-generate* sub-agent as its own component instead of an implicit threshold. Two design exports for any MCP-style multi-tool agent: (a) Query Rewriter → Search Fanout = parallel-query pattern Justin can apply over multiple MCP servers in one tick; (b) Sufficient Context Agent = a single small-model judge that produces feedback for the *next* tool call rather than just halting. Composes with [arxiv:2606.05158] StreamMA (Wednesday: stream reasoning *steps* to downstream agents) — stream the rewritten queries, gate at the Sufficient Context Agent.
- **Action signal:** `try-now` — pattern is reproducible on top of any retrieval stack; doesn't require Gemini.

### 5. Organizational Control Layer (OCL) — Execution-Boundary Governance Drops Unsafe Executions 88% → ~0%, Valid Success 12% → 96%
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.04306
- **Authors / org:** Tianyu Shi, Yang Mo, Yiou Liu, Zhuonan Hao, Yin Wang, Wenzhuo Hu, Nan Yu, Meng Zhou, Jiangbo Yu (13 pages, code released)
- **Focus area:** Agent safety / governance
- **What it is:** Model-agnostic governance layer that **intercepts generated actions before execution**, applies policy enforcement / escalation, doesn't touch the underlying LLM. On adversarial buyer-seller negotiation: **unsafe executions 88% → near-zero, valid task success 12% → 96%**. Surfaces a documented **safety-utility tradeoff**: strict policy reduces unsafe execution but cuts flexibility in constrained markets.
- **Why it matters for Justin's agents:** First numerical anchor for the execution-boundary cluster — [arxiv:2605.04785] AgentTrust (call-level interception, May 4), [arxiv:2605.06455] PrefixGuard (trajectory-level supervised monitor), [arxiv:2605.29082] Redpanda Agentic Data Plane (out-of-band metadata, May 31), and now OCL (synchronous gate at the execution boundary, with concrete tradeoff numbers). For a companion app shipping MCP tools that touch user accounts or filesystems, OCL's design — separate proposal generation from execution-facing action — is the cleanest "intercept layer" reference, with the explicit warning that compliance gains cost flexibility in constrained markets.
- **Action signal:** `track` — single-environment eval (buyer-seller negotiation); generality across MCP-tool deployments unproven.

### 6. Code2LoRA — Hypernetwork Generates Repo-Specific LoRA Adapters; Evolution Track +5.2pp Cross-Repo (RepoPeftBench, 215K Training / 87K Test)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.06492
- **Authors / org:** Liliana Hotsko, Yinxi Li, Yuntian Deng, Pengyu Nie
- **Focus area:** Coding agents (repository context as parameters, not prompt)
- **What it is:** Hypernetwork that **emits a per-repository LoRA adapter** for code models, with no inference-time hypernet overhead. Two variants: **Code2LoRA-Static** for stable codebases and **Code2LoRA-Evo** that maintains a GRU hidden state updated per code diff so the adapter tracks codebase evolution. On the new **RepoPeftBench (604 Python repos, static track 40K/12K, evolution track 215K/87K)**: 63.8% cross-repo / 66.2% in-repo exact match on the static track; **60.3% cross-repo on the evolution track — +5.2pp over baseline**.
- **Why it matters for Justin's agents:** Direct parametric counterpart to today's SkillComposer textual-skill cluster and last week's [arxiv:2606.06087] LatentSkill hypernetwork (Friday: textual skills → LoRA at inference). LatentSkill emitted skill adapters from natural-language descriptions; Code2LoRA emits *repository* adapters from code state. Pairs with [hf-blog-2026-06-04-hf-cli-for-agents] (yesterday) HF-CLI agent-native design: if Claude Code can drive `hf` to fetch a repo-LoRA on session start and hot-swap on diffs, the whole "repository context" problem moves out of the prompt window. Strong primitive for a repo-aware coding companion.
- **Action signal:** `track` — wait for RepoPeftBench numbers from independent groups; the evolution-track Δ is the harder claim.

### 7. AdaPlanBench — 307 Household Tasks, Dual World/User Constraints Surfaced on Violation, 10 LLMs Tested, Top Model 67.75%
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.05622
- **Authors / org:** Jiayu Liu, Cheng Qian, Zhenhailong Wang, Bingxuan Li, Jiateng Liu, Heng Wang, Jeonghwan Kim, Yumeng Wang, Xiusi Chen, Yi R. Fung, Heng Ji
- **Focus area:** Evaluation (adaptive planning under hidden constraints)
- **What it is:** Dynamic interactive benchmark where **constraints surface only when the agent proposes a violating plan**, forcing iterative revision. Scalable pipeline augments each task with dual constraint types (world-based + user-based). **307 household tasks, 10 frontier LLMs benchmarked, top performer 67.75% accuracy**, performance degrades as constraint count grows and **user constraints are harder than world constraints**.
- **Why it matters for Justin's agents:** Closest eval primitive yet for the constraint-revealing companion regime — Justin's stack will encounter user constraints the agent didn't see at plan time (calendar conflicts, account permission boundaries, hardware availability). The dominant-failure-mode breakout (world-grounding weakness + user-constraint sensitivity) is a usable diagnostic for any plan-and-execute MCP agent. Pairs with [arxiv:2605.30434] LongDS-Bench (Jun 1: 48.45% top, 47-pt early/late collapse) and [arxiv:2606.05080] AutoLab (yesterday: Opus 4.6 wins by persistence) as the third axis of long-horizon collapse benchmarks — AdaPlanBench measures *constraint adaptation*, LongDS measures *state maintenance*, AutoLab measures *iteration persistence*.
- **Action signal:** `track` — wait for the per-model leaderboard before treating 67.75% as canonical.

### 8. EVA-Bench Data 2.0 — Voice Agent Benchmark, 3 Enterprise Domains × 121 Tools × 213 Scenarios, MIT-Licensed

- **Link:** https://huggingface.co/blog/ServiceNow-AI/eva-bench-data
- **Authors / org:** Tara Bogavelli, Gabrielle Gauthier Melançon, Katrina Stankiewicz et al. (ServiceNow AI)
- **Focus area:** Evaluation (voice agents / structured-entity transcription)
- **What it is:** ~**4× scenario expansion** of the original EVA-Bench: **Airline CSM (50 scenarios) + Enterprise ITSM (80) + Healthcare HRSD (83), 121 tools**, ~**4× total scenarios**. Tests structured-entity transcription (confirmation codes, IDs), authentication, **single-intent / multi-intent up to 4 / adversarial / unsatisfiable goals / policy compliance**. **MIT license, fully open-source.** Validated against GPT-5.4, Gemini 3.1 Pro, Claude Opus 4.6 (numerical leaderboard not in the blog post).
- **Why it matters for Justin's agents:** First non-trivial *voice* agent benchmark released openly with multi-intent and adversarial subsets. For an MCP-tools-over-voice companion, multi-intent and unsatisfiable-goal scenarios are the regimes where Justin's current eval setups go quiet. The structured-entity-transcription subset is also the cleanest test surface yet for whether STT errors are caught before tool calls.
- **Action signal:** `track` — wait for the public leaderboard with numbers before deciding integration priority; MIT license means evaluation is free to fork now.

### 9. Nemotron-3.5 Content Safety — 4B Multimodal Guard With THINK Mode; 96.5% Multilingual Aegis Across 12 Languages, 3× Lower Latency
- **Source:** Hugging Face blog (NVIDIA)
- **Link:** https://huggingface.co/blog/nvidia/nemotron-3-5-content-safety
- **Authors / org:** Varun Singh, Isabel Hulseman, Anuj Doshi, Shyamala Prayaga (NVIDIA)
- **Focus area:** Local models for Apple Silicon / safety
- **What it is:** **4B-parameter unified multimodal safety model** built on **Gemma 3 4B IT** + LoRA adapter. Supports **custom policy enforcement** (per-deployment safety configs), **explicit reasoning traces via THINK mode**, and **~140 languages with explicit training in 12**. Benchmarks: **Multilingual Aegis 96.5% (12-lang avg), RTP-LX 88.8%, combined 92.7%**, ~85% on general multimodal benchmarks; **3× lower end-to-end latency vs LlamaGuard-4-12B** on a multimodal benchmark. NVIDIA Open Model License (research + commercial).
- **Why it matters for Justin's agents:** Practical pick for a local guard layer in front of MCP tool calls in a companion app. Gemma-3-4B base + LoRA = small footprint, fits comfortably on M5 Max alongside an executor. The **THINK mode → trace** export is the unusual feature: a safety classifier that emits a reasoning trace is directly auditable from Obsidian — Justin can store the trace as part of the agent's memory ledger rather than the safety decision being opaque. Custom-policy enforcement also makes per-vault, per-user safety configs trivially compose with the [arxiv:2606.04306] OCL execution-boundary pattern from item 5.
- **Action signal:** `local-fit` — fits cleanly inside M5 Max budget at FP16 (~8GB) and easily at Q4 (~2.5GB); check for MLX-converted weights.

## Local-model corner
- **Model:** Nemotron-3.5 Content Safety, 4B parameters (Gemma-3-4B IT base + LoRA), THINK mode optional
- **Memory fit:**
  - FP16 raw: ~8GB → fits 50GB+ free on M5 Max alongside a frontier-class executor
  - Q4 (GGUF/MLX): ~2.5–3GB → near-zero overhead next to Qwen3-32B-class reasoner or Holo3.1-9B Q4 CUA stack
- **Realistic tasks:** Pre-/post-call moderation for MCP tools, multilingual policy classification across ~140 languages (12 explicitly trained), audit-friendly safety decisions via the THINK trace (export to Obsidian as memory). NOT a general reasoner — single-purpose safety classifier.
- **How to run:** Wait for an MLX conversion (or run via llama.cpp / Ollama on the GGUF that NVIDIA's release path typically produces). Until then, vLLM on CUDA is the path of least friction; M5 Max users will likely see LM Studio pick it up within a few days of the official weights drop given the Gemma 3 4B lineage.
- **Speed estimate:** Gemma-3-4B IT at Q4 typically runs **~140–180 tok/s on M5 Max via MLX** per recent community benchmarks; expect roughly the same for the LoRA-merged Nemotron-3.5 because the base architecture is identical. THINK mode roughly doubles output token count, so policy-+-trace per-decision latency stays well under 1s for short prompts. NVIDIA's "3× lower end-to-end latency vs LlamaGuard-4-12B" claim is CUDA-side; the M5 Max gain over a 12B alternative will be even larger because the 12B class doesn't fit Q4 comfortably with full KV cache on a 64GB unified-memory system.
