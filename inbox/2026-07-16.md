### 1. Welcome Inkling by Thinking Machines
- **Source:** Hugging Face Blog (2026-07-15)
- **Link:** https://huggingface.co/blog/thinkingmachines-inkling ; model card https://huggingface.co/thinkingmachines/Inkling
- **Authors / org:** Thinking Machines (release post authored w/ HF: Burtenshaw, Merve, Cuenca, Roy Gosthipaty)
- **Focus area:** Frontier models + local & open models
- **What it is:** Open-source multimodal (text + image + audio) MoE: **975B total / 41B active**, 66-layer decoder-only, 256 experts, hybrid attention (5:1 sliding-window : global) with short conv layers and relative attention, **1M-token context**, trained on 45T tokens across modalities. Apache 2.0. Day-one support in Transformers / SGLang / vLLM / TokenSpeed / Unsloth; NVFP4 variant and **1-bit GGUF via Unsloth** at launch.
- **Why it matters for Justin's agents:** First ~1T-parameter open-weights frontier release with an in-window Apple Silicon quantization path. Headline benchmarks (**SWE-Bench Verified 77.6%, SWE-Bench Pro-Public 54.3%, AIME 2026 97.1%, GPQA Diamond 87.2%, MMMU Pro 73.3%, VoiceBench 91.4%, Global-MMLU-Lite 88.7%**) put it in the same league as Kimi-K2.6 / DeepSeek-V4-Pro / GPT-5.5 on the two axes Justin cares about (coding-agent + reasoning), plus native audio in — meaning a companion-app voice loop no longer requires a separate ASR/TTS layer if you're willing to serve it. The 1-bit GGUF (Unsloth `UD-IQ1_S`, retains "~74.2% of top-1% accuracy while being 86% smaller") is the operationally interesting bit; **41B active means MoE-cache-locality kernels (see ReMoE, LeanStral) dominate the M5 Max serving cost**, and 1-bit is the only regime where 975B total fits at all in 64 GB unified memory.
- **Action signal:** `local-fit` + `try-now` — pull `unsloth/inkling-GGUF:UD-IQ1_S` and llama-serve it; measure prompt-processing and decode tok/s on M5 Max. **Open empirical question:** is 1-bit accuracy retention (~74%) enough for coding-agent workloads, or does the quantization hit swe-bench harder than the aggregate top-1% number suggests? Also `compare` — extends the trillion-scale open-weight thread from DeepSeek-V4-Pro (2606.19348) + Kimi-K2.6 + MiniMax-M3 (2606.13392) with the first *natively audio* entrant.

### 2. Oracle Agent Memory as an Enterprise Memory Substrate for Long-Horizon AI Agents
- **Source:** arXiv (2026-07-14)
- **Link:** https://arxiv.org/abs/2607.13157
- **Authors / org:** Alake, Bernardis, Cayet, Engel, Hilloulin, Hong, Hosler, Kavantzas, Kossyk, Le, Patra, Talamadupula, Venzin (Oracle)
- **Focus area:** Agent memory (semantic + procedural, enterprise infrastructure)
- **What it is:** Database-native memory system built on Oracle Database with explicit **lifecycle** (ingestion → extraction → consolidation → retrieval → removal), **layered architecture** separating active from passive memory with explicit scope controls, evaluated by task accuracy *and* memory-specific metrics (retrieval quality, latency).
- **Why it matters for Justin's agents:** **93.8% LongMemEval accuracy at ~10.7× fewer tokens than flat-history baselines** is the strongest "token-normalized memory win" number this quarter and joins yesterday's Shared Selective Persistent Memory (2607.09493) result ("full history 71% < no memory 79% < selective persistent 96%") as a **second data point in 48 hours** that active memory beats passive context dumping *on real benchmarks*, not just anecdotally. The lifecycle vocabulary (ingestion / extraction / consolidation / retrieval / removal) also composes cleanly on top of yesterday's MemOps (2607.12893) *operation-level* vocabulary (remember / forget / update / reflect) — one gives you the pipeline, the other gives you the probe schema. Directly applicable to an MCP-tool loop's cross-session memory: implement the lifecycle stages as separate Skills, wire an operation-level probe as the memory CI.
- **Action signal:** `compare` — third memory paper this week that flips the naive "just give it everything" default. Ledger this as continuing evidence for the **over-context penalty** primitive. Also `track` — abstract doesn't specify open source; watch for a code release before staking on the Oracle-DB-specific parts.

### 3. Memory as a Controlled Process: Learned Adaptive Memory Management for LLM Agents (MemCon)
- **Source:** arXiv (2026-07-15)
- **Link:** https://arxiv.org/abs/2607.13591
- **Authors / org:** Eric Hanchen Jiang, Zhi Zhang, Yuchen Wu, Levina Li, Dong Liu, Xiao Liang, Rui Sun, Yubei Li, Edward Sun, Haozheng Luo, Zhaolu Kang, Aylin Caliskan, Kai-Wei Chang, Ying Nian Wu (UCLA + collaborators)
- **Focus area:** Agent memory (control policy / online adaptation)
- **What it is:** Models memory operations (retrieve / inject / consolidate) as a Markov Decision Process; learns a per-context policy via a **lightweight tabular contextual bandit with UCB exploration**. No LLM in the loop for the policy itself — task-level binary feedback only, converges in tens of tasks across memory backends.
- **Why it matters for Justin's agents:** **+15.2pp task success and 5–20% token reduction across 6 benchmarks × 3 agent frameworks × 3 backbones**, using a *tabular* bandit — this is the cheapest known memory policy learner and the first with a real Pareto win (accuracy up AND tokens down). Directly maps to a "should I retrieve / inject / consolidate this turn?" gate on top of any existing mem0- or LangMem-style store. **Load-bearing point Justin has been circling for months:** the memory *policy* deserves to be a first-class learned artifact separate from the *store*. MemCon is the first paper to demonstrate a policy learner light enough to run in a Claude Code MCP loop without an extra model, so this is the most transferable memory result of the week.
- **Action signal:** `try-now` — prototype the tabular bandit + UCB over a small action set (retrieve k=0,3,10 / inject-plan yes-no / consolidate now-later) around one of the vault's existing MCP loops, log the reward as binary task success. Also `compare` — extends and *refutes* the implicit "memory policies need an LLM" assumption in mem0/LangMem/Letta framings.

### 4. Experience Memory Graph: One-Shot Error Correction for Agents
- **Source:** arXiv (2026-07-15)
- **Link:** https://arxiv.org/abs/2607.13884
- **Authors / org:** Wenjun Wang, Yuchen Fang, Fengrui Liu, Zibo Liang, Kai Zheng
- **Focus area:** Agent memory (episodic) + agent orchestration (error recovery)
- **What it is:** Converts failed *and* successful trajectories into **directed action decision graphs**, mines common successful workflows, derives **graph-edit paths** (action add / delete / relabel) that transform a failing trajectory into a successful one. At inference, graph-match against the memory graph and apply the edit path — **single-pass, no reflection loop**.
- **Why it matters for Justin's agents:** Reflection loops (ReAct-style "critique-and-retry") are the default recovery mechanism in most MCP agent scaffolds, and they cost 2–5× the tokens of a clean run *and* introduce failure modes of their own (over-critique, false-refutal, infinite regress). EMG replaces the loop with a *lookup*, using both success and failure traces as first-class memory. Beats reflection baselines on ALFWorld / ScienceWorld on success + reward with zero test-time retries. Direct fit for durable Claude Code loops where the same task types recur (test-fix, PR-review, config-migrate): every failed run becomes a reusable correction primitive. Composes with Item 3 — MemCon decides *when* to retrieve; EMG decides *what to do with the retrieved trace*.
- **Action signal:** `try-now` — the pattern (action-graph + graph-edit correction) is prototype-able without waiting for code release; retrofit on top of an existing episodic memory store. Also `compare` — the "success + failure both go in the memory" framing directly contradicts most current mem0-style setups that only persist success signals.

### 5. Adaptive Filtering of the KV Cache: Diagnosing and Correcting Structural-Role Bias in LLM Inference
- **Source:** arXiv (2026-07-14)
- **Link:** https://arxiv.org/abs/2607.13205
- **Author:** Soumil Mandal
- **Focus area:** Context engineering (KV cache eviction)
- **What it is:** Diagnoses that H2O and other attention-mass eviction policies over-retain **structural** tokens (delimiters, whitespace, JSON braces) at the expense of **content** (VALUE) tokens: **structural KEY tokens over-retained at ~1.8× the rate of answer-carrying VALUE tokens**. On schema-dense inputs, H2O accuracy **collapses from 88% → 0% at 5% memory budget**. Fix: a **15 MB linear probe** that role-classifies tokens (KEY / VALUE / sink) and applies role-conditional retention on top of SnapKV-style windowed scoring. Retraining-free, single hyperparameter, recovers **63–98% of the accuracy loss**.
- **Why it matters for Justin's agents:** MCP tool observations *are* JSON. Every schema-dense response passes through the exact input distribution where H2O collapses. If Justin is running any long-context MCP loop with aggressive KV eviction (llama.cpp `--cache-type-k q4_0`, SGLang KV budget caps, vLLM chunked-prefill with eviction) on structured tool outputs, this is a live silent-failure mode. The mitigation is small (15 MB probe, deterministic), portable across backends, and doesn't need retraining. Direct pairing with yesterday's JoLT KV compression (2607.12550) — JoLT gets you 2–3× headroom, but only if the token *selection* on the retained side isn't biased toward `{`, `,`, and `}`; MemCon (Item 3) picks the *macro* memory op, this picks the *micro* KV token.
- **Action signal:** `try-now` (for anyone on llama.cpp/SGLang/vLLM with eviction turned on) + `compare` — extends the KV-cache-cluster of the week (JoLT compression, Jet-Long, TokenSelect, prior Tucker work) with the *first published diagnosis that content vs structural role matters more than attention mass on structured inputs*. Add to claims ledger under KV / long-context.

### 6. Do Agent Optimizers Compound? A Continual-Learning Evaluation on Terminal-Bench 2.0
- **Source:** arXiv (2026-07-15)
- **Link:** https://arxiv.org/abs/2607.14004
- **Authors / org:** Wenxiao Wang, Priyatham Kattakinda, Soheil Feizi (RELAI)
- **Focus area:** Agent orchestration + long-running loops + evaluation
- **What it is:** Two-phase continual-learning evaluation on **Terminal-Bench 2.0** (extends the TB2 line from 2607.08964 already in the ledger). Three optimization methods — GEPA, Meta Harness, and the paper's **RELAI-VCL** — get identical budgets, then are re-optimized on newly-introduced tasks in phase two. Measures whether gains transfer to unseen tasks and whether re-optimization compounds.
- **Why it matters for Justin's agents:** Numbers: **RELAI-VCL 76.4% lifelong pass, GEPA 66.0%, Meta Harness 64.6%, unoptimized baseline 58.7%**. Load-bearing finding: **"optimization gains compound *only when regression control is built into the optimization loop*"** — i.e., optimizers that don't test for regressions get shortcut-solved and *undo their own prior wins* on the next round. Direct implication for any repository of Claude Code skills or MCP scaffolds Justin evolves over time: **a gain-tracking layer that vetoes changes on regression is not optional, it's the difference between compounding and drifting**. Ties directly into today's Item 7 (QD-keyed harness archive, which is a specific form of regression control) and yesterday's `try-now` on Shared Selective Persistent Memory: skills, memory, and harnesses all need the same anti-drift protocol.
- **Action signal:** `compare` — direct continuation of the Terminal-Bench 2.0 evaluation thread ([arxiv:2607.08964] in ledger) with a *lifelong* framing, and the fourth "gate-before-commit" data point of the month. Add to claims ledger.

### 7. Self-Evolving Agent Harnesses via Gated Semantic Quality-Diversity
- **Source:** arXiv (2026-07-15)
- **Link:** https://arxiv.org/abs/2607.13683
- **Authors / org:** Xiaotian Luo, Fengxingyu Wang, Chuanrui Hu, Dizhan Xue, Yafeng Deng
- **Focus area:** Agent orchestration (harness evolution)
- **What it is:** Automated harness improvement (prompts / knowledge / runtime control / config, *no weight updates*). Key move: **separate change proposal from change crediting**. An LLM diagnoses failures and proposes patches; deterministic code measures whether the patch actually helps under significance testing. The **quality-diversity archive is keyed on failure pathology (WHERE × WHY)** rather than on task — an inductive bias against overfitting.
- **Why it matters for Justin's agents:** **+9 to +15.5pp on training domains, 86–147% of that gain retained on the sealed test set** — the >100% retention on some domains is the interesting number: pathology-keyed patches *generalize better than they train* because the patch fixes a class of failure rather than memorizing a task. This is the specific mechanism Item 6's regression control needs to actually compound. Directly transferable pattern: when maintaining Claude Code's skill library, index skills by *what failure mode they solve* (missing-tool-arg, refused-refactor, wrong-scope-edit) rather than by task, and gate additions on a sealed regression suite. Third harness-evolution paper this week — the field is converging on **diagnose → patch → deterministically credit** as the pipeline shape.
- **Action signal:** `compare` (with Item 6 and Harness Handbook Item 8) — three convergent papers means this is a real subfield now. Also `track` — code release worth watching for the archive-key schema; the WHERE × WHY taxonomy is the transferable core.

### 8. Harness Handbook: Making Evolving Agent Harnesses Readable, Navigable, and Editable
- **Source:** arXiv (2026-07-14)
- **Link:** https://arxiv.org/abs/2607.13285
- **Authors / org:** Ruhan Wang, Yucheng Shi, Zongxia Li, Zhongzhi Li, Yue Yu, Junyao Yang, Kishan Panaganti, Haitao Mi, Dongruo Zhou, Leoweiliang
- **Focus area:** Agent orchestration (harness engineering, self-editing agents)
- **What it is:** A **behavior-centric map** of the agent harness, auto-synthesized by static analysis + LLM structuring, linking each observable behavior to the source-code sites that implement it. Paired with **Behavior-Guided Progressive Disclosure (BGPD)** — an agent navigation policy that starts from a target behavior and progressively surfaces implementation details, validating candidate edit sites against current source before committing a change.
- **Why it matters for Justin's agents:** Third harness paper this week (with Items 6 and 7), addressing the *pre-optimization* step nobody else instruments: **where in the harness should the patch go?** Reports "largest gains on scattered sites, rarely executed paths, and cross-module interactions" — exactly the categories where an LLM-only edit blindly greps and produces a wrong-scope patch that Item 6's regression control has to catch after the fact. Concrete transplant to the vault: any Claude Code project with >~5 skills or a multi-file MCP scaffold benefits from a maintained `HARNESS.md` (behavior → file:line map) that the editing agent reads *first*. That single artifact plausibly halves the "wrong-file edit" failure mode in self-editing loops.
- **Action signal:** `try-now` — generate a behavior-map for one of Justin's existing multi-skill Claude Code projects (static analysis + a one-shot pass with `code-review` at high effort). Also `compare` — completes the harness-engineering trio (this + Item 6 + Item 7); add a claims-ledger entry for the trio as a subfield.

## Local-model corner
**Inkling (Item 1) is the whole story this run.**

- **Model:** Inkling by Thinking Machines — **975B total / 41B active MoE**, native text + image + audio, 1M context, Apache 2.0.
- **Memory fit:** BF16 ≈ ~1.95 TB (server-only); NVFP4 ≈ ~600 GB (multi-GPU only). **The M5-relevant variant is `unsloth/inkling-GGUF:UD-IQ1_S`** — dynamic 1-bit that claims 95% VRAM reduction and 86% smaller than BF16 while retaining ~74.2% of top-1% accuracy. Rough back-of-envelope: 975B weights at ~1.6 bits/weight (Unsloth dynamic 1-bit averages ~1.5–1.8 across critical vs non-critical experts) ≈ **~180–200 GB weights** at the low end — **still over the 64 GB M5 Max unified-memory limit for a single-machine load-and-serve.** Practical read: Inkling in the current 1-bit shape is **not runnable on a single M5 Max**. It's runnable on a 2-machine Unsloth-style setup or one 200 GB+ Mac Studio class box.
- **Realistic tasks (if you had the hardware):** given the 41B-active MoE profile and the 77.6% SWE-Bench Verified / 87.2% GPQA / 91.4% VoiceBench numbers, this is a *coding-agent + voice-first companion* candidate, not a chat model. Native audio input is the differentiator over DeepSeek-V4 / Kimi-K2.6 / MiniMax-M3.
- **How to run (target hardware only):** `llama serve -hf unsloth/inkling-GGUF:UD-IQ1_S`; Transformers / SGLang / vLLM / TokenSpeed at BF16 or NVFP4.
- **Speed estimate:** no M5-Max-specific numbers published yet — first Metal / MLX kernels are the item to track. The active-parameter regime (41B) is right in the Qwen3-30B-A3B / Holo3.1-35B-A3B / DiffusionGemma neighborhood on decode cost *per token*, so 1-bit prompt-processing on an M5 Max should be usable *if* the model itself can be split across memory tiers (mmap + swap).

**Adjacent local-relevant items:** KV cache filtering (Item 5) is architecture-agnostic and immediately portable to llama.cpp / MLX once anyone lands the 15 MB linear-probe kernel — same "watch upstream" posture as JoLT KV compression from yesterday. Nothing else in-window is a new local model release; no MLX-native drops.

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:

- **Over-context penalty (third data point in a week).** Oracle Agent Memory (Item 2) reports **93.8% LongMemEval accuracy with ~10.7× fewer tokens than flat-history**; MemCon (Item 3) reports **+15.2pp with -5–20% tokens** on 6 benchmarks × 3 frameworks × 3 backbones. Both extend yesterday's Shared Selective Persistent Memory (2607.09493) "full history 71% < no memory 79% < selective 96%". The three papers span three different mechanisms (lifecycle store, learned policy, static category filter) and three different domains (long-form dialog, general agent tasks, code-gen). **Recommend the claims-ledger add an "over-context penalty" primitive** — the pattern is now empirically robust across mechanism and domain. Open question: **at what context length does the crossover happen for tool-calling MCP loops specifically?** All three papers benchmark on suites (LongMemEval, GAIA-style, code-gen) that don't isolate the tool-response density axis. Justin's MCP loops are exactly that axis.

- **Harness engineering is a subfield now (three convergent papers in-window).** Items 6, 7, 8 all address distinct pieces of the same pipeline — Handbook (Item 8) tells the agent *where* to edit; QD-keyed archive (Item 7) tells it *what to keep*; Compound (Item 6) tells it *how to know if it worked over time*. **Recommend claims-ledger add "diagnose → patch → deterministic credit" as the emerging harness-evolution primitive**, on par with the existing gate-before-commit family. Reinforces the vault-tracked "wrapper matters more than backbone" finding (StructAgent yesterday, UniClawBench earlier). Open question: does the WHERE × WHY archive from Item 7 transfer *across* backbones (Qwen3.5 → Llama-4 → Claude Opus)? Item 7's 86–147% retention is same-backbone; cross-backbone would be a strictly stronger claim and would validate "pathology > task" as a design principle.

- **KV eviction has been benchmarked wrong.** Adaptive Filtering (Item 5) shows H2O collapses **88% → 0%** on schema-dense inputs at 5% budget — a failure mode invisible on the standard eviction benchmarks (RULER, LongBench) which don't stress structural-role bias. This partially undermines any "KV eviction is solved" reads from prior ledger entries (H2O, SnapKV, etc.) *specifically for the JSON-heavy tool-response distribution*. **Open question:** does yesterday's JoLT compression (2607.12550) — which does token-level factorization rather than eviction — suffer the same structural bias, or does the tensor decomposition average it out? Nobody has run the joint experiment; that's the natural next paper.
