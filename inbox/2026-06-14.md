# AI Research Digest — Sunday, June 14, 2026

## TL;DR
Today is a Sunday — arXiv didn't publish fresh listings overnight, so the signal comes from (a) two lab-blog drops worth tracking and (b) a sweep of strong June 11–12 arXiv items that didn't make yesterday's 8-item cut. No frontier model release, nothing local-fit.

- **Agent inference serving gets its first multi-vendor benchmark.** NVIDIA's June 12 post introduces **AA-AgentPerf (Artificial Analysis)** — concurrent-agents-per-megawatt under SLO, **measured on prerecorded agentic coding trajectories** (interleaved reasoning + tool use, 5K–131K tokens, ~27K avg, 12+ languages) rather than single-turn token throughput. On DeepSeek-V4-Pro the **GB300 NVL72 hits 61.4K concurrent agents per MW vs 2.6K on H200 (~20×)**. The benchmark methodology — not the H200/GB300 gap — is the real signal: per-MW-under-SLO is the inference economic unit agent serving has been missing.
- **Allen AI ships olmo-eval, an evaluation workbench with first-class agentic support.** Decouples **tasks / suites / harnesses** so the same benchmark can run under different runtime policies (lightweight Q&A vs containerized sandbox for tool-use/code-execution); explicit **pairwise checkpoint comparison view with standard error and minimum detectable effect**; multi-turn tool-using evals integrated from day one. This is the OLMES successor, and it's the cleanest open eval harness for the train-tweak-rerun loop that Justin would hit if he ever fine-tunes a coding agent.
- **Multi-agent communication via KV-cache, not text, matches or surpasses text-based communication at 2–3× lower compute.** [arxiv:2606.13594] aligns hidden states across Qwen3-4B / 8B / 14B via lightweight cache transformation + two-phase training. Worked across all six directional pairings, in-domain and out-of-domain. If this reproduces, it changes the architectural question for heterogeneous agent ensembles from "what tokens do agents exchange" to "what compressed states do agents share" — direct read-through to any local-LLM agent stack that runs multiple models side by side.
- **Self-supervised reward modeling for the orchestrator role specifically.** OrchRM [arxiv:2606.13598] trains the orchestrator without sub-agent rollouts by working **directly on orchestration-level decisions** via Bradley-Terry pairs over execution artifacts. **10× token-efficiency vs sub-agent-rollout baselines in training, +8% accuracy at multi-agent test-time scaling** across math reasoning, web QA, multi-hop QA. Pairs naturally with RAH from yesterday's digest — RAH names the harness pattern, OrchRM gives you a way to train the parent policy that drives it.
- **Agent eval becomes an agent task.** AgentBeats [arxiv:2606.13608] runs **judge agents that evaluate subject agents over standardized A2A + MCP protocols**, validated via a 5-month open competition with **298 judge agents and 467 subject agents across 12 categories**. The pitch is that fixed benchmark scaffolding can't keep up with diverse agent designs; agentified evaluation can. Worth tracking for whether MCP-as-evaluation-substrate becomes a real pattern.

## Items

### 1. NVIDIA + Artificial Analysis — AA-AgentPerf: agent-serving benchmark for inference economics
- **Source:** NVIDIA Developer Blog
- **Link:** https://developer.nvidia.com/blog/nvidia-achieves-leading-agentic-coding-performance-on-first-agentic-ai-benchmark/
- **Authors / org:** NVIDIA + Artificial Analysis
- **Focus area:** Evaluation / tools (agent serving economics)
- **What it is:** **Artificial Analysis AgentPerf (AA-AgentPerf)** — "the industry's first multi-vendor open benchmarks profiling trajectories that are representative of real-world AI agent coding tasks." Measures **concurrent agents per accelerator and per megawatt** while meeting predefined model-specific SLO tiers. Inputs are **prerecorded agentic coding trajectories** with interleaved reasoning + tool use drawn from public repos across **12+ languages**, sequence lengths **5K–131K tokens (~27K avg)**, with non-deterministic sequencing and tool-call latencies baked in. Model under test: **DeepSeek-V4-Pro**. Headline: **GB300 NVL72 = 61.4K concurrent agents/MW vs H200 = 2.6K under SLO #1**, ~20× per-MW improvement.
- **Why it matters for Justin's agents:** The hardware headline is product marketing; the methodology is what counts. **Agents-per-megawatt-under-SLO with realistic trajectory shapes** is the operational unit Justin needs to reason about whenever he priced "can my MCP/agent product run at this margin." The trajectory inputs are particularly important — averaging 27K tokens with interleaved tool calls is the realistic shape, not the 1K/4K single-turn approximations that older inference benchmarks used. For Justin's API-backed products this changes the cost model conversation; for self-hosted, it gives a first reference point for what the per-agent compute footprint is at modern serving stacks.
- **Action signal:** `track` — the AA-AgentPerf trajectory dataset and methodology are the durable artifact; revisit when more frontier models are scored on it. Also useful as the inference-economics counterpart to WeaveBench (yesterday's `track`) which scores task PassRate without addressing throughput.

### 2. Allen AI — olmo-eval: evaluation workbench for the model development loop
- **Source:** Hugging Face Blog (Allen AI)
- **Link:** https://huggingface.co/blog/allenai/olmo-eval
- **Authors / org:** Allen AI
- **Focus area:** Evaluation
- **What it is:** OLMES successor. **Modular task/suite/harness architecture** decouples benchmark logic from runtime policy — the same benchmark can run under lightweight direct evaluation (simple Q&A) or under containerized sandbox (tool-using / code-execution / agentic). Designed for the iterative developer loop: **pairwise checkpoint comparison view** that lines up the same questions across two checkpoints with **standard error and minimum detectable effect**, so real improvements separate from noise. **Multi-turn tool-using evaluations integrated from day one**, not bolted on. Normalized experiment schema for consistent result recording across runs.
- **Why it matters for Justin's agents:** Justin's eval thinking is shaped by frontier-model leaderboards, but the developer-loop eval problem (re-running benchmarks per checkpoint, separating real gain from noise, evaluating tool-using agents under realistic harnesses) is what he'd actually hit if he ever fine-tunes a small coding agent for an MCP-tool product. olmo-eval's **task/suite/harness separation** is the right abstraction — the same benchmark can be scored against a lightweight model (cheap, indicative) and against a full agent harness (expensive, definitive) without rewriting the eval. The **pairwise comparison with MDE** is the right report shape for "is this checkpoint actually better." Open-source workbench worth bookmarking even if not yet adopted.
- **Action signal:** `try-now` — workbench is open and immediately usable; even without fine-tuning, the pairwise+MDE pattern is portable to any eval Justin already runs by hand.

### 3. Dense latent communication across heterogeneous agents (KV-cache, not text)
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.13594
- **Authors / org:** Siyi Chen, Xiaoyan Zhang, Meng Wu, Jonathan Tremblay, Valts Blukis, Stan Birchfield, Rene Vidal, Alvaro Velasquez, Sijia Liu, Qing Qu (NVIDIA + academic collaborators inferred from authorship)
- **Focus area:** Agent orchestration (multi-agent communication primitives)
- **What it is:** Agents of different sizes exchange **compressed KV-cache representations** instead of text tokens. Demonstrated across Qwen3-4B / 8B / 14B in all six directional pairings. **Lightweight cache transformation + two-phase training (reconstruction → generation)** aligns the heterogeneous models' internal representations enough for one model to consume another's cache as context. Reports **matching or surpassing text-based communication in context-aware scenarios at ~2–3× lower computational cost**, with effectiveness on both in-domain and out-of-domain evals. Beats prior heterogeneous-communication baselines especially in context-unaware transfer, where text approaches fail.
- **Why it matters for Justin's agents:** This is the structurally novel item in today's set. Multi-agent systems today route messages over text — every cross-agent handoff incurs a tokenize/detokenize and a context-rebuild penalty. If KV-cache handoffs reproduce at scale, the architecture for **local heterogeneous ensembles** (a small fast model coordinating with a larger slower one, both Qwen-family or both MLX-supported) changes — the small model can "pass thought" to the large model without re-encoding, at meaningful compute savings. Direct read-through to any "router model + executor model" pattern Justin might use on M5 Max where both models live in the same memory pool. **Open empirical question:** does this generalize across model families (not just Qwen3 sizes) — if yes, MCP-style protocols eventually grow a "cache-handoff" verb.
- **Action signal:** `track` — repro on independent labs needed before integrating; the M5-Max-local-ensemble implication is the one to watch.

### 4. OrchRM — self-supervised reward modeling for the orchestrator role
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.13598
- **Authors / org:** King Yeung Tsang, Zihao Zhao, Vishal Venkataramani, et al. (5 co-authors)
- **Focus area:** Agent orchestration
- **What it is:** Trains the **orchestrator** of a multi-agent system **without expensive sub-agent rollouts and without human annotations**. Constructs Bradley-Terry training pairs **directly from execution artifacts at the orchestration-decision level** — i.e., the reward model scores orchestration choices rather than terminal task outcomes. Reports **~10× training-token efficiency vs sub-agent-rollout baselines** and **+8% accuracy at multi-agent test-time scaling** across math reasoning, web QA, and multi-hop QA.
- **Why it matters for Justin's agents:** Pairs naturally with yesterday's RAH ([arxiv:2606.13643]) — RAH formalizes the parent-agent-spawns-sub-harnesses pattern, OrchRM gives you a way to train the parent's dispatch policy without re-running the children. The 10× training-token efficiency is the bigger headline for indie developers: orchestrator improvements have traditionally required full agent-system rollouts (slow + expensive); orchestration-level RM training collapses that to artifact-level pairs. If you're going to train any orchestrator at all rather than just prompt one, this is the recipe to start from.
- **Action signal:** `compare` — directly composes with RAH (parent-policy structure) and HarnessBridge ([arxiv:2606.12882], learn-the-harness controller). All three target the orchestration layer; OrchRM is the one with the most actionable training recipe.

### 5. AgentBeats — agentified agent assessment over A2A + MCP
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.13608
- **Authors / org:** (authors not enumerated in abstract; framework paper)
- **Focus area:** Evaluation / tools (MCP)
- **What it is:** Concrete implementation of "Agentified Agent Assessment (AAA)": **judge agents evaluate subject agents** through **standardized protocols (A2A for task delivery, MCP for tool access)** rather than fixed scaffolded benchmarks. Validated by a **5-month open competition** with **298 judge agents and 467 subject agents across 12 categories**, including a coding-agent case study. The framing problem: fixed benchmarks suffer "test-production mismatch" and prevent fair comparison across diverse agent designs — judge-agent evaluation is reproducible because the judge is itself a versioned artifact subject to evaluation.
- **Why it matters for Justin's agents:** Two reads. (a) **MCP-as-evaluation-substrate**: if eval frameworks normalize on MCP for the tool surface, that further entrenches MCP as the agent interoperability layer, which is favorable for any product Justin ships behind MCP tools. (b) **Judge-agent design**: the same pattern is portable to internal QA — instead of writing hand-graded eval rubrics for an MCP tool, write a judge agent that interacts with the subject agent through the tool. The competition scale (298 + 467 agents across 12 categories) is a real reproducibility claim, not a demo.
- **Action signal:** `track` — methodology lens for evaluation; revisit if MCP-based evals become the dominant pattern.

### 6. SWITCH — boundary-tokenized switchable latent reasoning compatible with on-policy RL
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.13106
- **Authors / org:** (authors not enumerated in abstract)
- **Focus area:** Reasoning & inference-time compute
- **What it is:** Latent chain-of-thought via **explicit boundary tokens `<swi>` / `</swi>`** marking entry and exit of latent-reasoning mode. The boundary tokens make the policy ratio **well-defined at decision points**, which is what unlocks on-policy RL training (GRPO-style) for latent reasoning — prior hidden-state-recurrence approaches were stuck with off-policy or supervised training because policy ratios were ill-defined inside latent steps. Adds a **visible-to-latent curriculum** + **Switch-GRPO** objective. Mechanistic probing finds boundary tokens implement learned switching (not just stylistic markers), latent steps perform problem-specific computation, and that computation concentrates at a **single hidden-state transition upon entry**. Outperforms prior hidden-state-recurrence latent-reasoning approaches at similar scale (specific numbers in PDF).
- **Why it matters for Justin's agents:** Latent reasoning has been the "interesting in theory, hard to train" alternative to long-form CoT — SWITCH is the cleanest published path to making it compatible with the on-policy RL recipes everyone is already running. If this generalizes, the practical implication for agent products is **reasoning compute that doesn't blow up output token budgets** — the model thinks in hidden state, only emits when it's ready. For MCP-tool products that pay per-output-token at the API tier, that's directly cost-relevant if a frontier provider ships a SWITCH-style model. Worth tracking even if not actionable today.
- **Action signal:** `track` — research-methodology paper; revisit when a frontier provider ships a latent-CoT model trained this way.

### 7. Agents-K1 — agent-native scientific knowledge orchestration
- **Source:** arXiv
- **Link:** https://arxiv.org/abs/2606.13669
- **Authors / org:** (Chinese academic collaboration inferred; authors not enumerated)
- **Focus area:** Tools & connectors (RAG for research agents)
- **What it is:** End-to-end stack converting **2.46M scientific papers across six subjects** into agent-consumable knowledge graphs. Three components: **(a) multimodal parser** capturing entities, evidence, citations, relationships across full papers (not just abstracts); **(b) 4B information-extraction backbone** trained with GRPO + rule-based rewards; **(c) GraphAnything CLI** giving agents web search + multimodal graph retrieval + cross-document traversal. Releases the **Scholar-KG** dataset (1M-paper subset, larger version separate). Claims superior performance on scientific IE, KG construction, and multi-hop scientific reasoning (numerical comparisons deferred to PDF).
- **Why it matters for Justin's agents:** Not directly applicable to Justin's federal-data-engineer or companion-app work, but the **shape of the artifact** is the lesson: ship a CLI + curated KG + a small (4B) IE model trained for a specific knowledge domain, rather than relying on the agent's frontier model to ingest raw documents at query time. The pattern generalizes — any domain where Justin would otherwise dump documents into a context window is a candidate for this same architecture (domain-specific 4B IE + GraphAnything-style CLI). The **4B IE backbone is local-runnable on M5 Max** at FP16 (~8 GB) with headroom for the KG and the agent model alongside.
- **Action signal:** `track` — design pattern reusable for any domain-specific research-agent product Justin builds.

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:

- **OrchRM vs RAH (yesterday) vs HarnessBridge (yesterday)** — `compare`. All three target the orchestration / harness layer between LLM and environment. **RAH** ([arxiv:2606.13643]) is the architectural pattern (parent script spawns sub-harnesses); **HarnessBridge** ([arxiv:2606.12882]) is a learnable harness controller; **OrchRM** is a training-signal recipe for the orchestrator policy itself. They're compositional, not competing — RAH gives you the structure, HarnessBridge gives you the observation/action projection layer, OrchRM gives you the reward model to train the parent's dispatch decisions. Open question: does any of the three publish a head-to-head against the others on a shared benchmark (the natural candidate is Terminal-Bench 2.0 or Oolong-Synthetic, both already in ledger).
- **AA-AgentPerf vs WeaveBench (yesterday)** — complementary, not contradictory. WeaveBench scores **task PassRate** on 114 real-world hybrid-interface tasks (best frontier combo = 41.2%); AA-AgentPerf scores **agents-per-MW under SLO** on prerecorded coding trajectories. WeaveBench answers "can the agent do the task"; AA-AgentPerf answers "how many of these can I run at once at margin." Both belong in the eval stack but they're measuring different axes. Open empirical question: are the trajectories used by AA-AgentPerf representative enough that the per-MW ranking transfers to a WeaveBench-style task-completion ranking, or do high-throughput models lose more on long-horizon hybrid tasks than the throughput numbers suggest?
