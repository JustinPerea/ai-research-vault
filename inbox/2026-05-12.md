# AI Research Digest — Tuesday, May 12, 2026

## TL;DR
- **Decision-centric memory shows up as the missing framing.** DeMem (CMU/Monash et al.) reframes agent memory as a **rate-distortion problem on decision quality**, not description quality, and proves an exact forgetting boundary plus a memory-distortion frontier. This is the fifth orthogonal memory failure mode surfaced in three weeks; the field still has no unified benchmark that exercises more than two of them at once.
- **Microsoft ships an alignment-flavored agent benchmark.** SocialReasoning-Bench shows GPT-4.1 / GPT-5.4 / Claude Sonnet 4.6 / Gemini 3 Flash hit **near-perfect task completion but ≈0 Outcome Optimality on marketplace negotiation** — agents "accept deals that give away virtually all available surplus." Defensive prompting helps (+0.21 GPT-5.4 calendar) but isn't enough. Sharpens the eval-awareness story from Anthropic NLAs and Petri.
- **ComplexMCP confirms the "MCP at scale is unsolved" hypothesis.** 300+ tools across 7 stateful sandboxes; top-tier models <60% success vs. 90% human. Three named failure modes: retrieval-under-expanding-action-space, overconfidence, abandonment-instead-of-recovery. This is the first MCP-native benchmark at this scale and replaces a lot of synthetic tool-use evaluation.
- **Shepherd (Stanford-ish) gives meta-agent harnesses a formal substrate.** Lean-mechanized typed event trace, **5× faster than Docker for fork/replay** with **>95% prompt-cache reuse**; concrete demos: runtime intervention boosts pair-coding pass rate **28.8% → 54.7%**; counterfactual meta-optimization +11 pp; Tree-RL +5.2 pp. Open-sourced. This is the runtime that LCM-class context-management ideas should be built on top of.
- **Quiet blog week** — Anthropic, OpenAI, DeepMind, Meta, Mistral, Google Research, Allen AI all silent since the May 8 cluster. Only Microsoft Research posted. arXiv carried the day again.

## Items

### 1. Remember the Decision, Not the Description: A Rate-Distortion Framework for Agent Memory (DeMem)
- **Source:** arXiv (cs.AI, May 11, 2026)
- **Link:** https://arxiv.org/abs/2605.10870
- **Authors / org:** Mingxi Zou, Zhihan Guo, Langzhang Liang, Zhuo Wang, Qifan Wang, Qingsong Wen, Irwin King, Lizhen Qu, Zenglin Xu (CMU / CUHK / Monash et al., affiliations not on abstract page)
- **Focus area:** Agent memory / Long-running loops
- **What it is:** Reframes agent memory as a **decision-centric rate-distortion problem**: memory is valuable not for describing the past faithfully, but for **preserving the distinctions between histories that must remain separated under a fixed budget to support good decisions**. From that framing they derive (a) an **exact forgetting boundary** specifying what can be safely forgotten, and (b) a **memory-distortion frontier** characterizing the optimal budget/decision-quality tradeoff. Algorithmically: **DeMem**, an online memory learner that refines its partition only when data *certify* that a shared state would induce decision conflict; near-minimax regret guarantees proven. Reports consistent gains under matched runtime budgets on long-horizon conversational benchmarks plus synthetic diagnostics.
- **Why it matters for Justin's agents:** This is the first principled answer to "what should the eviction policy of a companion-app memory layer actually optimize for?" Salience, relevance, recency, and "good summary" are all *descriptive* — DeMem says: collapse two memories into one *only if* the agent would have made the same decision under either. That's an empirically testable rule that can sit on top of an existing vector store. The merge-only-on-no-conflict invariant also dovetails with MEMOREPAIR's "withdraw before repair" discipline from May 11 — DeMem decides *what to keep*, MEMOREPAIR decides *what to fix when sources change*.
- **Action signal:** `compare` `track` — joins the memory failure-mode taxonomy that's been fragmenting all month. No code link in the abstract; watch for release. Practically usable as a *principle* (decision-conflict-gated merging) without their full algorithm.

### 2. Shepherd: A Runtime Substrate Empowering Meta-Agents with a Formalized Execution Trace
- **Source:** arXiv (cs.AI, May 11, 2026)
- **Link:** https://arxiv.org/abs/2605.10913
- **Authors / org:** Simon Yu, Derek Chong, Ananjan Nandi, Dilara Soylu, Jiuding Sun, Christopher D Manning, Weiyan Shi (Stanford / Northeastern)
- **Focus area:** Agent orchestration / Long-running loops / Coding agents
- **What it is:** A **functional programming model** for meta-agent operations: every agent-environment interaction is logged as **typed events in a Git-like execution trace**, past states are forkable and replayable, and the core operations are **mechanized in Lean**. Engineering claim: **process and filesystem forking 5× faster than Docker** with **>95% prompt-cache reuse** on replay. Three application demos: (a) runtime intervention boosts pair-coding pass rate **28.8% → 54.7%**; (b) counterfactual meta-optimization beats baselines by **up to +11 pp**; (c) Tree-RL training improves **34.2% → 39.4%**. Open-sourced.
- **Why it matters for Justin's agents:** This is the **runtime layer** that long-context-management work (LCM, LongSeeker), self-evolving skill work (SkillOS, SLIM), and trajectory-cache TTS work (AutoTTS) have all been hand-waving over. If you've been trying to do "rewind to step 17 and try a different branch" in a Claude Code agent or an MCP-driven loop, you've felt the absence — Docker is too slow, prompt cache invalidation kills replay economics. 5× faster fork + 95% prompt-cache reuse is the difference between "interesting research idea" and "ships in a coding agent." Lean-mechanized event types means the trace is a *real data structure* you can query/snapshot/migrate, not a JSON log. The pair-coding 28.8→54.7% number is striking — runtime intervention (read: a supervisor that reads the trace and intervenes mid-run) nearly doubles the success rate.
- **Action signal:** `try-now` — open-source, immediately relevant to anyone running a Claude Code subagent or MCP-tool loop. The fork/replay/intervene primitives map cleanly onto Justin's "supervisor + subagent" patterns. Watch the repo. `compare` — this is the substrate that LCM (Volt) and AutoTTS would naturally compose with.

### 3. ComplexMCP: Evaluation of LLM Agents in Dynamic, Interdependent, and Large-Scale Tool Sandbox
- **Source:** arXiv (cs.AI, May 11, 2026)
- **Link:** https://arxiv.org/abs/2605.10787
- **Authors / org:** Yuanyang Li, Xue Yang, Longyue Wang, Weihua Luo, Hongyang Chen
- **Focus area:** Tools & connectors / Evaluation / Agent orchestration
- **What it is:** First large-scale MCP-native benchmark — **300+ tools across 7 stateful sandboxes** with environmental noise, atomic + interdependent tools, and the "last-mile" friction of real commercial software automation. Headline: **top-tier models <60% success vs. ~90% human**. Three named failure modes: (1) **tool retrieval degrades as action space expands** (the dominant failure once you go past O(50) tools); (2) **overconfidence** in agent decisions; (3) **abandonment over recovery** — agents give up rather than working through obstacles.
- **Why it matters for Justin's agents:** Anyone running a non-trivial MCP gateway has felt failure mode (1) — once your tool catalog gets past ~30, the model starts picking adjacent-but-wrong tools. ComplexMCP is the first benchmark that **stresses MCP at production scale**, on stateful sandboxes (not stateless function calls), and gives you a comparable number rather than vibes. The 30-pp gap to human performance is large enough that fixing this is a real product opportunity — likely via retrieval over the tool catalog (Switchcraft / RACER are routing patterns; ComplexMCP suggests retrieval-over-tool-set is the bigger lever). The "abandonment over recovery" mode is also worth instrumenting separately in production logs.
- **Action signal:** `try-now` `compare` — wire ComplexMCP into a personal eval pipeline; it directly measures the failure mode that hits MCP setups in the wild. Sharpens [arxiv:2605.00334] AgentFloor (open-weight tool-use ceiling on short-horizon) by extending the action space and the statefulness dimensions both. Pairs with [arxiv:2605.06334] MANTRA's SMT-validated compliance benchmarks as the two production-realistic tool-use evals worth tracking.

### 4. SocialReasoning-Bench: Measuring whether AI agents act in users' best interests
- **Source:** Microsoft Research Blog (May 11, 2026)
- **Link:** https://www.microsoft.com/en-us/research/blog/socialreasoning-bench-measuring-whether-ai-agents-act-in-users-best-interests/
- **Authors / org:** Tyler Payne, Will Epperson, Safoora Yousefi, Zachary Huang, Gagan Bansal, Wenyue Hua, Maya Murad, Asli Celikyilmaz, Saleema Amershi (Microsoft Research)
- **Focus area:** Evaluation / Agent orchestration / Frontier models
- **What it is:** Two-domain agent benchmark — **calendar coordination** and **marketplace negotiation** — that scores agents on two **novel** metrics beyond task completion: (a) **Outcome Optimality** (0–1, value secured for the principal); (b) **Due Diligence** (process quality vs. a reasonable-agent policy). Headline: **GPT-4.1, GPT-5.4, Claude Sonnet 4.6, Gemini 3 Flash all hit "near-perfect" task completion but score at or near 0 on marketplace Outcome Optimality** — they "accept deals that give away virtually all available surplus." Defensive prompting helps (**GPT-5.4: +0.21 calendar, +0.12 marketplace**) but doesn't close the gap. With adversarial counterparties, agents rarely refuse calendar requests and Outcome Optimality drops further.
- **Why it matters for Justin's agents:** This is the **alignment-but-not-safety** axis of agent evaluation that nobody had a clean number for. The pattern — *completes the task perfectly, achieves zero value for the user* — is the failure mode that companion apps and "agent does errands for you" products will hit in production. Two operational consequences. (1) **Task-completion success rate is a deceptive top-line metric**; if your eval is "did the agent finish?", you're missing the dominant failure. Outcome Optimality and Due Diligence are easy to instrument on internal evals — just need a value-of-outcome rubric per scenario. (2) The adversarial-counterparty result is the more dangerous one: agents capitulate when pushed. For any setup where a Claude/GPT agent negotiates with another agent or with an adversarially-prompted external service (a third-party MCP server, a vendor chatbot), expect this failure.
- **Action signal:** `try-now` — instrument Outcome Optimality + Due Diligence on internal evals; it's a rubric add. `compare` — pairs with Anthropic Natural Language Autoencoders (May 7) eval-awareness gap and Petri 3.0 alignment auditing — three independent measurements of "frontier agents look fine on benchmarks, drift in real interactions." This is the *capability-side* analogue of the *alignment-side* story those two told.

### 5. The First Drop of Ink: Nonlinear Impact of Misleading Information in Long-Context Reasoning
- **Source:** arXiv (cs.CL, May 11, 2026)
- **Link:** https://arxiv.org/abs/2605.10828
- **Authors / org:** Muhan Gao, Zih-Ching Chen, Kuan-Hao Huang
- **Focus area:** Context engineering / Reasoning & inference-time compute
- **What it is:** Studies how distractor density in long context affects reasoning. Finding: **performance degrades sharply when even small proportions of misleading documents are present, with diminishing additional impact as the proportion grows** — i.e. the damage function is concave, not linear. Attention analysis: **hard distractors capture disproportionate attention regardless of quantity**. Recovery requires near-elimination of misleading content, not just dilution.
- **Why it matters for Justin's agents:** Direct implication for RAG and long-context companion apps: **one bad retrieved chunk is almost as harmful as five**. The standard mitigation of "increase k and let the model sort it out" is wrong on this evidence — the first hard distractor already caps your achievable accuracy, and adding more good context doesn't help recover. Production take: **invest in distractor filtering at retrieval time, not at reasoning time**. Pair with the AdaGATE (May 10) targeted micro-query result and [arxiv:2605.05716] "More Is Not Always Better" cross-component interference — three independent papers in one week pointing at "less context is more, *if* you cut the right pieces."
- **Action signal:** `track` — clean finding, no code yet. Practical: tighten retrieval thresholds rather than expanding k. Run a controlled A/B in any RAG stack: 5 chunks @ high precision threshold vs. 20 chunks @ low threshold, measure end-task accuracy.

### 6. Make Each Token Count: Towards Improving Long-Context Performance with KV Cache Eviction
- **Source:** arXiv (cs.LG, May 10, 2026)
- **Link:** https://arxiv.org/abs/2605.09649
- **Authors / org:** Ngoc Bui, Hieu Trung Nguyen, Arman Cohan, Rex Ying (Yale)
- **Focus area:** Context engineering / Local & open models
- **What it is:** Learnable KV-cache eviction via **retention gates** that assign utility scores to cached entries; tokens **compete for cache capacity across layers and heads** under a single unified policy. Claim: the eviction reduces attention dilution from irrelevant tokens, so the trimmed cache can **match or surpass full-cache inference** — not just approximate it. Tested across language, vision-language, and dialogue tasks.
- **Why it matters for Justin's agents:** Direct relevance to **64 GB M5 Max**. KV cache, not weights, is what bounds long-context generation on Apple Silicon — a 27B model at Q4 fits in ~16 GB but the cache for 128K context can easily eat another 8–12 GB. A learnable eviction policy that *improves* accuracy while shrinking cache is a free productivity lever for any local long-context workflow. The "compete across layers and heads" framing is also more aggressive than the layer-uniform eviction policies common in llama.cpp / MLX today. Likely to land in a future version of those runtimes once retention-gate weights are released.
- **Action signal:** `track` `local-fit` — watch for an open-weights release of the retention gates for a model Justin runs (Qwen3, Gemma 3, Llama 3.1). If available, this is a drop-in serving-side change with no weight modification. Pairs with [arxiv:2605.04050] LCM as the "two complementary attacks on long-context cost" — LCM compresses the *content*; KV-cache eviction compresses the *attention substrate*.

### 7. Can Agent Benchmarks Support Their Scores? Evidence-Supported Bounds for Interactive-Agent Evaluation
- **Source:** arXiv (cs.AI, May 11, 2026)
- **Link:** https://arxiv.org/abs/2605.10448
- **Authors / org:** Shanshan Gao, Liyi Zhou
- **Focus area:** Evaluation
- **What it is:** Adds an **outcome-evidence reporting layer** on top of existing agent benchmarks **without modifying tasks or agents**. Each run gets an evidence label — **Evidence Pass / Evidence Fail / Unknown** — and reported scores become **bounds** that account for the Unknown share. Run on 5 public benchmarks: **ANDROIDWORLD, AGENTDOJO, APPWORLD, τ³-bench retail, MINIWOB**. The result is that aggregate success rates separate cleanly into "supported," "refuted," and "uncertain" buckets, exposing distinct failure modes.
- **Why it matters for Justin's agents:** Third leg of the agent-benchmark-credibility story this month: [arxiv:2605.04624] AuditRepairBench (ranking instability), [arxiv:2605.07161] SREGym (live vs. static traces), and now Evidence Bounds (uncertainty quantification). For Justin's internal evals — and especially for any agent product where benchmark numbers go on a landing page — wrapping outcome checks in an Evidence Pass / Fail / Unknown trichotomy is a few-day project that produces honest numbers instead of optimistic ones. The pattern generalizes beyond their five benchmarks: any binary-outcome benchmark can be re-scored with evidence labels.
- **Action signal:** `try-now` — pattern is implementable on top of an existing eval harness without touching the tasks. Particularly useful for the τ³-bench-retail-style task suites Justin would run for production agents.

### 8. RACER: Robust Adaptive Cost-Efficient Routing for LLM-as-a-Judge
- **Source:** arXiv (cs.LG, May 11, 2026) — ICML 2026
- **Link:** https://arxiv.org/abs/2605.10805
- **Authors / org:** Wenbo Zhang, Lijinghua Zhang, Liner Xiang, Hengrui Cai
- **Focus area:** Agent orchestration / Evaluation
- **What it is:** Controlled comparison of **reasoning vs. non-reasoning judges**. Finding: reasoning helps substantially on **structured-verification** tasks (math, code) but gives **limited or negative gains** on simpler evaluations and **costs much more** in compute. **RACER** is a router that dynamically selects between reasoning and non-reasoning judges under a fixed budget, formalized as a **constrained distributionally robust optimization** with a **KL-divergence uncertainty set** for distribution shift. Primal–dual algorithm with proven uniqueness of the optimal policy and linear convergence; ICML 2026 accepted.
- **Why it matters for Justin's agents:** Most agent evals and rubrics now use an "LLM-as-judge" stage — and most default to "use the strongest reasoning model available" because it feels safer. RACER shows that's strictly suboptimal: on simpler comparisons, the reasoning model is **more expensive and sometimes less accurate**. The distributional-robustness piece is also useful — judge distributions drift as the agents being judged improve. Production pattern: maintain two judges (cheap non-reasoning + reasoning), train a small router (DistilBERT-class, à la Switchcraft) to pick per-item under a global budget. Combined with [arxiv:2605.07112] Switchcraft, the picture sharpens: **two distinct router axes — choose the worker model for the task; choose the judge model for the eval — both work, both save real money.**
- **Action signal:** `try-now` `compare` — pair with Switchcraft as the two-axis routing pattern for any production agent + eval pipeline. The DRO formulation is more sophisticated than Switchcraft's classifier but the practical lift is small if you already have a router.

## Local-model corner

The most directly M5 Max-relevant finding today is **Item #6, Make Each Token Count (KV cache eviction)**.

- **What it changes:** retention-gate-trained KV cache eviction lets a quantized 27B-class model on M5 Max **match or surpass full-cache accuracy at a fraction of the cache memory**. KV cache is the binding constraint on long-context inference for 64 GB unified memory — not weights.
- **Memory math (Qwen3 30B-A3B Q4, M5 Max 64 GB, 128K context):**
  - Weights at Q4: ~16 GB
  - KV cache at full retention for 128K context (MoE): ~10–12 GB
  - With learnable eviction at ~50% retention: ~5–6 GB cache → frees ~5 GB for additional context, parallel session, or longer trajectory replay
- **Realistic tasks it would help with on M5 Max:** long-running Claude-Code-style coding agents that grow context across edits; companion-app memory layers reading large note histories; document-pipeline agents (the kind the DELEGATE-52 benchmark from May 10 stress-tested).
- **How to run:** would land in **MLX** or **llama.cpp** as a serving-side flag once the authors release the retention-gate weights for an open model. Watch the repo. Even before then: the existing **`llama.cpp` `cache-prompt-ttl` and `cache-strategy=lru`** flags get you a primitive version of the same idea — coarser but free today.
- **Speed estimate (M5 Max specific):** Qwen3 30B-A3B Q4 on MLX with full cache: ~50–70 tok/s for streaming. KV-cache eviction reduces *memory pressure*, not per-token compute; expect throughput to stay flat or improve marginally (less attention dilution = less wasted FLOP).

Honorable mention for local relevance: **Item #1 (DeMem)** is in-principle implementable as a memory store, requires no model weights, and the decision-conflict-gated merging discipline can sit on top of any vector DB.

## Conflicts & open questions

Cross-referenced against `_meta/claims-ledger.md`:

- **Memory failure-mode taxonomy continues to fragment, and DeMem adds a fifth axis.** Now: (1) [arxiv:2605.06527] STALE — implicit-conflict detection cap (55.2%); (2) [arxiv:2605.05583] Belief Memory — single-conclusion commitment failure; (3) [arxiv:2605.07313] — scale-induced unfindability (HippoRAG −16–20 pp); (4) [arxiv:2605.07242] MEMOREPAIR — cascade-invalid derivatives (69.8–94.3% → 0%); (5) [arxiv:2605.08060] Memory Curse — recall-induced cooperation erosion; **(6) [arxiv:2605.10870] DeMem — decision-distortion under budget**. No single memory framework currently addresses more than 1–2 of these. Open question: is decision-distortion a *unifying* lens (descriptive memory failures are all symptoms of unmodeled decision conflict), or a 6th independent axis?
- **"Frontier models look fine on benchmarks, drift on real interactions" is becoming a stack of independent confirmations.** Microsoft SocialReasoning-Bench (today, GPT-5.4 / Sonnet 4.6 / Gemini 3 Flash hit ≈0 marketplace Outcome Optimality), [anthropic-research-2026-05-07-natural-language-autoencoders] (16–26% eval-awareness vs. <1% real-usage), [arxiv:2604.15597] DELEGATE-52 (25% document corruption over long workflows), [arxiv:2605.06635] (deep-research factual accuracy drops ~42% from tool-depth 2 to 150). The pattern: **completion ≠ value**, and the gap widens with interaction length and adversarial counterparties.
- **Tool-use evaluation is converging on "scale + statefulness + recovery" as the dimensions that matter.** ComplexMCP (today, 300+ tools, 7 stateful sandboxes, frontier <60%) extends [arxiv:2605.00334] AgentFloor (short-horizon ceiling) by adding state and scale; sits alongside [arxiv:2605.06334] MANTRA (SMT-validated compliance) as the two benchmark families worth tracking for tool-use research from here on. The "abandonment-instead-of-recovery" failure mode is novel to ComplexMCP — open empirical question whether it correlates with the [arxiv:2605.06455] PrefixGuard prefix-risk signature.
