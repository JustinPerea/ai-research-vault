## Items

### 1. MCPEvol-Bench: Benchmarking LLM Agent Performance Across Dynamic Evolutions of MCP Servers
- **Source:** arXiv (2607.14642) — submitted July 16, 2026
- **Link:** https://arxiv.org/abs/2607.14642
- **Authors:** Huanxi Liu, Kun Hu, Jiaqi Liao, Qiang Wang, Pengfei Qian, YuanZhao Zhai, Dawei Feng, Bo Ding, Huaimin Wang
- **Focus area:** Tools & connectors (MCP)
- **What it is:** First large-scale benchmark that measures how agents cope when the MCP tools underneath them *evolve* (renamed params, deprecated methods, semantic drift, added/removed arguments). 123 MCP servers, 11 mutation operators, 12 SOTA models tested at Pass@1.
- **Why it matters for Justin's agents:** Every MCP tool Justin ships will version over time. This is the eval that quantifies the risk. GPT-5.4 drops 13.7 pp, Claude-Sonnet-4-6 drops 14.4 pp — frontier-agnostic fragility, not a model-selection fix. Suggests versioning discipline + tool-schema regression tests belong in the CI pipeline for any MCP server that plans to survive more than one release. Directly extends the ToolAnchor "tool behavioral inertia" primitive from a training-time defense to a production-eval frame.
- **Action signal:** `try-now` — adopt the mutation-operator taxonomy as a checklist for any MCP server before v0.2 → v0.3 bumps

### 2. Multi-Head Latent Control: A Unified Interface for LLM Agent Decision Making
- **Source:** arXiv (2607.14277) — submitted July 15, 2026
- **Link:** https://arxiv.org/abs/2607.14277
- **Authors:** Amirhosein Ghasemabadi, Ruichen Chen, Bahador Rashidi, Di Niu
- **Focus area:** Agent orchestration
- **What it is:** Two lightweight heads bolted onto a *frozen* LLM's hidden states — a **Capability Head** ("can I handle this or should I hand off?") and a **Resolution Head** ("Clarify / Tool-use / Abstain / Direct-answer"). Trained only on latent traces from the same backbone; no base-weight modification.
- **Why it matters for Justin's agents:** −90.7% large-model usage on AndroidWorld and 27–53% reduction across other benchmarks *while preserving quality*, +158% relative tool-use score with 65.5% fewer missed tool-calls. This is a strictly cheaper alternative to full router or harness rewrites. Composable with Writer Harness Effect (arxiv:2607.06906) — MHLC is the decision layer, Writer Harness is the execution layer.
- **Action signal:** `compare` — extends the "orchestration variable dominates" thread (Writer Harness Effect / IBM routing below); the frozen-base + latent-only training keeps parity with mem0-style bolt-ons

### 3. PReM: Learning What to Preserve and When to Refresh for Context Compression
- **Source:** arXiv (2607.14327) — submitted July 15, 2026
- **Link:** https://arxiv.org/abs/2607.14327
- **Authors:** Bohan Yu, Lei Shen, Chenxi Zhou, Chen Han, Junlin Liu, Wenbo Su, Yu Cheng, Bo Zheng
- **Focus area:** Context engineering
- **What it is:** Dedicated layer-wise KV memory + a special **memory token** that triggers dynamic refreshes *during* generation. "Phase-Separated Refresh Training" aligns memory selection with generation while keeping continuity across refresh cycles. Beats strong baselines at 16× and 32× compression ratios on 32K contexts.
- **Why it matters for Justin's agents:** Most compression schemes commit to what-to-keep at prefill time; PReM defers those decisions and refreshes when the model actually needs different evidence. Sits neatly next to Byte-Exact KV-Cache Grafting (arxiv:2607.14431) — Grafting is *reload* of frozen state, PReM is *reshape* of live state — and the Adaptive KV Cache Filtering finding (2607.13205) that structural KEY tokens over-retain. Combining PReM's memory-token with a KEY/VALUE-aware budget could plausibly rescue the 88→0% schema-dense collapse.
- **Action signal:** `track` — waiting on benchmark specifics (paper does not name the eval sets in the abstract); revisit when code + numbers land

### 4. RoboTTT: Context Scaling for Robot Policies
- **Source:** arXiv (2607.15275) — submitted July 17, 2026 (NVIDIA — Jiang, Chebotar, Fei-Fei, Zhu, Fan et al.)
- **Link:** https://arxiv.org/abs/2607.15275
- **Focus area:** Context engineering / long-context
- **What it is:** Test-Time Training grafted into a VLA policy, scaling visuomotor context to **8K timesteps (~3 OOM beyond SOTA)** *without increasing inference latency* — fast weights updated via gradient descent during both training and inference; training recipe combines sequence action forcing with truncated BPTT.
- **Why it matters for Justin's agents:** VLA is not Justin's stack, but the *technique* — TTT with fast weights as an alternative to attention-window growth for long context — transfers to any long-running agent that has a natural "episode" concept (chat sessions, ongoing coding tasks). 87% overall improvement over single-step baselines; completes a 10-stage 5-minute assembly task that baselines cannot start. The 8K-context model beats the 1K-context model with the same architecture by 62% — evidence that context scaling wins even when compute is held.
- **Action signal:** `track` — worth watching whether TTT-with-fast-weights migrates from VLA back to text agents

### 5. Model Routing Is Simple. Until It Isn't. (IBM Research)
- **Source:** Hugging Face blog (huggingface.co/blog/ibm-research/model-routing-is-simple-until-it-isnt) — July 15, 2026
- **Authors:** Yara Rizk, Eyal Shnarch, Jason Tsay, Merve Unuvar (IBM Research)
- **Focus area:** Agent orchestration
- **What it is:** Reframes model routing as *systems optimization*, not classification. Tests CodeAct on the AppWorld Test Challenge (417 tasks) with a lightweight cost-quality-latency optimizer; router itself takes ~6 ms and 2 KB per task.
- **Why it matters for Justin's agents:** Concrete numbers on a real agent benchmark — **Claude Sonnet total $79 ($0.19/task) vs GPT-4.1 total $155 ($0.37/task)**, with the delta driven by Claude's cheaper cache-read pricing, not per-token base cost. Configuration hits 84% accuracy at $93 / 83 s (21% cost, 9% latency reduction vs Opus alone). Two-line lesson: (a) audit actual deployment cost, not price sheets, and (b) treat cache behavior as a first-class routing input, not overhead.
- **Action signal:** `try-now` — adopt cost-per-task on a realistic benchmark as the routing spec, not $/1M tokens

### 6. On-Policy Delta Distillation (OPD²)
- **Source:** arXiv (2607.15161) — July 16, 2026
- **Link:** https://arxiv.org/abs/2607.15161
- **Authors:** Byeongho Heo, Jaehui Hwang, Sangdoo Yun, Dongyoon Han
- **Focus area:** Reasoning & inference-time compute (distillation)
- **What it is:** Instead of mimicking the teacher directly, uses the **delta signal** — the difference between the teacher and its base model *before* instruction tuning — as the distillation target. Isolates the "instruction-tuning improvement" from the base weights.
- **Why it matters for Justin's agents:** Consistent outperformance across math/science/code with shorter post-training cycles. If it holds on open weights (paper promises code), this becomes the cheapest path from a base checkpoint to a reasoning-tuned local variant — relevant for M5 Max fine-tuning of Qwen3 / Gemma 4 class models.
- **Action signal:** `track` — waiting on release; concept + name are cleaner than the "Instruction-Tuning + Merging" (2607.14895) alternative that lands the same day

### 7. In-Place Tokenizer Expansion for Pre-trained LLMs → LFM2.5-8B-A1B
- **Source:** arXiv (2607.15232) — July 17, 2026 (Liquid AI — Smith, Dakhran, Cabrera, Labonne, Amini, Lechner et al.)
- **Link:** https://arxiv.org/abs/2607.15232
- **Focus area:** Local & open models
- **What it is:** Method for upgrading a pretrained model's tokenizer by *continuing* the original BPE merges on multilingual corpora — most existing token IDs stay stable, new tokens initialize as averages of source sub-tokens, two-stage adaptation restores quality. Applied to **LFM2-8B-A1B** (8B MoE, 1B active) to produce **LFM2.5-8B-A1B** with a **128K vocab**.
- **Why it matters for Justin's agents:** Hindi 2.4×, Vietnamese 2.6×, Thai 4.0× fewer tokens → estimated 2.2–3.7× per-character decode speedup on reference devices. LFM2.5-8B-A1B is a direct M5 Max fit — 8B params at 1B active is trivial for 64 GB unified memory, and multilingual token efficiency compounds decode-throughput gains from MoE sparsity. Also a template Justin can borrow: *upgrade the tokenizer without retraining* is one of the cheaper personalization axes for a local companion app.
- **Action signal:** `local-fit` — grab LFM2.5-8B-A1B when weights hit the Hub

### 8. PolyQ: Codesigning End-to-End Quantization for Scalable Edge CPU LLM Inference (ICCAD 2026)
- **Source:** arXiv (2607.14618) — July 16, 2026
- **Link:** https://arxiv.org/abs/2607.14618
- **Authors:** Hyunwoo Oh, Suyeon Jang, Hanning Chen, KyungIn Nam, Sanggeon Yun, Ryozo Masukawa, Mohsen Imani
- **Focus area:** Local & open models (edge inference)
- **What it is:** CPU-focused compiler + quantization co-design; activation-aware channel-wise bit allocation from 2 to 16 bits within an average-bit budget. Compiler layout regularization reduces activation-reorder traffic by up to **70.8%** via channel permutation + bit-homogeneous clustering.
- **Why it matters for Justin's agents:** 2.4–32.1% perplexity improvement over prior methods at **3-bit targets** on Falcon-H1-3B, Llama2-13B, Qwen3-32B; energy overhead <2% vs optimized LUT backends. CPU-first framing is not M5-Max-native (Apple Silicon prefers MLX / Metal), but the *fractional-bit compilation* insight and the 3-bit Qwen3-32B numbers are useful reference points for calibrating what MLX Q3 quality should look like on the same models.
- **Action signal:** `track` — cross-reference the WikiText-2 3-bit Qwen3-32B numbers against MLX-community Q3 releases when they land

### 9. SmartRAG: Native Graph-Based RAG for Mobile Device
- **Source:** arXiv (2607.14661) — July 16, 2026
- **Link:** https://arxiv.org/abs/2607.14661
- **Authors:** Zhihan Jiang, Meng Li, Shenghao Liu, Keran Li, Ruiben Zhou, Xianjun Deng, Shuai Wang, Haipeng Dai
- **Focus area:** Agent memory / local models
- **What it is:** Four-module on-device framework (Perception / Memory / Focus / Thinking) built around **EvoNER** (a continually-learnable NER that grows its label inventory *without* retraining the LLM) and **MRGraph** (a provenance-preserving KG with hybrid retrieval: graph traversal + lexical + semantic). Backbone: a quantized 1.7B LLM.
- **Why it matters for Justin's agents:** Multi-hop QA competitive with models **up to 18× larger** on TriviaQA / Natural Questions / HotpotQA / MultiHopQA — from a 1.7B model running on a phone. For a companion app that needs private, offline memory over a growing personal KB, EvoNER's schema-growth without retraining is the exact primitive that mem0/LangMem lack. The MRGraph hybrid retrieval formula (graph + lexical + semantic) is a cleaner default than pure vector.
- **Action signal:** `local-fit` — study the EvoNER label-growth mechanism; it addresses a real gap in personal-memory agents on device

## Local-model corner

Two viable candidates today:

- **Model:** LFM2.5-8B-A1B (Liquid AI, 8B MoE / 1B active, 128K tokenizer vocab) — via the In-Place Tokenizer Expansion paper (2607.15232)
- **Memory fit:** 8B BF16 ≈ 16 GB; at Q4 ≈ 5 GB weights + KV headroom, trivially fits 64 GB M5 Max. MoE with 1B active means memory-bandwidth-bound decode uses ~2 GB of active weights per token — expected to be very fast on 600 GB/s.
- **Realistic tasks:** multilingual chat + assistant tasks where token efficiency (2.4–4.0× fewer tokens for Hindi/Vietnamese/Thai) actually matters; general instruction-follow for a companion app; probably not a coding-agent backbone.
- **How to run:** MLX (Liquid publishes MLX-compatible releases) or GGUF via llama.cpp once the community converts.
- **Speed estimate:** 1B-active MoE on M5 Max at Q4 should land in the 80–120 tok/s range extrapolating from Qwen3.6-35B-A3B numbers; no M5-Max-specific benchmark yet — verify next digest.

- **Model:** SmartRAG's 1.7B quantized backbone (from 2607.14661) — architecture is more interesting than the specific weights
- **Realistic tasks:** on-device personal-KB QA where the *EvoNER + MRGraph* stack matters more than raw model size; a template for a Justin-style companion app's memory layer rather than a model to grab.

## Conflicts & open questions

Cross-referenced against `_meta/claims-ledger.md`:

- **MCPEvol-Bench (2607.14642) + ToolAnchor (2607.14145):** Both name a version of the same failure mode. ToolAnchor calls it "tool behavioral inertia" and attacks it with post-training on counterfactual anchors; MCPEvol-Bench measures it in production-shaped MCP evolutions. **Open question:** does ToolAnchor's training-time defense hold up on MCPEvol-Bench's 11-operator mutation set? Neither paper cites the other.
- **Multi-Head Latent Control (2607.14277) vs Writer Harness Effect (arxiv:2607.06906) + IBM Model Routing (2026-07-15):** All three land on "orchestration/routing is the dominant variable." MHLC does it with two frozen-base latent heads (−90.7% large-model usage), Writer Harness does it with harness rewrites (−41% cost / −38% tokens / −44% wall-clock), IBM does it with a cost-optimization router (Sonnet ≈ ½ GPT-4.1). **Open question:** are these composable (stack all three) or do they compete for the same headroom? First empirical test would be running MHLC on top of an IBM-style cost-optimized router on AppWorld.
