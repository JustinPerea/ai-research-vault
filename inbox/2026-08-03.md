# AI Research Digest — Monday, August 3, 2026

## TL;DR
- **LongHorizon-Harness** [arxiv:2608.01964] is the cleanest "externalize task state, verify against the environment, give the executor a fresh context" paper of the week. Manage–Execute–Audit loop. Qwen 3.7-Plus: WeaveBench **51.8 → 80.7**, Terminal-Bench 2.1 **69.7 → 77.2**, OSWorld 2.0 **2.8 → 8.3**; Claude Opus 4.7 on an OSWorld 2.0 subset **20.0 → 34.3**. Adapter claimed to wrap native agent loops without rewriting them.
- **Skill-α** [arxiv:2608.01678] (Progressive Agent Skill Generation) is learning-based skill *generation* as sequential edits with a **rollback reward**: each edit is scored by downstream execution on an anchored query, original vs edited. Under a GPT-4o worker, **+3.3 pp on CL-Bench** and **+6.7 pp on τ²-bench** vs the strongest skill-generation baseline. Code: github.com/ejhshen/skill-alpha.
- **SKT** [arxiv:2608.02287] attacks the other half of the skill problem: models that *have* skills still fail to identify / apply / coordinate them. Verified synthetic data from **2,000 public skills → 4,000 task packages / 27,164 trajectories**, plus SkillEval. SFT on those trajectories consistently improves skill-use across models, benches, and harnesses; gains depend on verification, transfer across harnesses, and scale with skill coverage.
- **SWE-Touch** [arxiv:2608.02499] is the shared-workspace coding-agent eval Claude Code actually lives in. Counter-Edits (plausible user edits that conflict with the task) drop average resolve rate **7.7 pp** on SWE-bench Verified, and the hit persists on SWE-Bench Pro and DeepSWE. Agents keep conflicting code or overwrite without re-inspecting. Code: github.com/Trae1ounG/SWE-Touch.

## Items

### 1. LongHorizon-Harness: Advancing Long-Horizon Agents for Real-World Tasks
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.01964
- **Authors / org:** Ziyu Ma / Hailang Huang / Shun Zou / Yong Wang / Shidong Yang / Yiming Hu / Fei Wei / XiangXiang Chu
- **Focus area:** Long-running / autonomous loops + agent orchestration
- **What it is:** Diagnoses the standard harness as stuffing execution, task state, and completion assessment into one growing context, so state is untrackable and wrong self-assessments propagate. Reformulates long-horizon work as **task-state management**. **MEA loop:** a manager holds explicit task state *outside* execution and updates it only with facts independently verified from the environment; a **fresh-context executor** runs the next subtask; a **read-only auditor** verifies the resulting environment state before the next round. AgentAdapter claims to sit on interchangeable model/harness backends without modifying native loops. Qwen 3.7-Plus: WeaveBench **51.8% → 80.7%**, Terminal-Bench 2.1 **69.7% → 77.2%**, OSWorld 2.0 **2.8% → 8.3%**. Claude Opus 4.7 on an OSWorld 2.0 subset: **20.0% → 34.3%**.
- **Why it matters for Justin's agents:** This is the design Claude Code subagents should grow toward and the design Mitamaton's day-plan should already be: **state lives in a file, the worker gets a clean context, a third pass checks the world (calendar, files, git status) before you mark the subtask done.** Complements StateAct (code-first) and prefigures PILOT (live steer, Aug 28 digest) and OneDayAgent (Aug 4). The OSWorld absolute numbers are still low — the *delta* is the claim. Fresh-context executor is the piece to steal this week; the adapter claim needs a Claude Code experiment.
- **Action signal:** `try-now` — for the next multi-hour Claude Code job: `task-state.md` owned by a manager pass, each subagent starts empty, a verify pass runs `git status` / tests / the actual file before the manager updates state.

### 2. Progressive Agent Skill Generation via Reinforcement Learning (Skill-α)
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.01678
- **Authors / org:** Junhao Shen / Zhanqiu Zhang / Yiwen Guo / Hong Cheng
- **Focus area:** Agent skills (generation)
- **What it is:** Skill generation has no natural relevance/correctness label — value is "does the agent get better." Skill-α casts generation as a **sequential editing process** (each edit is individually evaluable) and introduces a **rollback reward**: run the worker on an anchored query under the original skill and under the edited skill, keep the edit only if downstream execution improves. Document-to-skill and experience-to-skill. Under the main GPT-4o worker: **+3.3 pp CL-Bench**, **+6.7 pp τ²-bench** vs the strongest skill-generation baseline. Ablations: rollback reward and progressive generation both load-bearing. Code: https://github.com/ejhshen/skill-alpha
- **Why it matters for Justin's agents:** This is WikiSkill's validation gate, three weeks earlier, as an RL objective. You do not need the RL. The rollback reward *is* the gate: proposed SKILL.md patch → run a 5-task personal set with and without → keep only if the score rises. Complements SkillRise (Jul 29, cross-task *curation* credit) and SKT (item 3, *use* training). Three papers, three layers: generate (Skill-α), curate across tasks (SkillRise), teach the model to actually invoke them (SKT).
- **Action signal:** `try-now` — implement rollback-reward as a shell script around `~/.claude/skills` before touching any trainer.

### 3. SKT: Skill-Use Training at Scale via Verified Synthetic Data Generation
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.02287
- **Authors / org:** Zelin Tan / Yiqun Zhang / Hao Li / Zhiyao Cui / Hejia Geng / Shao Zhang / Hangfan Zhang / Yang Chen / Xiaosong Wang / Lilong Wang / Zhenfei Yin / Shuyue Hu / Chen Zhang / Lei Bai
- **Focus area:** Agent skills (use / training data)
- **What it is:** Having a skill library ≠ the model will pick, apply, and coordinate the right ones. SKT is a verified synthesis pipeline: choose single- and multi-skill configs, synthesize tasks with rule-based + agent-based verification and feedback-guided repair, **keep only successful trajectories that substantially use every required skill**. From **2,000 public skills**: **4,000 task packages** and **27,164 verified trajectories**. SkillEval is a held-out executable benchmark from the same pipeline on a disjoint test pool. SFT on SKT trajectories consistently improves skill-use across diverse models, benchmarks, and agent harnesses. Verification ablations, cross-harness eval, and scaling experiments: gains require high-quality supervision, survive a harness swap, and rise with broader skill coverage.
- **Why it matters for Justin's agents:** SkillSight [arxiv:2607.18785] fixed retrieval bias in skill *descriptions*; SKT trains the *policy* to use the skill once retrieved. For a local Qwen3-4B / 30B-A3B that ignores `~/.claude/skills`, this is the data recipe (if you ever SFT). For Claude Code on Opus, you probably do not SFT — but SkillEval is the missing eval: "given 20 skills, does the agent actually invoke the right ones." Build a 15-task personal SkillEval before generating 27k trajectories.
- **Action signal:** `compare` — score current Claude Code / local Qwen skill-use on a 15-task personal SkillEval *before* any SFT; only then decide if SKT-style data is worth the run.

### 4. SWE-Touch: Benchmarking Coding Agents When Users Touch the Code
- **Source:** arXiv (Hugging Face Daily Papers)
- **Link:** https://arxiv.org/abs/2608.02499
- **Authors / org:** Yuqiao Tan / Jinxiang Meng / Fangyu Lei / Minzheng Wang / Shizhu He / Jun Zhao / Kang Liu
- **Focus area:** Coding agents + shared workspace
- **What it is:** Real coding is a shared workspace — the user inspects and edits during the task — but SWE-bench-style evals either leave the agent alone or restrict the user to messages. SWE-Touch injects validated **Counter-Edits**: plausible edits to task-relevant code that conflict with completion, plus a contextual user message, at the moment the agent reaches that code. Nine coding models on SWE-bench Verified; extra runs on SWE-Bench Pro and DeepSWE. Counter-Edit lowers average resolve rate by **7.7 pp** on Verified; the degradation persists on both longer-horizon benches. Trajectory analysis: agents retain conflicting code or replace it without re-inspecting the repo and without targeted tests. Code: https://github.com/Trae1ounG/SWE-Touch
- **Why it matters for Justin's agents:** This is Claude Code's actual working mode (you touch the file while it runs). A 7.7 pp drop from a *plausible* user edit is the number to put on "always re-read HEAD after a human save." Portable recipe: a hook that, on any file change not authored by the agent, forces `read` + a targeted test before the next edit. Complements Deletion Avoidance [arxiv:2607.28887] (models wrap rather than delete): both say the agent does not treat the workspace as a live, shared state.
- **Action signal:** `try-now` — add a "user touched the tree" re-inspect hook to Claude Code; measure whether the agent notices on the next 5 pairing sessions.

## Conflicts & open questions
Cross-referenced against `_meta/claims-ledger.md`:
- **Conflict flagged:** Skill-α's rollback-reward *generation* and SkillRise's cross-task *curation* both write skill documents from outcomes. They are not the same objective (one-edit A/B vs discounted downstream credit) and neither paper compares to the other. Do not implement both this week.
- **Convergent evidence:** LongHorizon-Harness's "state outside the executor, verify from the environment" is the same shape as StateAct's "program state, not screenshots" and PRO-LONG's "the log is the memory." The disagreement is *which object is the state file* (task-state.md vs repo vs interaction log).
- **Open question:** SWE-Touch's 7.7 pp is on models, not on Claude Code's specific harness. First personal measurement: 5 pairing sessions with the re-inspect hook on vs off.
